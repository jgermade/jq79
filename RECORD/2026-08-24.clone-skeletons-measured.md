# Cloning the skeletons, measured

**Status:** the measurement
[`2026-08-23.clone-static-skeletons.md`](2026-08-23.clone-static-skeletons.md)
asked for and could not make — it borrowed every number it had, and its open
question 1 was *"is 20% of create1k worth a second render path? Not a question a
profile answers."* This is that question answered with a working second render
path: a spike built out of tree (a copy of `src/`, patched, bundled with
esbuild), driven against an unpatched build of the same commit. `src/` is
untouched. Nothing here is a proposal to merge; it is what the idea is worth,
where, and what it costs when it costs.

The short version:

- **The win is real and larger than the file's estimate, but it comes from
  cloning ONE big skeleton per row.** The benchmark row: **-24% create1k**
  (13/13 rounds), **-27% create10k** (9/9). A wider static row: **-49%**
  (13/13).
- **Subsegments — the idea that a row broken by a component tag or an `:if`
  still clones the pieces around it — do not pay at 1-2 elements a piece.**
  Measured three ways, they are a wash at best and a **regression** on a row
  whose only fragments are that small (`+9% to +14%` create, 3-6/13).
- **A row with no static structure gets nothing** (-2.7%, 6/13 — chance).
- The skeleton recovers the *interpretation*, never the effects: a row where
  every element carries a binding still gains, but half as much (-10 to -18%).

## The spike

Narrow on purpose. A node is *planned* only when its whole subtree is plain
HTML whose **shape** is fixed. Bindings are holes in that shape and are allowed;
anything that changes the shape is not:

```ts
const SHAPE_ATTRS = [
  ":if", ":elseif", ":else", ":each", ":key", ":with", ":text", ":html",
  ":html.allowed", ":attrs", ":props", ":model", ":value", ":checked",
  ":selected", ":slot",
]

const plannableNode = (node: TemplateNode): boolean => {
  if (node.component || node.tag.includes("-") || isSlotTag(node.tag) || node.tag === "template") return false
  if (document.createElement(node.tag) instanceof HTMLUnknownElement) return false
  for (const key in node.attrs) {
    if (SHAPE_ATTRS.includes(key) || key.startsWith(":props.") || key.startsWith(":model.") || key.startsWith(":slot.")) return false
  }
  return node.children.every(child => typeof child === "string" || plannableNode(child))
}
```

A planned node keeps, once per definition: a detached skeleton element built by
walking the AST, and an op per hole — `{ kind, path, … }` where `path` is a
list of child indices from the skeleton root. `{{ }}` text becomes an empty text
node in the skeleton plus a `text` op; `@event`, `:class`/`:class.<name>` and
`:<name>` become `event`/`class`/`attr` ops. Rendering is then

```ts
const root = plan.skeleton.cloneNode(true)
for (const op of plan.ops) { /* walk op.path, register exactly the effect renderNode would */ }
```

hooked into `renderNode` right after the component-key scan, so anything
unplannable takes the interpreted path unchanged.

**The runtime guard is not optional, and it is the finding
`clone-static-skeletons.md` got wrong.** That file's conservative classifier
accepts a subtree when its tags are "known HTML". They aren't safe:
`findComponentKey` strips dashes and lowercases, and any PascalCase scope key
participates — so a variable named `Td` turns every `<td>` into that component,
and `Map`, `Data`, `Table`, `Form`, `Label`, `Option`, `Menu`, `Dialog`, `Main`
are all HTML tags *and* ordinary component names:

```
<td> with Td in scope   -> <!--Td--><span class="child">soy un componente</span><!--/Td-->
<map> with Map in scope -> <!--Map--><b class="child">componente Map</b><!--/Map-->
<td> with no Td         -> <td class="col-md-1">texto plano</td>
```

So the spike checks, per render, that no tag in the plan resolves:

```ts
const plan = planOf(node)
if (plan && !plan.tags.some(tag => findComponentKey(scope, tag))) return renderFromSkeleton(plan, scope, fx)
```

which costs what the interpreter already paid — `findComponentKey` once per
distinct tag, memoized per render pass — and keeps the upgrade watch and the
unresolved-component throw where they are, in the interpreted path. Turning the
guard off (a knob in the spike) changed nothing measurable.

### It is correct as far as the suite can tell

**761 tests pass** with the spike swapped in for `src/jq79.ts`, and in every
case measured below the rendered `innerHTML` is **byte-identical** to the
unpatched build's. That is not proof — the suite was not written to hunt for a
second render path's omissions — but it is the same bar the rest of the branch
cleared.

## The instrument, and the trap in it

Two builds, **one page each**, alternating rounds, every round printed, medians
of 13 rounds and the win count beside them.

**One page each because the obvious way is wrong.** The first version mounted
both apps in one document. Its null control — the same build on both sides —
read **+12.5% create and +16% clear**, 4/13. Two apps in one document is not a
pairing: the second one mounted pays for the first one's DOM. Every number in
this file is against a **per-case null control** (`base` vs `base`, or `base` vs
a spike that plans nothing in that case), because the noise floor turned out to
be per case:

| caso | nulo (create) | nulo (replace) |
|---|---|---|
| benchmark | ±2% (6/13) | **-17% (8/13)** |
| wide | ±0.3% (6/13) | +3% (9/13) |
| thin | ±4% (6/13) | -2% (6/13) |
| component | -4% (6/13) | +5% (6/13) |
| bound | +5% (6/11), once +21% (2/11) | — |

**`create` is the trustworthy operation here; `replace` is not** — its null
reaches 17% on the very case the headline is about. And `bound`'s null gave
+20.7% once and +4.7% on a re-run, which is why nothing below rests on a single
run.

## What it is worth, per shape of row

1,000 rows, `create`, 13 rounds, against that case's null:

| caso | fila | esqueletos/fila | create | rondas |
|---|---|---|---:|---|
| `wide` | 12 elementos, 2 huecos | 1 | **-49%** | 13/13 |
| `benchmark` | 8 elementos, 4 huecos | 1 | **-20 a -24%** | 10-13/13 |
| `benchmark`, 10.000 filas | | 1 | **-27%** | 9/9 |
| `bound` | 8 elementos, 12 huecos | 1 | **-10 a -18%** | 9-11/13 |
| `mixed` | bloque de 11 + trozos de 1-2 | 4 | -6% | 6/13 |
| `component` | fila rota, trozos de 1-2 | 4 | -4.7% | 9/13 |
| `conditional` | fila rota, trozos de 1-2 | 3 | **+9 a +14%** | 3-6/13 |
| `thin` | 1 `<td>`, 1 hueco | 1 | -2.7% | 6/13 |

Read down that column: **the win is a function of how much fixed structure sits
under one skeleton**, and nothing else. Twelve elements pay 49%, eight pay 24%,
one pays nothing. `bound` is the useful control on the other axis — same eight
elements, twelve bindings instead of four — and it still gains 10-18%, which is
the shape of the original budget: the skeleton removes the ~11ms of
interpretation and leaves the ~30ms of effects exactly where it found them.

For scale: after the skeleton, the benchmark row's create1k is ~20ms against a
hand-written `cloneNode` control's ~3.4ms for the same 1,000 rows. The idea
takes about a quarter of the distance to the floor. The rest is reactivity.

## Subsegments: measured, and they do not pay

The proposal that a row broken by a component tag or an `:if` should still clone
the pieces around it. The spike does this by construction — `renderNode` is
called per child, so an unplannable row still plans its plannable children — and
a `--min <N>` knob (plan only subtrees of at least N elements) turns it off
without changing anything else, so **`min4` on those cases plans nothing and is
the exact control**.

| pareado | caso | create | rondas |
|---|---|---:|---|
| `min4` vs `min1` | conditional | +10.7% | 6/13 |
| `min4` vs `min1` | component | +2.3% | 8/13 |
| `min4` vs `min1` | mixed | +12.8% | 5/13 |
| `base` vs `min1` | conditional | +9 a +14% | 3-6/13 |

Every one of them says the same thing: **planning subtrees of one or two
elements buys nothing, and on the `conditional` row it costs.** The per-node
overhead — the plan lookup, the tag guard, the path walks — is fixed, and at
that size it is the whole saving.

This is a correction to what an earlier, isolated DOM measurement suggested: at
the DOM floor `cloneNode` beat `createElement` at *every* subtree size, down to
one element (13/13 rounds, -35% at size 1). Inside jq79 it does not, because the
DOM call was never the whole cost of a small node.

`mixed` is the case built to give subsegments their best shot — a component tag
next to an 11-element static block — and there the big block alone (`min4`)
matches or beats planning everything (`min1`). So the rule a real
implementation wants is not "plan every static fragment" but **"plan a fragment
only if it is big enough to pay", and the threshold is somewhere above two
elements.**

## What this does and does not decide

**Decided, or as close as this box gets:**

- The ceiling is not 20% of create1k, it is 20-50% depending on the row, and it
  holds at 10,000 rows.
- The classifier cannot key on "is this a known HTML tag". It must ask whether
  any scope key captures the tag, which is what `findComponentKey`'s memo
  already answers.
- Subsegments are not the unlock the earlier discussion assumed. They are only
  worth having with a size rule, and their value is confined to templates with
  one large static block next to something dynamic.

**Still open, and none of it is a measurement:**

1. **The second render path.** Every directive added after this has to be
   taught to both paths, or force its subtree unplannable. The spike gets this
   for free by being narrow — its `SHAPE_ATTRS` list is the "not taught" list —
   but a shipped version has to keep that list correct forever, and getting it
   wrong shows up as stale DOM in one path only.
2. **Positional paths.** The spike addresses holes by child index from the
   skeleton root, and the AST keeps whitespace text nodes on purpose. Any future
   rewrite that merges or drops a node silently shifts every path after it.
3. **`<svg>`.** The spike builds its skeletons with `createElement`, so it
   inherits today's namespace behaviour exactly and changes nothing. Building
   them from the parser's own tree — which the file proposes, and which is free
   — would fix `<svg>` and take it out of the `HTMLUnknownElement` branch that
   the upgrade watch and the unresolved-component throw both rely on. Still its
   own decision.
4. **A one-off render.** Whether a definition that renders *once* pays for its
   plan could not be resolved: that instrument's null control is ±19%, and the
   whole parse+render is ~154µs, most of it parsing. Analytically the plan is
   one extra walk of the AST per definition against one saved per render, so it
   should be a wash at N=1 — but this box cannot show it.

## Reproducing it

The spike and its three drivers live out of tree (a copy of `src/` plus
`pair.mjs`, `mount.mjs`, and the DOM-floor instruments), as
[`wake-the-item-not-the-slot.md`](2026-08-23.wake-the-item-not-the-slot.md)'s
did. What matters is the method, and it is the one thing here worth keeping
whatever happens to the proposal:

1. Bundle both builds with esbuild, one `--global-name` each.
2. **One page per build**, one mounted app each, alternating rounds.
3. Run the null control for that exact case first, and read no delta that its
   null does not clear.
4. Print every round; a median without its win count says nothing on this box.
