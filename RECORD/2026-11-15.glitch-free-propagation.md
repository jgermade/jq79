# A write's propagation without glitches, and a window that re-measures

## Problem

An app's library pane lists one `:each` of `<ListRow>` components with
`:window="rowPx()"`: a row height in Songs (1,759 rows, ~36 drawn) and 0 in the
other views (Albums: 129 rows, drawn whole). Songs → Albums cost ~330ms, against
~105ms between two unwindowed views of the same size, and a `MutationObserver`
counted ~1,725 nodes added and removed again inside the one switch.

It is not `openWindow` miscounting. The rows and the height come from two
`$computed` over one store (`treeRows` and `activeRoot`), and one write
(`root.view = "albums"`) recomputes both - one after the other, and each
`$computed` write dispatches synchronously. The list effect reads both, so it
ran *between* them: `rowPx()` already 0, `listed()` still the 1,759 songs.
That pass rendered every song, unwindowed, and the next one (once `treeRows`
caught up) threw them all away. Measured in jsdom: 1,832 rows mounted, 1,759
destroyed, for a switch that needs 129 and 56. Declared the other way round
the glitch moves to Albums → Songs instead.

`$batch` (RECORD/2026-11-12.batch.md) already removes it - when the writer
knows to use it. Here nobody wrote two things: one write fans out through two
derived values, which is the library's own doing.

Reviewing the window's other transitions found two bugs of its own:

- **0 → a height.** The window kept `view.start` from when it closed. Scrolled
  to row 1,000 in Songs, back to the top in Albums, back to Songs: rows ~992
  rendered over an empty viewport until the next scroll event.
- **A height → another** (a density change). `start` and `count` stayed those
  of the old height until the next scroll: the wrong rows, and too few of them
  when rows get shorter.

## Proposal

1. **`dispatch` in reactive.ts.** A write outside any `$batch` still runs the
   effects it woke right away, in order - but what *their* writes wake is
   queued and runs once, after all of them, through the same flush `$batch`
   uses. Everything has run before the write returns, so "the write has
   rendered" still holds. The queue is allocated only when something is queued;
   a write that wakes plain bindings pays a counter.
   An effect that writes what it reads while it is running is not queued: it
   re-runs in its own loop and is cut off there with its own message, as before.
2. **`range()` re-measures on a new height.** When the height changes (0 → h
   included) and the list is connected, the window is computed from the
   container's geometry in that same pass, and written to the window's store
   raw: the effect doing it is the only reader, and a tracked write would wake
   it for a second pass over the same rows. One layout read, only on a height
   change.

Nothing else about `:window` moves: overscan, spacers, `$scrollTo`, the scroll
and resize listeners, the `ResizeObserver`, the first pass's screenful guess.

## Cost

- `dispatch`: one flag write per top-level notify, plus a `Map` when a
  cascade queues something.
- **A behaviour change.** An effect that reads a `$computed` for the first time
  in the same run that writes the computed's source used to miss that update -
  it was not subscribed yet when the computed rewrote, so it stopped on a value
  it never saw through. It now sees it. If that is a real cycle
  (`n = derived + 1` where `derived` is `n`), it is now cut off after 100 rounds
  with `a write kept waking effects for 100 rounds` instead of stopping silently
  at an inconsistent state. Pinned in tests/reactive.test.ts.
- Nested propagation order: an effect woken by another effect's write used to
  run nested, in the middle of the outer round; it now runs after the round.
  The whole suite, tutorial included, passes unchanged.

## Rejected

- **Fixing it in `openWindow`** (e.g. deferring a height change by a
  microtask). It would hide this one symptom and leave every other binding that
  reads two computeds glitching, and add a frame of stale rows on purpose.
- **Lazy (pull) `$computed`.** The principled fix, but it changes what a
  `$computed` is - eager, an effect over a store - and everything bridged to it.
- **Telling apps to `$batch`.** The writer wrote one value.
- **`schedule()` on a height change** instead of measuring in the pass: renders
  the stale window first, then the right one - the waste being removed.

## Open

- The first pass still renders a screenful of `window.innerHeight` before the
  list is in the document, then measures down (56 → 22 rows in the tests'
  geometry). By design (RECORD/2026-11-12.a-windowed-each.md), but it is the
  next waste on a windowed mount.
