# The comparison page measures each framework once, in its own minute

**Status:** the conclusions of the session that produced
[`2026-08-27.measuring-the-update-side.md`](2026-08-27.measuring-the-update-side.md)
and shipped in PR #17 / `0.6.6`, plus the one thing still to do. It closes two
open questions and opens a third, which is the only one with work in it.

---

## 1. The question that started it, answered

*"In the previous release it was level with Vue. Is it worse now?"*

No, in three ways, and none of them was visible from the page:

- **`0.6.5` did not regress against `0.6.4`.** Paired A/B, `regressions: []`,
  faster every round on `create1k`, `replace1k`, `selectRow` and `create10k`.
- **jq79 and Vue were tied**, 9.67× against 9.44× on the nine-operation suite,
  and the gap was smaller than the run-to-run spread of either — two runs of
  the same builds moved 4.3% and 6.9%. The bar chart sorts by that number, so
  which of the two appeared on top was a coin flip re-flipped on a different
  runner at every release.
- **The suite was measuring jq79's best operations at 30 timer steps.** Fixed
  in #17; `0.6.6` publishes the ten-operation suite, and on it jq79 leads Vue.

## 2. Closed: the `swap1k_x16` excursion was the runner, not the operation

PR #17's benchmark comment reported `swap1k_x16` **+36.3% slower every round**
on two builds of the *same library* — that branch never touched `src/`. Four
readings now exist:

| where | rounds | spread |
| --- | --- | ---: |
| this box, same code both sides | base 51.6 51.7 50.7 54.2 · head 52.0 51.6 49.8 54.6 | ±9.3% |
| CI, PR #17, base side | 53.5 55.4 57.6 53.45 | — |
| **CI, PR #17, head side** | **85.1 90.1 65.45 54.1** | **±47.8%** |
| CI, release `0.6.6` page | 50.6 | — |

Three normal readings against one excursion that decayed round by round while
the *other* build measured minutes apart stayed flat. **A batch of 16 swaps is
not an unstable measurement; that runner had a bad ten minutes inside head's
slots.** No change is needed, and the earlier lean toward reverting the batch to
a single click is withdrawn: its premise — that the batch traded ±9.7% of noise
for ±47.8% — is not what the numbers say.

What did work is the gate. `+36.3%` never counted as a regression because the
noise clause refused it: a delta smaller than the operation's own round-to-round
spread is not a result, and 36.3% is smaller than 47.8%.

## 3. Open, and the reason this file exists

The `0.6.6` page, generated 2026-08-28 on an AMD EPYC 9V74:

| | published | three other runs |
| --- | ---: | ---: |
| **Vue, `clearLarge`** | **406 ms** | 86.3 · 87.5 · 89.3 ms |
| **React, `clearLarge`** | **518 ms** | 106 · 112 · 116 ms |

Nothing else in either column moved: Preact cleared in 93.9ms and Svelte in
72.3ms in that same run, so it is not a drift the whole run shared.

**This is not one unlucky sample.** The page publishes the *median of ten*, and
those ten are taken back to back, from fresh page loads, inside the one stretch
of wall-clock time that framework's app is mounted. A runner excursion lasting a
minute takes all ten. That is exactly what §2 says happened to `swap1k_x16` on a
PR — the same weather, landing on a different victim.

What it costs, recomputed from the page's own (rounded) numbers:

| | published | with those two cells at their usual value |
| --- | ---: | ---: |
| Svelte | 3.83× | 3.83× |
| jq79 | 11.17× | 11.17× |
| Vue | **15.32×** | **13.13×** |
| Preact | 16.96× | 16.96× |
| React | **24.62×** | **21.12×** |

jq79 leads Vue either way — 11.34× against 13.07× when this box measured the
same ten operations, which is the corrected column, not the published one — but
**the published margin is inflated by a defect in the measurement of another
framework.** Had that minute landed on jq79's `clearLarge` instead, the page
would have said jq79 clears ten thousand rows five times worse than everyone,
and nothing in it would have said otherwise. That is the conversation this
session opened with.

**The A/B path earned rounds, alternation and a noise column
([`2026-08-23.where-the-create-time-goes.md`](2026-08-23.where-the-create-time-goes.md)).
The comparison page has none of the three.** It measures six frameworks in six
consecutive slots and publishes the result as if the six were comparable.

## 4. What to do

**Round-robin the comparison, and publish the spread.** Build the six apps and
start the six preview servers first, then loop *round → operation →
framework*, several rounds, and take the median across rounds rather than
within a slot. A minute of bad weather then lands on one round of everybody
instead of ten samples of one framework, and the disagreement between rounds is
measurable for the first time.

Concretely, in `scripts/run-comparison.mjs`:

- one `preview()` per app on its own port, all six alive at once (the apps are
  static builds; six servers is cheap, and it is what removes the ordering);
- the sample loop inverted: rounds outermost, framework innermost;
- per cell, the median across rounds and its round-to-round spread, both
  written to `comparison-results.json`;
- `scripts/build-site.mjs` marks a cell whose spread is beyond some threshold
  rather than printing it as a fact. A number the harness does not believe
  should not be the one the page prints in green or red.

**What it costs.** The measurement loop gets longer by roughly the number of
rounds (the install and build phase, which dominates today, does not repeat).
The results file grows a field. The page gains a caveat it can express.

**Smaller versions, if that is too much.** Re-measure only the cell that
disagrees with the rest of its own row by more than some factor, or drop the
median-of-ten in favour of a median-of-medians over three passes per framework.
Both are weaker: they still measure one framework at a time.

## 5. Not to be done, and why

- **Reverting `swap1k_x16` to a single click** — §2. The premise was wrong.
- **Lowering `GATE_MIN_MS`** — it was never lowered, and `run-ab.mjs` still
  reads 5. The change #17 made was to lift the operations above it, which is
  the direction that does not weaken the gate. `removeRow` measures 5.0-5.8ms
  and is the one sitting on the boundary; if it drifts under, it leaves the
  gate's reach and has to be repeated too, rebuilding the table between clicks,
  outside the clock.
- **Believing a release-to-release comparison of the published page.** Every
  release regenerates it on a different runner, with whatever npm serves that
  day. Only the paired A/B compares two things.
