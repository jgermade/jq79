# The depth guard lost its margin

**Status:** plan, written before `src/` was touched.

## The problem

`tests/multiTemplate.test.ts` — "cuts a component that recurses on cyclic data,
instead of dying by stack overflow" — fails on macOS arm64 / node 24.16 with
`RangeError: Maximum call stack size exceeded`. The guard it exists to prove
never fires: the stack gives out first, and what the user gets is the anonymous
overflow the guard was written to replace.

Nothing is wrong with the guard's logic. `MAX_NESTING_DEPTH = 200` is simply
above the machine's real ceiling. Moving that one constant, running the test on
its own:

| `MAX_NESTING_DEPTH` | 190 | 195 | 197 | 199 | 200 |
| --- | --- | --- | --- | --- | --- |
| | ok | ok | RangeError | RangeError | RangeError |

The ceiling is ~196 levels for this component's shape. Run under a bigger stack
(`node --stack-size=4000 ./node_modules/vitest/vitest.mjs run …`) the same 200
levels pass untouched. It is a stack budget, not a behaviour.

## When the line was crossed, and how close it always was

`git bisect` over the test names `441fc03` *perf(reactive): wake only the effects
a write concerns, not everything above it* — the commit that indexed effect deps
in a path trie. With the guard moved by hand at each end:

| | 200 | 220 |
| --- | --- | --- |
| `ba52844` (its parent) | ok | RangeError |
| `441fc03` | RangeError | — |

So the margin was never more than ~10%: before that commit the ceiling sat
somewhere in (200, 220], and the guard was already inside twenty levels of it.
`441fc03` ate what was left. It has failed on this machine ever since — checked
back to `a160d43`, and it fails at `HEAD` with or without today's other work.

This is the third time the same margin has been the thing that broke:

- `93fc2f4` — routing the synchronous first render through one shared closure
  overflowed *underneath* the guard, and the fix was to write the path out
  inline ([docs/development.md](../docs/development.md#load-bearing-invariants)).
- `2224b3b` — the render-pass memo added one frame per `:each` level, same
  symptom, same fix shape.
- `441fc03` — this one, which nobody noticed, because it does not touch the
  render path at all.

It stays green upstream because CI is `ubuntu-latest` x64 and this is macOS
arm64: different frame widths, different worker stack. A guard whose correctness
depends on the host's calling convention is not a guard.

## The proposal: 100, and a test that stops pinning the number

`MAX_NESTING_DEPTH = 100`. The number was never a feature — the guard's whole
job is to fire *before* the stack does, so that a cycle in the data gets named
instead of dying anonymously. 100 levels is far deeper than any real component
tree and leaves a margin no plausible frame-width change eats: on the machine
where 200 fails, 100 is half the ceiling.

The test stops asserting `.node` count `=== 200`. What it should hold is what
the guard promises — the render was cut, it was cut where the guard says, and it
said so on the console — not the depth the guard happens to use.

## What it costs

A component that legitimately nests itself more than 100 deep now gets cut. No
such tree exists outside a fuzzer: 100 levels of nested components is a DOM 100
boxes deep, and the data driving it would have to be 100 levels deep too.

The load-bearing invariant in `docs/development.md` — the synchronous render
path must not grow a frame, and a local added to `renderWith`/`renderNode` is a
local per level — **stays**, with its reasons intact. It is still the right rule
for the render path's cost, and both other guards (`openRenderPass`'s hand-rolled
open/close, the written-out sync render) are still doing their job. What changes
is that the *guard* no longer depends on that rule holding to within ten levels.

## Rejected: keep 200 and win back the frames

Find what `441fc03` added per level and shave it. Rejected: it treats the
symptom that showed up, on the one machine that showed it. The ceiling is a
property of the host — arm64 vs x64, worker vs main thread, node version — so
"200 fits" is not a fact the repo can hold true, and the next perf commit gets
to break the guard again. The measurements above are what the fix is; the
constant is what makes them stop mattering.

## Rejected: raise the stack in the test runner

`--stack-size` makes the test pass and makes the library's guarantee worse: the
guard would then be calibrated against a stack the browser doesn't give it.

## What is still open

- **The real ceiling is unmeasured on any other host.** 100 is chosen as "half
  of the one ceiling we measured", not from a survey. If someone hits the guard
  in a real tree, the answer is to raise it *and* re-measure, not to raise it.
- **The guard is per-component-depth, not per-stack.** It counts nesting levels
  because that is what it can count cheaply. A different shape of deep render
  (a `:each` a thousand rows wide inside a deep tree) is not what it protects.
