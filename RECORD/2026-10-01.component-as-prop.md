# A component that arrives as a prop, typed

**Status:** built the same day.

## The problem

A component can take another component as a prop (components.md, "The
signature decides where a name comes from"):

```html
<!-- Toolbar.html -->
<script :setup="{ Button }"></script>
<Button :label="'Save'" />
```

The editor extension checks a tag's props against the component it names
([2026-09-28.an-editor-extension.md](2026-09-28.an-editor-extension.md)), but
`Button` here is whatever the parent passes. Its type is `any`, so nothing is
checked on either side: not the `:label` Toolbar passes to it, nor what a
parent passes as `Button`.

It can't be inferred from the child, because two parents can pass two
different components. It can't be inferred from the parent either, because
Toolbar's template is checked once, not once per parent. What can be done is
what any typed signature does: Toolbar *declares* what its `Button` must
take, and both sides are checked against that.

## The proposal

A type in `jq79` that says "a component that takes these props":

```ts
import type { Component } from "jq79"

<script :setup="{ Button }: { Button: Component<{ label: string }> }" lang="ts">
```

- **In Toolbar**, `<Button :label="1" />` is a type error, `<Button :lable>`
  an unknown prop, and completion offers `:label`. This is the check that
  already exists for a component the checker can see.
- **In a parent**, `<Toolbar :Button="Fancy" />` is checked: `Fancy` has to
  take what Toolbar will pass it. A `Fancy` whose `label` is a `number`, or
  that requires a `title` Toolbar never passes, is an error on `:Button`.

`Component<P>` is `Component79` with a phantom property, `"~props"`, of
type `(props: P) => void`. It is optional, never set, and exists only in the
types, the way Standard Schema's `~standard` marks a vendor key. Two choices
in that shape:

- **A function type, so props are contravariant.** A component is something
  props are *passed to*. `Component<{ label: string }>` must accept a
  component that takes `{ label: string; size?: number }`, because it will
  only be passed `label`. It must refuse one that requires a `title`. A plain
  `P` would check it the wrong way round. (Without `strictFunctionTypes`
  TypeScript checks function parameters both ways, which is looser and never
  wrong.)
- **The key is the checker's own.** The editor extension already carries
  every component's props on a phantom property, for this check. It now uses
  the library's key, so a component from an `.html` file *is* a
  `Component<P>` to TypeScript, and the two can't drift apart.

## What it costs

- **Types only.** No runtime change, and nothing new in a page.
- **A new exported name**, `Component`. jq79 exports nothing by that name
  today.
- **A key in the public types that means nothing at runtime.** The `~` says
  so, by the same convention Standard Schema uses.

## Rejected

- **Inferring a component prop's type from the parents that pass it.** It
  would need every parent of every component, and the union of what they
  pass would be what the child could rely on. Nothing in the checker sees
  the whole project that way, and a new parent would change a child's errors.
- **The checker's private name in the library** (`__jq79Props`). The
  library would export a name that says "extension internals". `~props`
  says what it is.
- **A generic `Component79<P>`.** It changes the class's type for every
  user, and a class's type parameter is no phantom: it has to appear in its
  members to mean anything.

## Still open

- **JavaScript components** can declare it only where JSDoc reaches: a
  factory's `@param`. A `:setup` pattern has no place for a type in
  JavaScript.
- **Emitted events and slots** of a component prop aren't part of
  `Component<P>`. Completion on `<Button @|` offers nothing for one.

## Built

As proposed. One more piece: the brand's plain part, `Component79`, is only
named when `jq79` resolves from the file (decided when the code is generated).
An unresolved `import("jq79")` would make every props check `any`.
