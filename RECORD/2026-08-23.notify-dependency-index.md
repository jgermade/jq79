# Indexing `notify()`'s effect scan, instead of walking every effect in the store

**Status:** proposal. Nothing implemented; `reactive.ts` untouched.

## The problem (confirmed empirically, 2026-08-23 review)

`frameworks/keyed/comparison-results.json` (the js-framework-benchmark-style
suite added this week) has jq79's `partialUpdate` — writing `.label` on 100 of
1,000 rows — cost **more than building all 1,000 rows from scratch**:

| op (mean, ms) | jq79 | svelte | vue | react |
|---|---|---|---|---|
| create1k | 76.1 | 9.1 | 17.2 | 18.4 |
| **partialUpdate** (100 writes) | **189.6** | 1.1 | 5.1 | 7.8 |
| removeRow | 16.4 | 1.0 | 5.3 | 7.7 |
| selectRow | 3.6 | 1.0 | 4.4 | 7.1 |

No other framework in the comparison has a single-row update cost more than a
1,000-row rebuild. That inversion, not DOM-construction cost, is the thing to
explain — jq79 already batches inserts through a `DocumentFragment` in
`renderEach`/`renderNodes` (`src/jq79.ts`), so the create-path is not the
suspect.

The cause is `notify()`, `src/reactive.ts:139-148`:

```ts
const notify = (dotKey, value, isNewKey = false) => {
  exactListeners.get(dotKey)?.forEach(listener => listener(value, dotKey))
  anyListeners.forEach(listener => listener(dotKey, value))
  effects.forEach(effect => {
    if (isNewKey || Array.from(effect.deps).some(dep => pathsOverlap(dep, dotKey))) effect.run()
  })
}
```

`effects` is every `Effect` ever registered on the *whole store* — with a
1,000-row table that's on the order of 3,000 (three bindings per `<tr>`:
`:class`, `{{ row.id }}`, `{{ row.label }}`). There is no reverse index from a
written path to the effects that actually depend on it: every write, however
deep, walks all 3,000, and for every non-matching one allocates
`Array.from(effect.deps)` and runs `.some(pathsOverlap)` over it.

`create1k`/`replace1k`/`clearLarge` are cheap because they each fire **one**
top-level notify (`data = ...`) against a store that doesn't have the row
effects registered yet (they're created *during* that one call, not before
it). `partialUpdate` instead fires **one notify per write** — 100 of them —
each against the *already-populated* 3,000-effect store. `removeRow` and
`selectRow` pay the same per-notify cost, just fewer times; that's why they're
elevated relative to every other framework even though the work they do is
trivial in principle.

## The proposal: a path trie per store, alongside the existing `effects` set

`effects: Set<Effect>` stays exactly as it is — the `isNewKey` sweep (any
write to a genuinely new key must still wake everyone; see rationale in
`reactive.ts:143-145`) keeps using it unchanged, and it remains the source of
truth for the store's effect membership.

Add a second, private structure per store: a trie keyed by dot-path segment,
where each node holds the `Set<Effect>` of effects whose dep string is
*exactly* that node's path (not a prefix — the exact string, same units
`pathsOverlap` already compares).

```
type TrieNode = { children: Map<string, TrieNode>; own: Set<Effect> }
```

`pathsOverlap(dep, dotKey)` is `dep` is a prefix-or-equal of `dotKey`, OR
`dotKey` is a proper prefix of `dep`. The trie answers both halves directly
instead of scanning:

- **ancestor-or-equal** (`dep` prefixes `dotKey`): walk the trie down
  `dotKey`'s own segments (`"data"` → `"data.5"` → `"data.5.label"`),
  collecting each visited node's `own` set. Cost: O(depth of `dotKey`), a
  handful of Map lookups — not O(effects in the store).
- **proper descendant** (`dotKey` prefixes `dep`): once the walk above lands
  on the node for the *full* `dotKey`, recurse into just that node's
  `children` and collect their `own` sets. Cost: O(effects actually rooted
  under that path) — for a leaf write like `data.5.label` this subtree is
  empty; for a shallow write like the top-level `data` reassignment it's
  everything under `data`, same total cost the flat scan already pays today,
  paid only on the rare shallow writes instead of on every write.

Collect matches from both halves into one `Set<Effect>` (a node can be found
by both directions in principle) before calling `.run()` on each, so nothing
double-fires.

### Keeping the trie in sync with `effect.deps`

`effect.deps` isn't fixed at registration — it's recomputed on every run
(`reactive.ts:322-331`), and can name different paths than last time
(conditionals, `:if` branches). The trie has to track that, including across
`$__attach` (`ATTACH`, `reactive.ts:110`), where the same `Effect` object is
registered on more than one store — a scoped-slot effect that reads both the
parent's and the child's store needs *both* stores' tries updated on every
run of that one effect, not just its own store's.

Give `Effect` a small `reindexers: Set<(oldDeps, newDeps) => void>`. Each
store's registration path (`$effect`'s own add, and `$__attach`) pushes one
closure — bound to that store's trie — onto it, and removal
(`effects.delete`, and `$__attach`'s detach) drops it again. `effect.run`,
once a full settle completes (after the `dirty` loop in
`reactive.ts:320-338`, not per inner pass — only the final pass's deps are
ever meaningfully "current"), calls every registered reindexer with the old
and new dep sets before overwriting `effect.deps`. Each reindexer does the
trie's remove-old/insert-new walk: O(depth) per dep, same order as the
lookup.

Node pruning: removal walks back up deleting now-empty nodes, so effects that
come and go (rows added/removed across `:each` diffs) don't leave a
permanently growing trie.

## What it costs

- A trie per store: memory roughly proportional to the number of *distinct*
  dep paths currently held by live effects — same order as `effects.size`
  itself, just spread across nodes instead of one flat set.
- Every effect run does O(depth-of-each-dep) trie maintenance instead of
  nothing. Depth is small (2-4 segments in this app); negligible next to the
  O(store-size) cost it replaces.
- Structural change to the hottest, most heavily-pinned file in the codebase
  (`tests/reactive.test.ts`, 558 lines). The trie must reproduce
  `pathsOverlap` exactly, including the documented quirk pinned at
  `tests/reactive.test.ts:541` (a flat key containing a literal dot collides
  with the equivalent nested path) — splitting every dotKey on `"."` for trie
  segments reproduces that collision by construction, so it's preserved for
  free, not something to special-case.
- The `isNewKey` sweep stays O(all effects in the store). Confirmed above:
  none of the nine benchmarked operations hit it (every write in
  `App.html`'s handlers targets a key that already exists), so it's out of
  scope here — not because it's fine in general, just not what this
  benchmark is measuring.

## Rejected

- **Bucket by top-level key** (`Map<firstSegment, Set<Effect>>`): every row's
  bindings share the same top-level key (`"data"`), so every write would
  still land in one 3,000-effect bucket. Doesn't touch the actual problem,
  which is depth, not breadth.
- **Cache `pathsOverlap` results**: makes the per-comparison cost cheaper,
  not the O(effects) iteration count — still linear in total store effects
  per write, so `partialUpdate` stays superlinear in list size. Treats the
  symptom.
- **Batch/microtask-coalesce writes** (a Vue/React-style scheduler): would
  hide this specific benchmark shape by merging the 100 writes into one
  flush, but changes the synchronous update model the project has
  deliberately kept — see `docs/development.md` and
  `RECORD/2026-07-15.effect-runner-hardening.md`'s rejection of batching for
  the reentrancy problem: no scheduler, no microtask, no flush timing, tests
  stay await-free. Out of scope on principle, not just effort.
- **Flat `Map<dotKey, Set<Effect>>` (no tree) for both directions**: gives
  O(depth) ancestor lookups for free (build the prefix strings, look each up)
  but can't answer "every dep that starts with this write's dotKey" without
  either a real tree or scanning all distinct paths — and distinct paths are
  ~as numerous as effects here (one row = one set of unique index-based
  paths), so the descendant half would stay O(effects). A real trie answers
  both directions in the same structure at the same cost.

## Open

- Whether `reindexers` should live as a field on `Effect` (this proposal) or
  the store should instead keep its own `WeakMap<Effect, Unsubscribe[]>` —
  functionally equivalent; the field is simpler because `effect.run` already
  needs to reach it without a lookup.
- No decision yet on whether disposal-time pruning should be eager (walk up
  and delete empty nodes on every removal, as sketched above) or deferred
  (mark dead, sweep periodically) — eager is simpler and this doesn't seem
  hot enough to need deferral, but untested against the `appendToLarge`/
  `clearLarge` operations specifically.

## 2026-08-23 (same day) — implemented, measured, and the diagnosis above is wrong

The trie landed as proposed (`src/reactive.ts`: `TrieNode`, `insertDep`,
`removeDep`, `effectsFor`, `indexEffect`, `reindex` on `Effect`), 728 tests
green, `pathsOverlap` gone. **It bought nothing.** Measured on one machine,
same app, same methodology, 10 samples, before vs after:

| op (mean, ms) | before | with the trie |
|---|---|---|
| create1k | 82.6 | 121.5 |
| replace1k | 75.3 | 75.7 |
| **partialUpdate** | **171.9** | **173.4** |
| selectRow | 3.8 | 3.9 |
| removeRow | 17.3 | 21.7 |

The proposal identified a real inefficiency and called it the cause without
checking that it was. It was not: counting effect runs (rather than timing
them) shows what actually happens on those 100 writes.

```
1,000 rows, 1 list effect + 1,000 `{{ row.label }}` effects
100 × `data[i].label += "!!!"`   →  174.5ms
  list effect runs:     100  (item reads inside them: 100,000)
  label effect runs: 100,000
```

**Every write wakes every effect in the list.** Not because the scan is
linear — because they genuinely match. Reading `store.data[7].label` walks
three proxies and tracks all three paths: `"data"`, `"data.7"`,
`"data.7.label"`. That `"data"` dep is on every row's effects, and a write to
`data.5.label` is its descendant, so all 1,000 wake — plus the `:each` list
effect, which re-diffs 1,000 items. 100 writes × ~1,000 effects = 100,000
runs. An index over the same matching rule finds the same 1,000 effects
faster; the cost is the rule, not the lookup.

### What Svelte does instead (`svelte@5.46`, `internal/client/proxy.js`)

One `source` (signal) per property, held in a `Map` on each proxy — and
**no ancestor/descendant propagation at all**. Writing `obj.a.b` sets `b`'s
source; `a`'s source is untouched, so an effect that read `a` but not `b`
never wakes. What jq79 gets from its descendant rule, Svelte gets from two
explicit signals:

- `var version = source(0)`, per object, incremented **only when a key is
  added or removed**, and read **only by the `ownKeys` trap`** — so
  iteration and `Object.keys` stay reactive without every property write
  waking every iterator.
- `sources.set('length', source(value.length))`, created eagerly for arrays,
  so array growth/truncation has a real dependency to wake.

jq79's descendant rule is a coarse stand-in for both: it has no `ownKeys`
tracking and no per-object version, so "someone might be iterating this"
is answered by waking everything underneath. That is exactly the 100,000.

### Measured: what dropping the ancestor half costs

Behind a scratch flag, `effectsFor` was made to collect `own` only at the
node it lands on (dep is the write, or below it), skipping the nodes the
walk passes through (dep is an ancestor of the write):

```
100 × `data[i].label += "!!!"`   →  1.0ms   (was 174.5ms)
  list effect runs:     0
  label effect runs:  100        (one per write, which is the correct number)
```

**174.5ms → 1.0ms**, i.e. the whole gap to Svelte's 1.1ms on this operation.
The full suite under that flag: **10 failures out of 728**, and they name
precisely what the ancestor rule is standing in for:

- 7 in nested/bridged stores — "wakes the holder's effects when the store
  inside it changes", "carries a change up through a chain of stores",
  "keeps props live: deep parent mutations update the child", … The bridge
  re-notifies an inner change under the path it sits at (`"items.0"` →
  `"cart.items.0"`) and **drops `isNewKey` on the way through** (`$onAny`
  doesn't carry it), so a new key arriving from an inner store is only ever
  caught by a holder's ancestor dep.
- 1 array-length case — "truncating an array via length wakes effects
  reading its items", whose own comment says it relies on the rule.
- 2 integration tests downstream of the first group (the tutorial's
  highlight layer, `03-components/03`).

Nothing else in 728 tests depends on it.

### Where this leaves the trie

Inert on its own, and a prerequisite for the fix: once the wake set is one
effect instead of a thousand, a linear scan of every effect in the store to
*find* that one becomes the next bottleneck. Committed as substrate, with
this section as the reason it looks like it does nothing.

### Open — the actual proposal, not yet written

Replacing the ancestor rule needs jq79-shaped answers to the three things
Svelte spends signals on. None of these are decided:

- **Key add/remove**: a per-object version dep, tracked from an `ownKeys`
  trap the proxy doesn't currently have. Today's `isNewKey` full sweep is
  the coarse version of this and would ideally go at the same time.
- **The bridge dropping `isNewKey`**: `$onAny` would have to carry it, or
  bridges would need a channel that isn't `$onAny`.
- **Arrays**: whether `length` needs the eager source Svelte gives it, or
  whether the existing `length` notification is enough once the rule is
  narrowed (the one failing test suggests it is not).

Whether this is worth it is a real question and not settled here: it trades
a rule that over-wakes (never stale, sometimes slow) for one that needs
three mechanisms to be right (fast, stale if any of them is missed). The
174.5 → 1.0 is what is on the table.
