# An editor extension for components

**Status:** plan for three phases. Phase 1 (grammars) is built alongside it, in
[`editors/vscode/`](../editors/vscode/); phases 2 and 3 are plans only.

## The problem

The appended section of
[2026-09-06.typescript-in-setup-scripts.md](2026-09-06.typescript-in-setup-scripts.md)
added `type="text/typescript"` as a second mark because "that is what editors
read". Three weeks later, the opposite was reported:

> vscode sólo me colorea el código cuando lang="ts/typescript", pero no con type

Both reports are true. VS Code reads an inline `<script>` with two systems, and
each one looks at a different attribute. Read in VS Code's source (1.139):

| | reads | `lang="ts"` | `type="text/typescript"` |
|---|---|---|---|
| **Coloring**: the TextMate grammar, `extensions/html/syntaxes/html.tmLanguage.json` | `type` against a list of JS media types, and nothing else | ignores `lang`, so the block is `source.js`. The JS grammar is generated from the TypeScript one, so the annotations color fine | a `type` that isn't JS gets `source.unknown`: **no color at all** |
| **Checking**: the HTML language service, `extensions/html-language-features/server/src/modes/embeddedSupport.ts` | `type`: `text/typescript` (exactly, quoted) is TypeScript, and no `type` is JavaScript | JavaScript: "Type annotations can only be used in TypeScript files" on every annotation | TypeScript |

So in stock VS Code no mark gets both. And the TypeScript the service offers for
`type` is no prize either: it checks every inline script as a file of its own,
with `lib.es2020.full.d.ts` and nothing else (`javascriptMode.ts`), so a setup
script's implicit names (its props, a `$:` target, `$mounted`) are all
"Cannot find name". A `<style lang="scss">` has only the first half of the
problem: it is colored as CSS.

None of this can be fixed in `src/` or `dev/`. Both of VS Code's systems are
keyed to the attribute, not to jq79, and neither can be taught about jq79 from a
component. That takes an extension.

## The proposal: an extension, in three phases

| phase | what | size |
|---|---|---|
| 1 | Grammars: `script[lang]`, `style[lang]`, `` Component79(`…`) `` and `` lang`…` `` literals colored in their language | small, built |
| 2 | A language server: scripts and styles checked, completed and hovered in their language, jq79's implicit names included, plus a `check` CLI for CI | medium |
| 3 | Template expressions (`{{ }}`, `:attr`, `@event`, `:each`) checked against the component's scope | large |

Phase 1 stands on its own. Phase 2 is the one that answers "can it also be
validated?". Phase 3 needs phase 2's model of a component's scope.

## Phase 1: injection grammars

Four injection grammars (`editors/vscode/syntaxes/`) that VS Code layers on its
own. An injection's selector says where it applies, and an `L:` selector wins
over the host grammar's own rules at the same position. So `<script lang="ts">`
is matched before VS Code's `<script>` rule gets to it, and everything the
injection doesn't match is left to VS Code as it was.

- **`script-lang`**: a `<script>` carrying the TypeScript mark becomes
  `source.ts`. It copies VS Code's own `<script>` rule, with `source.ts` in place
  of `source.js`. Which blocks count is the plugin's `typescriptAttr` in
  [`dev/vite.ts`](../dev/vite.ts), rule for rule: `lang="ts"` or
  `lang="typescript"` in any quoting, or a TypeScript `type` only when there is
  no `lang`. A lang answers on its own. So `type="text/typescript"` now gets
  color from the extension and TypeScript checking from VS Code, and
  `lang="ts"` gets color and JavaScript checking.
- **`style-lang`**: `<style lang="scss|less|sass|styl|stylus">` in the language
  it names. `scss` and `less` ship with VS Code. `sass` and `stylus` only get
  colored when an extension for them is installed. Without one, the block goes
  uncolored rather than wrong. That needed the content in a rule of its own:
  vscode-textmate drops a rule whose only include is a missing grammar, and when
  the content shared a rule with the tag's `>`, dropping it also took the `>`'s
  scopes and left the tag unterminated. A test covers both sides.
- **`template-literal`**: the source passed to `Component79(`…`)` is HTML,
  because it is a component. So are literals tagged `html` and `svg`. The tags
  `css`, `scss`, `less`, `js` and `ts` get the language they name. Component79's
  match starts at the backtick and uses a lookbehind for `Component79(`, so the
  call itself is still the JS grammar's to color. The HTML is VS Code's
  *derivative* grammar, the one `.html` files use, so `<UserCard>` is a tag and
  not `invalid.illegal`. The embedded HTML still goes through `script-lang` and
  `style-lang`, so a component string's `<script lang="ts">` is TypeScript.
- **`template-substitution`**: `${…}`, `\${` and `` \` `` inside those literals.
  This is its own injection and not a pattern of the literal's rule, because
  when the embedded grammar meets a `${` it is usually several rules deep (in a
  tag, in an attribute value), where only an injection reaches.

### What it can't do, and why

TextMate reads one line at a time, and a rule's end is only tested while that
rule is the innermost open one. Every limit follows from those two facts:

- **The mark must be on the line the tag opens on.** When it isn't, the block is
  what VS Code makes of it without the extension, which is JS. A test holds that
  fallback.
- **A one-line JS/TS statement left open runs past the backtick.** In
  `` js`let x = 1` ``, the JS grammar's rule for the declaration is still open
  at the backtick, and it reads that backtick as the start of a template of its
  own. `` js`let x = 1;` `` and a closing backtick on its own line are fine.
- **A `//` comment after code on the closing line swallows `</script>`.** VS
  Code's HTML grammar does the same to plain JS. Only a comment that starts a
  statement is handled, again as VS Code does it.
- **It applies to every `.html` file.** A grammar can't tell a component from a
  page. This is harmless in practice, because `lang` on a `<script>` means
  nothing to a browser and so is rarely found outside jq79.

### Rejected

- **Owning every `<script>` rule, so a mark on a later line could still be
  read.** The decision has to be made at `<script`, and a rule that took every
  script would have to re-implement VS Code's `type` handling (JS media types
  and `module` as JS, template types as HTML, anything else uncolored) and then
  drift from it. The other way in, worked through on paper rather than built,
  doesn't work either: injecting at the `lang` attribute, mid-tag, and running
  to `</script>` from there. VS Code's attribute rule only ends at a `>`, and
  once it has, its next rule opens the content as JS again, running to the
  *next* `</script>` in the file.
- **Vendoring VS Code's grammars for the tests.** They are about 1MB of
  somebody else's JSON. The tests fetch them once instead
  ([`test/fetch-grammars.mjs`](../editors/vscode/test/fetch-grammars.mjs)),
  pinned to one release in `VSCODE_TAG`. Bumping the pin is how to find out
  whether a newer VS Code broke an injection.
- **A separate repository.** The rule for which blocks are TypeScript lives in
  the plugin. The extension copies it, and the two should change in the same
  pull request.

### Tested how

[`test/grammars.mjs`](../editors/vscode/test/grammars.mjs) tokenizes with
vscode-textmate and VS Code's own grammars, and registers each injection for the
grammars its `package.json` `injectTo` lists, the way VS Code does. So a test is
also a test of the manifest. `node test/tokenize.mjs <scope> <file>` prints
every token of a file with its scopes, which is the fastest way to see why an
assertion failed. A workflow
([`vscode-extension.yml`](../.github/workflows/vscode-extension.yml)) runs the
tests when `editors/vscode/` changes. Nothing in `src/` or `dev/` reaches the
extension, so it runs only then.

## Phase 2: a language server (plan)

**Why a grammar can't do it.** Squiggles, completion and hover come from a
language service, and VS Code's HTML service decides an inline script's language
by itself, as the table above shows. VS Code does let an extension forward
requests for an embedded block to the service of its language
(`executeCompletionItemProvider` and the like), but only for requests. There is
no way to forward diagnostics, because diagnostics are pushed, not requested. So
checking needs a server that runs TypeScript itself.

**How: a [Volar](https://volarjs.dev) language plugin.** Volar is the framework
under the Vue, Astro and MDX tooling. It is built for exactly this: a plugin
turns a file into *virtual code* (one `.ts` per script and one `.scss` per style
here) together with source maps. Volar then runs the real TypeScript with the
project's `tsconfig` (so `import type` resolves) and maps every diagnostic,
completion, hover and rename back onto the `.html`. The same plugin runs from a
CLI, as `vue-tsc` does, which gives CI a `check` without an editor.

**The virtual code is where the work is.** If it doesn't reproduce jq79's
semantics, the result is the same false errors VS Code's service gives today.
Here is what reaches a setup script, and what each thing becomes:

| in the component | what the runtime does | in the virtual `.ts` |
|---|---|---|
| `:setup="{ step = 1 }: Props"` | the props pattern | the parameter of the function the body is wrapped in |
| top-level `let` / `const` | a store variable; reactivity doesn't change its type | as written |
| `$: doubled = count * step`, `doubled` undeclared | declares it on the store | `let doubled = count * step` (svelte2tsx does the same) |
| an assignment to a name declared nowhere | goes to the store, not to `globalThis` (the `has` trap in `runSetupScript`) | a declaration, like a `$:` target |
| `$`, `$$`, `$create`, `$reactive`, `$toRaw`, `Component79`, `$mounted`, `$self`, `$$self`, `$emit`, `$updateModel`, `$slots` | positional parameters (`SETUP_HELPER_NAMES`, `INSTANCE_HELPER_NAMES` in [`source.ts`](../src/source.ts)) | declared from a `jq79/types` module that doesn't exist yet |
| top-level `await` | the body runs in an async IIFE | an `async` function |
| `import` | hoisted | at module top, and `declare module "*.html"` for components |
| a factory script (`export default`) | plain lexical JS | as written |

**What makes this tractable is that jq79 already has the parser.**
[`source.ts`](../src/source.ts) reads a component as text with no DOM, and
[`transform.ts`](../src/transform.ts) knows which top-level declarations become
store variables. The generator can call both, so what the checker sees is what
the runtime compiles *by construction*, not by a second implementation keeping
up with the first. Neither is exported today. The extension either bundles them
from source, or the package exports them.

**Styles** are the easy half: `vscode-css-languageservice` already checks css,
scss and less, and Volar has a service for it.

**What it costs.**

- TypeScript and Volar as dependencies of the extension, and never of the
  library. They are about the size of Vue's tooling.
- Volar's API changes between majors, and the extension has to follow it.
- A virtual-code generator that must track the runtime's semantics. Drift shows
  up as false errors, so the corpus that holds it is the tutorial: every
  exercise solution must check clean, just as every one already has to mount
  ([`tests/tutorial.test.ts`](../tests/tutorial.test.ts)).
- VS Code's HTML service keeps checking scripts as JS or TS alongside it, so its
  diagnostics would be duplicated and wrong. The extension has to turn it off
  (`html.validate.scripts: false`), ideally by default.

## Phase 3: template expressions (plan)

The same scope model, applied to the markup. Every `{{ }}`, `:attr`, `@event`,
`:each="user of users"`, `:with` and scoped slot becomes a small function in the
virtual code, typed against the component's store and props. This is what Vue's
template type-checking does. It is the largest phase, and it depends entirely
on phase 2 getting the scope right.

Coloring those expressions as JS is separate from checking them, and cheap. It
is a grammar change, and could come as a phase 1b before any of this.

## Appended 2026-09-30: phase 1b, the template syntax, is built

The open item *Phase 1b* is closed. Two more injections in
[`editors/vscode/syntaxes/`](../editors/vscode/syntaxes/):

- **`template-attribute`**: the value of every `:name` and `@name` attribute is
  read as a JS expression (`source.js#expression`, the rule Vue's grammar uses:
  an expression, not a statement, which is also all jq79 accepts there, since
  it compiles each one as `return (…)`). Three are not expressions and have a
  rule of their own: `:each`, whose bindings (`EACH_PATTERN`) are colored as
  parameters and whose `in` is an operator; and `:setup` and `:slot[.name]`,
  which are a parameter pattern and are read with the TypeScript grammar's
  `function-parameters-body`, so `{ step = 1 }: Props` gets its type colored in
  a JS component too. `...spread` is an attribute with no value and is colored
  as a spread. Each rule copies the shape of VS Code's `attribute-interior`
  (name, then `=`, then a quoted or unquoted value), so the quotes keep their
  HTML scopes.
- **`template-interpolation`**: `{{ … }}` in text as JS, ending at the first
  `}}` as `INTERPOLATION_RE` does. Not in a tag, a `<script>`, a `<style>` or a
  comment, which is where the runtime doesn't read it either.

### The one thing that had to be designed

The first version put the embedded grammar straight inside the quotes, and
`:setup="{ step = 1 }: Props"` ran to the end of the file. The TS grammar's
type annotation is a rule whose end is a lookahead for `,`, `)` or `=`, and a
closing `"` is none of those. So the annotation was still open at the quote,
and only the innermost rule's end is tested (the limit from phase 1). What the
fix does instead is match each line's stretch of a value (`[^"]+`) as one token
and hand it to the embedded grammar through the match's `captures`.
vscode-textmate tokenizes a capture on its own and closes whatever is open at
its end, so nothing inside a value can outlive its quote. `{{ }}` does the same
with `(?:[^}]|}(?!}))+`.

What that costs: state across lines of one value. A template string or a
`/* */` comment spanning two lines of an attribute is colored as if each line
started over. Expressions that span lines are otherwise fine (a chain of
`.filter()` / `.length`, an `&&` per line). This was preferred over the
alternative, keeping state and accepting that one unclosed construct recolors
the rest of the file, because in an editor it's the second failure that people
report.

### Two selectors for `{{ }}`

A selector can't say "the innermost `text.html`". `{{ }}` has to be excluded in
a page's `<script>` (`text.html … source.js`), yet included in a component
string that sits *inside* that script (`text.html … source.js …
meta.embedded.template-literal.jq79 text.html.basic`), whose stack contains the
same pair. So the injection has two selectors: a page's text, with no
template literal in the stack, and a component string's text, where the
exclusions are written relative to `meta.embedded.template-literal.jq79`. Both
cases have a test. The attribute injection doesn't need this: its exclusion,
`meta.tag source`, only matches a `source` *below* a tag, which is its own
value.

### Still open

- **Coloring is not checking.** A misspelt name in `{{ usr.name }}` is colored
  like a correct one. That is phase 3, and still needs phase 2 first.
- **`{{ }}`, `:attr` and `@event` are colored in every `.html` file.** Vue,
  Alpine and Angular templates use the same spellings for the same thing
  (JavaScript), so the coloring is right there too. A plain page that happens
  to write `{{` in its text gets it colored as JS. That seemed acceptable for
  the same reason as `lang` in phase 1.
- **`/* html */`** is still unhandled, and still not needed for jq79's case.

## Appended 2026-09-30: phase 2, the language server, is built

The server is in [`editors/vscode/src/`](../editors/vscode/src/): a Volar
language plugin ([`language.ts`](../editors/vscode/src/language.ts)), the
server ([`server.ts`](../editors/vscode/src/server.ts)) with Volar's TypeScript
and CSS services, a client ([`extension.ts`](../editors/vscode/src/extension.ts)),
and `jq79-check` ([`check.ts`](../editors/vscode/src/check.ts)), the same
checker from a terminal. The work is in the virtual-code generator,
[`component.ts`](../editors/vscode/src/component.ts), as this file predicted.

### The open question, answered first

*Whether multiple scripts in one component share a store.* They do.
`renderWith` builds one store per instance and runs every script against it
(`this.scripts.forEach`). So a name one script declares is visible in the
others. The virtual code declares each component's store names once, at the
component's level, as `any`, and each script's own declarations shadow them
with their real types. So inside the script that declares `count` it's a
`number`, and in the others it's `any`. Inferring the type across scripts would
need them in one scope, and they are separate functions at runtime.

### What the virtual code is

One virtual file per `.html`, not per script. It is `.ts` when any script in
the file carries the TypeScript mark, and `.js` otherwise:

```ts
declare const $mounted: () => Promise<void>; …              // the helpers, typed from "jq79"
export default __jq79Component                               // import X from "./X.html" gets a component
{                                                            // one block per component of the file
  let count: any; let doubled: any                           // the store: every script's names
  const Row = __jq79Component                                // siblings not taken by a prop
  async function __jq79Setup0(__props: any) {
    let { step = 1 }: Props = __props                        // the :setup pattern, mapped from the attribute
    let count = 0                                            // the script, mapped
    let doubled = count * step                               // `$:` → `let` when nothing declares it
    ;return { step, count, doubled }                         // read by the template: not "unused"
  }
}
```

Each row of the table in *Phase 2* is there, and each has a test in
[`test/check.mjs`](../editors/vscode/test/check.mjs). Decisions the table didn't
settle:

- **`.js` for JavaScript components, not `.ts`.** As `.ts`, every untyped
  parameter and every expando object would be an error under `strict`. As
  `.js`, a JavaScript component is checked the way any JS file is: completion
  and hover always, types when `checkJs` says so. `jq79-check --checkJs` turns
  that on.
- **The TypeScript parser, not `transform.ts`, finds what to rewrite.** Store
  names, factory detection and the props pattern come from the runtime's
  functions, as planned. But the rewrite needs positions (where a `$:` is,
  which `import(` calls to replace, which names are assigned and never
  declared), and `transform.ts` returns code, not positions. The AST is used for
  those, and only where the answer can't disagree with the runtime's scanner
  about which statements are top-level.
- **Static imports stay where they are in a setup script.** The runtime compiles
  a setup script as a function body, where `import x from` is a SyntaxError
  (only `await import()` works, per setup-scripts.md). So TypeScript's
  "An import declaration can only be used at the top level" is the right
  error, on the right line. In a factory script they are hoisted, which is what
  `transformFactoryScript` does too.
- **`import()` of an `.html` or a URL becomes the runtime's `$__import`**, and
  gives a component or `any`. A relative or bare specifier to anything else is
  left alone, so TypeScript resolves the module and knows its types.
- **The helpers' types.** `$`, `$$`, `$create`, `$reactive`, `$toRaw` and
  `Component79` are `typeof import("jq79").…`, so they follow the library's own
  declarations. When the project doesn't resolve `jq79` (a CDN import), the
  failing import is in unmapped code, so nothing is reported and they become
  `any`. The per-instance ones (`$mounted`, `$self`, …) have no exported type,
  so their signatures are copied from `renderWith`. A factory's `ctx` is typed
  the same way, through a `__Jq79Factory` type on the default export.
- **`$: schedule(query)` is not "Expected 0 arguments".** Passing the
  dependencies as arguments is the documented idiom (setup-scripts.md). The
  arguments of the call a `$:` labels are mapped with
  `verification.shouldReport` returning false for TS2554, and nothing else.
  Getting that to hold took a detail of Volar's worth knowing: it maps a
  diagnostic back with `fallbackToAnyMatch`. So a range whose two ends touch
  the mappings on either side is mapped through *those* and reported anyway.
  The filtered range includes the parentheses, so the arguments sit strictly
  inside it.
- **Plain `<style>` is left to VS Code**, which already checks it as CSS. The
  server takes `scss` and `less` only, so no problem is reported twice.
- **Pages are skipped.** A file with `<!doctype>`, `<html>`, `<head>` or
  `<body>` is not a component, and its scripts are the browser's.
- **TypeScript 5.9 ships inside the extension.** `typescript@latest` is 7,
  the native compiler, and it has no JavaScript API; Volar is built on that API.
  So the server can't use the workspace's TypeScript or VS Code's, and the
  extension carries its own (5.2 MB `.vsix`).
- **`html.validate.scripts` is turned off by the extension**
  (`configurationDefaults`). That answers the last open item of the first
  section as far as the manifest goes: the extension sets it, though it
  hasn't been seen taking effect in a running VS Code (see below). Without it,
  VS Code's
  service reports every script a second time as JavaScript, wrongly. The cost:
  the setting also covers pages' inline scripts, which this server doesn't
  check. The README says so and how to turn it back on.

### The split needs offsets the runtime doesn't keep

The runtime and precompile find a file's components with `parseHTML` over
`prepareSource(text)`. That text is rewritten before it is parsed (name case,
spreads, self-closing tags), and the parse keeps no positions. A checker needs
positions, so `splitComponents` in `component.ts` is a second, smaller split
over the original text. It tracks `<template>` depth, skips comments, and reads
`<script>`/`<style>` as raw text. It follows parseComponentString's rules:
a top-level `<template name>` with a valid, untaken name is a component, and
a script inside a nested `<template>` belongs to none. It diverges in one
place: a `<script>` inside some other element is taken here and ignored at
runtime. That's rare enough not to be worth a full HTML parser with positions.

### How it was tested

- **The corpus.** Every component in `tutorial/` (64 files, the `_app`
  included) checks with no errors or warnings. With `checkJs`, what is left is
  five errors, all DOM typing that is TypeScript's own rather than the
  generator's: four `$self(...).focus()`/`.value`, because `$self` returns
  `Element` as `$` and `querySelector` do, and one `ChildNode.outerHTML`. The
  test holds that set: any other error under `checkJs` fails it. Getting there
  found the `$:` idiom above, and that props and `$:` targets were "declared but
  never read" until the virtual code returned them.
- **Fixtures**, one per row of the table, asserting the exact diagnostics and
  where they land in the `.html`.
- **The server over LSP**
  ([`test/server.mjs`](../editors/vscode/test/server.mjs)): `dist/server.js` in
  its own process, spoken to over stdio as VS Code would, answering
  diagnostics, hover (`doubled: number`) and completion (`$emit`). It was also
  run against the server unpacked from the `.vsix`, to check that the packaged
  TypeScript is found.
- **Not tested: a real VS Code.** Downloading one is blocked by the network
  policy of the environment this was built in. The client is type-checked
  against `@types/vscode`, and it's thirty lines of `vscode-languageclient`, but
  activation, the `configurationDefaults` override and the interaction with
  VS Code's own HTML service have not been seen running.

### Rejected

- **A virtual file per script.** Scripts share one store, and a factory's
  default export and the file's `import X from "./X.html"` both want one module
  per file. One file per `.html`, with a block per component, gives both.
- **Declaring every name a script reads but nobody declares.** At runtime such
  a read is `undefined` (the scope's `has` trap answers for any name that isn't
  a global), so it is never a ReferenceError. But it is almost always a typo,
  and a component that wants a name from its parent should declare it in its
  `:setup` pattern (components.md). So a read is an error and an assignment
  isn't. This is where the checker is stricter than the runtime, on purpose.
- **Bundling TypeScript into the server with esbuild.** It is ~9 MB of CJS
  that also loads its lib `.d.ts` files from disk next to itself. It ships as
  an ordinary dependency.

### Still open

- **Publishing `jq79-check`.** It is built into the extension's `dist/` and
  runs from a clone. It can't be a bin of the `jq79` package, which must not
  depend on TypeScript or Volar. It would be a package of its own, which is
  the author's to name and publish, with the Marketplace and Open VSX accounts
  that are already open.
- **`$` and `$self` return `Element`.** It is the honest type (it is what
  `querySelector` returns), and it's why `$self("input").focus()` is an error
  under `checkJs`. A generic `$self<E extends Element = HTMLElement>` would read
  better in components, but it's a change to the library's types
  (`src/dom.ts`), not to the checker, and it hasn't been made.
- **Components inside `` Component79(`…`) `` strings** are colored but not
  checked. The plugin would need to read JS/TS files and find the literals.
- **Phase 3.** The template's expressions, against the store the virtual code
  already returns from each setup function (`return { step, count, doubled }`)
  - that return is there for noUnusedLocals today, and is the store's type

## Appended 2026-10-01: phase 3, the template, is built

Every expression a template evaluates is checked against the scope the
runtime evaluates it in. It lives in
[`template.ts`](../editors/vscode/src/template.ts), with changes to
[`component.ts`](../editors/vscode/src/component.ts) so the scripts' code
exports what the template needs. As this file said, phase 3 rested on phase 2
getting the scope right. Two things phase 2 got wrong only showed up once the
template read them; both are below.

### Two virtual files

The template's code is a second virtual file, `<file>.html.template.ts`, beside
the scripts' one (Volar's "extra service script"). It is **always
TypeScript**, and that is the reason for the second file. The scripts' file is
`.js` in a JavaScript component, and TypeScript only type-checks a `.js` under
`checkJs`. In one file, a JavaScript component's template would only be checked
with `checkJs` on, which leaves out most components, and the tutorial's. As TypeScript,
the template is checked everywhere, against the types TypeScript infers for a
JavaScript store.

The scripts' file exports one function per component that runs its scripts and
returns its store. The template's file imports its type:

```ts
// Card.html (the scripts)                         // Card.html.template.ts
export async function __jq79Component0() {         import type * as __jq79Scripts from "./Card.html"
  async function __jq79Setup0(__props) {            async function __jq79Template0() {
    let todos = [{ text: "a" }]                       const __s = … as Awaited<ReturnType<typeof __jq79Scripts.__jq79Component0>>
    ;return { get todos() { return todos } }          let { todos } = __s
  }                                                   for (const [todo, i] of __jq79Each(todos)) {
  return Object.assign({}, await __jq79Setup0(…))       const $index = 0 as number
}                                                       (todo.text);   // ← mapped from {{ todo.text }}
                                                      }
                                                    }
```

### Decisions

- **The store is returned through getters.** A value returned at the end of
  the setup function has the type control flow narrowed it to there. So
  `let user: User | null = null`, assigned in a callback, is `null` at the
  return, and `{{ user?.name }}` read `never`. A type query (`typeof user`)
  is narrowed the same way; both were tried. A getter is a closure, and in a
  closure TypeScript reads a reassigned `let` at its declared type. Its cost is
  TS7034 ("implicitly has type 'any' in some locations") on an unannotated
  `let x = null` under `noImplicitAny`. It is reported on the declaration
  because of the getter, not the script, so setup scripts' mappings drop that
  one code.
- **Only what reaches the store is in the template's scope.** That means props,
  top-level `let`/`const`/`var`, `$:` targets, siblings, `$emit`,
  `$updateModel`, `$slots` and the globals. A top-level `function` is *not*:
  `transformSetupScript` leaves it a lexical binding, and the runtime warns
  about exactly this trap (`MISSING_NAME_RE` in jq79.ts). Phase 2 returned
  functions too, and that would have hidden the error. A test holds it now.
- **The store's names in a TypeScript script come from the AST.** At runtime
  `transformSetupScript` reads the script *after* the Vite plugin has stripped
  its types. On the source, `let count: number = 0` isn't a declaration to it.
  Phase 2 never noticed, because it only used those names to declare `any`s.
- **What a name the store doesn't have means depends on the signature.** A
  component that declares one takes only those props (components.md, "A
  signature is a contract both ways"), so an unknown name is an error. One
  that declares none (`_`, a script with no `:setup`, a factory's `_`, no
  script) takes whatever its parent passes, so "Cannot find name"
  (TS2304/TS2552) is dropped from its template's mappings. Any other error
  stays.
- **`:each`** becomes `for (const [item, i] of __jq79Each(list))`, with
  overloads for an array (item, index), `null`/`undefined` (nothing) and an
  object (value, key), plus `$index`. The bindings and the list are mapped, so
  an error in either lands on the attribute.
- **`@event`** declares `$event` as the DOM's type for a known name
  (`HTMLElementEventMap`) and as a `CustomEvent` for any other name, since an
  `$emit` bubbles to the elements around the tag. Its `target` is `any`, so
  `$event.target.value` reads as it does in the docs. The value goes through
  `__jq79On($event, …)`, whose parameter type is a function of that event or
  anything else, so an inline arrow's parameter is contextually typed and a
  statement-like value (`count = count + 1`) is fine. The first corpus run
  found that it also has to accept `void`, a call to a function that returns
  nothing.
- **`:with`** puts the object's keys in scope, but which keys is the runtime's
  to know. So the names the region reads are collected (from the TypeScript
  AST: `freeIdentifiers` in transform.ts refuses any expression that assigns,
  and assigning is most of what a `:with` region does) and declared from the
  object, typed by its key where it has one and `any` where it doesn't. The
  store's own names and `$`-names are left alone. The tutorial's form exercise
  is what found this: without it, `name` under `:with="draft"` was the DOM's
  global `name`, typed `void`.
- **A factory's default export `satisfies` the factory type** instead of
  being annotated with it. The annotation typed `(props, ctx)` but also made
  the return `any`, so the template knew nothing of what the factory returned.
  `satisfies` (`@satisfies` in JavaScript) types the parameters and keeps the
  return.

### What TypeScript decides, kept as it is

A property missing from an object that a **JavaScript** script built is not
an error without `noImplicitAny`. TypeScript treats an object literal in a JS
file as open, so reading what it lacks gives `any`. The template inherits that
through the inferred store type. It was not worked around: the alternative is
the scripts' file as `.ts`, which phase 2 rejected for good reason. A name
that doesn't exist is reported regardless. The test states both halves.

### How it was tested

- **The corpus**, with an exception list now. The tutorial's starting files
  are exercises, and four of them read a name the exercise is to add
  (`doubled`, `todo`, `fruit`, `count`). The checker reports exactly those
  four, and nothing in any solution or in the `_app`. The test lists them by
  file, line and message, so a fifth error, or one of them disappearing, fails
  it. The four DOM errors under `checkJs` from phase 2 are unchanged.
- **Fixtures** for each row above (`test/check.mjs`, *templates*), including
  `import type`, which follows.
- **The server**: diagnostics, hover (`doubled: number` inside a `{{ }}`) and
  completion in a template, over LSP. That shows Volar routes a position in
  the `.html` to the extra file.
- **The rest of the repo's components**, `tests/fixtures/` and
  `frameworks/keyed/jq79/`. They found that `import type` inside a setup script
  is valid (the Vite plugin erases it with the types), where phase 2 had called
  every static import an error. A setup script's type-only imports are now
  hoisted like a factory's. They also found one real error: `ts-card.html` uses
  a `Props` it never declares. It works because the plugin strips types without
  checking them. The fixture belongs to the Vite plugin's tests, so it was left
  as it is.

### Still open

- **Props against the child's signature.** `<Card :titel="x">` is checked as
  an expression in the parent, not against the props `Card` declares. The
  scripts' file already exports each component's store, so a component tag
  could be checked against the `:setup` pattern of the file it imports. This is
  the natural next step.
- **Rename and go-to-definition across script and template.** A name in the
  template is a destructured copy of the store's property, so renaming

  with mappings that link the two; it hasn't been done here.
- **HTML entities in attribute values** are read as written.
- **Performance.** Each change re-reads the file twice, once per virtual file,
  each with its own parse. That's fine for the tutorial's sizes, and not
  measured beyond them.
- Everything still open from phase 2: publishing `jq79-check`, a real VS Code

## Appended 2026-10-01: props against the child's signature

The first open item of phase 3 is built. A component tag's props are checked
against the props the component declares, when the checker can see that
component: a `<template name>` of the same file, or a file imported with
`await import("./Card.html")` (setup) or `import Card from "./Card.html"`
(factory). What TypeScript reports is what the runtime warns about
(`warnUndeclared`, "`:extra` is not declared by `<Field>`"), on the attribute,
plus what the runtime can't know: a value of the wrong type.

### How a component carries its props

Each component function in the scripts' file now returns `{ store, props }`.
`props` is a type only. The `.html` module's default export carries it, as
`__Jq79Typed<P> = Component79 & { __jq79Props?: P }`. So `import Card from
"./Card.html"` has it, and so does `await import("./Card.html")`, which no
longer becomes `$__import` (`any`). It stays a real `import()`, unwrapped to
the module's default (`.then(__jq79DefaultOf)`), because the runtime answers it
with the component and not the module. A side effect: a misspelt file is now
"Cannot find module" on the specifier.

`P` comes from the signature:

- **A setup pattern** is copied a second time, *unmapped*, as the parameter of
  an arrow that is never called, and `P` is that parameter's type. With an
  annotation that is the annotation. Without one it is what TypeScript infers
  (`{ step = 1, label }` is `{ step?: number; label: any }`). The arrow sits in
  the setup function's body because a type the script declares (`interface
  Props`) is only visible there, which was checked first: on the function's
  own parameter, `Props` is "Cannot find name". Being unmapped, the copy
  reports nothing; the mapped `let <pattern> = __props` still does.
- **A factory's first parameter** gives names and nothing else (`{ label?:
  any }`). Its parameters are contextually typed by `__Jq79Factory`, whose
  props are `any`, so there's no inferred type to read.
- **A closed signature** (`:setup`, `{}`) is `{ __jq79NoProps?: never }`,
  because `{}` would take any object without an excess-property check.
- **No signature** is `any`, so any prop is accepted, as at runtime.

At the tag, the props are read as `renderNestedComponent` reads them. `:x` is
prop `x`, kebab-case is camelCase, `:model.x` is prop `x`, and a plain
attribute is a *string* prop. `:props` and `...x` are spreads, which the
runtime narrows without a warning, so they are only checked as expressions.
Each prop becomes its own call, `__jq79Props(__c0, { key: (value) })`, against
`NoInfer<Partial<P>>`:

- **Partial**, because a prop left out is `undefined` in the child, which the
  default fills. That isn't an error.
- **NoInfer**, so the props written can't widen `P`.
- **One object per prop**, because TypeScript reports only the *first*
  unknown key of an object literal. The first version, one object per tag,
  silently reported one misspelt prop out of two. The cost: `:user` beside
  `:model.user` is no longer a duplicate key. The runtime warns about that one.
- **The key is mapped onto the attribute name**, with a mapping whose
  generated length differs when `:user-name` is written `userName`
  (`generatedLengths`, which the `Writer` didn't have).

### A cycle avoided

A sibling can't be typed with its props in the store. The store is part of
the component function's return type. A component that renders itself
(`Folder` in `Folder`, the tutorial's one-file exercise) would then need its
own return type to compute its own return type, and TypeScript makes that
`any` (TS7022/7023). So in the scripts' file a sibling is a plain component.
The template types it separately: `let Row = … as __Jq79PropsOf<typeof
__jq79Scripts.__jq79Component1>`. That only reads `["props"]`, which depends on
no store.

The default export has the same risk, which is why the `props` type depends
on the signature arrow and nothing else. A component that imports *its own
file* (`await import("./Self.html")` inside Self.html) still closes the loop
through its store. Nothing in the repo does that; it is noted and not handled.

### Found on the way

- **The file's own component was dropped when it had no `<script>` or
  `<style>`.** `splitComponents` filtered it out, so a template-only file's
  markup went unchecked in phase 3. It is always there now, at index 0, which
  is also what the default export points to.
- **A factory returning `=> ({ Card })`** had no store names: `factoryNames`
  only read `return` statements. A test caught it, because the tag was
  silently unchecked.
- **The tutorial, under `checkJs`, imports components from where the
  tutorial serves them**: the exercise folder above a `solution/`, and
  `tutorial/_app/examples/`. Its app builds that layout, and the filesystem
  doesn't have it. Now that `import("./X.html")` resolves, those are
  "Cannot find module", in JavaScript only under `checkJs`. The corpus test
  accepts exactly those, and only when the file exists where the tutorial
  serves it from.

### Still open

- **A component that arrives as a prop** (`:setup="{ Button }"`) is `any`.
  Its props are the parent's business.
- **Typing a factory's props.** Only their names are known, for the reason
  above. Typing them would mean dropping the contextual `any` and asking
  factories to annotate, a trade not worth making blind.
- **The severity.** The runtime *warns* about an undeclared prop. The checker
  reports an error, as it does for anything TypeScript reports. A mapping's
  data can drop a diagnostic but not change its severity. Changing it would
  take a language-service plugin of the server's own, which hasn't been tried.
- The rest of phase 3's list: rename across script and template, HTML
  entities, performance. And phase 2's: publishing `jq79-check`, a real
  VS Code run, `$self`'s `Element`, components in `` Component79(`…`) ``.

## Appended 2026-10-01: rename across script and template

The second open item of phase 3 is built. A name a script declares and the
template reads is one name to rename, go to definition and find references.
That holds whatever the editor's alias setting is, and across the scripts of
a component.

### Why TypeScript alone doesn't carry it

The template's `count` and the script's `count` are two variables in two
virtual files. What connects them is the store: the script returns it and the
template destructures it. Phase 3 returned it through getters, and a getter's
name is a property that no rename of the variable reaches. Shorthands (`({
count })` / `let { count } = __s`) were the obvious fix, and both halves were
tried:

- **VS Code asks TypeScript for aliases by default** (`useAliasesForRenames`).
  Renaming `count` then turns `{ count }` into `{ count: total }` and stops
  there. The alias lands in unmapped code, so even that is dropped. Forcing the
  preference off in the server was built and reverted, because it isn't
  enough on its own (next point).
- **Even without aliases, TypeScript doesn't cross a shorthand
  transitively.** Checked against the language service directly: from the
  script's variable, rename reaches `({ count })` and stops; from the
  template, it reaches the same `({ count })` and doesn't go on to the
  variable.

### What does: Volar's linked code

When a rename edit lands on a position of a virtual code that has
`linkedCodeMappings`, Volar renames again from the linked position, and
keeps going until nothing new turns up. It's what Vue uses to keep a tag's
two names in step. So the store is written `({ count: count })`, and the
template destructures `let { count: count } = __s`. In each file the key is
linked to the value. TypeScript reaches the key from one side and the value
from the other, and Volar walks across the link. No shorthand means no alias
to worry about, so the preference is left alone. Go to definition and find
references follow the same links; that came for free.

The scripts of a component are one virtual file, so the same mechanism
crosses them. A name one script uses and another declares resolves to the
component-level `let count: any`. Its name is linked to the value in the
declaring script's store, so a rename from either script, or the template,
reaches all three. A `:with` region's destructuring is linked the same way, so
renaming `name` under `:with="draft"` renames the property `draft.name` in the
script. That one needed no link to the script, only TypeScript's own property
rename.

The closure still returns the store (`store: () => ({ … })` rather than the
object), for the reason the getters had: a closure reads a reassigned `let` at
its declared type, not the type control flow narrowed it to.

### Tested how

Over LSP (`test/server.mjs`), with the client answering every configuration
request with nothing, which is VS Code's default and the hard case: aliases
on.

- rename from the script's declaration;
- rename from a template read;
- rename from a `:with` key;
- rename from each of two scripts and the template;
- rename of a prop, which reaches its `:setup` pattern;
- definition from the template;
- references from the script.

`test/check.mjs` holds the invariant underneath: both ends of every link are
the same identifier, in both virtual files.

### Still open

- **A prop's rename stops at its component.** The parents that pass it
  (`:step="…"`) are checked against the signature through an *unmapped* copy
  of the pattern (the props type, appended the same day), which no rename
  reaches. Linking that copy to the mapped pattern would carry it into every
  parent's `__jq79Props` call, but those are other files' templates, and
  renaming a component's API from inside it is a decision a refactoring
  should ask about. It isn't done.
- The rest as before: HTML entities, performance, publishing `jq79-check`, a
  real VS Code run, `$self`'s `Element`, components in `` Component79(`…`) ``,
  a factory's prop types, a component passed as a prop, the severity of an
  undeclared prop.

## Appended 2026-10-01: components written as literals

The open item from phase 2 is built. A component handed to
`new Component79(\`…\`)`, `C79(\`…\`)` or `parseComponent(\`…\`)` as a literal
is checked like an `.html` file: scripts, template, props, rename. That holds
in a JavaScript or TypeScript file and in a page's `<script>`
([`literal.ts`](../editors/vscode/src/literal.ts); the grammar learnt `C79` and
`parseComponent` the same day).

### How

- **The string the runtime receives.** A literal's code is generated from
  its *cooked* text (`` \` `` is a backtick, `<\/script>` is `</script>`, a
  CRLF is `\n`), with a table of where each character sits in the file. Every
  mapping is moved through that table and split wherever the file's
  characters stop being consecutive. A character an escape wrote maps to
  nothing. The generators (`component.ts`, `template.ts`) didn't change: a
  literal is a `.html` file to them.
- **One literal, two extra scripts**: `<file>.literal<n>.ts|js` for its
  scripts and `<file>.literal<n>.template.ts` for its template, which imports
  the first (`.js` in the specifier reaches either).
- **A literal with `${…}` is not read.** It isn't a
  `NoSubstitutionTemplateLiteral`, and what it holds depends on what runs.
  Blanking the substitutions was considered: `:title="${t}"` would become
  `:title="   "`, which is a shorthand reading `title`, a false error.

### A script is the editor's TypeScript's, outside its literals

The client now sends `.js`/`.ts` documents to this server too. Two things keep
that from doubling what VS Code's own TypeScript says:

- **The file's own code is its service script**, so the program still has it
  (an `.html` that imports it, a literal that does), but it is mapped with
  every feature off. The server answers nothing outside a literal.
- **A script without literals gets that code too.** Returning nothing for it,
  the first version, hands the file to Volar's TypeScript service, which then
  reports every error in every script of the project a second time. The server
  test caught this, and was checked to fail with that line reverted.

### What the library's own tests showed

`tests/` is hundreds of inline components, many of them written to fail on
purpose. That makes it a corpus to read rather than one to hold to zero.
Running `jq79-check` over it found:

- **A crash, since the props work**: `parseFactoryProps` *throws*, by design,
  for the pre-0.4 factory signature. That is the runtime's migration error.
  One such component stopped the whole checker. Now it declares nothing here,
  and the runtime still says so when it renders.
- **A factory's props weren't in its template's scope.** `declareProps`
  seeds them on the store before the factory runs, so `export default ({
  label }) => …` with `{{ label }}` is fine at runtime and was "Cannot find
  name" here. That bug dated from phase 3.
- **TS18004** ("no value exists in scope for the shorthand property"), as
  in `{ active }`, is "Cannot find name" in another form. A component without
  a signature now drops it too.
- **A root's mount data.** `new Component79(\`…{{ msg }}…\`).mount(host, { msg
  })` is the commonest way to write a root, and a root reads what it is
  mounted with whatever its signature says (components.md). Where the data is
  an object literal at the end of a chain of calls on the literal
  (`.mount(el, data)`, `.render(data)`, through any `.on(…)`), its keys are put
  in scope, as `any`.

After that, 14 errors remain. Thirteen are what the tests are about or are
real:

- props the tests pass undeclared, to check they render empty;
- syntax errors on purpose;
- a `</script>` inside a string, which the runtime also ends the script at;
- an assignment to a slot prop, which the runtime warns about;
- `ts-card.html`'s `Props`.

One is a false positive the heuristic can't reach: data passed through a
test helper, `mount(app, { Child, who })`.

### Still open

- **Mount data passed any other way** (a variable, a helper) is invisible,
  and a closed root that reads it is reported.
- **Performance.** Every script the editor opens is now parsed once more,
  by the server's own TypeScript program, which duplicates the editor's for
  the workspace's scripts. Not measured.
- The rest as before: HTML entities, publishing `jq79-check`, a real VS Code
  run, `$self`'s `Element`, a factory's prop types, a component passed as a
  prop, the severity of an undeclared prop, a prop's rename in its parents.

## Appended 2026-10-01: character references

The open item *HTML entities in attribute values* is closed, along with the
same thing in text, which the item didn't name. The checker now reads an
attribute value or a text as the runtime does, after the HTML parser has
decoded its character references. `:if="ready &amp;&amp; count &gt; 0"` is
`ready && count > 0`, not three syntax errors, and `:setup="{ label =
&quot;Total&quot; }"` is the pattern the Vite plugin writes back into a
compiled component (vite-plugin.md), not a broken one.

### A change to src/

The checker needs the decoded text *and* where each character of it came
from, to map errors back. `src/html.ts` already decodes as the browser does,
for precompile, and `tests/precompile.test.ts` holds it against `DOMParser`.
But it returned only the decoded string. The change is a refactor that keeps
behaviour: the decoding of one reference moves out of `decode`'s replacer
into an exported `decodeReference`, which `decode` calls with the same
arguments, and `CHARACTER_REFERENCE_RE` is exported beside it. The extension
([`entities.ts`](../editors/vscode/src/entities.ts)) walks the same matches,
asks `decodeReference` about each, and keeps segments: a run of the file as
is, or one reference and the text it writes. html.ts sits in the precompile
bundle and the service worker, not the runtime page, so no page carries
more. The precompile tests and the library's build pass unchanged.

Rejected:

- **A decoder of the extension's own**, such as a table of the five markup
  references. It would disagree with precompile wherever the two tables
  differ, and the two exist to read a component the same way.
- **Decoding by calling html.ts's `decode` on each match with the character
  after it.** It is right only because of how the legacy no-semicolon rule
  reads one character ahead, which makes it fragile. It was considered,
  not built.

### How it maps

A plain run is copied, so it maps one to one. A reference is written as the
character it decodes to, mapped onto the whole reference with a mapping whose
generated length differs (the `mapText` that kebab props already used). So an
error that starts on a character a reference wrote starts on the reference:
`{{ &#110;ope }}` is "Cannot find name 'nope'", at `&#110;`. Text is decoded
*before* `{{ }}` are found, as the runtime finds them, so `&#123;&#123; nope
}}` is an interpolation, at runtime and here. Attribute values use the
attribute rule for a legacy reference without a semicolon (`?a=1&copy=2`
stays), text uses the text rule.

### Still open

- **A reference html.ts doesn't know** (its table is the ones a component
  plausibly writes, out of over two thousand) is read as written. Precompile
  has the same gap, and safe mode reports it there.
- The rest as before: a real VS Code run, `$self`'s `Element`, a factory's
  prop types, a component passed as a prop, the severity of an undeclared
  prop, a prop's rename in its parents, mount data passed other than beside
  the literal, performance; publishing (jq79-check, the extension).

## Appended 2026-10-01: a factory's props, typed

The open item *typing a factory's props* is closed, without the trade the
props section feared. Asking factories to annotate is not needed.

The props were `any` because the export `satisfies __Jq79Factory`, whose
first parameter is `any`. That types `ctx` without an annotation, and it also
makes an unannotated props pattern `any` by context. The setup script's trick
works here too. The first parameter's text is written again, unmapped, as
the parameter of an arrow with no context. That arrow sits at the end of the
factory's function, where a type the script declares is visible:

```ts
;const __jq79Signature = ({ label = "Total", user: who }) => ({ label: label, user: who });
;return { run: __jq79Default, signature: __jq79Signature };
```

Its parameter's type is the child's props, for the tags that use it:
`{ label?: string; user: any }`, or the annotation when there is one. What it
returns is the props as they are bound (`label: string`, the default filling
it), which goes on the store before what the factory returns. That is the
order the runtime has: `declareProps` seeds them, then the return is merged
over them. So the factory's own template reads `label` as a `string` too.
Inside the factory's body the parameter is still the contextual `any`, as
before.

A nested pattern (`{ user: { id } }`) binds no single name; there the
store's `user` is `any`.

## Appended 2026-10-01: completion and hover in tags

What phases 1 to 3 never planned, and what the extension lacked most in use.
In a tag, where TypeScript has nothing to say, the server now offers what jq79
reads there ([`completion.ts`](../editors/vscode/src/completion.ts), a Volar
service plugin of the extension's own):

- the directives, as snippets (`:each="${1:item} in ${2:items}"`);
- events, and after `@click.` their modifiers;
- on a component's tag, the props it declares, typed;
- `:setup`, `:mounted` and `lang` on a `<script>`; `scoped` and `lang` on a
  `<style>`;
- the components in scope after `<`;
- a line of documentation on hovering a directive.

Each list is template-syntax.md's, written once, and an attribute already on
the tag is left out.

### The props come from TypeScript

A tag's props are what the check already used: the template's code checks
them against `__jq79Props` on a variable per tag (`const __c0 = Card`, the
props work). The generator now records, for each component tag, where its `<`
is and that variable's name, on the template's virtual code. The plugin
asks TypeScript's language service, which Volar's TypeScript service
`provide`s to other plugins, for the brand's type on that variable and
lists its properties: name, type, whether optional, JSDoc. So a prop's type
in the list is the type the check enforces, for a `:setup` child, a
factory, or an imported file.

### Two things in the way, found by the tests

- **A tag's name was mapped into the template's code**, for the "Cannot find
  name" on `<Buton>`. That made TypeScript answer completion there, with every
  name in scope, before this plugin. The name keeps its mapping for errors
  and navigation, with completion turned off.
- **TypeScript's completions in an expression offered the virtual code's own
  names**: `__s`, `__c0`, `__jq79Each`, `__jq79Props`, `$__import`, in every
  `{{ }}`. The TypeScript service's answers for an embedded document of a
  component are now filtered of those. A test asserts they are gone, and it
  was checked to fail with the filter off. A user's own script, served by the
  editor's TypeScript, never went through this server.

### Still open

- **In a literal** (`` new Component79(`…`) ``) nothing of this is offered yet.
  A JS/TS file's own code is mapped with every feature off, the literal
  included, so the plugin is never asked there. A mapping with only
  completion on, over each literal, would let it in. It needs care, because
  Volar's TypeScript service would then answer inside the literal too.
- **Events a component emits** aren't offered on its tag: an `$emit` name is
  a string the checker doesn't collect yet.
- **Slot names** (`<template :slot.|`, `<slot.|`) aren't offered.
