# `$attached` and `$detached`

**Status:** proposed and implemented on the same branch, after
[the destroy hook](2026-10-01.a-destroy-hook.md).

## The problem

`$destroyed` covers what lives as long as the component. It doesn't cover what
should live only while the component is **on the page**: polling, an
animation loop, an `IntersectionObserver`, a listener on `window`. A component
kept with `detach()` (tabs, a cached view) keeps all of that running
off-screen, and nothing tells it when it's back. `$mounted()` can't: it's a
promise, and it resolves once.

## The proposal

```html
<script :setup>
  let data = []
  let timer
  const poll = () => fetch("/api").then(r => r.json()).then(d => { data = d })

  $attached(() => { poll(); timer = setInterval(poll, 5000) })
  $detached(() => clearInterval(timer))
</script>
```

- `$attached(fn, { immediate = true })` runs `fn` **every time** the component
  goes onto the page, the first mount included. `$detached(fn)` runs `fn` every
  time it leaves. Both return an unregister.
- **`immediate`, on by default:** if the component is on the page already
  when the hook is registered (after `await $mounted()`, in a handler), `fn`
  also runs right away. "Run this while I'm on the page" then holds wherever
  the line is written. `{ immediate: false }` waits for the next attach. It's
  the option `$on` has, with the opposite default: a listener is about
  *changes*, and this hook is about a *state*. Registered before the first
  mount (the ordinary case), it changes nothing, because the first mount is
  still ahead.
- **"On the page" means in the document**, with the template rendered. It
  doesn't mean "`attach()` was called". A nested component is mounted into a
  fragment that its parent then inserts, and a root can be mounted into an
  element that isn't in the document. A hook that fires there would query a
  DOM nobody can see. A render that a script holds back (`let rows = await …`)
  fires `$attached` when it paints, not when the empty markers go in.
- **Nested components hear their root.** When a root detaches, every component
  inside it, slot content included, detaches with it. That's the point of the
  hook: a tab's child polls too. The same goes for the attach.
- **Pairs balance.** `$detached` only runs for a component that heard
  `$attached`, so a `clearInterval` never runs for a `setInterval` that never
  ran.
- **`destroy()` of a component on the page runs `$detached` first**, then
  `$destroyed`, both before anything is taken apart. A resource tied to being
  on the page is released by its own pair, and doesn't have to be cleaned up a
  second time in `$destroyed`.
- **Order:** document order, so a parent runs before what it rendered. That's
  the same direction `$destroyed` runs in.
- A `$detached` registered after the component is gone runs at once, for the
  reason `$destroyed`'s does. A late `$attached` is dropped: nothing will
  attach that generation again.
- A hook that throws is logged, and the rest still run.

### How it's found

The DOM decides, not a tree of instances. Instances that registered a hook go
in one module-level set, and leave it when destroyed:

- **Attach:** a root's `attach()`, the deferred paint of a held render, and a
  microtask after any registration check that set. An instance is due when
  it's rendered, its start marker `isConnected`, and it hasn't been told. The
  microtask is what catches a component inserted by its parent's `:if`, `:each`
  or component tag, which build their DOM in a fragment and insert it later on
  the same stack. One microtask late, never early.
- **Detach:** a root's `detach()` collects the nodes between its markers, and
  tells every told instance whose start marker sits under one of them, before
  moving anything. A component removed by `:if` or `:each` is destroyed, and
  `destroy()` tells it directly. Its DOM may already be out of the document by
  then, so connection can't be the test there.

A page where no component registers either hook pays one `size` check per
attach, detach and deferred paint. That's why the set is limited to instances
that asked: walking the instances of a 10,000-row table on every mount would
be paid by everyone.

## Rejected

- **`$destroyed` on detach too.** The tab would come back without its timers,
  and the script doesn't run again to restart them.
- **`$attached` only after the first mount**, with the first one left to
  `await $mounted()`, which was the earlier version of this proposal. It made
  the ordinary hook asymmetric, because the start code had to be written twice.
  With `immediate` on by default, a hook registered after `await $mounted()`
  runs for the attach already in progress, so the split never has to be
  written.
- **`immediate` off by default**, as on `$on`. It was the first draft. It made
  the line's position matter: the same `$attached(start)` would start the
  timer above `await $mounted()` and not below it.
- **A registry of child instances** (each component tag registering with the
  instance that rendered it). Slot content is rendered by the child but
  belongs to the parent's scope, so "who rendered it" and "whose DOM it's in"
  disagree, and the DOM is the one that answers "is it on the page".
- **Firing for a root mounted into a disconnected element** once that element
  is inserted. Nothing tells the runtime that happened. Mount into the
  document, or call `mount()` again after inserting.

## Still open

- A root inserted into the document by moving its mount target, not by
  `mount()`, isn't seen, as said above. A `MutationObserver` would see it, at a
  cost every page would pay.
