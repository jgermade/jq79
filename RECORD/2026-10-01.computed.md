# `$computed`: a derived value, the way `$reactive` is a stored one

**Status:** proposed and implemented on the same branch.

## The problem

Inside a setup script a derived value is one line, `$: total = sum(cart.items)`,
and it lives and dies with the component. Outside a component there is nothing
like it. A shared-state module (`store.js`, handed to components as a prop, see
[reactive-data.md](../docs/reactive-data.md#shared-state-pass-a-store-not-an-object))
has to recompute by hand in every place that writes, or derive in every
component that reads, each with its own `$:`:

```js
// store.js
export const cart = $reactive({ items: [] })
// …and every component that shows the total writes
// $: total = cart.items.reduce((sum, item) => sum + item.price, 0)
```

The store already knows how to do it (`cart.$effect(() => { … })`), but an effect
writing into a second store by hand is plumbing every user has to get right:
which store holds the result, how to stop it, how to keep it from being
written by mistake.

## The proposal

```js
import { $reactive, $computed } from "jq79"

export const cart = $reactive({ items: [] })
export const total = $computed(() => cart.items.reduce((sum, item) => sum + item.price, 0))

total.value        // 0, and a dependency of whatever effect reads it
cart.items.push({ price: 3 })
total.value        // 3
total.$dispose()   // stops following cart
```

- `$computed(get)` runs `get` right away and again whenever anything it read
  changes, in any store, and keeps the result on `.value`.
- **What it returns is a store**: a `$reactive({ value })`, behind a read-only
  view. Everything a store does it does: `$on("value", …)`, `$effect`, being
  passed as a prop, or held in another store, where it is bridged like any
  nested store (the holder re-notifies `total.value` under the key it sits at).
  That is why it is `.value` and not a call (`total()`): a function is not a
  store, so it could not be passed down or listened to, and a template would
  need to know which names are calls.
- **Read-only.** Writing `.value` (or any key) warns and is ignored. A write
  would be silently overwritten by the next recompute, which is a worse failure
  than being told.
- **Eager, not lazy.** It recomputes on every change of what it read, whether or
  not anyone reads `.value`. That is what every other effect in the store does:
  writes push, and nothing pulls. Lazy evaluation (a dirty flag, computed on
  read) would be a second evaluation model beside the one the trie is built for,
  and would make "who woke whom" order-dependent in a new way. The cost is one
  run per change for a computed nobody reads. `$dispose()` is the way out of it.
- **A same-value result notifies nobody**, for primitives. That comes free from
  the store, which drops a write of an equal primitive. So `$computed(() =>
  items.length > 0)` only wakes its readers when the answer flips. An object
  result always notifies, as a new object always does.
- **`get` throwing** is reported (`console.error`) and `.value` keeps its last
  value. Left to propagate, the exception would surface in whatever write
  triggered the recompute: `cart.items.push(x)` would throw because of code
  that has nothing to do with it.
- **In a component's scripts, it dies with the component.** The instance's
  `$computed` (an instance helper, like `$mounted`) is the library's, plus a
  `$dispose()` when the component is destroyed. Without that, a computed made in
  a component over a shared store is held by that store forever, and keeps
  running for a component that is gone. Imported from `jq79`, it is the plain
  one, and lives until `$dispose()`.

### When to use it over `$:`

In a setup script, `$:` is still the way to derive a value the template shows:
`{{ total }}` reads better than `{{ total.value }}`. `$computed` is for a
derived value that has to *be* a value: exported from a module, passed as a
prop, shared between components.

## What it costs

One store and one effect per computed, both made by the existing `$reactive`.
No change to the store's internals. One export, and one name in
`INSTANCE_HELPER_NAMES` (precompiled scripts need the same version, as for any
new helper).

## Rejected

- **A getter on the computed (`total.value` computed on read).** It would track
  nothing on the computed's own store, so nobody reading it would be woken.
- **Writable computeds (`{ get, set }`, Vue's form).** Not asked for, and the
  setter is just a function the caller can write themselves.
- **Lazy evaluation.** See above. It stays possible later behind the same API,
  since nothing in it promises when `get` runs, only what `.value` holds.

## Still open

- Order between a computed and the other effects woken by the same write is
  creation order, as for any effect. A template effect that reads both
  `cart.items` and `total.value` may run once before the computed and once
  after (it is woken again by the computed's write). The result on screen is
  right, but there is one extra run. A real fix is topological ordering, which
  is a change to the store, not to this helper.
