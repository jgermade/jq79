# A context mechanism? (to evaluate)

Status: question, not a decision. Written to start the next session's evaluation.

## The problem

A consumer app (doomus-rs) needs a value that almost every component reads and few
components own: the UI language (and, with it, a `t(key)` function). Its rules forbid
components from importing app stores (components are store-agnostic; views wire
stores to components), so today the only way down is a prop - through every
component, including the ones that only pass it on (`Topbar` → `BookmarkMenu` →
each menu row; `BookmarkTree` → `BookmarkForm` → `BookmarkDialog`…). Twenty-odd
components, most of them two or three levels deep. Theme, user, feature flags and
"am I inside a dialog" have the same shape.

What jq79 offers now:

- props (explicit, checked by the signature and by the VS Code checker; verbose for
  pass-through values);
- a `$reactive` store imported by the component (works, but couples a "component" to
  an app module, which is what the consumer's layering forbids);
- slots (content keeps the parent's scope, which helps for markup, not for values a
  child's own script needs).

## Options to weigh

1. **Provide / inject, scoped to the subtree.** A component provides `{ lang, t }`
   under a key; any descendant (through component boxes and slots) reads it. Needs a
   lookup through the instance tree - jq79 has the parent links (boxes, `:each` rows,
   slot content belongs to the writer's scope: whose context does slot content see?).
   Reactivity: provide a `$reactive` store and let the store bridge do the rest
   (the "a store nested in another store is bridged" invariant), or re-provide.
2. **Context as a reserved prop that flows down by itself.** e.g. `$context`, merged
   from the parent's into every child's store unless the child overrides a key. Cheap
   to read (`{{ $context.t('save') }}`), costly to keep live across every instance.
3. **App-level injection at mount.** `Component79.provide(name, value)` once, visible
   to every component as a `$`-name. Simplest; global (no per-subtree override), and
   it breaks the "what carries a `$` comes from the library" rule unless prefixed.
4. **Nothing.** Document the prop pattern (and `...spread` for pass-through) and keep
   the library smaller.

## What it costs, whichever is chosen

- Runtime size and creation time (the *regression* benchmark gate: every component
  instance would pay for a lookup or a merge).
- The checker (`editors/vscode`): a template reading `t(...)` must type-check, so the
  checker needs to know what a component can receive from context - a declaration in
  the component (like the `:setup` signature) seems unavoidable.
- Docs, tutorial exercise, safe mode / precompile (no new `eval` paths).
- HMR: a provider re-rendered in place must keep its consumers' values.

## Open questions

- Declared or ambient? (a consumer declaring `:context="{ t, lang }"` keeps the
  "a signature is a contract" spirit and gives the checker its names).
- Slot content: provider of the place it is written, or of the place it lands?
- Override per subtree needed for the first use case? (a language switch preview in
  a styleguide: yes; the app itself: no.)
- Is option 4 enough once `...spread` and a single "ui" object prop are used?

## 2026-11-26 (later) - Evaluation: build option 1, with option 3 as its root case

Evaluated with a prototype (local branch `claude/context-prototype`, against
v0.8.2), so the costs below are measured, not guessed.

### What the prototype is

```html
<!-- a provider: any component, before it renders -->
<script :setup>$provide("i18n", i18n)</script>

<!-- a consumer, any depth below - through components that forward nothing -->
<script :setup lang="ts">
  const i18n = $context<I18n>("i18n")          // or $context("i18n", fallback)
</script>
<button>{{ i18n.t("save") }}</button>          <!-- $context() reads in templates too -->
```

```js
// option 3 falls out as the root case: app-wide values where the app mounts
new Component79(src).provide("i18n", i18n).mount("#app")
```

- **Two instance helpers, `$provide` and `$context`**, next to `$emit`/`$slots`
  (`injected`), so both script modes and templates have them, and safe mode /
  precompile pick them up from `INSTANCE_HELPER_NAMES` (positional order updated;
  `tests/precompile.test.ts` green). They carry a `$` and come from the library.
- **The map rides on the scope chain**, a `CONTEXT` symbol beside `SLOTS` and
  `PENDING_SCRIPTS`: a null-prototype object whose prototype is the enclosing
  provider's map. A lookup walks providers innermost first; nearest wins, siblings
  never see each other's.
- **Cost per instance: one symbol read at the usage site** (`scope[CONTEXT]`) and,
  only when something above provides, one `defineProperty` on the raw store. A
  component that does not provide allocates nothing - it shares its parent's map.
  A provider allocates one object on its first `$provide`.
- **Not reactive by itself.** The map is plain; a value that changes is provided
  as a `$reactive` store, and the consumer's `const i18n = $context("i18n")` is a
  store variable holding a store - bridged, by the existing invariant. No new
  tracking path. (Tracking is global - `activeEffect` - so a template reading
  `$context("i18n").lang` directly is live as well.)

### The open questions, answered

- **Declared or ambient?** Ambient reads, declared *by the script*: a component
  says what it takes from context with a `const x = $context<T>("key")` line, which
  is a store variable like any other, so the checker needs nothing new - only the
  helper's type (`<T = any>(key, fallback?: T) => T`). Checked with `jq79-check`:
  a wrong use of `i18n.lang` and an unknown `i18n.nope` in the template are both
  reported. A `:context="{ t, lang }"` attribute was rejected: it would add a
  second signature for the same thing a script line already says, with its own
  parser, Vite plugin rule and checker path.
- **Slot content: written place or landing place?** Landing place. Content written
  by the page inside `<Tabs>` must read what `Tabs` provided - that is the
  compound-component case provide/inject exists for (React, Vue and Svelte all
  answer the same). The slot renderer gives the content's scope the `<slot>`'s
  map; the content keeps the writer's *names* (slot rule 1 is untouched - only the
  context, which is about position, follows the landing).
- **Per-subtree override?** Free with the prototype chain, and tested.
- **Is option 4 (props, `...spread`) enough?** For doomus, no: ~20 components,
  most of them forwarding only. Props stay the right answer for anything a
  component *owns*; context is for the few values every component reads.

### Late provides

A child reads the map when it is created. A `$provide` after the provider's first
render (below an `await $mounted()`) reaches only children created later, and warns
once. A `$context(key)` nobody provides warns once per instance and key; with a
fallback it is silent.

### Measured

- `npm test`: 1311 passed (8 new, `tests/context.test.ts`: grandchild through a
  forwarder, templates, nearest wins, root `provide()`, a `$reactive` value stays
  live, slot content lands, `:each` rows, missing key warning, sibling isolation).
  `editors/vscode` `npm test`: 69 passed.
- Size: `dist/jq79.js` +1,012 B raw, **+323 B gzip** (31,735 → 32,058).
- `npm run benchmark:ab -- --base v0.8.2 --rounds 3` (4-core Xeon, Chromium 158):
  **no regressions**; every delta inside its noise. Three operations came out slower
  in every round but under their noise (update 1k ×16 +7.0% / ±8.0%, select +6.6% /
  ±7.2%, full→windowed +4.1% / ±11.0%); none of them creates a component, which is
  the only path the change touches, so they read as the box, not the change.
  Component creation (the path that pays the symbol read): -3.7% / ±34.1%.

### Decision

Build it (option 1, with `Component79#provide` as the root case of option 3). The
cost is one symbol read per component instance and ~320 B gzip; it breaks no
invariant (no compiler, no eval path, `$` names from the library, proxies
untouched), and it removes a prop from twenty-odd components in the first consumer.

### Before a release

- Docs: a "Context" section in `docs/components.md` (and the helpers list in
  `docs/setup-scripts.md`), `index.d.ts` types for `Component79#provide`.
- A hot-reload test (a provider replaced in place; a consumer replaced in place
  keeps its `context` - it is outside the render generation, like `slots`).
- A tutorial exercise, optional.
- A benchmark round on the CI runner (the *Benchmark* workflow) on the PR.

## 2026-11-26 (later still) - One name: `$ctx`

Reviewed with the owner: `$provide` / `$context` become a single **`$ctx`**, told
apart by arity as `$updateModel` already is, and the root method is **`.ctx()`**.

```html
<script :setup>$ctx("lang", "es")</script>        <!-- two arguments: set -->
<div :lang="$ctx('lang')">…</div>                  <!-- one argument: read -->
```

```js
new Component79(src).ctx("lang", "es").mount("#app")   // root; app.ctx("lang") reads
```

What changed with it, and why:

- **No fallback argument, no "nobody provides it" warning.** With two arguments
  meaning "set", `$ctx(key, fallback)` is no longer available; the default is
  written `$ctx("lang") ?? "en"`, and an unset key reads `undefined` quietly
  (warning on it would make every `??` default noisy).
- **Templates only read.** A template expression re-runs whenever what it reads
  changes, so a set there would repeat on every re-render. The template's `$ctx`
  (served through `injected`) reads, and with two arguments warns once and changes
  nothing; scripts get the full `$ctx` (the same key position in the instance
  helpers, so precompile's positional order holds).
- The late-set warning stays (once per generation).

The props-vs-module-store comparison raised in review (a `$reactive` in
`lib/ctx.store.js`, imported by components): equivalent for one app-wide value in
a browser-only app; what it cannot do is a value per subtree (a styleguide showing
`es` and `en` side by side), per-instance state for compound components
(`Tabs`/`Tab`), or keep a component free of the app's modules (which the first
consumer's layering requires). Svelte keeps both tools for the same reasons, plus
SSR, where module state is shared between requests.

Tests: `tests/context.test.ts`, 10 (the earlier 8 rewritten for `$ctx`, plus "a
template set warns and changes nothing" and "a late set warns once"). `npm test`
1313 passed; `editors/vscode` 145 + 69 passed; `jq79-check` types
`$ctx<I18n>("i18n")` and reports a wrong use and an unknown property.
