# A context mechanism? (to evaluate)

Status: question, not a decision. Written to start the next session's evaluation.

## The problem

A consumer app (doomus-rs) needs a value that almost every component reads and few
components own: the UI language (and, with it, a `t(key)` function). Its rules forbid
components from importing app stores (components are store-agnostic; views wire
stores to components), so today the only way down is a prop - through every
component, including the ones that only pass it on (`Topbar` → `BookmarkMenu` →
each menu row; `BookmarkTree` → `BookmarkForm` → `BookmarkDialog`…). Twenty-odd
components, most of them two or three levels deep. Theme, user, feature flags and
"am I inside a dialog" have the same shape.

What jq79 offers now:

- props (explicit, checked by the signature and by the VS Code checker; verbose for
  pass-through values);
- a `$reactive` store imported by the component (works, but couples a "component" to
  an app module, which is what the consumer's layering forbids);
- slots (content keeps the parent's scope, which helps for markup, not for values a
  child's own script needs).

## Options to weigh

1. **Provide / inject, scoped to the subtree.** A component provides `{ lang, t }`
   under a key; any descendant (through component boxes and slots) reads it. Needs a
   lookup through the instance tree - jq79 has the parent links (boxes, `:each` rows,
   slot content belongs to the writer's scope: whose context does slot content see?).
   Reactivity: provide a `$reactive` store and let the store bridge do the rest
   (the "a store nested in another store is bridged" invariant), or re-provide.
2. **Context as a reserved prop that flows down by itself.** e.g. `$context`, merged
   from the parent's into every child's store unless the child overrides a key. Cheap
   to read (`{{ $context.t('save') }}`), costly to keep live across every instance.
3. **App-level injection at mount.** `Component79.provide(name, value)` once, visible
   to every component as a `$`-name. Simplest; global (no per-subtree override), and
   it breaks the "what carries a `$` comes from the library" rule unless prefixed.
4. **Nothing.** Document the prop pattern (and `...spread` for pass-through) and keep
   the library smaller.

## What it costs, whichever is chosen

- Runtime size and creation time (the *regression* benchmark gate: every component
  instance would pay for a lookup or a merge).
- The checker (`editors/vscode`): a template reading `t(...)` must type-check, so the
  checker needs to know what a component can receive from context - a declaration in
  the component (like the `:setup` signature) seems unavoidable.
- Docs, tutorial exercise, safe mode / precompile (no new `eval` paths).
- HMR: a provider re-rendered in place must keep its consumers' values.

## Open questions

- Declared or ambient? (a consumer declaring `:context="{ t, lang }"` keeps the
  "a signature is a contract" spirit and gives the checker its names).
- Slot content: provider of the place it is written, or of the place it lands?
- Override per subtree needed for the first use case? (a language switch preview in
  a styleguide: yes; the app itself: no.)
- Is option 4 enough once `...spread` and a single "ui" object prop are used?
