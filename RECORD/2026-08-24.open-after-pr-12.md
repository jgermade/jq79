## 1. The SVG camelCase attribute table — a decision, and it is narrower now

**Blocked on a product call, not on engineering.** Binding a camelCase SVG
attribute does not work: the name-casing rewrite turns `:viewBox` into
`:view-box` before parsing, and SVG has no such attribute. Written-out
`viewBox="0 0 10 10"` is fine, and so is any binding already kebab or lowercase
(`:fill`, `:cx`, `:stroke-width`) - most of them.

What changed is that **one of the two options is dead.** "Ask the SVG IDL
whether to camelCase this name" passed every jsdom probe and fails in Chromium
141 on three of sixteen real names - `stdDeviation`, `attributeName`,
`repeatCount` - silently ([`2026-08-24.svg-namespace.md`](2026-08-24.svg-namespace.md),
dated section at the bottom).

So it is a table of ~55 names, or the documented limitation that ships today.
The table is under a kilobyte minified and it is bytes on every page of a
library whose pitch is having no dependencies. A **partial** table is worse than
none: it would be silently inconsistent.

Worth knowing before deciding: a reactive library drawing charts is a natural
use, `viewBox` is the attribute such a page most wants to bind, and today it
fails without a word.

## 2. MathML is untested

Free with the namespace change and never exercised. `elementToAST` records any
non-HTML namespace, so `<math>` should work exactly as `<svg>` now does. One
test file's worth of work, and it either confirms it or finds the second case
that the `<svg>` corpus did not cover.

## 3. The clone-path coverage check is a manual procedure

**New, and it will rot.** The check that keeps the differential test honest -
make `renderFromSkeleton` mark its root, run `tests/skeleton.test.ts`, confirm
**26 of 83** entries fail - lives in prose in
[`2026-08-24.plan-on-the-second-render.md`](2026-08-24.plan-on-the-second-render.md).
Nothing runs it.

That is exactly the shape of thing this branch caught by accident and would not
have caught twice: the count silently fell to 5/83 and every test stayed green.
Automating it needs a way for a test to ask "did the clone path run" without
shipping a counter to the browser - a debug-only hook, or a spy the test
installs. It is small, and it protects the invariant the whole area rests on.

## 4. `:each` + `:if`, and the invisible wrapper

**A design decision, deferred three times now**, and explicitly parked by the
author during PR #12. Two things are worth separating, because the original §3
conflated them:

- **`:each` + `:if` on one element is not blocked.** Filtering the list
  expression - what the warning already says - works in both states, verified.
  There is nothing to fix.
- **The group wrapper is the real gap**, and it is small: `<template :if>`
  renders inert and says nothing, so it looks like it should work and shows
  nothing.

[`2026-08-24.template-directive-warning.md`](2026-08-24.template-directive-warning.md)
is written, unimplemented, and covers the cheap half (a parse-time warning). It
also records the correction that matters here: `<template>` **is** available for
a wrapper at nested position, because `<template :slot.header>` already is one -
the 2026-08-05 prohibition was about the top level and is broader than its own
reasoning.

If the wrapper is ever built, the work is not the `:if`. It is `boundsOf`, which
resolves a fragment as `{ first: node.firstChild!, last: node.lastChild! }` and
breaks on an empty one.

## 5. `:html` in the cloner

Parked with a reason rather than forgotten. `:html.allowed` is a second
attribute feeding the same effect, and the warning `renderNode` emits for an
`:html.allowed` with no `:html` fires once per *render* interpreted and would
fire once per *definition* cloned. That is an observable behaviour change in a
directive whose job is sanitizing untrusted input, so it wants its own decision.

## 6. Two measurement gaps this branch left

- **`renders=8` never resolved.** Two attempts at the break-even curve gave
  +2.2%/46% and +8.5%/39%, both with a p25..p75 spanning ~55 points, because a
  chunk there is 480 renders and ~19ms - a big enough target that the stalls
  came back. It needs a smaller chunk. Not needed for any answer so far; 1 and
  100 bracket it.
- **The order axis is differential only.** It compares the two paths against
  each other and does not assert either matches a written-down expected order,
  so a change that reorders *both* identically still passes. That is the right
  trade for a differential test, and it is worth knowing it is the trade.

## 8. Housekeeping

- **The regression baseline moves at the next release, and this branch is why.**
  That job measures against the last released tag; the release after PR #12
  re-baselines every operation. Nothing to do - but anyone reading a surprising
  delta afterwards should know the floor shifted here.
- **`moveRangeAfter` still moves a reorder one node at a time**, the open item
  [`2026-08-23.batch-range-removal.md`](2026-08-23.batch-range-removal.md) left:
  *"not worth it until it is"*. `swapRows` is 7.8ms. Still not worth it.
- **The tutorial differential test waits a fixed tick.** §9 of the previous list
  called it one scheduling change away from flaky, and PR #12 made each arm
  mount twice instead of once. One failure was seen, on
  `03-components/06-spreading-props`, in a run with the test in a
  half-fixed state; eleven runs since have been clean. Not a demonstrated
  problem, and the fixed tick is still the thing that would cause one.
- **`removeRow` and the clone path.** §4 of the previous list recorded +1.8%
  with cloning on, under that operation's own spread. PR #12's report reads
  -5.9%, inside the noise - but that is branch-against-`main`, not flags-off
  against flags-on, so it says nothing about §4 either way. §4 stands as
  written.

## 9. The part none of this touches

Unchanged and still honest: of the ~8ms of DOM, ~11ms of interpretation and
~30ms of effects per 1,000 rows in
[`2026-08-23.where-the-create-time-goes.md`](2026-08-23.where-the-create-time-goes.md),
the clone path took the middle third. The remaining ~30ms is one effect per
binding, and the two things priced against it - grouping a row's bindings, and
dropping `with` from expression evaluation - were both refused for good reasons.

`create1k` is ~33ms where Svelte is ~9ms. Closing that is a claim about what the
library is, not an optimization anybody has left.
