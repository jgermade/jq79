# A destroy hook: `$destroyed(fn)`

**Status:** proposed and implemented on the same branch.

## The problem

A setup script can say "when I'm on the page" (`await $mounted()`) but not "when
I'm gone". Whatever it starts outside the store has no way to stop:

```html
<script :setup>
  let now = new Date()
  setInterval(() => { now = new Date() }, 1000)   // runs forever
  window.addEventListener("resize", onResize)      // so does this
</script>
```

`destroy()` disposes the component's effects and styles, but a timer, a
listener on `window`, a socket or a third-party widget belongs to nobody. It
keeps running, and keeps writing to a store nothing renders any more. The same
happens on every re-render (`render(data)`, hot reload), because a re-render is
a destroy followed by a fresh run of the scripts, so each pass adds one more
interval.

The only workaround today is to hold the instance from outside and wrap
`destroy()`, and a child component that `:if` or `:each` removes has no outside.

## The proposal

One more instance helper, registered like `$mounted`:

```html
<script :setup>
  let now = new Date()
  const timer = setInterval(() => { now = new Date() }, 1000)

  $destroyed(() => clearInterval(timer))
</script>
```

- `$destroyed(fn)` registers `fn` to run once when this render generation is
  torn down: `destroy()`, a re-render, a hot reload, or a parent's `:if` / `:each`
  removing the component (which all go through `destroy()`). It returns a
  function that unregisters `fn`.
- **It runs on destroy, not on detach.** `detach()` keeps state, and a later
  `mount()` resumes it with every effect alive. A cleanup that ran on detach
  would hand the remount a component with its timers gone and nothing to start
  them again: the setup script does not run a second time. Destroy is the only
  moment that is final.
- **It runs first,** before anything is taken apart: the DOM is still where it
  was, the store still answers, and the effects are still live. Cleanup code
  that reads the DOM (saving a scroll position) or the store (persisting a
  draft) works. A parent's hooks run before those of the children it rendered,
  because the children are destroyed when the parent's effects are disposed,
  and that comes after the hooks.
- Hooks run in registration order. One that throws is reported
  (`console.error`) and the rest still run: one broken cleanup must not leave
  the others' timers running, or the teardown half done.
- **Registered after the fact, it runs at once.** A script that awaits a fetch
  and is destroyed before the fetch lands still reaches its `$destroyed(...)`
  line afterwards. Holding that `fn` for a destroy that already happened would
  leak exactly what it was written to stop, so it runs on the spot. The
  generation check is the one `$emit` and `$updateModel` already make (the
  start marker the closure captured is no longer the instance's).
- Both script modes get it: a setup script by name, a factory in its ctx
  (`(props, { $destroyed }) => …`).
- A non-function is a `TypeError` at the call, not later at destroy time, when
  the stack would no longer say who passed it.

## What it costs

One array per render generation, created on the first `$destroyed` call only,
and a null check in `destroy()`. A component that never calls it pays the null
check. One new name in `INSTANCE_HELPER_NAMES`, so precompiled scripts change
their parameter list and have to be rebuilt with the same version (as for any
new helper).

## Rejected

- **`$unmounted`.** jq79 has no unmount: it has `detach()` (reversible) and
  `destroy()` (final). Named after the method it follows, the hook says which
  of the two it means. `$unmounted` would read as the counterpart of `detach`.
- **A promise (`await $destroyed()`), mirroring `$mounted()`.** The code after
  it would be the cleanup, so the script's tail would stay suspended for the
  whole life of the component, and a second cleanup would need a second
  suspended script. A callback can be registered anywhere, any number of times.
- **Returning a cleanup from `$:`, or from the setup script.** A `$:` effect
  re-runs, so its cleanup would have to run before every re-run too. That is a
  different feature (effect cleanup), and worth its own plan. A cleanup returned
  from the script clashes with factories, whose return value is their bindings.
- **Running it on detach as well, with a `$mounted` that fires again on remount.**
  That makes a setup script a repeating lifecycle, which it has never been: it
  runs once per generation.

## Still open

- Effect cleanup (a `$:` that tears down what its last run set up) is not
  covered. `$destroyed` covers the case where the thing lives as long as the
  component.
