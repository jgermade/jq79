# Removing a list's rows in runs, instead of one node at a time

**Status:** proposal. Follows the profile at the end of
[`2026-08-23.component-key-scan.md`](2026-08-23.component-key-scan.md), which
named this as the next thing worth doing. Nothing implemented at the time of
writing.

## The measurement

Clearing 10,000 rows (`clearLarge`), profiled:

| self | share | frame |
|---|---|---|
| 109.9ms | **40.1%** | `removeChild` (native) |
| 102.7ms | 37.5% | `(program)` |
| 13.9ms | 5.1% | `$effect`'s registration/disposal closure |
| 11.2ms | 4.1% | `removeDep` |
| 10.0ms | 3.6% | `indexEffect`'s disposer |

`removeChild` is three times everything the dep index costs put together. It is
also the last substantial regression on the branch (`clearLarge` 103.9 → 155,
of which the index is ~13%) — but the native half was there before any of this
work and is the bigger number either way.

## Why

A `:each` row's `NodeRange` is one `<tr>`, so `removeRange` issues exactly one
`removeChild` per row and `renderEach` issues one `removeRange` per dead entry:

```ts
previous.forEach(bucket => bucket.forEach(entry => {
  entry.fx.dispose()
  removeRange(entry.range)      // 10,000 separate removeChild calls
}))
```

Every one of those is a separate mutation of the same `<tbody>`. The rows are
contiguous siblings and they are all going — the browser is being asked to
unlink them one by one for no reason.

## The proposal

Dead entries are already known as a set, and the old `entries` array is still
in hand and in DOM order. Walk it, group consecutive dead entries into runs
(confirming adjacency as it goes — `run.last.nextSibling === next.first` — so a
gap left by an entry removed earlier in the same pass starts a new run rather
than swallowing a live one), and delete each run with a single DOM `Range`:

```ts
range.setStartBefore(run[0].first)
range.setEndAfter(run.at(-1).last)
range.deleteContents()
```

Both boundaries sit *between* nodes, so nothing is partially selected and
`deleteContents` unlinks whole nodes only. A run of one keeps using
`removeChild`, which is cheaper than building a `Range` for it.

`entry.fx.dispose()` still runs per entry — this changes how the DOM is
unlinked, nothing about teardown of effects.

Operations this can help: `clearLarge` (10,000 rows, one run), `replace1k`
(1,000 rows, one run — `buildData` hands out fresh ids, so no old key survives
and every old entry is a leftover). `removeRow` removes one row and is
unaffected by design; `appendToLarge` removes nothing.

## What it costs

- One `Range` object per run, against N-1 saved `removeChild` calls.
- The adjacency check is one property read per dead entry.
- `removeRange` itself is untouched, so the `:if` branch swap and the
  single-entry replacement inside the diff behave exactly as they do now.

## Rejected

- **Emptying the parent** (`tbody.textContent = ""`) when every entry is dead:
  the fastest possible clear, and wrong — a `:each` does not own its parent. Its
  anchor comment lives there, and so can any sibling markup the template put
  around it.
- **Removing into a `DocumentFragment`** (append the run to a throwaway
  fragment, drop it): still one move per node, so it trades `removeChild` for
  `appendChild` and saves nothing.
- **Batching the removal inside `removeRange`** rather than in `renderEach`:
  `removeRange` sees one range and cannot know another one follows it. The
  grouping needs the caller's knowledge of what else is going.

## Open

- The same grouping would apply to `moveRangeAfter` during a reorder
  (`swapRows` moves rows one node at a time too), but that operation is 7ms and
  nowhere near the profile's top. Not worth it until it is.

## 2026-08-23 — implemented

Landed as proposed: `contiguousRuns` groups the dead entries out of the old
`entries` array (confirming `last.nextSibling === next.first` as it goes),
`removeRuns` deletes each run with one `Range` and falls back to `removeChild`
for a run of one. `renderEach`'s leftover pass collects the dead into a set,
disposes each entry's effects as before, and hands the runs over. 735 tests
green, unchanged.

**The container's baseline drifted mid-session** — `create1k` measured 50.6 and
50.8 earlier in the day and 124.2 on the first run of this change, on code that
does not touch the create path. So this was measured as a back-to-back A/B
against the same build with the change stashed, rather than against the numbers
in the previous file:

| op (mean, ms) | HEAD, now | with runs |
|---|---|---|
| **clearLarge** | **150.2** | **135.8** (and 120.1 / 126.7 on two more runs) |
| replace1k | 64.2 | 60.5 (60.3 / 62.1) |
| create1k | 58.5 | 58.3 |
| create10k | 557.6 | 572.1 |
| appendToLarge | 208.4 | 212.1 |
| removeRow | 22.3 | 21.9 |
| partialUpdate | 1.50 | 1.48 |

`clearLarge` ~150 → ~127 (-15%), `replace1k` ~64 → ~61 (-5%). Everything else
is unchanged, as expected — they remove nothing, or remove one row.

### The win is smaller than the profile implied, and here is why

The profile put `removeChild` at 40.1% of `clearLarge`; removing that call
10,000 times over did not remove 40% of the time. `Range.deleteContents` still
has to unlink all 10,000 nodes — what it saves is the per-call overhead of
entering the DOM 10,000 times, not the unlinking itself. A sampling profile
attributes the whole cost to the frame that does the work, which reads as if
the frame were the cost; it is worth remembering next time a native frame looks
like an easy 40%.

`clearLarge` is therefore still above its pre-branch 103.9ms, at ~127. The
remainder is the dep index's teardown (~13% of the operation, profiled in the
previous file) plus the unlinking that no batching removes.
