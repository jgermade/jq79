# Closing the gap with Svelte

**Status:** a plan, five proposals, nothing built. Written before `src/` is
touched. It starts from a question - *why is Svelte this much faster, and what
can jq79 do about it* - and from a correction the author made the same day:
jq79 is **"no bundler required", not "no compiler"** (the same line
[`2026-09-23.no-unsafe-eval.md`](2026-09-23.no-unsafe-eval.md) drew). Code
generated in the browser, once per definition, is inside the line.

[`2026-08-27.what-is-still-open.md`](2026-08-27.what-is-still-open.md) §3 said
the `create1k` gap "is the price of an interpreter with a cache in front of it,
and closing it is a claim about what jq79 is rather than an optimization
anybody has left." That was true of the interpreter. Proposal E is the claim.

## What a list operation costs today, counted

Counting, not timing - it is exact and machine-independent (the method of
[`2026-08-23.where-the-list-operations-go.md`](2026-08-23.where-the-list-operations-go.md)).
The benchmark row, 1,000 rows, on `main` at `0.7.14`, jsdom, every binding
routed through a counter; `key` is `:key` evaluations, so `key / 1000` is the
number of whole-list diff passes:

| operation | key | class | text | in Aug. (that file) |
| --- | ---: | ---: | ---: | --- |
| create | 1,000 | 1,000 | 2,000 | |
| select | 0 | 1,000 | 0 | 1,000 runs |
| **swap** (`data[1] = …; data[998] = …`) | **2,000** | 3 | 6 | 2.0 passes |
| the same swap inside `$batch` | **1,000** | 2 | 4 | |
| update every 10th | 0 | 0 | 100 | 100 runs |
| **remove** (4th of 1,000) | 999 | **0** | **0** | **2,997 runs** |

Two things follow, and the second rewrites part of this plan before it starts:

- **`swap` still diffs the list twice**, once per indexed write, and `$batch`
  (which exists since [`2026-11-12.batch.md`](2026-11-12.batch.md)) halves it.
- **`remove` no longer wakes a single row binding.** The 2,997 runs that
  [`2026-08-23.wake-the-item-not-the-slot.md`](2026-08-23.wake-the-item-not-the-slot.md)
  set out to remove are gone. What `removeRow` still costs is one diff pass and
  one row's teardown - so the proposal that existed to fix the wake
  (dependencies keyed by object, C below) has lost its main reason.

So where Svelte wins is no longer *how many* things re-run. Svelte 5 also
re-runs 1,000 class effects on select. It wins on **what each of them costs**,
and on doing every pass once.

## Why, in one example

Svelte compiles the row into straight-line code, once, at build time:

```js
const tpl = template(`<tr><td class="col-md-1"> </td>…</tr>`)
// per row
const tr = tpl()                                   // one cloneNode
const t0 = child(child(tr))                        // paths resolved by the compiler
template_effect(() => {                            // ONE effect for the row
  set_class(tr, selected === row.id ? "danger" : "")   // compares a cached string
  set_text(t0, row.id)
})
```

jq79 clones the same skeleton (`renderFromSkeleton`, `src/jq79.ts`) and then
**interprets** the plan's ops for every row:

```ts
for (const op of plan.ops) {                       // a 9-way kind dispatch per op per row
  const target = atPath(root, op.path)             // childNodes[i] from the root, every time
  if (op.kind === "text") fx.effect(() => { const t = renderText(op.parts, scope); … })
  else if (op.kind === "class") …                  // classNames + a classList diff
}
```

one closure and one effect per binding, every read through the store's proxy
and its path index. The benchmark's Svelte app also uses `$state.raw` with
immutable updates, so there is no proxy in it at all.

## A. Batch every event handler

**Problem.** Writes notify synchronously, so a handler that writes twice runs
every woken effect twice and shows them a state the author never wrote:
`swapRows`'s first pass diffs a list holding the same row twice.

**Proposal.** `bindEvent` and `wireTagEvent` run the handler inside `$batch`:

```ts
// bindEvent
const handler = evalHandler(expr, scope, { $event: event })
if (typeof handler === "function") $batch(() => handler.call(el, event))

// wireTagEvent
untracked(() => $batch(() => { … }))
```

- `$on` / `$onAny` listeners still hear every write - `$batch` already
  guarantees it, so bridges between stores are untouched.
- A handler that calls `$batch` itself is unchanged: batches flush at the
  outermost.
- An `async` handler is batched up to its first `await`; what it writes after
  that notifies as it does today.
- A throw still flushes and is rethrown - `$batch`'s existing contract.
- `:model`'s input listener is one write, so batching it changes nothing; it
  gets the wrapper anyway, so "a handler is a batch" has no exceptions.
- Behind `Component79.debug({ batchHandlers })`, for `--flags batchHandlers`
  and an off switch.

**What it breaks.** The DOM is not updated until the handler returns:

```js
const edit = () => {
  editing = true
  $self("input").focus()   // today: the <input :if="editing"> exists. Batched: null
}
```

Nothing in this repository does that - every `focus()` and `scrollIntoView`
in the tutorial, the landing and the docs is after `await $mounted()`, not in
a handler - but users' code may. The way out is **`$tick()`**, Svelte's name
for the same thing: a promise that resolves after the pending flush (at once
when nothing is pending), in scope in every setup script.

```js
const edit = async () => { editing = true; await $tick(); $self("input").focus() }
```

Rejected: an `@click.sync` opt-out. One more modifier to learn, it only
covers handlers, and `$tick` is the pattern people already know.

**Expected.** `swap1k_x16`: one diff pass instead of two (counted above:
2,000 → 1,000 key evaluations). Everything else: a `try/finally` per event,
which should not be visible. It is a breaking change for the migration note
even while it sits behind the flag.

**Not proposed here:** batching writes from timers and `fetch` callbacks. That
is a microtask scheduler - every write asynchronous, as in Svelte - and a far
bigger change to what `$reactive` promises.

## B. Setters that compare a cached value

**Problem.** `:class` was measured as the most expensive directive in the row
(~5.5µs, ~4× a text interpolation) in
[`2026-08-23.where-the-create-time-goes.md`](2026-08-23.where-the-create-time-goes.md):
the effect plus `classNames` plus a `classList` diff, and the spelling makes
no difference. Select is 1,000 of them. And `{{ x }}` costs ~1.4µs more than
`:text="x"` for the same binding, because `interpolate` runs its regex per
instance.

**Proposal.** Two fast paths, both on the clone path and in `renderNode`:

```ts
// :class whose expression is an object literal (the benchmark's, and the
// common case): the static classes are known when the plan is built, so the
// effect computes one string and writes className only when it changed
let last: string | undefined
fx.effect(() => {
  const next = staticPart + toggled(evalExpr(expr, scope))
  if (next !== last) el.className = last = next
})

// a text node that is exactly one {{ expr }}: no parts, no regex
let prev: string | undefined
fx.effect(() => {
  const v = evalExpr(expr, scope)
  const s = v == null ? "" : String(v)
  if (s !== prev) node.nodeValue = prev = s
})
```

**What it costs.** Writing `className` owns the attribute: a class added by
other code (a library, `el.classList.add` in a handler) is overwritten on the
binding's next change, where the `classList` diff leaves it alone. That is
observable, and the fast path must stay off any element whose classes jq79
does not own entirely - or it is a decision to document. Open below.

**Expected.** `select1k_x16`, and `create1k` by the regex.

## C. Dependencies keyed by object, not by path - deferred

The proposal from
[`2026-08-23.wake-the-item-not-the-slot.md`](2026-08-23.wake-the-item-not-the-slot.md):
per-key dependency sets on the raw object (Vue's model) instead of the path it
was reached through, so a row binding stops depending on the slot its item
sits in.

**Deferred, because its motivation is gone.** It existed to stop `removeRow`
re-running 2,997 bindings, and the count above says it re-runs none. What it
would still buy - a wake that does not depend on the trie walk - is not a
measured problem. It stays the right model if one appears, and it has to keep
the invariants in `AGENTS.md`: one cached proxy per raw object per store,
identity keyed to the object, nested stores bridged rather than wrapped.

## D. A list jq79 does not wrap

**Problem.** Every `row.label` in a template goes through the store's `get`
trap and registers a path. Measured on a one-cell row: `{{ 1 }}` costs +1.3µs
over the bare row, `{{ row.id }}` +3.4µs - so roughly 2µs of every binding
that reads an item is the proxy and the index, ~6ms of `create1k`'s 3,000
bindings by arithmetic.

**Proposal.** `$raw(value)`, the counterpart of Svelte's `$state.raw`: the
variable stays reactive (reassigning it notifies), but what it holds is never
wrapped, so its items are plain objects and changes come from replacing them:

```js
let data = $raw([])
const update = () => {
  data = data.map((row, i) => i % 10 ? row : { ...row, label: row.label + " !!!" })
}
```

**What it costs.** A second way to hold data, and a footgun: `data[i].label =
…` on a raw list changes nothing on screen, silently. It is only worth it if
the A/B says the proxy is a large share of create - so it is measured last, on
top of A, B and E, with the benchmark app duplicated into a raw variant rather
than changed.

## E. Compile the plan into a function, in the browser

**Problem.** The clone path already does the work once per definition that can
be done once (the skeleton, the ops); what is left per row is interpreting
those ops - the dispatch, `atPath`, `renderText`, a closure and an effect per
binding.

**Proposal.** When a `SkeletonPlan` is built (on the second render, as today -
[`2026-08-24.plan-on-the-second-render.md`](2026-08-24.plan-on-the-second-render.md)),
generate a factory for it:

```ts
type SkeletonPlan = { skeleton: Element; ops: SkeletonOp[]; factory?: RowFactory }
```

For the benchmark row, roughly:

```js
// new Function("tpl", "h", "e0", "e1", "e2", `…`) - once per plan
return (scope, fx) => {
  const tr = tpl.cloneNode(true)
  const n1 = tr.firstChild.firstChild                       // paths resolved at codegen,
  const n2 = tr.firstChild.nextSibling.firstChild           // shared prefixes reused
  const n3 = n2.firstChild
  h.bindEvent(n2, "@click", "select(row.id)", scope)        // modifiers stay where they are
  let c, v1, v3
  fx.effect(() => { const x = h.cls("", e0(scope)); if (x !== c) tr.className = c = x })
  fx.effect(() => { const x = h.str(e1(scope)); if (x !== v1) n1.nodeValue = v1 = x })
  fx.effect(() => { const x = h.str(e2(scope)); if (x !== v3) n3.nodeValue = v3 = x })
  return tr
}
```

- **The generated text holds no user code.** `e0`…`eN` are the functions
  `compileScoped` already builds, passed in; the body is paths and setters. So
  it is a function of the plan's *shape*, it can be cached by that shape, and
  under a CSP without `'unsafe-eval'` it is one more `[params, body]` pair for
  `precompile.ts` and the service worker to emit - the safe-mode table answers
  it like any other.
- B's setters are what E emits, so B lands first and E inherits it.
- Behind `Component79.debug({ compileSkeletons })`, beside `cloneSkeletons`;
  off is the interpreter, unchanged.

**In two phases, because one of them may lose:**

1. **One effect per binding**, exactly today's semantics, generated. Measured
   with `--flags compileSkeletons` on `create1k`, `select1k_x16`,
   `update1k_x16`.
2. **One effect per row**, Svelte's shape: one closure, one effect, one set of
   deps instead of three. This was built in the interpreter and **rejected**
   in [`2026-08-27.grouping-a-row-s-bindings.md`](2026-08-27.grouping-a-row-s-bindings.md):
   `create1k` did not move and `partialUpdate` was 8-18% slower, because a
   label write re-runs the whole row. Generated, the re-run is a few inline
   comparisons rather than three closures - which may change the answer, and
   may not. It is a separate flag value so it can be thrown away alone.

**What it costs.** A third render path. The skeleton differential test
([`2026-08-24.skeleton-differential-test.md`](2026-08-24.skeleton-differential-test.md),
`tests/skeleton.test.ts`) grows a third side - interpreter, clone, factory -
on both of its axes (the DOM and the registration order). One more
`new Function` per plan, amortized the way the plan already is.

**Rejected:**

- *Inlining the user's expressions into the factory.* It ties the generated
  text to the component, breaks the cache by shape and the precompiled table,
  and nothing says a direct call to `e0(scope)` is the cost.
- *Compiling `:if` and `:each`.* They change the shape of the tree and are
  outside the skeleton today. A plan of their own, if E pays.

## Still open

- **B and foreign classes.** Does a bound `:class` own `className` outright
  (Svelte's answer, and faster), or keep the `classList` diff that tolerates
  classes other code added? It is a decision, not a measurement.
- **`$tick` across components.** A handler in a parent whose write re-renders
  a child: `$tick` must resolve after the child's effects too. Since the
  flush is one queue it should, and a test should say so.
- **Where the rest of `swap` and `remove` goes.** After A, both are one diff
  pass over 1,000 rows (999-1,000 `:key` reads, `longestIncreasingRun`, the
  moves) against Svelte's one. Nobody has budgeted that pass on its own; it is
  the next measurement after A, before anything is proposed for it.
- **`appendToLarge` (5.7×) and `create10k` (4.6×)** are not addressed by
  anything here except through E. If E does not move them, they need their own
  profile.
- **The comparison page is three months old.** Regenerating it
  (`npm run benchmark:comparison`) before starting gives every proposal a
  current baseline to be compared with.

## 2026-11-17, later: A built, and the hole it uncovered

A is implemented as planned - `bindEvent` and `wireTagEvent` run the handler
inside `$batch` behind `Component79.debug({ batchHandlers })`, **on by
default** - with `$tick` beside it (`src/reactive.ts`, in scope in every setup
script, typed in the editor). `tests/batchHandlers.test.ts` holds it: one run
per handler against the final state, one diff pass for a two-write swap (three
`:key` reads on a three-row list, not six), the DOM behind until
`await $tick()`, tag events, a throwing handler. With the flag off, four of
them go red. The 1,184 tests that existed pass with it on, the tutorial
included, and so do the extension's 69.

Two things the plan got wrong:

- **`:model` has no input listener to wrap.** It binds component tags only;
  its writeback is the child's `$updateModel`, which runs inside the child's
  handler - and that is now a batch already. Nothing to do.
- **The breakage it named was the small one.** The plan worried about a
  handler that writes and then reads the DOM. The worse one was in
  `docs/reactive-data.md` all along: *"A `$computed` read inside the batch
  still holds its value from before it."* With every handler a batch, this
  stopped working, silently:

  ```js
  const double = $computed(() => n * 2)
  const go = () => { n = 5; send(double.value) }   // sent 2, not 10
  ```

  Writing and then reading what derives from it is the ordinary thing a
  handler does; reaching for the DOM is the rare one. So `$computed`'s proxy
  grew a `get` trap: a read of `.value` while its effect sits pending in the
  batch queue takes it out of the queue and runs it there (unless it was
  disposed while it waited - the flush's own check), so the read is current
  and the flush does not run it again. A computed nobody woke costs a Map
  lookup on `batched`, which is `null` outside a batch. It changes `$batch`'s
  documented behaviour for the better and the doc says so now; two tests
  (one through a handler with a computed of a computed, one through an
  explicit `$batch`) go red without it.

`$tick` is `Promise.resolve()`. That is not a placeholder: every batch -
explicit, a handler's, a write's own dispatch - opens and flushes inside one
call stack, so nothing pending survives to a promise callback. If writes
outside handlers ever become asynchronous (the scheduler this plan declined),
`$tick` is the one place that has to learn about it.

## 2026-11-17, later still: B built, and not yet measured above the noise

B is implemented behind `Component79.debug({ cachedSetters })`, on by
default, in its non-breaking variant: the open question - does a bound
`:class` own `className` outright? - was put to the author and not answered,
so the binding keeps going through `classList` and keeps leaving foreign
classes alone. What it does instead:

- one `bindClass` for both render paths (they had two copies of the effect);
  the names collected with `for...in` into one array instead of
  `Object.entries` + `flatMap`;
- a re-run naming the same classes as the last one touches nothing; a change
  adds and removes only the difference;
- `{{ }}` compares against the last string it wrote instead of reading
  `textContent` back, and renderNode splits each distinct text once instead
  of per instance.

The cost written down in the plan held, plus one it did not name: the old
effect called `classList.add(...next)` on every run, which **put back** a
bound class other code had removed; now it stays removed until the binding's
value changes. `tests/cachedSetters.test.ts` pins it, on both render paths,
and the docs say it. What is exact is the DOM traffic: selecting one row of
fifty produces two attribute mutations, where the old effect produced one per
row (the `classList.add()` call with no names still sets the attribute). Four
of the eleven tests go red with the flag off.

### Measured, and what that is worth

This box was far noisier than the one the earlier sessions used - every
operation's own round-to-round spread came out at ±30-85%. Full suite, 5
rounds × 10 samples: nothing outside the noise. Then the three operations B
is about, on their own, 6 rounds × 30 samples:

| operation | off | on | delta | per round | noise |
| --- | ---: | ---: | ---: | --- | ---: |
| select1k_x16 | 30.4ms | 25.7ms | −18.5% | −4.8 / −30.7 / −33.1 / −17.3 / +12.2 / −19.7 | ±34.4% |
| update1k_x16 | 14.1ms | 12.3ms | −7.4% | −6.4 / −21.2 / −2.3 / −8.5 / −5.0 / −26.4 | ±36.1% |
| create1k | 33.2ms | 35.3ms | +5.5% | −5.2 / −2.2 / +8.2 / +17.2 / +2.8 / +14.8 | ±36.0% |

By the rule in `AGENTS.md` none of that is a result. It leans the right way
on the two operations the change targets (select faster in five rounds of
six, update in six of six) and it shows no sign on create, where the first
full-suite run said +11.8% in every round and this one changed sign twice.
The *Benchmark* workflow on a pull request, or this harness on a quieter
machine, is what has to say it before B is called a win. Until then it is
on by default because it removes DOM writes that were measured, not because
it was measured faster.

## 2026-11-17, last: E1 built, and it did not move create

E1 is implemented as planned, behind `Component79.debug({ compileSkeletons })`
(on by default, and only when `cachedSetters` is too, since the setters it
writes out are that flag's). The benchmark row compiles to:

```js
"use strict"
{ const el = r, c = o[0], k = K[0]; let bound = []; fx.effect(() => { … :class, inline … }) }
const n0 = r.firstChild.nextSibling
const n1 = n0.firstChild
{ const t = n1, e = o[1].parts[0].expr, k = K[1]; let last = t.data; fx.effect(() => { const v = h.ev(k, e, s); … }) }
const n2 = n0.nextSibling.nextSibling
const n3 = n2.firstChild
h.bindEvent(n3, o[2].attr, o[2].expr, s)
…
```

One thing beyond the plan: `evalKeyed`, an `evalExpr` whose key is built once
per plan. `exprKey` concatenates a fresh string per evaluation, and the Map
lookup then hashes it; a held string carries its hash. It holds the key, not
the entry, so a demotion to `with` (which replaces the entry) is still seen.

The skeleton differential test now runs twice - `tests/skeleton.ops.test.ts`
re-imports it with the flag off - because the interpreter is still what
renders a plan under safe mode, and it would otherwise have lost its only
coverage. A sabotaged generated text setter turns 16 tests red. The factory's
params start with `r`, not `$scope`, so `check:precompile` does not count it:
correct for now (safe mode falls back), and phase 3's to change.

| update1k_x16 | 9.8ms | 9.9ms | +2.5% | +39.4 / +7.6 / −9.0 / −3.1 / −2.6 / +7.9 | ±55.3% |
| replace1k | 34.8ms | 33.3ms | −3.8% | −6.2 / −7.3 / −2.6 / +4.5 / −0.7 / −5.0 | ±8.4% |
| create10k | 285.7ms | 279.5ms | −3.5% | −3.9 / −5.1 / −3.9 / −1.3 / +3.9 / −3.2 | ±10.9% |

Nothing outside the noise. `select1k_x16` was faster in all six rounds, and
the create-side operations lean a few percent faster in most rounds, but by
the rule in `AGENTS.md` none of it is a result - and none of it is the 3×
the plan was about.

That is the expected answer, read the right way. E1 removed what the
*interpreter* spent per binding - the dispatch, the path walk, the key - and
left what `what-is-still-open.md` §3 named as the only structural lever: the
number of objects per binding. A row still costs three effects, their
closures, their trie nodes and their dep sets, and a compiled function
creates exactly as many as the interpreter did. Removing the interpretation
was worth single digits; the objects are the rest.

Which makes E2 - one effect per row - the proposal this plan actually rests
on, with its known risk (`partialUpdate` re-running the whole row) now the
only question left. E1 stays on: it is no slower anywhere, it is the
structure E2 needs (a per-plan function can hold one effect as easily as
three), and E2 is a change to what `skeletonBody` emits rather than a new
render path.

## 2026-11-17, E2: built, measured, and off by default

E2 is built as planned, behind `Component79.debug({ rowEffects })`: a compiled
skeleton puts every run of consecutive *guarded* bindings - the ones that
compare before they write: text, `:class`, `:text`, `:value`, `:checked`,
`:selected` - into one effect. Attribute bindings and `:html` write
unconditionally, so a sibling's wake would rewrite them; they keep their own
effect, and they close the run, because the first attempt (one group at the
end of the instance) registered `:text` after `:html` and the skeleton
differential test's order axis caught it. The benchmark row becomes one
effect where it was three:

```js
fx.effect(() => {
  { /* :class */ … }
  { const v = h.ev(k1, e1, s); const x = v == null ? "" : String(v); if (x !== last1) t1.data = last1 = x }
  { const v = h.ev(k3, e3, s); const x = v == null ? "" : String(v); if (x !== last3) t3.data = last3 = x }
})
```

| **update10k_x16** | **101.2ms** | **122.4ms** | **+22.8%** | +24.6 / +20.8 / +28.4 / +24.5 / +21.2 / +14.2 | ±15.4% | **slower, every round** |

The two regressions are the only results this whole session produced besides

### Why, and why Svelte gets away with it

It is the August answer
([`2026-08-27.grouping-a-row-s-bindings.md`](2026-08-27.grouping-a-row-s-bindings.md))
with the interpreter taken out of the excuse. Selecting a row wakes 1,000
rows; per binding that was 1,000 `:class` runs, grouped it is 1,000 runs of
all three bindings - three evaluations where one was needed, and each one a
read through the store's proxy that re-registers its path in the dep index.
An update wakes one row per changed label and now pays for the `:class` and
the id beside it. What creation saved by building one effect instead of three
it gives back, and more, on every wake.

Svelte groups a row's bindings into one `template_effect` and does not pay
this, because a re-run there is a few signal reads - a property access and a
push onto an array - and comparing a cached string. Here a re-run is a proxy
`get`, a path built, and a trie updated, per read. **Grouping is only cheap
when re-reading is cheap.** So this is not a proposal to retry with a better
generator; it is the same wall as C and D from the other side: the cost
that matters is what a *read* costs in the store, and nothing in E touches it.

### What changed

`rowEffects` defaults to **off**, and the comment on the flag says why. The
code stays for now, held to the interpreted render by
`tests/skeleton.row-effects.test.ts` (the differential test a third time, with
the flag on), so the measurement can be repeated on a quieter machine -
whether to delete it is the author's call. E1 stays on: it is unaffected, and
it is the per-binding factory that now renders by default.

### What the plan rests on now

- **A** is the one shipped win (swap −64%).
- **B** and **E1** are on and lean faster on select, unproven by the rule.
- **E2** is rejected for the second time, now with a mechanism.
- The create gap is the cost of a reactive read - which is **D** (`$raw`,
  no proxy under the list) or a store whose reads are cheaper (the territory
  of **C**). Neither is a codegen problem.

## 2026-11-17, D: `$raw`, built and measured - the largest result of the plan

`$raw(value)` is implemented in `src/reactive.ts` as a mark on the object (a
`WeakSet`) that `isPlainData` answers *no* to - so to the store a raw array is
what a class instance always was: held, never wrapped, and replaced whole
rather than diffed (`replaceable` asks the same question). Two rules on top:

- **A raw value's replacement is raw.** The mark is checked in the `set` trap
  against the value being replaced, so `let data = $raw([])` and then
  `data = data.map(...)` keeps the list raw without the author repeating it.
  The plan wrote the mark as the variable's; the variable is not an object,
  so it lives on the value and is handed on at each assignment.
- **The mark travels with the value**, into a second store, a prop, a
  child's store - it is the object that is marked, not the key.

Nothing else had to change. A keyed `:each` already re-runs a row whose key
maps to a new item (`swapped`, PR #25), which is what an immutable update
produces; and an item scope is `Object.create(scope)` holding the item as it
came out of the list, so a raw list's rows are plain objects all the way down.
`tests/raw.test.ts` holds both halves, including the footgun: a change made
in place renders nothing.

replaces every tenth row, `swapRows` as a sliced copy - which is what Svelte's

### What it says about the plan

This is what E2's section concluded from the other side: the cost that
matters is what a reactive read costs, and the way to make it cheap is to not
make it. B, E1 and E2 worked on what happens *around* the reads and moved
single digits (or went backwards); D removed the reads under the list and
moved everything. **It is opt-in and changes nothing for code that does not
use it**, which is also why it is the only one of the five that cannot be
measured on the committed benchmark app.

Open:

- **The benchmark app.** The table above came from an app that is not
  committed. Committing the raw variant behind `?raw=1` would let the A/B
  harness re-measure it at will; changing the app's default to `$raw` would
  change what the comparison page compares - closer to how Svelte's app is
  written, but a decision about the page, not about the library.
- **The footgun has no warning.** A write into a raw object is invisible by
  design, and nothing in dev says so. A dev-only check that a raw object was
  mutated between two reads would be possible and would cost a proxy - the
  thing `$raw` exists to avoid - so it is not proposed here.

## 2026-11-17, E2 removed, and the migration note

**E2 is deleted**, at the author's word: the `rowEffects` flag, the
per-plan `rowFactory`, the grouping in `skeletonBody` and
`tests/skeleton.row-effects.test.ts`. A compiled skeleton gives every binding
its own effect, which is what it measured faster with. The sections above
are the record of why; the comment in `skeletonBody` points here.

### Migration note

The library's release notes are generated from pull request titles
(`gh release create --generate-notes` in `release.yml`) and it keeps no
changelog, so the place this reaches someone upgrading is the description of
the pull request that carries this branch. The text, ready to paste:

> **Breaking: an `@event` handler now runs as one batch.** Everything its
> writes update - bindings, `$:`, `$effect` - runs once, after the handler
> returns. A handler that writes state and then reaches for the DOM that
> write produces must wait for it:
>
> ```js
> const edit = async () => {
>   editing = true
>   await $tick()              // new: the DOM has caught up
>   $self("input").focus()
> }
> ```
>
> Reading state is unaffected: a handler sees its own writes, and a
> `$computed` it reads is current. Code after another `await`, `$:` blocks,
> `$effect` and everything after `await $mounted()` are unaffected too.
> `Component79.debug({ batchHandlers: false })` restores the old behaviour.
>
> **Changed: a bound `:class` does not put back a class other code removed**
> until the binding's own value changes. Classes other code *adds* are still
> left alone.
>
> **New:** `$tick()`, and `$raw(value)` for large lists that are replaced
> rather than edited - see
> [reactive data](docs/reactive-data.md#big-lists-you-replace-rather-than-edit-raw).
> And inside an explicit `$batch`, a `$computed` is now current when read,
> where it used to hold its value from before the batch.

### The benchmark app keeps the raw variant, behind `?raw=1`

At the author's word, option (b) of three: the variant `$raw` was measured
with is committed to `frameworks/keyed/jq79/src/App.html`, switched by `?raw=1`
and read by the app itself (it is not a `Component79.debug` flag; `main.js`
says so). Absent, the app is exactly what it was, so the comparison page still
measures jq79 written the idiomatic, mutable way. The measurement above can be
repeated with `npm run benchmark:ab -- --flags raw`; a one-round smoke run
after committing it gave swap −66.9% and removeRow −77.8%, in line with it.

Rejected for now: making `$raw` the app's default. It would put `$raw`'s
numbers on the comparison page - the way the Svelte app there is written -
but it changes what the public page says jq79 costs, which is a decision
about the page and was left with its author.
