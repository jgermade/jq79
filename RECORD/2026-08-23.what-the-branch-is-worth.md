# What this branch is worth, against main

**Status:** the end-to-end measurement, recorded because the per-change files
each answer a different question and none of them answers this one. Also
because the baseline is easy to get wrong: a stale `origin/main` in a fresh
clone read 0.5.12, and measuring against *that* credits this branch with the
whole previous campaign - the dep trie, the wake rule, the container diff, the
fragments. **main is 0.6.0**, and what follows is three commits:

- `perf(each): stop building a scope per row per pass, and write only what moved`
- `perf(each): move only the rows that moved, not every row behind them`
- `perf(each): read a plain :key off the item instead of compiling and evaluating it`

## Counted, exact, machine-independent

| | main (0.6.0) | HEAD |
|---|---|---|
| `insertBefore` to swap two rows of 1,000 | **997** | **2** |
| bindings re-run per operation | — | *identical* |
| DocumentFragments per 1,000 rows | 0 | 0 |

The wake counts do not move, and that is correct: none of these commits touches
reactivity. The 3,006-to-6 reduction on a reorder belongs to the previous
campaign and is already in main - worth stating, because measuring against
0.5.12 makes it look like this branch's.

## Timed

adjacent-row swap so no DOM volume gets in the way):

| clearLarge | 122.6 | 125.3 | +2.2% |

**`selectRow` is the control.** It is one write waking 1,000 class bindings with
no diff pass anywhere in it, so nothing here can move it - and it reads -9.8%.
The noise band is still ±10%, and it swallows `removeRow`, `partialUpdate` and
much of `create10k`.

`swapRows` is the one number outside all doubt: -27%, separated in every round
(9.9/9.45/9.35 against 6.9/6.6/8.1). It is also the operation that runs the diff
pass twice and reorders, so it collects both of this branch's wins at once.
`appendToLarge` and `replace1k` are outside the band and in the right direction -
both run a full pass with 1,000 key evaluations - but with rounds that overlap:
real, and not to be quoted to the decimal.

## Why the pass number and the operation numbers disagree

A pass got 1.9x cheaper and no operation did. An operation is one or two passes
plus everything else: the click dispatch, the store writes, the DOM, and - on
`removeRow` - 2,997 binding re-runs that this branch does not touch and
[`wake-the-item-not-the-slot.md`](2026-08-23.wake-the-item-not-the-slot.md)
proposes removing. The pass is where the work was; the operation is where the
user is, and most of the operation is still elsewhere.
