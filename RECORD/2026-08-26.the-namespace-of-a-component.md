# The namespace of a component is its parser's, not its usage site's

**Status:** a plan, and it proposes nothing yet. `src/` untouched. It states a
question that came out of §1's browser work
([`2026-08-25.what-the-browser-said.md`](2026-08-25.what-the-browser-said.md)),
gives it the measurements it needs, and lays out four answers with what each
costs. The decision is the author's.

---

## The symptom

```html
<svg viewBox="0 0 100 100"><Dot /></svg>

<template name="Dot"><circle r="8" /></template>   <!-- draws nothing -->
```

The `<circle>` **is in the DOM** and does not paint. Measured in chromium 151,
firefox 153 and webkit 26.5 - unanimously, so it is not a browser's opinion.
It is pinned by a test and documented in
[`docs/template-syntax.md`](../docs/template-syntax.md), which tells the author
to root such a component at `<svg>`.

## The mechanism, and why nobody saw it before

`elementToAST` takes the namespace from the parser and nowhere else:

```ts
const ns = el.namespaceURI
```

A component's template is parsed **on its own** - `parseComponentString`, once
per definition, its AST shared by every instance - and there `<circle>` sits
inside no `<svg>`, so it comes out HTML and `createFor` calls
`createElement("circle")`.

Underneath: **a namespace is a parse-time fact and a usage site is a render-time
fact.** For one template they always coincide, which is why this held for years.
A nested component is the first thing that separates them - the usage site knows
its namespace (`node.ns` is exactly what decides whether it gets a box), and the
child's AST was built without it.

## The question

**Should a component take the namespace of where it is used, or is a template
deciding its own namespace the right answer?**

Nobody has argued it. What follows is what an argument would need.

## Nobody in this repository hits it

Checked rather than assumed: **no component tag appears inside an `<svg>`
anywhere in this repo** - not in the tutorial, not in the site, not in the
benchmark app. So today nothing here would be fixed by a change, and nothing
here would pay for one. The demand is real (an icon or a chart piece as a
component is an ordinary thing to want) and it is entirely outside these tests.

## The four answers

### 1. Leave it, as it is today

The limitation is documented and pinned. Cost: nothing. Price: the failure is
silent - an element in the DOM, no drawing, no message.

### 2. Warn

`renderNestedComponent` already knows `node.ns`; when it is set and the resolved
child's first root has no `ns` of its own, say so once per usage site. No
behaviour change, cheap, and it turns a blank diagram into a sentence. It is the
shape this codebase already uses for everything that silently does nothing.

**It stays useful even if 3 or 4 ships**, for the case neither covers: a
component written for HTML, used inside an `<svg>` by mistake.

### 3. Re-namespace at create time

Thread the usage site's `ns` down the child's render and call
`createElementNS`. This is what Vue does (its `isSVG` flag through patch).

It decides by **our** rule rather than by the parser's, and the rule has to
answer things the parser answers for free: what happens to a `<div>` inside, to
`<foreignObject>`, to the case-sensitive names. This repository has been here
before and picked the other side - see
[`2026-08-25.svg-attribute-names.md`](2026-08-25.svg-attribute-names.md), where
shipping a table lost to asking the parser.

### 4. Re-parse the child's template in a foreign context

When a usage site is foreign, parse that definition's template again inside an
`<svg>` (or `<math>`) wrapper and render *that* AST. The parser decides
everything, exactly as it would for the same markup written inline.

**Measured in chromium, parsing the way `parseComponentString` parses (a
`<template>` wrapper, self-closing tags already expanded):**

| written in the template | parsed today | parsed inside `<svg>` |
| --- | --- | --- |
| `<circle r="8">` | `CIRCLE` html | `circle` **svg** |
| two roots, `<circle>` + `<rect>` | both html, siblings | both **svg**, siblings |
| `<linearGradient>` | `LINEARGRADIENT` html | `linearGradient` **svg**, case intact |
| `<foreignObject><p>` | html | `foreignObject` svg, `p` **html** - the parser hands the namespace back for free |
| a nested component tag (`c79-dot`) | html | **svg**, which is what makes the no-box rule apply to it too |

Two things it also found, and they are the reason this is a plan and not a patch:

- **An HTML root escapes the wrapper.** A component whose root is `<div>` does
  not become an SVG `div` - the HTML parser *breaks out* of foreign content for
  it, and it lands **outside** the `<svg>` entirely. Measured: `inside: []`,
  `escaped: ["DIV:html"]`. So the re-parse does not merely re-label nodes, it
  can relocate them, and a component that renders HTML would come back with a
  different shape than it was written in.
- **`<script>` and `<style>` change class.** In a foreign context they parse as
  SVG-namespace elements whose `tagName` is lowercase, and `componentPartsFrom`
  splits on `el.tagName === "SCRIPT"` / `"STYLE"`. Re-parsing the whole
  component source in context would file a setup script as *markup*. The fix is
  to re-parse **only the template markup**, after the ordinary parse has lifted
  the blocks - which needs the template's source, and today the parts pipeline
  keeps only its AST.

**What it costs to run:** one extra parse of ~170 µs, *once per definition per
context* (measured: 169 µs for a typical component, 171 µs for the same inside
an `<svg>` wrapper, 245 µs for a 40-node template). Against ~48 µs per instance,
a definition pays about three and a half instances, once, and only if it is used
in a foreign namespace at all.

**What it does not disturb:** the memo caches are `WeakMap`s keyed by the AST
*node* (`skeletonPlans`, `eachPlans`, `chains`), not by a definition's name, so
two ASTs of one definition coexist without colliding.

## What is still open, and would have to be answered before any of this

- **Hot reload with two ASTs.** `hotReplace` assigns `this.template = parts.template`
  from one parse. A second, context-specific AST has to be rebuilt or discarded
  there, and nothing today says which.
- **A definition used in both contexts at once.** Two ASTs, two stamps to apply
  (`stampScope` walks the AST) - the hash is the source's, so both should agree,
  but "should" is not a measurement.
- **`<math>` too, or only `<svg>`?** The exception in `componentBox` covers both;
  a re-parse would need a wrapper per namespace.
- **Where the second parse is triggered from.** Lazily, on the first foreign
  usage site, is the only shape that costs nothing for the common case - but it
  puts a parse inside a render pass, which is where nobody wants surprises.
- **Whether an HTML-rooted component in an `<svg>` should be an error rather
  than a relocation.** The breakout above is the platform's answer to markup
  nobody should write; a library repeating it silently is a different decision
  from refusing it.

## How each claim would be checked

Sabotage first, per the rule PR #13 earned - written here so the list exists
before the code does:

| claim | sabotage that must turn it red |
| --- | --- |
| a foreign usage site renders its child in the foreign namespace | keep using the HTML AST |
| an HTML-rooted child is refused or warned, not silently relocated | let the escaped node through |
| the second parse happens once per definition per context | count parses across N instances |
| a `<foreignObject>` still hands HTML back | assert the namespace of its children |
| scripts and styles are still scripts and styles | re-parse the whole source in context |
| hot reload rebuilds both ASTs | patch a definition used in both contexts |

## What I would do

**2 now, 4 as its own change** - and 4 only once someone wants it, because no
component in this repository is waiting for it. The warning is small, it cannot
break anything that works, and it converts the failure this whole file is about
into one line on a console. The re-parse is the right shape when the demand
turns up: it asks the parser instead of us, which is the move this codebase has
already made once and has not regretted.

## Update, 2026-08-27: the question was answered, and it is answer 1 + 2

The author's call, in their words: *an SVG partial does not need to be a
component — `<svg>` is a special node and its content has to live inside it from
the start.* So **a component's template decides its own namespace**, which is
what the code already did, and answers 3 and 4 (re-namespacing at create time,
re-parsing the child in a foreign context) are closed rather than deferred. The
measurements for 4 stay in this file because they cost a morning and because
they are what a future argument would have to beat, not because anyone is going
to build it.

What shipped is answer 2, which this file recommended and which is now the whole
of the change: `warnForeignRoot` says, once per usage site,

```
jq79: <Bare> is used inside <svg> and its template starts with <circle>, which is
parsed as HTML - it renders and never draws. A component's template decides its
own namespace, so root it at <svg>
```

Once per usage site and not per instance - a `:each` of 1,000 rows shares one AST
node, and a `WeakSet` on it is what keeps the console readable. Four tests, three
sabotages red: the warning silenced, the root check inverted (it must stay quiet
for a template that *is* rooted at `<svg>`), and the once-per-site guard removed.

The limitation it reports was already documented; what it did not have was a
voice. That was the whole complaint.
