# A key is a row, not an object

**Status:** implemented. Reported against 0.6.4 alongside the nested-store
over-wake (already fixed by then; checked in Chromium on 0.7.2), with a
reproduction.

## The problem

```html
<script :setup>
  const { store } = await import("./store.js")
  $: rows = store.items.map(item => ({ ...item }))
</script>
<ul><li :each="row in rows" :key="row.id">{{ row.id }}</li></ul>
```

Every time `rows` is recomputed, every `<li>` is removed and created again, with
the same keys. That costs time, and it throws away focus, scroll and anything
the user typed.

`renderEach` reused an entry only when **both** the key and the item reference
matched (`Object.is(existing.item, item)`). A new object under an old key was
disposed and rendered again. The comment said so ("changed/added ones are
(re)rendered"), so this was by design, but it is not what `:key` promises.
Deriving rows with a spread is the ordinary way to write a view model, and it
makes every row "changed" on every pass.

## The fix

With an explicit `:key`, a known key with a new object keeps the row:

1. The loop name in the row's scope is set to the new item, along with `$index`
   and the second binding. These are plain assignments, as on the existing
   reuse path.
2. The entry goes through the positioning pass like any other reused row.
3. After positioning, the row's effect scope is **re-run**
   (`EffectScope.rerun`). Each effect re-runs **tracked**, so its deps move from
   the old object to the new one.

The tracking is the important part. The loop name is a plain scope var, so
nothing wakes a binding when it changes, and a binding that is re-run untracked
(as `refresh` did) keeps the old object's paths. It would then follow writes to
the old object and miss writes to the new one.

### Reaching what a row rendered in scopes of its own

A row's bindings are not all on the row's scope. An `:if` branch, a nested
`:each` and its rows, a component's prop sync, and slot content the row hands a
component each live in an effect scope of their own. Slot content is created by
the child component's `<slot>`, so it is not even created by the row's renderer.

What they all share is the **data scope**: each is created over a scope whose
prototype chain passes through the row's item scope. So a keyed row's item scope
carries `OWNER` (a symbol, non-enumerable), pointing at the row's effect scope.
`Scope`'s constructor reads it the same way it already reads `ALSO_WAKEN_BY` and
registers itself as a child. `rerun` walks the row's own effects, then its
children's, in creation order. A child disposed by an earlier re-run (an `:if`
that switched branch) has nothing left to run, and the branch that replaced it
was rendered against the new item.

The array-replacement sweep often reaches these bindings anyway (`rows = [...]`
wakes everything under `rows`), so a test of the plain case passes without the
registry. It doesn't reach them once a reorder has left an object tracked under
the path it was first read at. The test reorders first and then swaps one item,
and it fails without `OWNER`.

### `refresh` re-runs tracked too

`Scope` now keeps the effect records (from a module-level `created`, set as
`$effect` returns) instead of the raw `run` functions. `refresh`, which reaches
moved rows that name a position, goes through them as well. Its callers still
wrap it in `untracked`, so nothing lands on the list effect. A re-run that reads
what it read before hits `indexEffect`'s unchanged fast path.

## What it costs

- One `defineProperty` per **keyed** row rendered (the `OWNER` mark), and one
  more symbol lookup up the scope chain per effect scope created.
- A `Set` per keyed row that renders a scope of its own, and only then.

## Rejected

- **Keyed rows only re-run their own effects** (`refresh`, made tracked). This
  misses `:if` branches, nested lists, prop syncs and slot content: everything
  the registry exists for.
- **Making the loop name a tracked read** (a getter that records a synthetic
  dep, woken by the list). This would reach everything with no registry, but it
  gives every row binding a second dep, and `indexEffect` keeps a binding with
  one dep in two slots and allocates a `Map` for the second. That is a `Map` per
  binding per row on `create1k`, to serve a case most lists never hit.
- **Doing the same without `:key`.** Without `:key` the key is a position, and a
  different object at the same position is not "the same row" in any sense the
  author stated. A component instance in that row would keep its internal state
  across what is really a different item. Unkeyed lists keep rendering a
  changed item again.

## Later the same day: the CI benchmark, and a slot the registry missed

**The cost was measurable.** The Benchmark workflow on the PR measured
*Replace all 1,000 rows* at +3.9%, slower in all 4 rounds, against ±2.8% noise.
Replacing the rows creates 1,000 new keyed rows, and each one paid for the
`OWNER` `defineProperty`. Every other operation was inside the noise. Most rows
have nothing to register (the benchmark's rows have no `:if`, list, component or
slot), so the mark is now set only when the item template can render into an
effect scope of its own (`rendersScopes`, decided once per template in
`eachPlanOf`). That means a conditional chain, a `:each`, a component (a
capitalized or dashed tag, the only spellings `componentKeyOf` resolves) or a
`<slot>`. A row without any of these is fully covered by re-running its own
effects.

**Slot content reached the wrong way round.** The first version covered slot
content the row hands *down*: written in a keyed row, so the content scope's
chain passes through it. It missed the reverse case, where the keyed row is the
child's and holds `<slot :item="row">`, and the content was written in the
parent. That content's chain is the parent's and never meets the row; it reads
`row` through the slot prop's thunk, evaluated against the slot site. So slot
content now also registers with the owner of the slot site
(`EffectScope.ownedBy(slotScope)`), and a scope can have more than one owner.
The test that covers it reorders first, like the one above, and fails without
the line.
