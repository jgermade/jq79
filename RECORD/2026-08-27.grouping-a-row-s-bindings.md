# Grouping a row's bindings, once the names are known

**Status:** a plan, written before touching `src/`. It is phase 2 of
[`2026-08-27.name-resolution-without-with.md`](2026-08-27.name-resolution-without-with.md),
whose §"What it does not do" names this as the larger half of the same
milliseconds - and it is only proposable because that change built the
instrument it needs.

---

## The problem, priced again on this box

`renderNode` and `renderFromSkeleton` create **one effect per binding**. An
effect costs about as much to exist as its dependencies cost to track. Measured
here - 1,000 rows of three bindings, `store.$effect` straight over a
`$reactive`, no DOM at all:

| arrangement | create |
| --- | --- |
| 3 effects, one dep each - what the renderer does | 16.6 ms |
| 1 effect reading three deps - what Svelte compiles | **8.7 ms** |
| 1 effect, one dep - the floor | 3.9 ms |

So an effect is ~3.9 µs of fixed cost on this runner, and a benchmark row pays
three of them. `create1k` is ~34 ms for 1,000 rows.

## Why the obvious version of this is a regression

[`2026-08-23.where-the-create-time-goes.md`](2026-08-23.where-the-create-time-goes.md)
priced "group a row's three bindings into one effect" at ~8% of `create1k` and
left it as a decision nobody had made. **Made naively it would hand back the
win that just landed.** The benchmark row is

```html
<tr :each="row in rows" :key="row.id" :class="{ danger: row.id === selected }">
  <td>{{ row.id }}</td><td>{{ row.label }}</td>
</tr>
```

and `selectRow` writes **one** name, `selected`, that only the `:class` binding
reads. One effect per row means every row's two text bindings re-evaluate on
every selection - 2,000 evaluations that today do not happen. `selectRow` is
5.8 ms and was just measured 15-22% faster; this would spend that twice over.

## What makes it answerable now

`freeIdentifiers(expr)` says which names a binding reads, at plan time. So the
rule is not "a row" but **the same names**:

| binding | names | |
| --- | --- | --- |
| `{{ row.id }}` | `row` | ⎫ one effect |
| `{{ row.label }}` | `row` | ⎭ |
| `:class="{ danger: row.id === selected }"` | `row`, `selected` | its own effect |

Three effects become two, and **nothing wakes that did not wake before**: a
group's dependency set is the union of members that already had the same names,
and `selected` never enters it.

Two restrictions keep it honest:

- **Only a contiguous run of ops.** Effects run in registration order, and
  `renderFromSkeleton` relies on it (a `:value` on a `<select>` must run after
  the `<option>`s). Grouping only ops that are already neighbours in `plan.ops`
  means no op ever moves.
- **Only ops whose write is compared.** `text` already compares before writing,
  and `value` does. `textContent`, `checked` and `selected` are one comparison
  away. `attr`, `attrs` and `class` write unconditionally, so grouping them
  would put an extra DOM write on the wire for every wake of a sibling's
  dependency - which `tests/skeleton.test.ts`'s order axis would see, and
  rightly. They stay out of this change.

## The residual, stated plainly

**The same names are not the same dependencies.** `{{ row.id }}` and
`{{ row.label }}` both read `row` and record `rows.7.id` and `rows.7.label`.
Grouped, they share one effect whose dep set is both, so a write to `row.id`
re-evaluates the label binding too. That is the trade Svelte makes and the
reason `set_text` compares: it is one extra *evaluation* (~316 ns now) and zero
extra DOM writes.

Bounded: a write wakes a group once and re-evaluates its members, so the cost is
(group size − 1) evaluations per wake, against 3.9 µs saved per effect removed
at create.

## Where it goes, and where it does not

**The skeleton plan only.** `plan.ops` is already a flat, ordered list built
once per definition, which is exactly where a grouping decision belongs - and
the clone path is what renders a `:each` row from the second instance onward.
The interpreted path (`renderNode`) keeps one effect per binding, so the two
paths differ in *how many effects* they create and not in what they render,
which `tests/skeleton.test.ts` is built to check.

## What I expect it to be worth

The benchmark row loses one effect of three: ~3.9 ms per 1,000 rows against a
34 ms `create1k`, so **~10% if the isolated number carries**, and nothing on
`selectRow`. A row of five text cells over one item loses four effects of five.

It will be measured the way the last one was: `Component79.debug` flag,
`npm run benchmark:ab -- --flags groupBindings`, two independent runs, signs
across rounds.

## How each claim will be checked

| claim | sabotage that must turn it red |
| --- | --- |
| grouped bindings still render | make the group run only its first member |
| a group's members keep their order | reverse the group before running it |
| only same-name ops group | group by op kind instead of by names |
| an unextractable expression is never grouped | group it anyway and assert the effect count |
| `selected` never joins a row's text group | group contiguous ops regardless of names |
| a grouped write is still compared | drop the comparison and watch the order differential |

## What is still open

- **`attr`, `attrs` and `class`**, left out above. Each needs its write
  compared before it can join, and `attrs` needs its remove-then-add rewritten
  as a diff.
- **The interpreted path**, which keeps one effect per binding. A definition
  rendered once pays no plan and no grouping.
- **Cross-element grouping beyond a contiguous run** - `{{ a }}<span>{{ b }}</span>{{ a }}`
  leaves two groups where one would do.

## Update, 2026-08-27: built, measured, and rejected

It was implemented exactly as proposed - a signature per op, contiguous
same-signature runs off one effect, a `groupBindings` flag to pair it against
itself - and **it does not pay**. `src/` keeps none of the grouping; what
follows is why, because the next person to price this should start from here
rather than from the isolated number at the top of this file.

### The benchmark found a defect the tests could not

The first run measured **nothing at all** - every operation inside the noise,
`create1k` at +4.7%. The reason is the benchmark row:

```html
<td class="col-md-1">{{ row.id }}</td>
<td class="col-md-4"><a @click="select(row.id)">{{ row.label }}</a></td>
```

`plan.ops` is `class, text, event, text, event`, and the rule said *contiguous*.
The `@click` sits between the two text bindings, so **no group ever formed** on
the one template this was written for. An event installs a listener and creates
no effect, so stepping over it moves nothing; with that fixed the row grouped
three effects into two.

Worth stating plainly: six sabotages went red against the grouping tests, and
none of them could see that the feature never fired on real markup. The
benchmark was the test.

### What it costs, once it works

Two independent runs, chromium 141, one bundle against itself, `groupBindings`
off then on:

| operation | run 1 (4×10) | run 2 (4×12) |
| --- | --- | --- |
| Create 1,000 rows | +0.2%, mixed | −0.8%, mixed |
| Create 10,000 rows | +1.1%, mixed | −2.7%, mixed |
| **Update every 10th row** | **+18.0%, slower every round** | **+8.3%, slower every round** |
| Select a row | −0.7%, mixed | +4.0%, slower every round |
| Clear 10,000 rows | −7.3%, faster every round | −6.4%, faster every round |

**The create saving never appears, and the update cost does.** The trade this
file proposed was "one effect fewer per row, one extra evaluation per wake";
what the runner says is that the first half is unmeasurable and the second half
is 8-18% of `partialUpdate`, in every round of both runs.

The one consistent gain is `clearLarge`, −6 to −7% in every round of both runs,
which is the same fact from the other end: two effects per row are cheaper to
*dispose* than three. Teardown can see the effect count; creation cannot.

### So the isolated number was wrong about the renderer

The table at the top of this file says an effect costs ~3.9 µs to exist. If that
carried into the renderer, removing one of a row's three would be ~15% of a
25.7 ms `create1k`, and it is not there at all. The micro built 1,000 effects by
calling `store.$effect` in a loop, each closing over its own `store.rows[i]`
read; a binding inside a `:each` row goes through `Scope.effect`, whose options
object and disposer list are already shared per row
([`2026-08-23.where-the-create-time-goes.md`](2026-08-23.where-the-create-time-goes.md)
took that apart). **The fixed cost of an effect in situ is much smaller than the
fixed cost of an effect in a micro**, and this file is the evidence.

That is the third time on this project that a per-element/per-binding saving
priced in isolation has failed to show up in the renderer - the `WeakMap` node
plan, the `NodePlan` on the node, and now this.

### What was kept

Nothing of the grouping. Two things that stand without it:

- **`:text`, `:checked` and `:selected` compare before they write**, on both
  paths, which `:value` and the text-node binding already did. An unchanged
  `el.textContent = same` still replaces the element's child text node, so
  anyone holding a reference to it gets a different node for the same string.
  Pinned by a test that had to be written twice: the first version set the same
  value on the store, which the store's own guard drops before any effect runs,
  so it could not fail.
- **The measurement path**: `npm run benchmark:ab -- --flags <name>` now prices
  any `Component79.debug` flag, not only `cloneSkeletons`.

### What would change the answer

- **A row with several bindings over one item and no event between them** - a
  read-only table, a card list - is the shape this helps, and it is not the
  shape the benchmark measures. Nobody has that app in this repository.
- **`attr`, `attrs` and `class` joining the group** once their writes are
  diffed: the benchmark row's `:class` is the one binding that would matter, and
  it reads `selected`, which is precisely the name that must NOT join a row's
  group.
- **A cheaper effect**, which is the same wish from the other side: if
  `Scope.effect` got cheaper, grouping would matter less, not more.
