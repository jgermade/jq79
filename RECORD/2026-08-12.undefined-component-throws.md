# A `<PascalCase>` tag that names no component should throw

**Status:** proposal.

## The problem

A component tag whose name resolves to nothing renders as an inert unknown
element, and nothing is logged:

```html
<script :setup>
  import UserCard from "./UserCard.html"
</script>
<UserCrad :user />          <!-- the typo -->
```

renders `<usercrad></usercrad>` and says nothing. The same silence covers the
import that was never written, the component renamed in one file and not the
other, and the sibling `<template name="Row">` that was deleted.

This is the last silent hole in the render path. Everything nearby now speaks up:
an expression that throws is a `console.error`
([`2026-08-08.expression-errors.md`](2026-08-08.expression-errors.md)), a name
that resolves nowhere is a warn
([`2026-08-08.reporting-issue.md`](2026-08-08.reporting-issue.md)), a component
*variable* holding a non-component is a `console.error`
([`2026-08-05.multi-template-file.md`](2026-08-05.multi-template-file.md)). Only
the tag that names nothing at all is quiet — and it is the loudest failure of
the three, because the whole subtree is missing rather than one value.

### Why this one throws where the others log

Every diagnostic before this one described something that still rendered. A
misspelled `:` directive
([`2026-08-07.unknown-directive-warn.md`](2026-08-07.unknown-directive-warn.md))
rejected throwing on exactly that ground: "a bug to live with while you find it,
not a reason to refuse to render."

This is the case where there is nothing to live with. `<UserCrad />` renders no
markup, no styles, no children, and no script — the page is missing a region,
and the runtime knows the name is unresolvable at the moment it renders. A
diagnostic on the console competes with whatever else is on the console; an
exception stops on the frame that has the usage site in it.

## What "names no component" has to mean

Three things separate this from the cases that stay quiet.

**1. The author wrote it capitalized.** `<UserCard />` is never valid HTML and
never a custom element (those must be lowercase and contain a dash), so an
uppercase-initial tag can only ever have meant a component. A lowercase unknown
tag cannot be judged: `<lable>` is a typo, `<my-widget>` is a legitimate
custom element, and — measured, not assumed — `document.createElement("svg")`
returns an `HTMLUnknownElement` too, so `el instanceof HTMLUnknownElement` as
the test would make every inline SVG fatal.

The casing is **not** available today. `DOMParser` lowercases tag names, and
`expandNameCase` deliberately leaves component tags alone ("findComponentKey
already matches them case-insensitively... rewriting it would only obscure what
the author wrote"). It has to be captured before the parse.

**2. Nothing in scope matches.** `findComponentKey` already answers this, and it
is a different question from the ones `renderNestedComponent` reports: those
have a key and an unusable *value*. This one has no key.

**3. No script is still in flight.** The load-bearing exception, and it is not
hypothetical — verified against the current build:

```html
<script>
  export default async () => {
    await $mounted()                    // render now, fill in after
    return { Late: await import("./Late.html") }
  }
</script>
<div><Late /></div>                     <!-- renders when the import lands -->
```

A factory publishes its names by returning them, so before it returns none of
them are on the store — the tag genuinely resolves to nothing at paint time and
`mayUpgrade`'s watcher is what makes it work. `93fc2f4` made the first render
wait for every script, so this is now the *only* way a component name arrives
after the paint, and it is an explicit opt-in: the author called `$mounted()` to
release the render early.

So the question is not "is the name missing" but "is the name missing **and**
has everything that could still supply one finished". A live count of unsettled
scripts answers it exactly, at paint time and at every later re-render.

## The proposal

**Capture the source casing in an attribute value.** `expandNameCase` already
rewrites every start tag and already knows the trick — `expandPropsSpread` moves
`...userData` into a value precisely because "the parser leaves [values]
untouched". A tag matching `/^[A-Z]/` gets `:jq79-component="UserCard"` appended,
inside the tag but before a self-closing slash, which `expandSelfClosingTags`
has not seen yet.

**Lift it off `attrs` in `elementToAST`** into a `component?: string` field on
`TemplateNode`, so nothing downstream can mistake it for a prop, a directive or
an attribute, and the render path reads a field rather than pattern-matching a
name. The lift is unconditional, which is what fixes the name: a stamp called
`:component` would silently eat the prop off `<Card :component="Widget" />`.

**Count unsettled scripts per render generation**, in the loop that already
builds the gates, and hang the counter on the store under a symbol, beside
`UNFILLED_PROPS` and `SLOTS`. Read live rather than snapshotted: an `:if` that
turns true an hour later must be judged against the scripts as they are then.

**Throw in `renderNode`**, where `findComponentKey` returns null:

```
jq79: <UserCrad> is not defined. No component of that name is in scope - import
it in a :setup script, declare it as a prop, or add a <template name="UserCrad">
to this file. In scope: UserCard, Button.
```

Naming what *is* in scope is what makes the typo case a one-look fix, and
`findComponentKey` is already walking the chain that has the answer.

## What it costs

- **The throw lands where the render is.** On the synchronous path it propagates
  out of `render()`/`mount()` and the stack points at the usage site, which is
  the whole point. On the deferred path (a component held back by a script) the
  paint happens inside `Promise.all(gates).then(...)`, so the same throw is an
  unhandled rejection with a much worse stack. Accepted rather than solved: the
  message carries the tag name, and the alternative — deferring the report to
  where it can be caught — is what
  [`2026-08-08.expression-errors.md`](2026-08-08.expression-errors.md) already
  weighed and rejected for arriving detached from the render that caused it.

- **One unresolved tag takes down its whole component**, where today it takes
  down only itself. That is the deliberate direction: a component missing a
  region is not a component that half-works.

- **`:with` gets louder about a gap it already had.** `<div :with="lib"><Chart /></div>`
  does not resolve `lib.Chart` today — `createWithScope`'s proxy has no `ownKeys`
  trap, so `findComponentKey`'s `Object.keys` walk never sees the object's own
  names. Verified: it renders `<chart></chart>`. Under this proposal it throws
  instead of rendering nothing, which is strictly more informative, but it is a
  behaviour change for markup someone may have written and not noticed was dead.

- **A `<template name="...">` typo now throws twice over.** The declaration
  already warns when the name isn't PascalCase; the tag that references the
  misspelling throws. Both are right and they name the same mistake from the two
  ends.

## Rejected

- **`el instanceof HTMLUnknownElement && !tag.includes("-")` as the test.** No
  pre-parse pass, no new field — and it makes every `<svg>` fatal, because
  `createElement` builds SVG names in the HTML namespace. Measured before
  discarding. It also cannot tell `<lable>` from `<Lable>`, and only the second
  is a claim about a component.

- **Rewriting `<UserCard>` to `<user-card>` pre-parse** so the tag itself carries
  the signal. Collides with the custom element an author may have meant, and
  `expandNameCase` already argues against rewriting component tags.

- **Reporting after every script settles**, so the deferred path gets a real
  report too. Covers more, but the throw then lands in a microtask with no stack
  worth reading and nothing able to catch it — a worse version of the timer
  `efe5ea1` removed for arriving detached from its cause.

- **Throwing for the other two unresolved cases** (a key holding a non-component,
  a declared prop the parent left empty). Both already `console.error` with a
  message that names the fix, and both describe a *value* that may yet change —
  `jq79.data.Card = ...` after the fact is a supported move, and a throw would
  have already killed the render that would have picked it up.

- **Giving `createWithScope` an `ownKeys` trap** so `:with` can supply
  components. A real feature, and a separate one: the trap would have to
  re-evaluate the expression during an enumeration that no effect is tracking.
  Named here so the cost above doesn't read as a decision against it.

## Test

- `<Missing />` throws from `render().mount()`, and the message names both the
  tag and the components that *are* in scope;
- a factory that returns `{ Late }` after `await $mounted()` still renders, and
  throws nothing — the regression this file exists to prevent;
- `<my-widget>`, `<svg>`, `<lable>` and every other lowercase unknown tag render
  exactly as before;
- a component named by a prop the parent passed late still resolves through the
  existing `mayUpgrade` path.

## Still open

- **Whether the message should name the file.** `renderNode` has no path back to
  the `Component79` it is rendering, and the tag name is usually enough to grep
  for. If the stack turns out to be unhelpful under a bundler, the instance's
  `filename` could ride the same symbol the script counter does.
- **`:with`**, per the cost above.
