# A windowed `:each`

**Status:** proposed and implemented on the same branch. Issue
[jgermade/jq79#42](https://github.com/jgermade/jq79/issues/42).

## The problem

`:each` renders a node per item. With a few thousand rows that is the whole DOM
to style and lay out on every width change, and the whole list to build on the
first render and on a rebuild. jackbird (1,200 tracks as 120 albums) measured
~75 ms of layout per pane resize in Chromium and felt it more in WKWebView;
`content-visibility: auto` took most of it back, but the nodes are all still
there.

## The proposal

```html
<div class="tracks" style="overflow-y: auto; height: 400px">
  <div :each="track in tracks" :key="track.id" :window="28" class="row">{{ track.title }}</div>
</div>
```

`:window="rowHeight"` (pixels, an expression) on a `:each` renders only the rows
in the scroll container's viewport plus an overscan, between two spacer
elements whose heights stand in for the rows that are not there.

- **The scroll container** is the nearest ancestor with `overflow-y` `auto`,
  `scroll` or `overlay`, else the page. Found once the list is in the document
  (a microtask after the first pass; renderEach runs before mount).
- **The pass is the same keyed diff**, over `list[start..end)` instead of
  `list[0..length)`. Rows that stay in the window are reused, rows that leave
  are disposed, `:key` identity holds as they come and go. `$index` and the
  `, at` name are the real ones. It reads only the items in the window, so a
  write to a row off-screen wakes nothing.
- **Scrolling** writes the window (`start`, `count`) into a private `$reactive`
  the list effect read, coalesced per animation frame. That is an ordinary
  wake of the list effect through the existing cross-store adoption, not a
  second rendering path.
- **`$scrollTo(index)`** is defined on the element that holds the rows (the
  spacers' parent): it scrolls the container so the row is in view (nearest
  edge) and renders the window *synchronously*, so the row exists when it
  returns - which is what `aria-activedescendant` needs. Returns the row's
  first node.
- **The spacers** are the row's own tag (`<tr>` in a `<tbody>`, `<li>` in a
  `<ul>`), `aria-hidden`, with an inline `height` - an element of another kind
  would be invalid where rows are.
- **Before layout** (not attached, or a jsdom), the viewport is taken to be the
  window's height, so a list renders a screenful, not nothing.

## Why an attribute and not `:each.window` or a component

`:each.window` puts a modifier into the attribute name every reader keys on:
`node.attrs[":each"]` in the renderer, the planner, precompile and the editor's
template checker. `:window` is a control attribute beside `:key`, which each of
those already knows how to skip or compile (one line in precompile; the editor
checks any valued `:x` as an expression). A `VirtualList` component would need
scoped slots for the row and would put a component box (and a prop sync)
between the list and every row.

## Cost

A branch on `plan.window` per pass, nothing for an ordinary `:each`. A windowed
list holds a scroll listener and a ResizeObserver (where there is one), dropped
with the list.

## Rejected

- **Measured / estimated row heights.** A fixed height makes offset ↔ index
  arithmetic, which is what makes `$scrollTo` exact without rendering what lies
  between. Variable heights need a measured-offsets cache and a correction on
  every measurement; worth its own plan if a fixed height turns out to be the
  wrong default.
- **Horizontal windowing, grids.** Not asked for.

## Open

- Variable row heights (above).
- Two windowed lists in one parent share the parent's `$scrollTo` (the last one
  rendered wins).
- Find-in-page and the browser's own `scrollIntoView` cannot reach rows that do
  not exist: that is the trade, and `$scrollTo` is the in-app answer.
