# Two small costs on the create path: `atPath` and `insertDep`

**Status:** a plan, with the measurements it rests on. Small by design. It does
not touch the structural gap (one effect per binding) that
[`2026-08-27.what-is-still-open.md`](2026-08-27.what-is-still-open.md) §3 and §7
describe; it removes two per-binding costs that don't need to be there.

## Problem

A CPU profile of `create1k` on the benchmark app, built against `src/`
unminified, 30 profiles of the `#run` click alone (25µs sampling, Chromium
headless, 4 cores). Shares of the JS the click runs:

| part | share |
|---|---|
| creating effects (`$effect` → `sync` → `indexEffect` / `insertDep`) | ~38% |
| DOM: `cloneNode`, `atPath`, `insertBefore`, `addEventListener` | ~35% |
| evaluating expressions, and the rest | ~27% |

Two of those lines are costs of how the code is written, not of what it does:

- **`atPath` is ~12% of the click's JS by self time.** It walks a clone with
  `at.childNodes[path[i]]`, once per op, from the root. In Chromium the first
  `childNodes` read on a node allocates a live `NodeList` for it, so every
  freshly cloned row pays one allocation per node on every op's path. Nothing
  else ever reads those lists.
- **`insertDep` splits every dep** with `dep.split(".").forEach(...)`: an array
  of segments and a closure per binding, built to walk the trie once and then
  thrown away.

## Proposal

1. `atPath` walks siblings: `firstChild`, then `nextSibling` `path[i]` times.
   It is the same node: `buildSkeleton` appends a DOM child for every
   `TemplateNode` child, text included, so a path index is a `childNodes`
   index, and a sibling count is the same index.
2. `insertDep` walks the dots with `indexOf` and takes each segment with
   `slice`, in a plain loop. Same segments, same trie, same nodes.

Neither changes behaviour, so neither needs a new test. What would catch a
mistake is already there: the clone-path differential corpus (wrong node →
wrong DOM) and every reactive test (wrong trie node → an effect that never
wakes).

## Measured, before touching `src/`

Three builds of the benchmark app, against copies of `src/` in a scratch
directory: **A** = this branch, **B** = A + (1), **C** = B + (2). Paired, one
browser, alternating order each round; the number per round is the median
of 15-30 clicks, timed synchronously around the click (script time only,
not paint).

The control first, because nothing below means anything without it:

| pair | op | median delta | range | faster in |
|---|---|---|---|---|
| A vs A | create1k | 0.0% | −12.5..+5.2% | 5/12 |
| A vs B | create1k | −5.6% | −8.3..+5.4% | 13/16 |
| B vs C | create1k | −2.6% | −12.3..+6.3% | 13/16 |
| **A vs C** | **create1k** | **−6.7%** | −15.8..+1.1% | **15/16** |
| A vs C | replace1k | −9.1% | −21.8..+4.2% | 11/12 |
| A vs C | update (every 10th row) | 0.0% | −18.2..+11.1% | 4/12 |

Each delta is smaller than this box's round-to-round spread, so the evidence
is the sign, not the size: A against itself is faster in half its rounds, and C
against A in 15 of 16. `update` doesn't build rows and doesn't move, which is
what it should do. (2) on its own is the weakest number here and is kept for
the sign, and because it costs nothing to read.

**Not done here, and owed:** `npm run benchmark:ab`. Its `chromium.launch()`
cannot find a browser in this container (the pinned Playwright build is not
the one installed), so the paired run the project trusts happens on the pull
request, through the *Benchmark* workflow.

## Cost

Two functions, each a few lines longer. No API, no flag, no new test.

## Rejected

- **Resolving every op's target in one walk of the clone**, sharing path
  prefixes. Faster in principle, but it changes `renderFromSkeleton`'s loop
  shape for the four ops a benchmark row has, and the sibling walk already
  removes the allocation that made `atPath` expensive. Not worth measuring
  until the profile says `atPath` still matters.
- **Caching path → trie node per prefix** in `insertDep` (a row's bindings
  share `data.5`). More state per store for the part of `insertDep` that is
  left after (2): map lookups, not allocation.

## Open

- The ~38% in effect creation is still there, and it is the thing worth a plan
  of its own: compiling a `:each` row into one function with one effect per
  row rather than one per binding. The grouping attempt that was rejected in
  [`2026-08-27.grouping-a-row-s-bindings.md`](2026-08-27.grouping-a-row-s-bindings.md)
  is the first thing that plan has to answer.
