[`2026-08-25.open-after-the-box.md`](2026-08-25.open-after-the-box.md) - *nobody

## The four claims

| claim | Chromium 141 |
| --- | --- |
| `display: contents` leaves flex layout unchanged | **holds** - rect for rect identical to the same strip with no component in it |
| ...and grid | **holds**, including a `grid-column: 2 / span 2` on the component's own root |
| `:where()` lets `c79-panel { display: flex }` win | **holds** - computed `flex`, children side by side, with the author's stylesheet inserted *before* the library's existed |
| a component in table-row position is foster-parented out | **holds** - the box lands in the `<div>` before the table, the `<tr>` inside it never reaches `<tbody>` |
| a wrapper inside `<svg>` takes its children with it | **holds, and worse than the plan assumed** |

Two of them are now gates, and a third joined them (below). The rest report.

## `display: contents` inside `<svg>` computes to `none`

Decision 4 withheld the box in a foreign namespace on the reading that SVG
renders neither an unknown element nor its children, and said `display: contents`
is not the escape hatch there that it is in HTML. That is right, and the
measurement is sharper than the reasoning: with the library's own rule applied to
a wrapper inside `<svg>`, the wrapper's **computed display is `none`** - CSS
Display's rule that `contents` on an element whose rendering is not defined by
CSS computes to `none`. The children do not paint with the rule, and do not paint
without it either (`inline`, and SVG ignores it).

So the exception is not conservatism. Removing it - run as a sabotage, with
`componentBox`'s `ns` check deleted - turns a red circle into an empty box in a
real browser.

**That promoted the probe from level 2 to level 1.** "A component inside `<svg>`
still paints" is a claim about our code, not about the platform, and it now gates
against a control: the same drawing written inline with no component in it. What
stays a report is the counterfactual - if some engine ever renders a wrapped
child anyway, the exception is merely unnecessary there, which is news and not a
defect.

## And the thing nobody was looking for

A component whose template's root is a **bare SVG element** lands in the HTML
namespace and never draws - box or no box, `<svg>` ancestor or not:

```html
<svg><Bare /></svg>
<template name="Bare"><circle r="4" /></template>   <!-- an HTML <circle>. Nothing appears -->
```

A component's template is parsed on its own, where `<circle>` is not in a foreign
context, so `node.ns` is never set for it. The existing jsdom test asserts
`container.querySelector("svg circle")` is not null and says *the component still
renders* - and it is not null, and it does not render. jsdom finds an element by
name; a browser draws nothing.

The fix for a user is one line - root the component's template at `<svg>`, which
is a foreign context of its own and draws correctly - and that is now in
[`docs/template-syntax.md`](../docs/template-syntax.md), with a test pinning both
halves. Whether the library should instead re-namespace a component's root to
match its usage site is a design question nobody has asked; it is filed, not
answered.

## The costs, now lived rather than deduced

- **A parent's `:empty` stops matching** when its component child renders
  nothing. Confirmed; the box is an empty element, not nothing.
- The box computes `contents` in HTML, so **nothing about flex or grid changed**
  for anyone who is not styling `c79-*` themselves.
- `<Row />` and `<Tr />` get the **same** answer from the parser, which is what
  step 1 was for: a component is no longer positioned correctly by accident of
  its name. It is now uniformly positioned *wrongly* in table-row position, which
  is the honest version of the same limitation.

## What the checks cost to trust

Three sabotages, each red before it was reverted:

| sabotage | what went red |
| --- | --- |
| the rule written without `:where()` | the cascade gate, alone |
| the default as `display: block` | both layout gates, with the rects |
| `componentBox`'s `ns` check deleted | the new `<svg>` gate |

And the rule's second half paid immediately. **The grid probe's own counterfactual
failed it on the first run**: three equal tracks and three plain children, where a
`display: block` box lands in cell 2 and the child fills it - so the sabotage
measured exactly what the real thing measured, and the probe could not have
failed. Uneven tracks and `grid-column: 2 / span 2` fixed it. A check that says
"identical" when nothing could have differed is the same vacuity
[`2026-08-24.clone-path-coverage-check.md`](2026-08-24.clone-path-coverage-check.md)
caught one level down, and it is why every gating probe here carries its
counterfactual and fails when it does not move.

Two more things the first draft got wrong, both found by re-reading the diff
rather than by any check:

- **The `<svg>` probe read `document.head` for the library's rule after mounting
  only components inside `<svg>`** - where the exception means no box is ever
  made, so the rule was never injected and the "with the rule" reading was the
  same page as the one without it. It seeds an HTML component first now.
- **The layout probes' sabotage was `c79-item { display: block }`**, 0-0-1, which
  loses to a default rule written without `:where()`. A broken cascade therefore
  reported itself as three blind probes instead of one real failure. The sabotage
  is `!important` now: the layout probes ask what `contents` does to layout, and
  the cascade is the other probe's question.

## What this does not settle

- **Firefox and WebKit.** Same position the oracle was in the day it was written,
  and the same answer: `.github/workflows/box-layout.yml` has never run.
- Hot reload, `:each` moves and the swap path in a browser. Untouched.
- Whether the `<svg>` exception could ever be lifted. The measurement says not in
  Chromium 141, and the check will say so in the other two.

## Update, 2026-08-25: the other two engines answered, and they agree name by name

`.github/workflows/box-layout.yml` ran for the first time on
[PR #15](https://github.com/jgermade/jq79/pull/15). Everything above was
Chromium 141's; this is all three, and the runner's Chromium is **ten major
versions past the one the probes were designed on**:

```
   chromium   Chrome/151.0.7922.34
   firefox    Firefox/153.0
   webkit     Version/26.5

   12 of 12 answers identical across chromium, firefox, webkit
```

| fact | chromium 151 | firefox 153 | webkit 26.5 |
| --- | --- | --- | --- |
| box display | contents | contents | contents |
| table: box lands in | div | div | div |
| table: the `<tr>` inside the table | false | false | false |
| table: `<Tr />` agrees with `<Row />` | true | true | true |
| svg: the same drawing without a component | true | true | true |
| svg: component paints (no box) | true | true | true |
| svg: and the point hits | d | d | d |
| svg: paints inside a box | false | false | false |
| svg: box display with the rule | **none** | **none** | **none** |
| svg: paints inside an unstyled box | false | false | false |
| svg: bare-rooted child namespace | XHTML | XHTML | XHTML |
| parent still matches `:empty` | false | false | false |

Every level-1 gate passed in each engine, so the three claims that are ours -
flex, grid, the cascade - hold in all of them, and so does the fourth: **no
engine renders a child inside a box in a foreign namespace**, and all three
compute `display: none` there rather than `contents`. The exception in
`componentBox` is not a Blink quirk.

The bare-SVG-root finding is unanimous too: XHTML in every engine, which makes
it a fact about how a component's template is parsed rather than about any one
browser.

Five checks green. What is *not* settled by this run: `benchmark` and the SVG
attribute-name oracle did not trigger on the PR at all, so the oracle still has
not run since the tag rename.
