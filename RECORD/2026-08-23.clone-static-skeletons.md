# Clone the static skeletons instead of building them node by node

**Status:** a proposal, and deliberately **not a decision**. **Superseded in
part on 2026-08-24**: the spike this file asked for was built and measured, and
two of its claims did not survive — the conservative classifier's "a tag that is
known HTML" is not safe, and the win is 20-50% rather than ~20%. See
[`2026-08-24.clone-skeletons-measured.md`](2026-08-24.clone-skeletons-measured.md);
what follows is the original text.

**Status:** a proposal, and deliberately **not a decision**. `src/` is
untouched and nothing here was measured for this file - every number is
borrowed from
[`2026-08-23.where-the-create-time-goes.md`](2026-08-23.where-the-create-time-goes.md),
which measured it and then declined to bundle it with anything else. This file
exists because
[`2026-08-23.notify-a-splice.md`](2026-08-23.notify-a-splice.md) named it as
the largest piece left on the create path and said it needs "its own file, its
own decision", and there wasn't one. What it adds is what the change would
touch, what it would cost, and what somebody would have to decide before
writing a line of it.

## The number it rests on

Per 1,000 rows of the benchmark table, re-measured on HEAD in that file:

| | |
|---|---:|
| hand-written control, `createElement` per node | ~8ms |
| hand-written control, `cloneNode` of the row | ~5ms |
| jq79, 8 elements per row, zero bindings | ~19ms |
| jq79, the full benchmark row | ~50ms |

So of a ~50ms `create1k`: ~8ms is DOM anybody would pay, ~11ms is jq79 walking
the AST and deciding what to build, and ~30ms is one effect per binding.
Cloning attacks the ~11ms plus the ~3ms between the two controls - **about 20%
of create1k**, and it composes with everything else on the create path.

It does **not** attack the ~30ms. Nothing in this proposal makes an effect
cheaper or rarer.

## What `renderNode` does per element, per instance

For one `<td class="col-md-4">` inside a `:each` row, on every one of a
thousand rows:

- reads `:with`, and builds a scope if present
- tests for `<slot>` and for misplaced `<template :slot>`
- **`findComponentKey(scope, node.tag)`** - a walk up the scope chain, matched
  case-insensitively with dashes stripped
- `document.createElement(node.tag)`
- decides whether the element may still upgrade to a component
  (`HTMLUnknownElement`, or a dash in the tag) and, if so, registers an effect
  that watches for the key
- walks `node.attrs`, classifying each name: `@`, `:`, `:class.`, `:props.`,
  the scope stamp, plain
- recurses into `children`, splitting each text node on `{{`

For a subtree with no directives, no interpolation and no component in it,
all of that produces byte-identical DOM every single time. That is the work
this proposal removes.

## The proposal

Once per **definition** (not per instance): find the maximal contiguous
subtrees that are static, keep a `<template>` holding each one, and give each
instance `content.cloneNode(true)` plus a precomputed path
(`firstChild`/`nextSibling` steps) to every point where a binding attaches.

The parse already hands this over almost free. `parseComponentString` builds a
real DOM tree with `DOMParser` and then `elementToAST` walks it into plain
objects and throws the tree away. The skeleton to clone is a subtree of a tree
that already existed at definition time, derived from the same parser output
the AST is - so the two cannot disagree about what the HTML meant (`<td>`
reparenting, `<p>` auto-closing, entity decoding are already baked into both).
The `data-jq79` scope stamp is written into the AST once per definition too
(`stampScope`), so it is already on the skeleton.

## What "static" means here, which is the hard part

Staticness is **not a property of the AST**, and this is the finding that
decides how much of the template a real implementation would ever get to
clone:

- **`findComponentKey` resolves against the runtime scope.** `<drop-area>`
  is a plain custom element in one instance and `DropArea` in another, decided
  by what the scope holds when it renders. The same AST node is static or not
  depending on where it is used.
- **A tag with no component *yet* is watched, and swapped later.** The
  `HTMLUnknownElement`-or-dash rule registers an effect that upgrades the
  element when an async factory writes the key in. A node that looks static at
  clone time can stop being static after mount.
- **`node.component` throws** when a capitalized tag resolves to nothing and
  the component's scripts have all settled - a runtime check against
  `PENDING_SCRIPTS`, not a parse-time one.

So a classifier has two shapes, and picking between them is part of the
decision:

1. **Conservative and per definition.** A subtree is static only if every
   descendant has no directive attribute, no `{{` in text or attribute values,
   no `node.component`, no dash in the tag, and a tag that is known HTML. One
   classification per definition, cached with it. A `<drop-area>` anywhere in a
   row makes that whole row's subtree non-static, forever, for everybody.
2. **Per scope, cached.** Ask `findComponentKey` at classification time and
   key the result by whatever identifies the scope. Cloning more of the
   template, at the price of a second cache with a subtle invalidation rule -
   a scope that gains a key must drop it, which is the same new-key sweep the
   upgrade watch already listens to.

The benchmark row is entirely plain HTML, so shape 1 already collects the
~20%. A real app's row, with a `<user-avatar>` in it, may collect none of it.
**That gap is the argument, in both directions, and no measurement in the repo
speaks to it.**

## What it costs

- **A second implementation of the render path**, and the classifier that
  chooses which one runs. `renderNode` is currently the single place where a
  template becomes DOM. Every directive added after this has to be taught to
  both, or has to force its subtree non-static - and "forgot to teach the
  cloner" fails as *stale DOM in one code path*, which is the worst kind of
  bug this library can have.
- **Binding points addressed positionally.** A path of `firstChild`/
  `nextSibling` steps is fragile in a way an AST walk is not: whitespace text
  nodes are load-bearing (the parse keeps them on purpose - see the comment
  above `elementToAST`), and any future rewrite that drops or merges a node
  silently shifts every path after it.
- **A `<template>` per definition held for the life of the page**, plus the
  path tables. Small, but it is per definition, not per file.
- **The dev server and the tutorial** both re-parse a component on every edit.
  The per-definition artefacts have to be rebuilt with it and never outlive
  it, exactly like `compileExpr`'s cache.

## What it would also change, which is not a speed question

`document.createElement("svg")` builds an `HTMLUnknownElement` in the HTML
namespace, so `<svg>` renders nothing useful today
([`2026-08-12.undefined-component-throws.md`](2026-08-12.undefined-component-throws.md)
records this, and leans on it: `<svg>` is an unknown element, which is why the
capitalization check exists). Cloning a subtree parsed from the source gives
correct namespaces **for free** - and takes `<svg>` out of the
`HTMLUnknownElement` branch, so the upgrade watch and the unresolved-component
throw stop seeing it.

That is a behaviour change riding along with a performance one, and it is
better as its own decision than as a side effect of this one.

## What this is not

- **Not grouping a row's bindings into one effect.** Priced at ~8% of
  `create1k` and rejected in `where-the-create-time-goes.md` and again in
  `notify-a-splice.md`: fine-grained updates are where jq79 actually wins
  (`partialUpdate` 1.6ms against Preact's 11.9 and Svelte's 1.7). This
  proposal leaves every effect and every dep exactly where it is.
- **Not `NodePlan`.** Deriving the per-node classification once and keeping it
  on the `TemplateNode` was built and measured: a wash in both directions,
  reverted. The classification was never the cost.
- **Not a build step.** `AGENTS.md`'s "no compiler" is a claim about the
  build, and `compileExpr` already calls `new Function` per expression. Even
  so, this is the point where the runtime stops being an interpreter with a
  cache in front of it, which is a claim about what the library *is* and
  belongs to whoever owns that claim.

## Still open

1. **Is 20% of `create1k` worth a second render path?** Not a question a
   profile answers.
2. **Which classifier** - conservative per definition, or per scope with a
   second cache - and what a real app's templates would actually get out of
   each. Nothing in the repo measures a template with components in the row.
3. **Does the SVG change ship with it, separately, or not at all?**
4. **How would it be measured?** This box cannot price a change under ~50%
   (`where-the-create-time-goes.md`: HEAD against itself swung +50% to -23% on
   `create1k`). The isolated instrument from
   [`2026-08-23.each-pass-allocations-and-moves.md`](2026-08-23.each-pass-allocations-and-moves.md)
   and agreement-by-sign across separate processes are the two methods that
   have survived here.
5. **What happens to `renderNode`'s comments.** They are the specification of
   a good deal of this library's behaviour, and half of them describe
   decisions the clone path would have to make differently.

## 2026-08-25 — why "a tag that is known HTML" is not safe, and what shipped instead

The note at the top of this file records that the conservative classifier's rule
did not survive. It does not say *why*, and it points at
[`2026-08-24.clone-skeletons-measured.md`](2026-08-24.clone-skeletons-measured.md),
which measured the win rather than answering this. §7 of
[`2026-08-24.open-after-pr-12.md`](2026-08-24.open-after-pr-12.md) calls the
section wrong rather than merely out of date, and it is right. Here is the
concrete part.

**`findComponentKey` strips dashes and lowercases**, and every PascalCase key in
scope participates. So a variable named `Td` makes every `<td>` under it a
component:

```html
<table class="a"><tr><td class="c1">plano</td></tr></table>
```

Interpreted, with `Td` in scope, each `<td>` renders that component. A classifier
that accepts the subtree because `td` is "a tag that is known HTML" would clone
the `<td>`s as elements, and the two paths would disagree - silently, in
markup that looks perfectly ordinary. `Map`, `Data`, `Table`, `Form`, `Label`
and `Object` are all HTML tags somebody might name a component after. **Being a
known HTML tag is not on its own an answer**, and shape 1 as written above rests
entirely on it being one.

**What shipped is neither shape.** Still open #2 asked "conservative per
definition, or per scope with a second cache", and the answer turned out to be a
third option that needs no cache and no invalidation rule:

- **Plannability is per definition**, decided by `plannableNode` and cached in a
  `WeakMap` on the AST node - shape 1, minus the tag rule.
- **The scope question is asked per render, at the moment it is answerable.**
  The plan records the distinct tags its subtree contains, and `renderNode` runs
  `findComponentKey` over them before cloning; one hit and the subtree is
  interpreted for that render. It costs what the interpreted path already pays,
  memoized per render pass.

So shape 2's "subtle invalidation rule - a scope that gains a key must drop it"
never had to be written: nothing is cached across renders, and a scope that
gains a key is simply asked again on the next one. The corpus entry
*"a scope key that captures an HTML tag"* in `tests/skeleton.test.ts` is what
pins this, and it renders the table above with `Td` in scope.

The rest of *Still open*, for a reader arriving here from a search:

1. **Is it worth a second render path?** Answered yes, and measured: 20-50% of
   `create1k` depending on how much fixed structure a row has
   ([`2026-08-24.clone-skeletons-measured.md`](2026-08-24.clone-skeletons-measured.md)).
   Shipped in PR #11, extended in PR #12.
2. **Which classifier** - above.
3. **Does the SVG change ship with it?** Separately, and it was not an
   optimization at all but a rendering bug -
   [`2026-08-24.svg-namespace.md`](2026-08-24.svg-namespace.md).
4. **How would it be measured?** By the `benchmark:ab` harness, alternating two
   builds on one machine, plus counting where the clock could not resolve the
   difference ([`2026-08-24.plan-on-the-second-render.md`](2026-08-24.plan-on-the-second-render.md)).
5. **What happens to `renderNode`'s comments?** They stayed where they are, and
   the clone path grew its own header stating the two rules that keep it honest.
   The differential test is what makes them enforceable -
   [`2026-08-24.skeleton-differential-test.md`](2026-08-24.skeleton-differential-test.md)
   and [`2026-08-24.clone-path-coverage-check.md`](2026-08-24.clone-path-coverage-check.md).

## 2026-08-24: the constraint is about the build, and the author has said so

> Written on 2026-08-24 on a branch that was never merged, and landed here on
> 2026-09-06. It sits after the 2026-08-25 section because that is when it
> arrived, not when it was thought. The two do not conflict: that one is about
> which classifier is safe, this one about whether the shape underneath is free
> to change at all.

The **"Not a build step"** bullet above ends by handing a question to whoever
owns the claim. It has been answered, so the answer belongs here rather than
in a chat log:

> "no compiler" means you do not need a front-end bundle to use jq79. How it
> works underneath does not matter, as long as it respects the contract.

### So the identity objection is withdrawn

Emitting code at runtime breaks no promise this library makes.
`new Component79(src)` takes a string and mounts it, with no build step
anywhere in the user's way, and that stays true whether the thing between the
string and the DOM is an interpreter, a cache, or a generated function. The
sentence above - "this is the point where the runtime stops being an
interpreter with a cache in front of it" - was a real consideration and is no
longer one.

**What remains against this proposal is engineering, and none of it moved:**
a second implementation of the render path to keep in sync, where forgetting
to teach the cloner a new directive fails as stale DOM in one code path only;
binding points addressed positionally, in a tree whose whitespace text nodes
are deliberate; and staticness not being a property of the AST at all, since
`findComponentKey` resolves against the runtime scope and an unknown tag can
still upgrade after mount.

### Which widens what is being proposed

If the shape underneath is free, "clone the static skeletons" is no longer the
honest version of this - it is the timid one. The full version is **one
emitted render function per definition**, built with `new Function` and cached
beside the definition exactly as `compileExpr` caches one per expression,
invalidated by the same HMR that re-parses the file. That attacks the ~11ms
AST walk *and* the per-element attribute classification together, rather than
only the contiguous static parts of the tree.

It also changes the shape of open question 2. "Which classifier" stops being
*what can be cloned ahead of time* and becomes *what the emitted function
branches on at runtime* - a `<drop-area>` can be a `findComponentKey` call
inside the generated code rather than a reason to give up on the subtree
around it.

The measurement does not move with it: the ~20% in this file is what was
priced, for the static-skeleton half. What the fuller version is worth has
never been measured, and the same instrument problem applies (open question 4).

### What the contract is, concretely

The one place where "how it works underneath" reaches the contract is **CSP**:
`new Function` needs `unsafe-eval`. jq79 already needs it - `compileExpr` for
every expression, and every setup script - so a runtime compiler adds nothing
new on that axis. Already paid for, and worth stating so nobody rediscovers it
as a blocker.

The rest a generated path must preserve, in the order it would break them:

- **`new Component79(src)` parses and mounts at runtime**, no build step, no
  dependencies, and `src/` importing nothing from `dev/`.
- **The template semantics as `docs/` specify them** - those files are where
  the behaviour is written down, not the implementation.
- **The load-bearing invariants** in `AGENTS.md`, none of which are about
  rendering, but all of which a second render path could quietly step on.
- **The public API**: `$reactive`, `$effect`, `$on`, `$onAny`, `$toRaw`,
  `$dispose`.
- **The suite and the tutorial**: 751 tests, and the exercises that fail the
  build when a library change breaks one. A codegen path that cannot keep
  those green is not a codegen path.

Open question 1 - is it worth a second render path - is untouched by any of
this. It was always the real question, and it still is.
