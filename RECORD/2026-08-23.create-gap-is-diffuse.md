# The create gap is all JavaScript, and it is diffuse

**Status:** a result, not a proposal. It closes the question every earlier file
on this branch left open — where `create1k`'s distance from Svelte lives — and
it closes it with "nowhere in particular", which is worth writing down so the
next person does not spend the day I spent finding out.

## The instrument

Every profile on this branch was a sampling CPU profile, and every one of them
charged 55-68% to `(program)` — a frame that means "V8 was busy and the stack
could not be attributed". Three files here speculated about it and one
explicitly parked it as needing "a `devtools.timeline` trace that separates
style, layout and script". This is that trace: CDP `Tracing`, categories
`devtools.timeline` + `disabled-by-default-devtools.timeline` + `v8`, self time
computed by subtracting nested durations.

`create1k`, jq79 (tracing inflates the click from ~51ms to 132ms; the shares
are the point):

| self | share | event |
|---|---|---|
| 116.3ms | **76.6%** | `v8.callFunction` |
| 20.0ms | 13.2% | `RunTask` |
| 9.6ms | 6.3% | `V8.GC_SCAVENGER_SCAVENGE_PARALLEL` |
| 0.7ms | 0.4% | `EventDispatch` |
| — | — | the rest is GC sub-phases, all under 0.6% |

**No `Layout`. No `RecalculateStyles`. No `ParseHTML`.** The measured window is
JavaScript and garbage collection and nothing else. `(program)` was the
sampler, exactly as suspected but never confirmed until now.

The same trace for Svelte, same operation:

| self | share | event |
|---|---|---|
| 12.3ms | 65.4% | `FunctionCall` |
| 3.1ms | 16.7% | `V8.GC_SCAVENGER_SCAVENGE_PARALLEL` |
| 1.7ms | 9.0% | `v8.callFunction` |
| 0.1ms | 0.7% | `ParseHTML` |

Same shape. Both are pure JS plus a GC scavenge. So the 5.6x is not a hidden
browser cost, not a layout thrash, not a DOM-shape difference: **jq79 simply
executes about six times more JavaScript to build the same thousand rows.**

## And it is not in one place

That is roughly 7.3µs per element against Svelte's 1.3µs, and this branch has
now looked for the difference four times:

- `findComponentKey` was the one real hot spot (13.7%), and memoizing it per
  render pass took `create1k` from ~80ms to ~51ms.
- Per-effect allocations and the per-element `DocumentFragment`: a few percent,
  and only visible in one of two paired runs
  (`2026-08-23.create-path-constants.md`).
- Removing the redundant-dep pruning, on the theory that it made the container
  sweep walk more trie nodes: nothing outside noise
  (`2026-08-23.positional-refresh.md`).
- **Caching per-`TemplateNode` derivation** — `renderNode` re-derives its
  attribute classification, `:class.` toggles and static class set from
  `node.attrs` for *every instance*, so a 1,000-row list re-classifies the same
  `<td class="col-md-1">` a thousand times, allocating three arrays each time.
  Hoisting all of it into a lazily-built plan behind a `WeakMap` measured
  **worse**: `create1k` 56.9 against 55.1, `appendToLarge` 90.3 against 81.9,
  `create10k` 477 against 506. The `WeakMap` lookup per element costs about
  what the `Object.entries` it replaces costs. Reverted.

Four attempts, one hot spot, three diffuse. The remaining distance is the sum
of many small things a runtime interpreter does per element and per binding
that compiled straight-line code does not do at all: classify attributes,
resolve names through a scope chain, allocate an effect and index its deps,
build closures. There is no single change left that recovers a large fraction
of it.

## What that means for the project

The gap is the price of the design, not a defect in it. `AGENTS.md` opens with
"No compiler, no virtual DOM, no dependencies — `new Component79(src)` parses
and mounts at runtime", and ~6x Svelte on pure element construction is what
that buys and costs. Worth saying plainly on the results page rather than
leaving it as an open TODO that reads like unfinished work.

If someone does want to close it, the honest options are structural, not
incremental:

- **Derive per-node work at parse time** rather than caching it at render time
  — the same idea the `WeakMap` spike failed at, but with the plan stored *on*
  the node by the parser, so there is no lookup at all. The spike says the
  saving is real but smaller than a `WeakMap` probe; a field read might clear
  the bar where a probe did not. Cheap to try, and the only one of these that
  does not change what jq79 is.
- **Compile the template to a closure tree once per component**, so rendering
  a row is calling a prepared function rather than walking an AST. This is
  what "no compiler" means jq79 does not do — at runtime it would still not be
  a build step, but it is a different library inside.

## Open, still
