## The four items

### §6 then §1 — the cloner learned five directives

[`2026-08-24.more-holes-in-the-cloner.md`](2026-08-24.more-holes-in-the-cloner.md)

`:text`, `:attrs`, `:value`, `:checked` and `:selected` are holes a skeleton
fills now. Before this, one `:text` anywhere in a row cost the whole subtree
containing it, not just that element.

§6 (op order) went first because §1 said so, and it earned it: the differential
test grew an axis that compares the *order* bindings register in, through a
scope of accessors that log their own name. Verified by sabotage - moving the
form-state ops before the children turns it red while the DOM diff stays green,
which is exactly the gap §6 described.

`:html` was deliberately left out: its `:html.allowed` companion carries a
warning that fires per render interpreted and would fire per definition cloned.

**Found on the way in:** `:model` is the one directive `renderNode` treats
specially that `CONTROL_ATTRS` does not name, so the allowlist accepted the bare
form as a generic `:<name>` binding. `<input :model="who">` rendered
`model="ada"` cloned and nothing interpreted. The corpus entry for `:model` sat
on a component tag - unplannable for a different reason - so it could never have
caught it. **A trip wire has to sit on a tag that would otherwise be planned.**

The ops loop also stopped falling through to the class branch: it ends in a
`never` now, so a kind added and not implemented is a compile error.

### §2 — not an optimization, a rendering bug with four parts

[`2026-08-24.svg-namespace.md`](2026-08-24.svg-namespace.md)

§2 filed `<svg>` under the clone path as "measured as free, but it is a
behaviour change". It is neither. `<svg>` did not render at all, it predates the
clone path, and two of its four parts were written down nowhere:

1. the namespace was XHTML, so no browser drew it;
2. `viewBox` was flattened to `viewbox` by `setAttribute`;
3. **no binding inside an `<svg>` worked** - `mayUpgrade` is true for any
   `HTMLUnknownElement`, so `:fill` reached the DOM verbatim;
4. `tagName.toLowerCase()` would have destroyed `clipPath` and `linearGradient`.

The fix was to stop throwing away what the parser already knew:
`parseComponentString` builds a real tree with `DOMParser` - correct namespace,
`viewBox` intact - and discards it after `elementToAST`. The namespace now rides
on the AST node and one shared creator builds elements for both render paths.
None of the "two changes wearing one coat" §2 worried about was needed.

### §5 — the instrument, and an answer that contradicted the guess

[`2026-08-24.one-shot-render-measured.md`](2026-08-24.one-shot-render-measured.md)

§5 asked whether a definition rendered once pays for its plan, and said the
instrument was the problem: it timed parse+render as one block against a null
control of ±19%.

The fix was measuring a smaller thing, not a better clock. Parsing left the
timed region (identical in both arms, ~90% of it), K distinct definitions are
timed as a chunk, and the arms interleave in chunks of ~60 so a stall corrupts
one chunk of a hundred rather than half a round. Null control: a median of
+0.0% at 43/100 chunks - a coin.

**§5's analytical guess ("should be a wash at N=1") was wrong.** The cost is
real and monotone in size: +23.1% at three elements, +11.5% at six, break-even
around nine to twelve.

### The follow-up §5 did not ask for

[`2026-08-24.plan-on-the-second-render.md`](2026-08-24.plan-on-the-second-render.md)

`MIN_SKELETON_ELEMENTS = 3` was tuned on list rows, where the plan amortizes
over a thousand instances - and it is the one-shot case that pays. So `planOf`
returns null the first time it sees a node and plans on the second: a one-shot
definition never builds a plan, a `:each` interprets row 1 and clones the other
999. Both one-shot costs now land exactly on the null control.

## Four things worth carrying, none of them about the code

These are the transferable part, and three of them are mistakes.

- **A differential test can go vacuous without failing.** Making the plan lazy
  dropped the corpus entries that actually reach the cloner from 26/83 to 5/83,
  silently, with every assertion still green. Marking every cloned root and
  counting which entries notice is the only thing that showed it.
- **One run per arm is not a measurement, including when I do it.** A
  well-powered run said the lazy plan had destroyed the list win. Alternating
  the builds three times each showed eager's own worst pass at -0.0%/52%,
  indistinguishable from lazy's worst. `where-the-create-time-goes.md` exists to
  warn about exactly this and it caught me anyway.
- **Counting beats clocking for a small structural effect.** The same question
  the clock could not resolve is exact by counting: eager clones 50 of 50
  renders, lazy 49. One interpreted render per definition, once, ever - 0.1% of
  `create1k`. An arithmetic bound, not an error bar.
- **jsdom passing is not evidence a browser agrees.** The "ask the SVG IDL"
  trick for bound camelCase attributes passed every jsdom probe and fails on
  three of sixteen real names in Chromium 141 - `stdDeviation` among them, and
  silently. `applyAttr`'s comment already recorded that this class of
  introspection burned the project once; it was right.

Two smaller ones, both discovered by being wrong first:

- `mountShadow` only renders when the instance has no content: mounting an
  already-rendered component **re-attaches** the DOM it built rather than
  rendering again.
- `performance.now()` is clamped to 100µs in a page that is not cross-origin
  isolated, so a single small render cannot be timed at all.
