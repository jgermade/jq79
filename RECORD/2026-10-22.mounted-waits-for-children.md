# `$mounted()` waits for the components its template renders

**Status:** proposed and implemented on the same branch.

## The problem

A component whose script awaits an import paints a microtask (or a fetch)
after the rest of the page:

```html
<!-- child.html -->
<script :setup>
  const Leaf = await import("./leaf.html")   // holds this template back
</script>
<b><Leaf /></b>

<!-- parent.html -->
<script :setup>
  await $mounted()
  $(".leaf")        // null - the child hasn't painted yet
</script>
<div><Child /></div>
```

`settleMounted()` resolves the parent's promise once *its own* template is
built and attached (`renderDone && mountRoot`). The child is created on that
same stack, but its render is held by its own gate (see the render gate in
`renderWith`), and nothing tells the parent. So `await $mounted()` - documented
as "rendered and on the page, so code below can query the DOM" - wakes up to a
page with holes in it, and only when a descendant happens to import something.

## The proposal

A component is **painted** when its own template is built *and* every nested
component created by that render has painted, recursively. `$mounted()`
resolves on painted + attached, instead of built + attached.

- Each instance counts the nested first paints it is still waiting for
  (`held`). The usage site (`renderNestedComponent`) finds the owner through
  the generation's box that already rides the scope chain (`PENDING_SCRIPTS`,
  which now also names its `owner`) - so `:each` rows, `:with` scopes and slot
  content all find the component whose render created them.
- A child that is not painted when its usage site finishes rendering it bumps
  the owner's count and gets an `onPaint` callback; `settleMounted()` fires it
  once the child is painted, and that re-runs the owner's `settleMounted()`.
- A child destroyed before it paints (an `:if` closing, a key changing)
  releases its owner too - otherwise the owner waits for something that will
  never arrive.
- Only the first render counts. A component created later (an `:if` that opens,
  a row added) bumps a count nobody is waiting on any more; `resolveMounted`
  has already run and running it again is a no-op.

## What it costs

- Per nested instance: one symbol read on the scope and one check of two
  fields. A callback is allocated only for a child that is actually held.
  Nothing new in `renderWith`'s frame beyond one more field in an object it
  already builds (the depth guard depends on that frame staying small).
- **A stuck child now holds its parent's `$mounted()` too.** Before, the
  parent's tail ran with the child missing; now it waits. The child's own
  "waiting 5s" warning still names the culprit. That is the honest version of
  the contract: "on the page" with a hole in it was the bug.

## Rejected

- **Resolve `$mounted()` a microtask later.** Fixes `modules` maps and nothing
  that goes to the network.
- **A separate `$painted()` helper.** `$mounted()` is already documented as the
  point where the DOM can be queried; a second promise would leave the first
  one wrong.
- **Waiting in `$attached` too.** `$attached` is about being in the document,
  and a held child's own `$attached` fires when *it* paints. Left alone.

## Open

- A nested instance re-rendered by hand before it paints consumes its
  `onPaint` in `destroy()`, so its new generation won't release the owner a
  second time - the owner was already released by the destroy. Fine for the
  owner, but noted.
