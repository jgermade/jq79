# The signature gets teeth — a bare `:setup` is closed, and an undeclared parameter says so

**Status:** decided (user's proposal and user's call). Two changes in one file
because neither should ship without the other. Extends the contract
`2026-07-14.component-signature.md` opened and `efbca33` made two-way.

## The problem

A component's prop signature is a contract both ways: what it declares is what a
parent may pass, and `pickDeclared` drops the rest. Two holes in it.

**A bare `<script :setup>` opts out of the contract by accident.**
`parsePropsPattern("")` returns `null`, which means "declared no signature", which
means permissive — every parameter a parent passes lands on the store. So the
difference between taking nothing and taking anything is a pair of braces
somebody didn't type:

```html
<script :setup>        <!-- permissive: :foo, :bar, anything -->
<script :setup="{}">   <!-- closed: takes nothing -->
```

**And a parameter the signature doesn't declare vanishes without a word.**

```html
<!-- Comp.html -->
<script :setup="{ foo }">

<Comp :foo="foo" :bar="bar" />
```

`bar` is silently absent from the child's store. That was deliberate —
`pickDeclared`'s comment defends it — but the defence is about a `:props`
*spread* of an object wider than the component (`...sdk`), where taking only the
declared few is the point. A hand-written `:bar` has no such excuse. It is a
typo, or a rename that missed a usage site, and the symptom is an empty `{{ bar }}`
at the other end of the file.

## The proposal

### A bare `:setup` is a closed signature

`<script :setup>` parses as `[]`, exactly like `<script :setup="{}">`: declares
zero props, takes none.

- **Only the empty-string case moves.** `attrs[":setup"]` is `""` for a bare
  attribute and `undefined` for a factory `<script>` that has no `:setup` at
  all; the latter keeps returning `null` and keeps reading its signature from
  the factory's first parameter.
- **Permissive stays reachable, and now has to be asked for**:
  `<script :setup="_">`. `parsePropsPattern` returns `null` for any pattern that
  doesn't start with `{`, so this already works — it is the same `_` convention
  factory scripts use for "takes no props", read here as "declares nothing".

### An undeclared written parameter warns

At the usage site, once the child's definition has resolved and its declared set
is known, a `:name` the signature doesn't list warns:

```
jq79: :bar is not declared by <Comp> - add it to the :setup signature, or drop it
```

Three conditions keep it honest:

- **Written parameters only, never `:props` spread keys.** This is the whole
  distinction that makes the warn defensible: `renderNestedComponent` already
  keeps `sources` in source order with `name` absent for a spread, so the two
  are told apart where the warn goes. `:props="sdk"` stays as silent as
  `pickDeclared`'s comment promises.
- **Once per name per instance**, or a `:each` over 200 rows says it 200 times.
- **Only when the child declared a signature.** After the change above that is
  nearly always — which is the point, and also why the two ship together.

## Why they ship together

Alone, the first change breaks quietly: every component already written with a
bare `:setup` that receives parameters loses them, and loses them the way
`pickDeclared` loses things, which is silently. That is the failure mode this
project has refused to ship before (see `2026-08-07.update-model-helper.md` on
the `$emit('model:update')` break).

The second change is what turns that silence into a sentence. A component whose
bare `:setup` now drops `:foo` says `jq79: :foo is not declared by <Comp>` at
the usage site that passed it. One change breaks, the other explains — so
neither goes in without the other.

## What it costs

Patched the bare-`:setup` case in and ran the suite: **644 of 649 pass, and the
whole tutorial is green** — no exercise depends on a bare `:setup` receiving
parameters. The five failures:

- `propsSignature > stays permissive when no signature was declared` — pins the
  old semantics; it becomes the `:setup="_"` test.
- Two `transform` unit tests on `parsePropsPattern`/`parseFactoryProps` — an
  artifact of the probe conflating `""` with `undefined`. The real change only
  touches `""`, so these should not move.
- Two `Component79 > :model on component tags` tests whose fixture components use
  a bare `:setup` and receive the model as a parameter. Fixtures; they gain the
  signature they should always have had.

Plus the warn itself (the declared set is already computed by
`declaredPropSet`), its once-per-name bookkeeping, and docs:
`docs/components.md` on the signature, `docs/setup-scripts.md` on `:setup="_"`.

## Rejected

- **Keeping the bare `:setup` permissive and warning anyway.** The warn needs a
  declared set to compare against; a permissive component has none, so exactly
  the components most likely to be sloppy would be the ones that never warn.
- **Making the drop an error instead of a warn.** An undeclared parameter is a
  bug to find, not a reason to refuse to render — consistent with every other
  it-does-nothing case in jq79.
- **Warning on `:props` spread keys too.** `...sdk` wider than the component is
  the documented, intended use; the warn would fire on the legitimate case, which
  is the same reason `2026-08-07.update-model-helper.md` refused to warn on an
  unbound `$updateModel`.
- **A rest element (`{ foo, ...rest }`) as the permissive escape.**
  `parsePropsPattern` already skips rest elements (`a rest element names no
  prop`), so it would read as a closed signature naming `foo`. Changing that to
  mean "and everything else" overloads a pattern that currently means the
  opposite. `_` is unambiguous and already the convention.

## Open

- **The warn's wording when the name is close to a declared one.** `:usre` next
  to a declared `user` could say so; a near-miss suggestion is cheap and is the
  case the warn exists for. Not proposed here — it wants its own decision about
  whether jq79 does fuzzy matching anywhere.
- Whether `docs/` should stop showing bare `<script :setup>` in examples where
  the component takes props. Mechanical, but it is most of the doc snippets.

## 2026-08-07 — implemented

As proposed, both halves together.

`setupSignature(script)` replaced the three bare
`parsePropsPattern(script.attrs[":setup"])` call sites. It is the only place
that knows a bare `:setup` is closed: `parsePropsPattern` itself is untouched, so
an absent attribute still reads as `null` and a factory's `()` still means what
it meant. That is why the two `transform` unit tests the probe knocked over
never actually moved — the plan predicted this and it held.

`warnUndeclared` sits next to `pickDeclared` and is called where `declared` is
already computed. Two details the proposal left implicit:

- **The dedupe is keyed by the template node, not the instance.** A `:each` over
  200 rows calls `renderNestedComponent` 200 times, so a per-instance (or
  per-call) set would say it 200 times. The AST node is the usage site itself,
  built once and shared by every instance it renders, so a `WeakMap` on it says
  it once — and a definition swap doesn't repeat what the last one said.
- **The warn covers `:model`'s prop too.** The plan said "written parameters",
  and a model's prop is written by hand; it is folded into `props` before the
  warn runs, so it came along for free. It is worth having: a child that doesn't
  declare the model's name never sees the value coming down, and the two-way
  binding half-works in a way that is hard to see.

The open question about near-miss suggestions (`:usre` next to a declared
`user`) stays open — nothing here does fuzzy matching.

Fallout was the five predicted tests, minus the two that were probe artifacts.
`stays permissive when no signature was declared` became `… when the signature
is \`_\``, plus a new test that a bare `:setup` is closed *and* warns; four
fixtures across `Component79.test.ts` gained the `{ model }` they always should
have declared. One of those four was only found by instrumenting the warn — a
`$:` effect writing its model back, whose child never read `model`, so the
signature had been silently wrong and nothing had ever noticed. That is the
class of bug this change exists for, and it caught one inside the test suite on
the first run.

New tests: the spread's extra keys staying silent, once-per-usage-site over a
`:each`, an undeclared `:model` prop warning, and a `_` signature saying
nothing. `propsSignature.test.ts` also gained a file-level
`afterEach(vi.restoreAllMocks)` — `spyOn` returns the mock already installed, so
without it each new spy inherited the previous test's call log.

662 tests pass; the tutorial has no bare-`:setup` component that takes
parameters, so it never moved.
