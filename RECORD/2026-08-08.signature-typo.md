# A `:setup` value that isn't a props pattern says so

**Status:** proposal. From an outside report (`2026-08-08.outside-report.md`, item 4) by someone
building an app against the CDN build. Closes the last silent hole in the
contract `2026-07-14.component-signature.md` opened and
`2026-08-07.signature-teeth.md` gave teeth to.

## The problem

`parsePropsPattern` returns `null` for anything that doesn't start with `{`, and
`null` means "declared no signature", which is the most permissive mode there
is. So a typo in the signature doesn't fail — it silently opts the component out
of the contract it was trying to write:

```html
<script :setup=",{ Component79, $reactive }">   <!-- leading comma: null -->
<script :setup="{ label, step">                 <!-- unbalanced: null -->
<script :setup="props">                         <!-- not a pattern at all: null -->
```

The reporter wrote the first one, from the factory-mode `(props, ctx)`
signature, taking `:setup` for an injection list rather than a props signature.
It looked like it worked, because `Component79` and `$reactive` come from
`SETUP_HELPERS` whatever the signature says. Nothing anywhere said the signature
was being ignored.

**And it got worse, not better, in `2026-08-07.signature-teeth.md`.** Before that
change a bare `:setup` was permissive too, so permissive was somewhere you
landed by accident all the time and a typo was one more way in. Now a bare
`:setup` is *closed* and `_` is the explicit opt-out — which means a typo is the
only remaining accidental route to permissive, and the one that comes with no
diagnostic. The mode you can now only ask for on purpose is still reachable by
getting it wrong.

## The proposal

Warn, once per script block, when the `:setup` value is non-empty, isn't `_`,
and doesn't parse as an object pattern:

```
jq79: :setup=",{ Component79, $reactive }" is not a props pattern, so this
component declares no signature and takes whatever a parent passes - write the
props it takes ("{ a, b }"), a bare :setup for none, or "_" to stay open on
purpose
```

Three conditions, each carrying its weight:

- **Non-empty.** `""` is the bare attribute, and `setupSignature` already reads
  that as a closed signature. It never reaches `parsePropsPattern`.
- **Not `_`.** The documented permissive escape. It parses to `null` by the same
  rule as the typos, and only intent separates them, so it has to be named.
- **Doesn't parse.** Which is `parsePropsPattern` returning `null` — both of its
  `null` returns, the not-an-object one and the unbalanced-braces one. The
  second is worth as much as the first: `{ label, step` is a typo nobody would
  defend, and today it is permissive.

**Dedupe on the script block**, a `WeakSet<TagBlock>`. The blocks are parsed once
and shared by every instance of a definition, which is the same reason
`warnUndeclared` keys on the template node. It matters here for a smaller reason
too: `setupSignature` is called from three places per render (`declaredPropNames`,
`declaredPropSet`, and `declareProps` in the script loop), so even a single
mount would say it three times.

**Warn, not throw.** Consistent with every other it-does-nothing case in jq79,
and with `2026-08-07.signature-teeth.md` rejecting the same escalation: an
ignored signature is a bug to find, not a reason to refuse to render.

## What it costs

The check runs once per script block per session and is a `WeakSet` lookup after
that. `parsePropsPattern` is untouched — the warn sits in `setupSignature`, the
one place that already knows what an empty value means, so factory scripts
(whose first parameter legitimately reads as `null` for `(props, ctx)`) never
reach it.

The false-positive risk is a component that means to be permissive and spells it
something other than `_` — `props`, `_props`, `any`. Those warn. That is
deliberate: the message names `_`, the fix is one character, and the alternative
(exempting every bare identifier) would exempt `props`, which is precisely the
mistake the reporter made.

## Rejected

- **Warning inside `parsePropsPattern`.** It is a pure `transform.ts` function
  the Vite plugin calls too, and it cannot tell a `:setup` value from a
  factory's first parameter — where a bare identifier (`props`) is the correct,
  idiomatic spelling. The distinction only exists at the `setupSignature` call
  site.
- **Treating an unparseable value as a *closed* signature.** More aggressive
  than the warn and it would drop props on a component whose author is already
  confused. Silence is the bug here, not permissiveness.
- **Naming the component in the message.** `setupSignature` takes a `TagBlock`,
  not the instance, so `filename`/`name` would need threading through three call
  sites for one string. The pattern text is quoted in the message and is
  distinctive enough to grep for. Left open below.

## Open

- **The message could name the file.** Worth doing if a page ever warns twice
  and the two patterns look alike; it needs `setupSignature` to take the
  component, or the warn to move up to `renderWith`.
- **`docs/` still shows a bare `<script :setup>` in examples where the component
  takes props** — the same open item `2026-08-07.signature-teeth.md` left, and
  now those examples warn at the usage site instead of the definition.

## Test

In `tests/propsSignature.test.ts`, beside the `_` and bare-`:setup` cases:

- a leading-comma pattern warns and names `:setup=` — the reporter's own line;
- unbalanced braces warn;
- `_` and a valid `{ … }` stay silent;
- two instances of one definition warn once between them.

---

## 2026-08-08 — implemented

As proposed. `warnUnreadableSignature` sits under `setupSignature`, which is the
only caller: `parsePropsPattern` is untouched, so the Vite plugin and
`parseFactoryProps` are unaffected and a factory's `(props, ctx)` still reads a
bare identifier as the correct spelling it is there.

One thing the proposal had the wrong way round: the `_` check belongs *inside*
the warn, not at the call site. `setupSignature` should read as "parse it, and
say so if it couldn't"; which spellings are deliberate is a fact about the
warning, and keeping it there puts it next to the sentence that names `_`.

No existing test moved — nothing in the suite or the tutorial had a `:setup`
value that failed to parse, which is the answer to "is this warning going to
fire on correct code". Five new tests in `propsSignature.test.ts`: the reported
leading-comma pattern (warns, and is still permissive), unbalanced braces, a
bare identifier, `_` staying silent, and once-per-definition over a `:each` of
three. Plus one asserting a readable signature says nothing at all, which is the
regression that matters most if the condition is ever loosened.

Both open items stay open.
