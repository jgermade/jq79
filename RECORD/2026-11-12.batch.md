# `$batch`: several writes, one wake

**Status:** proposed and implemented on the same branch. Issue
[jgermade/jq79#41](https://github.com/jgermade/jq79/issues/41).

## The problem

Every write notifies synchronously: `notify` → `runMatched` runs the woken
effects before the assignment returns. A change that takes several writes wakes
each effect once per write, and the runs in between see a state that never
existed as far as the author is concerned:

```js
playback.queue = next   // effects run: new queue, OLD index
playback.index = 0      // effects run again: new queue, new index
```

jackbird hit it twice. A player started the wrong track for a moment (the old
index into the new queue). And two frames syncing a store over a
`BroadcastChannel` sent both states; the other side applied both, its own effect
sent them back, and the two ping-ponged until each grew a `queueMicrotask` and a
"this was just applied" flag. That dance is now in several places in one app,
which is the library's job to remove.

## The proposal

```js
import { $batch } from "jq79"   // also in scope in every setup script

$batch(() => {
  playback.queue = next
  playback.index = 0
})
// every effect either write woke has run once, against both
```

- Inside `fn`, writes land and notify **listeners** (`$on`, `$onAny`) as today -
  they are the store's change log, and bridges between stores are built on
  them, so they must hear every key.
- **Effects** woken inside `fn` are queued instead of run, once each however
  many writes woke them, and run after `fn` returns, oldest first (the same
  order `runMatched` keeps). `$computed` is an effect, so it settles once too;
  the cost is that a `$computed` read *inside* the batch is the value from
  before it.
- Nested batches flush at the outermost. A write made by a flushed effect queues
  into the same flush, so the batch settles before `$batch` returns - still
  synchronous, still nothing left for a microtask. Cut at 100 rounds with a
  console error, as `$effect` cuts an effect that wakes itself.
- `fn` throwing still flushes (the writes it made did land) and rethrows.
- It returns what `fn` returns.

Module-level, not per store: one change commonly spans two stores (a store and
the one it is bridged into), and only one queue can order them.

## Cost

A counter and a map, read once per notify (`if (batchDepth)`) on the hot path.
One more name in the setup scripts' compiled parameters (`SETUP_HELPER_NAMES`).

## Rejected

- **Batching listeners too.** `$onAny` is how a bridge re-notifies a holder; a
  deferred listener would deliver the holder's notify after the flush and wake
  its effects a second time - the double run this is meant to remove.
- **`store.$batch`.** Per store means two queues for a write that crosses a
  bridge.
- **Microtask-flushed effects by default.** Every binding in the library relies
  on the write having rendered by the time it returns.

## Open

- `$effect(run, { flush: "microtask" })`, from the issue, for an effect that
  never wants an intermediate state without its writers knowing to batch. Not
  done: it changes what "the write has rendered" means for one effect, and
  needs its own argument.
