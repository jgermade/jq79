# TypeScript in a component's scripts

**Status:** plan, written before `dev/` or `src/` was touched.

## The problem

`<script :setup>` bodies are plain JS by construction: the runtime hands them to
`new Function` and the only thing between the author's text and the compiler is
[`transformSetupScript`](../src/transform.ts), a scanner that rewrites top-level
declarations and `$:` labels. It is deliberately not a parser.

A type annotation therefore doesn't fail — it does something worse:

```
IN   let count: number = 0
vars []                        <- count is never declared on the store
OUT  count: number = 0         <- a labeled statement that assigns to `number`
```

`interface`, `type`, `as` and generics all throw at `new Function`, loudly. But
`let x: T = v` — the single most common line in a typed setup script — parses as
a label, runs, and leaves `x` non-reactive. There is no error anywhere.

So today the answer to "can I write TypeScript in a component?" is *no, and the
failure is silent*. Either half of that is worth fixing on its own.

## The proposal: `<script lang="ts">`, compiled by the Vite plugin

The plugin already has this exact shape, one function up: `<style lang="scss">`
is compiled to plain CSS in [`dev/vite.ts`](../dev/vite.ts) and the `lang` is
dropped from the emitted tag, so the runtime only ever sees CSS. `lang="ts"` is
the same move on the other kind of block — compiled to plain JS, `lang` dropped,
the runtime only ever sees JS.

Nothing in `src/` learns about TypeScript. The scanner keeps scanning JS.

## What it costs, measured before writing it

Vite's own transform preserves everything the runtime scanner depends on. Run
against a setup script and a factory script:

```
let count: number = 0                     ->  let count = 0;
$: doubled = count * 2                    ->  $: doubled = count * 2;
const fmt = (n: number): string => …      ->  const fmt = (n) => …;
const Row = await import("./row.html")    ->  const Row = await import("./row.html");
import Row from "./row.html"              ->  import Row from "./row.html";
import type { User } from "./types"       ->  (gone)
```

Top-level `let`/`const`, the `$:` label and the `import()` calls the plugin
hoists all survive. It also emits the semicolons, which means the ASI heuristics
in `findStatementEnd` have nothing left to guess about.

Two flags are load-bearing, and both were found by testing rather than by
reading:

- **Unused value imports must be preserved.** Both transforms drop them by
  default (a TS transform can't tell a type-only import from an unused one). A
  factory script's `import Row from "./row.html"` would vanish, and with it the
  specifier `hoistableImports` needs to pull the child into the bundle — a
  component that silently loses its children. esbuild needs
  `verbatimModuleSyntax: true`; oxc needs `onlyRemoveTypeImports: true`.
- **A trailing bare `export {}` must be stripped.** A script whose only imports
  were `import type` comes back marked as a module, and `export {}` is a
  SyntaxError inside the Function body the runtime compiles it into.

## Decision: oxc when it exists, esbuild otherwise

`transformWithEsbuild` works across the whole declared peer range (`vite >=5.0.0`)
but logs a deprecation warning on every build under Vite 8. `transformWithOxc`
is what Vite is moving to but only exists from Vite 7. Neither alone is right,
so the transform is looked up at call time and esbuild is the fallback. The two
produce different formatting and identical semantics for the subset that matters
here.

Rejected: pinning esbuild. It puts a deprecation warning in every user's build
output today and breaks the plugin outright the day Vite removes the export.

## Decision: `lang`, not `type`

The question that started this asked for `<script :setup type="ts">`. `lang` wins
on one argument that outweighs the rest: `<style lang="scss">` already exists in
this repo, and one attribute meaning "this block is written in something else"
is better than two. It's also what Vue and Svelte spell it.

`type` would carry a second, unwanted meaning — `<script type="module">` is real
HTML with real semantics — and buys nothing here, since components are parsed
inside a `<template>` and the browser never executes these scripts anyway.

## Decision: bundler-only, and the runtime says so out loud

`lang="ts"` ties a component to the bundler, exactly as `lang="scss"` does. The
[dev server](../dev/dev.ts) is "a static file server and nothing else" and does
not compile scss either; a component fetched from `public/` or a CDN never meets
the plugin at all.

That's acceptable for styles because a browser dropping an unparseable
stylesheet is visible. It is *not* acceptable for scripts, because of the
labeled-statement failure above. So the runtime gets the same warning
`<style lang>` has, worded for what actually goes wrong:

```
jq79: <script lang="ts"> needs the jq79/vite plugin to compile it. This
component didn't go through the bundler, so its types were never stripped:
the script will throw, or - for a plain `let x: T = …` - silently fail to
declare x.
```

Ten lines in `src/`, next to the `<style lang>` warning it copies, and no
TypeScript knowledge anywhere in the runtime.

## What is still open

- **Line numbers.** The runtime names each compiled script with
  `//# sourceURL=<file>?jq79-script=N` so it is findable in devtools. The
  compiled JS no longer has the `.html`'s line numbers (a multi-line type
  annotation collapses), and `load()` already returns `map: null`, so the
  offsets drift for typed scripts. Fixing it means threading a real sourcemap
  through a module whose source is inlined as a JSON string — a separate piece
  of work, not smuggled into this one.
- **The props signature stays JS.** `<script :setup="{ label = 'Total' }">` is
  read from the *attribute* by `parsePropsPattern`, which the plugin never
  compiles. `:setup="{ label }: Props"` is not supported and is not part of
  this.
- **No type checking.** This strips types; it does not check them. `vue-tsc`'s
  equivalent for `.html` components doesn't exist, and editors won't see these
  blocks as TS without an extension. The value on offer is annotations that
  don't break the runtime, not a checked component.

## Appended the same day, after building it

Three things the plan got wrong or didn't know, found while writing the code.

**`transformWithEsbuild` doesn't just warn under Vite 8 — it throws.** The
section above says it "logs a deprecation warning on every build", which is what
calling it looked like from outside. Vite 8 also requires esbuild to be
installed *separately* by then, and raises `Failed to load transformWithEsbuild`
when it isn't. That strengthens the decision rather than changing it: preferring
oxc where it exists isn't cosmetic, it's the only thing that works on Vite 8,
and esbuild is there for the Vite 5/6 versions that still ship it.

**The fallback can't be tested under jsdom.** esbuild refuses to start when
`new TextEncoder().encode("")` isn't a real `Uint8Array`, which is jsdom's, so
the test that mocks `transformWithOxc` away lives in its own file with
`@vitest-environment node` ([`tests/vitePluginFallback.test.ts`](../tests/vitePluginFallback.test.ts)).
It asserts against a spy on the real transform rather than against the shape of
the output: esbuild and oxc format differently today (`const user = { a: 1 }` on
one line vs. broken across three), and pinning that would be a test of a version
number.

**The `<script>` regex was widened on the way past.** `compileScriptBlocks`
needs the attribute string, which `SCRIPT_BLOCK_RE` wasn't capturing, so it was
rewritten to `STYLE_BLOCK_RE`'s quote-aware shape. That is a fix in its own
right, and one nobody asked for: the old `<script\b[^>]*>` ended the tag at the
first `>`, so `<script :setup="{ n = a > 1 }">` cut the block in the wrong place.
Its two existing callers (`hoistableImports`, `declaredComponents`) needed one
changed destructure between them.

## Appended the same day: the signature is compiled too

The "what is still open" section above says the props signature stays JS, and
that `:setup="{ label }: Props"` is not part of this. **That was the wrong
line to draw**, and it was drawn from the plan rather than from the behaviour.
What `lang="ts"` promises is that the block is written in TypeScript; the
signature is part of the block, and half a promise is worse than none.

Measured before deciding — what the four TS-shaped signatures do *today*,
unbundled:

| signature | today |
| --- | --- |
| `{ label, step = 1 }: Props` | parses correctly, by accident |
| `{ label }: { label: string }` | parses correctly, by accident |
| `{ label, step = 1 as number }` | **silent**: the default is evaluated, fails, `step` is `undefined`, nothing logged |
| `_: Props` | **warns** "is not a props pattern" and opens the signature |

The first two work because `parsePropsPattern` reads to `patternCloseIndex` and
ignores everything after the pattern's closing brace. That is not support — it
is an annotation surviving into a component the plugin just declared was JS,
and the two rows below it are what "by accident" costs.

**Decision: the plugin compiles the attribute, through the same transform as
the body.** Wrapped as a parameter list (`(<value>) => <marker>`) and read back
from the output, rather than cut with a scanner of its own. The annotation can
sit on the pattern, on the permissive `_`, or inside a default expression, and
only a parser separates those — which is the same argument that kept the
type-stripper out of `src/` in the first place. Both transforms hand the wrapper
back on one line with the parens intact, so reading the parameter out is a slice
at the marker, not bracket matching.

**The `"` has to be escaped on the way back in.** Both transforms normalize
string literals to double quotes, so a default written `{ label = 'Ada' }` comes
back as `{ label = "Ada" }` and would end the `:setup="…"` attribute early. It
is written as `&quot;`, which the HTML parser hands back to `parsePropsPattern`
unchanged. `&` is deliberately *not* escaped: `&&` in a default is not an
entity and survives the parse, while escaping it would double-encode a source
that already wrote `&quot;` itself.

A factory script needs none of this: its signature is its first parameter,
which is in the body, so the body's transform already covers it. That asymmetry
is the whole reason the setup half needed its own pass.
