# MathML, and the one tag with a hyphen in it

**Status:** proposal, then implementation. It is §2 of
[`2026-08-24.open-after-pr-12.md`](2026-08-24.open-after-pr-12.md), which files
it as *"free with the namespace change and never exercised… one test file's
worth of work, and it either confirms it or finds the second case that the
`<svg>` corpus did not cover."*

It found the second case.

---

## What §2 predicted, and what is true

[`2026-08-24.svg-namespace.md`](2026-08-24.svg-namespace.md) records the
namespace on the AST node for **any** non-HTML element, not for SVG in
particular, so MathML was supposed to come along for free. Nearly all of it
does. Rendered against the library as it stands:

```html
<math display="block"><mrow><mi :mathcolor="c">{{ sym }}</mi></mrow></math>
```

```
math ns  http://www.w3.org/1998/Math/MathML
mi   ns  http://www.w3.org/1998/Math/MathML   mathcolor="red"
```

Namespace, interpolation, `:attr` bindings, `:each` inside `<mrow>`, and the
integration points (`<mtext>`, `<annotation-xml encoding="text/html">` hand the
namespace back to HTML, exactly as `<foreignObject>` does) - all correct, none
of it tested until now.

## The case the `<svg>` corpus could not cover

**`<annotation-xml>` is the only element in either foreign namespace whose tag
has a hyphen**, and a hyphen is how this library recognizes a custom element:

```ts
const mayUpgrade = el instanceof HTMLUnknownElement || node.tag.includes("-")
```

The first clause was made false for foreign elements by the namespace change -
an `SVGElement` is not an `HTMLUnknownElement`. The second was not, because no
SVG tag has a hyphen and nothing in the corpus had a reason to. So a real
MathML element is treated as a custom element that might become a component,
and `mayUpgrade` decides three things:

```html
<math><annotation-xml encoding="text/html" :id="v"><p>{{ v }}</p></annotation-xml></math>
```

1. **Every `:` binding on it is written verbatim** and never bound - the
   rendered element carries a literal `:id="v"` attribute. On a tag that may
   upgrade, a `:` attribute is a *parameter* being held for the component that
   arrives; on a MathML element it is a binding that silently does nothing.
2. **A component named `AnnotationXml` appearing in scope replaces the
   element**, at any point after the render:

   ```
   <math><!--AnnotationXml--><b class="wrong">tomado</b><!--/AnnotationXml--></math>
   ```
3. `:model` on it warns nothing, on the theory that the upgrade will handle it.

And one effect nobody sees: every `<annotation-xml>` on the page registers an
upgrade-watch effect that waits forever for a name that can never legitimately
arrive.

## The proposal

One condition, in the place the namespace change already taught this lesson
once:

```ts
const mayUpgrade = node.ns === undefined && (el instanceof HTMLUnknownElement || node.tag.includes("-"))
```

A foreign element's namespace does not come from a tag list - it comes from the
HTML parser's foreign-content algorithm having run over the authored source. So
`node.ns !== undefined` means the author wrote this element inside a `<math>` or
an `<svg>`, where no custom element and no component can live. `plannableNode`
makes exactly this argument for exactly this reason, two hundred lines away.

In practice this changes MathML only: no SVG tag has a hyphen, and a foreign
element is not an `HTMLUnknownElement` either way.

## What it costs

One comparison per element, on a path that already builds the element. Nothing
on the benchmark.

## What was rejected

- **Making `annotation-xml` plannable too.** `plannableNode` rejects a dashed
  tag for the same custom-element reason, and with `mayUpgrade` fixed the reason
  no longer applies to a foreign one. Left alone anyway: it makes the subtree
  containing it interpreted, which is slower and *correct*, and "the interpreted
  path stays the fallback for everything else" is the rule that keeps this area
  honest. There is no measurement asking for it.
- **Skipping the component scan for foreign elements entirely.** `renderNode`
  calls `findComponentKey` for every element before anything else, so a
  component named `Mi` *already in scope* captures `<mi>` - the same trade the
  corpus records for `Td` and `<td>`. Changing that for foreign tags is a wider
  behaviour change than this bug asks for, and it would make foreign elements
  the one place where a PascalCase scope key does not capture. Left as it is,
  and noted below as the asymmetry it leaves.

## The parse hazard, which is not a bug and is worth writing down

`annotation-xml` is an HTML integration point only when its `encoding` is
`text/html` or `application/xhtml+xml`. Bind that attribute instead of writing
it out and the parser never sees the value:

```html
<math><annotation-xml :encoding="e"><p>x</p></annotation-xml></math>
```

```
<div><math><annotation-xml :encoding="e"></annotation-xml></math><p>x</p></div>
```

The `<p>` is **outside the `<math>`**. That is the HTML parser doing exactly
what the spec says - `<p>` is on the breakout list for foreign content, and
without a recognized `encoding` the `annotation-xml` is not an integration point
- but the author wrote nesting that silently is not there. It is the same shape
as the `viewBox` limitation for SVG: a name that has to be *written*, not bound,
and for the same underlying reason (the rewrite and the parser both run before
jq79 sees anything). Documented in `docs/template-syntax.md` beside its SVG
sibling rather than left to be discovered.

## What is still open

- **The capture asymmetry above.** A key already in scope captures a foreign
  tag; a key that arrives later no longer does. Both are defensible, they are
  not the same rule, and only the second one is changing here.
- **`<annotation-xml>` stays off the clone path**, and takes its whole `<math>`
  ancestor with it (`plannableNode` is recursive). A page whose maths is one
  annotated formula rendered once pays nothing for that; a page that renders a
  thousand does. Nobody has one.
- **A camelCase MathML attribute** would hit the same rewrite `viewBox` does.
  MathML's attribute names are lowercase almost everywhere (`mathcolor`,
  `linethickness`, `scriptlevel`, `displaystyle`), so unlike SVG there is no
  table to argue about. `definitionURL` is the exception, it is deprecated, and
  nothing here handles it.
