# `<svg>` renders nothing, and the parser already knew better

**Status:** proposal, then implementation. Takes §2 of
[`2026-08-24.what-is-still-open.md`](2026-08-24.what-is-still-open.md), and
reclassifies it: §2 files this under the clone path as *"measured as free, but
it is a behaviour change"*. It is not an optimization at all. It is a rendering
bug, it predates the clone path, and it has four parts.

---

## What actually happens today

```html
<svg viewBox="0 0 10 10"><circle cx="5" r="4" :fill="color" /></svg>
```

```
<svg viewbox="0 0 10 10"><circle cx="5" r="4" :fill="color"></circle></svg>

svg:  HTMLUnknownElement · ns http://www.w3.org/1999/xhtml · instanceof SVGElement === false
```

1. **The namespace is wrong.** `document.createElement("svg")` builds an
   `HTMLUnknownElement` in the XHTML namespace. A browser does not draw it.
2. **`viewBox` became `viewbox`.** `setAttribute` lowercases the qualified name
   on an HTML element. SVG's attributes are case-sensitive, so `viewBox`,
   `preserveAspectRatio`, `gradientUnits` and the rest are all lost. The AST is
   innocent here - `elementAttrs` reads `attr.name` verbatim off the parsed
   tree, which really does hold `viewBox`.
3. **No binding inside an `<svg>` works.** `:fill="color"` is written to the DOM
   *literally*. `mayUpgrade` is true for any `HTMLUnknownElement`, and
   renderNode's rule for a tag that may still become a component is to leave
   `:` attributes verbatim as parameters. So every directive under an `<svg>`
   is silently inert - this is the worst of the four, and it is not in §2.
4. **A camelCase SVG tag would be flattened.** `elementToAST` does
   `el.tagName.toLowerCase()`, which is right for HTML (`DIV` → `div`) and
   destroys `clipPath`, `linearGradient`, `textPath`, `feGaussianBlur`.
   Also not in §2.

Plus one thing that merely wastes work: every `<svg>` element registers an
upgrade-watch effect that waits forever for a component named `Svg`.

## The proposal

**Carry the namespace on the AST node.** `elementToAST` already walks a real
DOM tree built by `DOMParser`, and that tree is correct - verified:

```
svg ns: http://www.w3.org/2000/svg | ctor: SVGSVGElement
attrs kept: ["viewBox"]
```

So `el.namespaceURI` is sitting right there, one property away, and
`parseComponentString` throws it out. Record it for foreign elements only (an
HTML node keeps the shape it has today), and stop lowercasing a foreign
`tagName`.

Then both render paths build the element the same way:

```ts
node.ns ? document.createElementNS(node.ns, node.tag) : document.createElement(node.tag)
```

That is 1, 2 and 4. And 3 falls out for free: an `SVGElement` is not an
`HTMLUnknownElement`, so `mayUpgrade` is false and the `:` attributes take the
ordinary binding path.

### Why not a tag list

Whether `<a>` or `<title>` or `<style>` is SVG depends on where it sits, not on
its name, and `<foreignObject>` switches back to HTML mid-subtree. That is the
HTML parser's foreign-content algorithm, and it is not worth reimplementing
against a list of ~80 names when the parser has already run it on the very tree
we are reading.

### Why the skeleton learns it too, rather than opting out

Once the namespace is right, an `<svg>` stops being an `HTMLUnknownElement` and
`plannableNode`'s guard stops rejecting it - so it becomes plannable, and
`buildSkeleton` would build it with `createElement` and diverge from the
interpreted path. Two ways out: exclude foreign elements from the cloner, or
teach it the same one-line creator. Teaching it is the same line twice and keeps
the two paths honest, which is the whole design rule of that file.

The differential test carried an `"an svg"` entry in `SHAPE_CORPUS`, written
when `<svg>` was unplannable and belonging there only for that reason. It moves
to `CORPUS` and grows bindings, a camelCase tag and a `<foreignObject>`: what it
proves changes from "this falls through" to "both paths agree on a namespaced
subtree, `viewBox` included".

## What this costs

Nothing measurable, and nothing on the benchmark - the row has no SVG in it.
One optional property on the AST node, set only for foreign elements, and one
branch in each of the two element creators. `plannableNode` trades an
`HTMLUnknownElement` construction for a property check on the foreign path.

The risk is `plannableNode`'s guard. Its `createElement(...) instanceof
HTMLUnknownElement` test is what keeps a tag that might still become a component
out of the cloner, and a foreign element must skip that test rather than fail
it. Getting that backwards makes every `<svg>` interpreted (slow, correct) or
every unknown tag plannable (fast, badly wrong). The corpus entries for a dashed
tag, an unknown tag and a late-arriving component are the ones that speak to it.

## What is still open

- **A bound camelCase SVG attribute.** `expandNameCase` rewrites a `:`-prefixed
  attribute name to kebab before parsing (the HTML parser would lowercase it
  anyway), so `:viewBox="box"` arrives as `:view-box` and is written as
  `view-box`, which SVG ignores. Confirmed. Static `viewBox="0 0 10 10"` is
  unaffected, which is the common case, and so is any binding already kebab or
  lowercase (`:fill`, `:cx`, `:stroke-width`) - most of them. Documented in
  docs/template-syntax.md#svg rather than left to be discovered.

  Two ways to fix it, and picking is the work:

  - **A table of SVG's camelCase attribute names** (~55: `viewBox`,
    `preserveAspectRatio`, `gradientUnits`, `stdDeviation`, `refX`…). Exact,
    and it is bytes on every page of a library that advertises having none.
  - **Ask the element.** `kebabToCamel("view-box")` round-trips to `viewBox`
    exactly (the rewrite is designed to), so the only question is *whether* to
    camelCase a given name - and the SVG IDL answers it. Probed in jsdom:

    ```
    "viewBox" in <svg>              true    -> camelCase it
    "preserveAspectRatio" in <svg>  true    -> camelCase it
    "strokeWidth" in <rect>         false   -> leave stroke-width alone
    "clipPath" in <rect>            false   -> leave clip-path alone
    ```

    Zero table, and it discriminates correctly on every case tried. **Not taken
    here**, because `applyAttr` carries a comment explaining that this exact
    technique - asking the DOM which family a name belongs to - was rejected
    once already: jsdom and Chrome disagreed, and the tests would have pinned a
    semantics no browser has. SVG's IDL is specified far more tightly than
    HTML's boolean attributes, so the objection may not carry. It needs checking
    in a real browser before it is believed, and this session had only jsdom.
- **MathML** gets the same treatment for free, and is untested here.
- §3 and §5 of the previous file, untouched.

## 2026-08-24 — "ask the element" is dead, checked in a real browser

The section above parks the bound-camelCase-attribute fix on the grounds that
the DOM-as-table trick "needs checking in a real browser before it is believed,
and this session had only jsdom". The instrument built for
[`2026-08-24.one-shot-render-measured.md`](2026-08-24.one-shot-render-measured.md)
brought a real Chromium along with it, so it got checked.

**It does not work.** Chromium 141, 28 attributes, testing whether
`kebabToCamel(name) in element` answers "should this name be camelCased":

```
should camelCase, but the IDL says no:
  feGaussianBlur/std-deviation  -> stdDeviation
  animate/attribute-name        -> attributeName
  animate/repeat-count          -> repeatCount
should stay kebab, and the IDL agrees:  all 12
```

Three of sixteen wrong, and wrong the silent way - the attribute is written as
`std-deviation` and SVG ignores it. `stdDeviation` is on every blur filter, so
this is not an exotic corner. jsdom passed the trick because it only implements
the cases where the trick happens to work, which is precisely the failure
`applyAttr`'s comment describes: the tests would have pinned a semantics no
browser has.

So the earlier note's "the objection may not carry" is **withdrawn**. It
carries. The options are now a table of SVG's camelCase attribute names, or the
documented limitation that ships today - there is no third one.

## 2026-08-25 - there was a third option, and it is the parser's own table

The dated section above closes with "the options are now a table of SVG's
camelCase attribute names, or the documented limitation that ships today - there
is no third one." There is, and it was one question away the whole time.

**Ask the parser, not the IDL.** The HTML parser carries a table for adjusting
foreign attribute names - it is what makes a written-out `viewBox` survive - and
it can be asked by writing the name into markup and reading back what the parser
called it. Chromium 141, the same build in which the IDL trick failed:

| | IDL (buried above) | the parser's table |
|---|---|---|
| `stdDeviation` | **wrong** | right |
| `attributeName` | **wrong** | right |
| `repeatCount` | **wrong** | right |
| 62 camelCase names | 3 of 16 wrong | 58 of 62, and the 4 are SVG 1.1 names Chromium lowercases written-out too |
| disagreement with the written-out attribute | not measured | **0 of 62** |
| false positives over must-stay names | - | **0 of 16** |

The objection recorded above - "the tests would have pinned a semantics no
browser has" - is what distinguishes the two, and it does not carry here. The
IDL question ("which family does this name belong to") has no ground truth. This
one is answered by the table that decides the static case, in the engine
rendering the page, so the acceptance criterion is self-checking: a bound
attribute behaves like the same attribute written out. jsdom returns the same
58/62 and the same 0/0 as Chromium.

Implemented in [`2026-08-25.svg-attribute-names.md`](2026-08-25.svg-attribute-names.md),
which also records the four other routes that were measured and rejected on the
way (XML parsing, desugaring to `:attrs`, a separate renderer or dynamic
`innerHTML`, and assigning the IDL property), and what Vue and Svelte do
instead.

Also withdrawn from the section above: **"today it fails without a word" was
half the story.** `:attrs="{ viewBox: box }"` has always worked - the rewrite
does not reach inside an expression, and `setAttribute` only lowercases on HTML
elements. The table would have bought a spelling, not a capability. That is
worth knowing about any future limitation filed here: check whether `:attrs`
already does it.
