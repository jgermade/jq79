# The safety net for a second render path

**Status:** landed, **on**, with an off switch. The renderer is in `src/`,
`tests/skeleton.test.ts` proves the two paths agree, and
`Component79.debug({ cloneSkeletons: false })` turns it off at runtime without a
rebuild. The decision this file originally left open - whether to flip it - was
made by the owner along with the shape of the switch; see *The switch* below.

The objection that kept
[`2026-08-23.clone-static-skeletons.md`](2026-08-23.clone-static-skeletons.md)
from being decidable was never the speed:

> Every directive added after this has to be taught to both, or has to force its
> subtree non-static - and "forgot to teach the cloner" fails as *stale DOM in
> one code path*, which is the worst kind of bug this library can have.

Two things answer it, and only together.

## The walkthrough

One row of the benchmark table, from the template to the DOM, naming every
function it goes through. Written to be read cold - this is a second render
path, and the next person to touch a directive needs to know where it lands.

```html
<tr :each="row in rows" :key="row.id" :class="{ danger: row.id === selected }">
  <td class="col-md-1">{{ row.id }}</td>
  <td class="col-md-4"><a @click="select(row.id)">{{ row.label }}</a></td>
  <td class="col-md-1"><a @click="remove(row.id)"><span class="glyphicon glyphicon-remove"></span></a></td>
  <td class="col-md-6"></td>
</tr>
```

### Getting there

`renderNodes` sees `:each` on the `<tr>` and hands it to `renderEach`, which
asks `eachPlanOf` for the item node (the same node without `:each`/`:key`,
derived once per definition) and then calls **`renderNode(itemNode, itemScope,
itemFx, shadow)` once per row**. That call is where this lives: after the `:with`
check, the slot checks and `findComponentKey`, and before `createElement`.

```ts
if (debugFlags.cloneSkeletons) {
  const plan = planOf(node)
  if (plan && !plan.tags.some(tag => findComponentKey(scope, tag))) return renderFromSkeleton(plan, scope, fx)
}
```

### Row 1: the plan gets built

`planOf` misses its `WeakMap` and asks two questions.

**`plannableNode`** walks the subtree. Every element must be a plain HTML tag -
no `node.component`, no dash, not `<slot>` or `<template>`, and
`createElement(tag)` must not give an `HTMLUnknownElement` - and every attribute
must pass **`plannableAttr`**, which accepts exactly four things: a static
attribute, `@event`, `:class`/`:class.<name>`, and a single `:<name>` binding
with no dot in it. The `<tr>`'s `:class` is a hole; every `class="col-md-…"` is
static; both `@click`s are holes. Nothing else is in the way, so: plannable.

**`countElements`** gives 8 (`tr` + four `td` + two `a` + one `span`), which
clears `MIN_SKELETON_ELEMENTS`.

**`buildSkeleton`** then walks the same tree once, building two things at the
same time:

| | |
|---|---|
| `plan.skeleton` | a detached `<tr>` with every static attribute set, every static text node in place, and an **empty text node wherever a `{{ }}` was** |
| `plan.ops` | one entry per hole: `{ kind, path, … }` |
| `plan.tags` | `{tr, td, a, span}`, for the guard below |

The `path` is a list of **child indices**, and the reason it can be that simple
is that the skeleton is built from `node.children` in order - including the
whitespace text nodes the parse keeps on purpose. Both sides count the same
nodes, so index 3 means the same thing in the AST and in the clone.

For this row the ops come out as:

```
class  []        { danger: row.id === selected }     the <tr> itself
text   [1,0]     row.id                              inside the first <td>
event  [3,0]     @click="select(row.id)"             the first <a>
text   [3,0,0]   row.label
event  [5,0]     @click="remove(row.id)"             the second <a>
```

The `<td>`s sit at the odd indices because the newlines between them are text
nodes at the even ones - which is the whole fragility of addressing holes
positionally, stated as concretely as it can be.

Order matters and is not cosmetic: `buildSkeleton` pushes ops in exactly the
order `renderNode` registers them - the attribute walk first, then `:class`,
then the children depth-first - because effects run in registration order.

### Every row, including the first

`renderFromSkeleton` does the whole job in two steps:

```ts
const root = plan.skeleton.cloneNode(true)
for (const op of plan.ops) { /* atPath(root, op.path), then the same effect renderNode would register */ }
```

`atPath` walks `childNodes[i]` down the recorded indices. Each op then registers
**the identical effect** the interpreted path would: `renderText` into the text
node, `bindEvent` for a listener, `applyAttr` in an effect for an attribute, and
the `classNames`/`classList` diff for `:class`. Nothing about reactivity changes
- same effects, same count, same dependencies.

So per row: **one `cloneNode`, four memoized `findComponentKey` lookups, five
path walks and five bindings**, against ~25 questions per element for eight
elements.

### The guard, every time

`plan.tags.some(tag => findComponentKey(scope, tag))` runs on **every** row, not
once. It has to: whether `<td>` is a `<td>` depends on the scope this row
renders against, and a `Td` in it makes every one of them a component. It costs
what the interpreted path already paid - `findComponentKey` is memoized per
render pass - and when it fires, the row falls through to `renderNode` and
nothing else changes.

### When it does not apply

Put a `<Tag>` in one `<td>` and the whole `<tr>` stops being plannable, because
`plannableNode` is recursive. `planOf` caches that `null`, `renderNode`
interprets the row as it always did - and then, rendering the row's children, it
reaches each `<td>` and asks again. The plain ones with three or more elements
get their own skeleton; the one holding the component does not.

That is subsegmenting, and it falls out of `renderNode` being per-node rather
than being designed. `MIN_SKELETON_ELEMENTS` is what keeps it from being a
pessimisation - see *Size rule* below.

## 1. The holes are an allowlist

`plannableAttr` names the four things a skeleton knows how to fill - `@event`,
`:class`, `:class.<name>`, a single `:<name>` attribute binding, plus static
attributes. **Every other attribute makes its subtree unplannable.** A `:`
attribute with a dot is rejected wholesale except `:class.`, because
`:model.`, `:props.`, `:slot.` and `:html.allowed` all live in that shape and so
would the next directive family somebody invents.

So a directive added to `renderNode` and not to the cloner is **slower** until
somebody teaches it, never mis-rendered. The failure mode is the difference
between shippable and not, and it is a property of the classifier rather than of
anyone's diligence.

## 2. The corpus is rendered both ways and diffed

`tests/skeleton.test.ts` renders 34 templates and all 43 tutorial exercises
through `renderNode` and through the cloner, and requires byte-identical DOM -
then mutates the data and requires it again, because a shape that matches proves
nothing if the holes are wired wrong.

Every tutorial exercise is also rendered **twice interpreted first**, as a null
control: an exercise that does not render the same way twice fails as *that*,
not as a clone bug. It earned its place immediately - `03-components/08-slots`
settles a tick later than the rest, and without the control it read as the
cloner dropping a component's content.

### It was checked by breaking it

A net nobody has tried to get through is a guess. Six deliberate sabotages:

| sabotaje | ¿lo caza? |
|---|---|
| un hueco de texto que renderiza pero no registra su efecto | ✅ 4 tests |
| `:text` admitido en la allowlist sin implementarlo | ✅ |
| `:if` admitido en la allowlist | ✅ |
| `:value` admitido en la allowlist | ✅ |
| `<template>` aceptado como clonable | ✅ |
| un tag desconocido aceptado como clonable | ✅ |
| el orden de los ops invertido | ❌ **no lo caza** |

**Two of those started as failures of the corpus, not of the net**, which is the
only reason they are worth listing:

- `:text` in the allowlist went unnoticed because nothing in the corpus put a
  shape-changing directive *inside* a subtree that was otherwise plannable and
  big enough to plan. That is now a whole corpus of its own - one entry per
  shape directive, each wrapped in a clonable container.
- An unknown tag accepted as clonable went unnoticed because `<svg>` clones to
  the same `HTMLUnknownElement` either way. The case that separates them is a
  tag that **becomes** a component after mount - an async factory writing the
  key in - which nothing in the corpus did. It does now.

**The one it does not catch is op order**, and that is a limit worth stating
rather than papering over: reversing the ops changes no DOM, because every
directive whose registration order is observable (`:value` after the children
that `<select>` needs) is rejected by the allowlist. If a future hole is
order-sensitive, this net will not tell you.

## The tag guard, which is not optional

```ts
if (plan && !plan.tags.some(tag => findComponentKey(scope, tag))) return renderFromSkeleton(plan, scope, fx)
```

`findComponentKey` strips dashes and lowercases, and every PascalCase scope key
participates - so a variable named `Td` makes every `<td>` under it a component,
and `Map`, `Data`, `Table`, `Form`, `Label`, `Option`, `Menu` and `Dialog` are
all HTML tags somebody might name a component after. "It is a known HTML tag" is
not on its own an answer. Removing this line turns the corpus red on one test.

## Size rule

`MIN_SKELETON_ELEMENTS = 3`: below it the fixed cost of a plan is the whole
saving. Measured in the previous file, and the effect is visible here - the
`conditional` row, whose only clonable fragments are one and two elements, read
**+9 to +14% with no threshold** and reads **+2.8% (9/13, chance) with one**.

## What the switch is worth

Same bundle on both pages, only the flag differs, each case against its own null
control:

| caso | create | rondas | replace | rondas |
|---|---:|---|---:|---|
| `wide` (12 elementos/fila) | **-41.8%** | 12/13 | **-42.6%** | 11/13 |
| `benchmark` (8 elementos/fila) | **-28.3%** | 13/15 | -15.0% | 10/15 |
| `benchmark`, 10.000 filas | **-10.3%** | 8/9 | -13.6% | 5/9 |
| `conditional` | +2.8% | 9/13 | — | — |

840 tests pass with the flag off; the differential test turns it on, so CI
exercises both paths on every run.

## The switch

```js
Component79.debug()                            // { cloneSkeletons: true }
Component79.debug({ cloneSkeletons: false })   // off, and hands the flags back
```

Global to the page rather than per component: these change how the renderer
works, and a page rendering two ways at once is the one state nobody could
debug. An unknown key warns and names the flags it does know, so a typo is not a
silent no-op.

Two things this buys beyond the obvious:

- **A bug report that names the file.** A page that renders wrong is a bug
  either way; one whose reporter can say "it comes right with `cloneSkeletons:
  false`" arrives already bisected.
- **A pairing no git ref can express.** `npm run benchmark:ab -- --flags`
  measures one build against *itself* with only the flag differing - one dist,
  two URLs, because the benchmark app reads `?clone=0` and calls
  `Component79.debug` (`frameworks/keyed/jq79/src/main.js`). The app is staged
  once instead of per side, so the rounds cost what one build's rounds cost.

## What the repo's own harness says

`npm run benchmark:ab -- --flags --rounds 3`, base = off, head = on, so a
negative delta means cloning is faster:

| operation | off | on | delta | per round | noise | verdict |
|---|---:|---:|---:|---|---:|---|
| **Create 1,000 rows** | 43.4ms | 33.3ms | **-23.3%** | -24.1 / -22.8 / -23.3 | ±7.3% | **faster, every round** |
| **Replace all 1,000 rows** | 50.6ms | 38.8ms | **-20.7%** | -17.3 / -26.3 / -20.7 | ±9.4% | **faster, every round** |
| **Create 10,000 rows** | 421.1ms | 353.8ms | **-12.4%** | -9.5 / -12.4 / -20.0 | ±10.2% | **faster, every round** |
| Append 1,000 to 10,000 | 77.5ms | 70.8ms | -15.3% | -15.3 / -20.7 / -4.8 | ±16.1% | under the noise |
| Clear 10,000 rows | 130.9ms | 117.1ms | -10.6% | -3.8 / -10.6 / -32.9 | ±36.5% | under the noise |
| Select a row | 4.6ms | 4.3ms | -8.7% | -1.2 / -10.2 / -8.7 | ±13.0% | under the noise |
| Swap rows | 6.9ms | 6.3ms | -3.9% | -3.9 / -9.3 / -3.6 | ±8.7% | under the noise |
| Update every 10th row | 1.8ms | 1.6ms | 0.0% | -15.4 / 0.0 / 0.0 | ±17.1% | inside the noise |
| **Remove a row** | 5.5ms | 5.6ms | **+1.8%** | +3.7 / +1.8 / +0.9 | ±3.6% | slower every round, under the noise |

Three operations clear the runner's own noise, and they are the three the change
is about. The rest move in the right direction and say nothing, as they should -
`partialUpdate` and `selectRow` touch no create path at all.

**`removeRow` is slower in all three rounds** - by 1.8%, against ±3.6% of noise,
which is small enough that the gate would not look at it twice and consistent
enough to be worth writing down rather than rounding away. Nothing in the clone
path runs during a removal, so the likeliest reading is that the rows it removes
were built by a different path and lay out differently in memory. If it grows,
this is the note that says it was already there at -23% on create.

## Still open

1. **`<svg>` unchanged.** The skeletons are built with `createElement`, so
   namespaces behave exactly as today. Building them from the parser's own tree
   would fix `<svg>` and take it out of the `HTMLUnknownElement` branch the
   upgrade watch relies on. Still its own decision.
2. **The regression job compares against the last released tag**, so the first
   release after this one re-baselines everything. Nothing to do, but the next
   person reading a suspicious delta should know the baseline moved here.
3. **Op order is still uncovered** by the differential test (see above).
