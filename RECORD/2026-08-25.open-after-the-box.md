# What is open after the box

**Status:** a list, and the successor to
[`2026-08-25.open-after-pr-13.md`](2026-08-25.open-after-pr-13.md), whose §1
closed (both steps landed) and whose §5 capture asymmetry went with it. That
file is not edited; this one replaces it as the map. What the two steps *did* is
[`2026-08-25.what-the-tag-rename-did.md`](2026-08-25.what-the-tag-rename-did.md).

Not a proposal. Each item says what it is, what evidence exists, and how big it
looks. Ordered by what I would do first, which is not by size.

---

## 0. The rule still stands, and it grew a second half

**Write the sabotage before trusting the check** - and *re-read your own diff for
what no test would have caught*. Twelve sabotages went red on this branch, and
the one defect actually found (a string inside a selector being renamed:
`[title="a > Boo"]`) was found by reading the diff adversarially, not by any of
them. A sabotage proves a check can fail. It says nothing about the cases nobody
wrote a check for.

## 1. Nobody has opened a browser

**The largest gap, and the cheapest to close.** Two steps changed what every
component renders, and every assertion behind them is jsdom's - a DOM
implementation with no layout and no cascade. Four claims are specification
reasoning with a jsdom-shaped test under them:

- **`display: contents` leaves flex and grid layout unchanged.** The original
  proposal says it was measured; it was not re-measured after the rule became
  `:where([data-c79-box])`.
- **`:where()` really does let `c79-panel { display: flex }` win.** Zero
  specificity is what the spec says; nothing here has watched it happen.
- **A component in table-row position is foster-parented out.** Tested through
  jq79's own parse, which is jsdom's.
- **A wrapper inside `<svg>` would take its children with it** - the reason
  decision 4 skips the box there. If this is wrong, the exception is unnecessary
  and a component inside an `<svg>` could have a box like everything else.

`.github/workflows/svg-attribute-names.yml` already runs three engines and is
the shape this wants: a page, a probe, a table printed even when it passes.
The four claims above are one page each.

## 2. The anchors are now redundant for a component, and only for a component

§4 of the previous list was waiting on the box. It has it.

`renderNestedComponent`'s own comment says why the anchors exist - the
instance's DOM is dynamic, so a caller that needs to move or remove the chunk
later holds the anchors instead of any of it. **The box is that handle, and it
is stable by construction**: `boundsOf` already resolves an element as
`{ first: el, last: el }`, and a component row in a `:each` now moves as one
node instead of a walked range.

So `<!--Name-->…<!--/Name-->` inside every box is four nodes per instance
(five with a conditional root) that nothing reads any more. Retiring them is a
real simplification with a real risk - `current?.destroy()` detaches the child's
*own* marker range from between them, and the swap path, hot reload and the
`:if`/`:each` ranges all touch this code. The anchors stay regardless for `:if`,
`:each` and `<template :slot>`, which mark ranges with no element of their own.

**Except in a foreign namespace**, where there is no box and the anchors are
still doing the whole job. Whatever this becomes has two cases now.

## 3. The version, and the shape of the pull request

Neither is a code question and both are the author's:

- **Two `feat!` commits and no version bump.** The migration note is four lines:
  a component tag out of table-row position; `<mychip>` no longer upgrading; a
  capitalized tag that resolves to nothing no longer falling back to the native
  element; and a component being an element in the DOM.
- **The plan said step 1 and step 2 should be two changes.** They are two
  commits on one branch, because that is where this session could push. Splitting
  them into two pull requests is still open.
- **PR #14's description is stale**: it describes step 1 only, and its inline
  code was stripped to empty backticks (`e.g. `` no longer becomes a ``
  element`), which is the same defect §7 of the previous list recorded for
  PR #13.

## 4. The costs step 2 introduced, which are documented but not lived with

None of these is a bug. They are the bill, and the next person to be surprised
by one should find it written down rather than discover it:

- **A component cannot style its own box.** The box belongs to the parent's
  template and carries the parent's stamp, so `c79-panel { display: flex }`
  inside Panel does nothing. Whether a component should be able to reach its own
  box - a `:host`-shaped selector, say - is a question nobody has asked yet.
- **Global CSS combinators stop crossing the boundary.** `.grid > .item` no
  longer matches an `.item` a component rendered. Scoped rules lose nothing.
- **A parent's `:empty` stops matching** when a child renders nothing, because
  the child is now an empty element rather than nothing.
- **A component named with no lowercase letter (`ABC`) cannot be styled by
  name**, since a shouty type selector stays an element in CSS.
- **A dashed usage site loses its own tag**: `<drop-area>` renders
  `<c79-drop-area>`, because the box is named after the component. Defensible,
  and a small loss of fidelity in the inspector.

## 5. The wrapper stylesheet is never released

`ensureWrapperStyle()` injects one `<style>` into `document.head` on the first
box and leaves it there - one rule, no refcount, deliberately. A page that ever
rendered a component keeps forty bytes of CSS after the last one is destroyed.
Recorded because the styles beside it *are* refcounted, so the asymmetry looks
like an oversight and is not.

## 6. Unchanged from the previous list, and still the right trade

- **`:attrs` writes a dead attribute without a word.** `{ strokeWidth: 4 }` on a
  foreign element writes an attribute SVG ignores as silently as a good one. The
  oracle already computes the signal. Still a diagnostic decision, not just work.
- **`:submit.prevent`** has a structural signal `plannableAttr` already computes
  and cannot fire on a legal binding. Small and safe. **`:iff`** has no
  structural signal at all and needs a near-miss table nobody has argued about.
- **`<annotation-xml>` stays off the clone path**, taking its `<math>` ancestor
  with it. Slower and correct.
- **`renders=8` never resolved**; the break-even curve needs a smaller chunk.
- **The order axis is differential only** - it compares the two paths against
  each other, so a change that reorders both identically still passes.

## 7. Housekeeping

- **The baseline moves at the next release**, as always. Both benchmark runs on
  this branch measured against 0.6.4.
- **`moveRangeAfter` still moves a reorder one node at a time**, and `swapRows`
  is still ~5-8ms depending on the runner. What changed is narrower than it
  looks: a *component* row is one node now, so its reorder is one
  `insertBefore`. The benchmark app's rows are plain `<tr>`s, so the number does
  not move.
- **jsdom and Chromium disagree about a component inside `<select>`** - jsdom
  drops an unknown child, Chromium 151 keeps it. This repo's tests are not
  authoritative about that position.
- **`tests/vitePlugin.test.ts` writes to a fixed bundle path**; two concurrent
  vitest processes would overwrite it mid-import. Latent, not a flake: CI is
  single-process.
- **The stress harness is still not in the repo.** If a flake shows up, the
  method is a shell loop per core plus repeated `npx vitest run`, then read
  *which assertion* failed.

## 8. The part none of this touches

Unchanged and still honest: `create1k` is ~24ms on the current runner where
Svelte is a fraction of that, and the remaining time is one effect per binding.
The two things ever priced against it - grouping a row's bindings, and dropping
`with` from expression evaluation - were both refused for good reasons. Closing
that gap is a claim about what the library is, not an optimization anybody has
left.

## Update, 2026-08-25: §1 is closed in one engine, and §4 grew a measurement

Somebody opened a browser: [`2026-08-25.open-a-browser.md`](2026-08-25.open-a-browser.md)
is the plan, [`2026-08-25.what-the-browser-said.md`](2026-08-25.what-the-browser-said.md)
the results. All four of §1's claims hold in Chromium 141, and the `<svg>` one
holds harder than it was argued: `display: contents` on an element SVG renders
itself computes to `none`, so the exception in `componentBox` is load-bearing
rather than cautious - deleting it turns a drawing into a blank. Firefox and
WebKit are the workflow's to answer; it has never run, exactly as the oracle's
had not the day it was written.

§4's costs are no longer deduced: a parent's `:empty` really does stop matching,
and nothing about flex or grid moves for anyone not styling `c79-*` themselves.

One thing outside every item on this list came out of it: a component whose
template root is a **bare SVG element** (`<circle>`, not `<svg>`) is created in
the HTML namespace and never draws, box or no box - the jsdom test that says "the
component still renders" is finding an element by name. Documented and pinned;
whether the library should re-namespace such a root to match its usage site is
open and nobody has argued it.
