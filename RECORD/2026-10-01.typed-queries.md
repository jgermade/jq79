# What `$` and `$self` return

**Status:** built the same day.

## The problem

`$`, `$$` (`src/dom.ts`) and the instance's `$self`, `$$self` (`renderWith` in
`src/jq79.ts`) are typed `Element | null` and `Element[]`. That is what
`querySelector` without a type argument says, and it is the honest answer for
a selector the type system can't read. But it makes the docs' own idiom an
error wherever a component is type-checked:

```js
await $mounted()
$self(".search").focus()       // setup-scripts.md - and: Property 'focus' does not exist on type 'Element'
```

The editor extension's checker ([2026-09-28.an-editor-extension.md](2026-09-28.an-editor-extension.md))
made this visible. Under `checkJs` the tutorial has four such errors: two
`focus`/`blur`, two `.value` on a textarea. The checker's own copy of the
types had to say `Element` to match the library, and the record left the
question open: "a change to the library's types, not to the checker".

## The proposal

The overloads `querySelector` has, with one different default:

```ts
$("input")                  // HTMLInputElement | null   - a tag name gives its element (HTML first, then SVG)
$("circle")                 // SVGCircleElement | null
$(".search")                // HTMLElement | null        - any other selector: HTMLElement, not Element
$<HTMLInputElement>(".q")   // HTMLInputElement | null   - or what you say it is
$$("li")                    // HTMLLIElement[]
```

The same for the element form (`$(el, selector)`), and for `$self` and
`$$self`, which are typed with the same call signatures. Those are exported
from `jq79` as `QueryOne` and `QueryAll`, so a factory can name them.

**The default is the decision.** `querySelector` defaults to `Element`
because it can't know. Neither can `$`. But a component's template is HTML,
and an element a component looks up is an HTML element almost every time. An
SVG one is found by its tag name, or said with the type argument. The cost is
that `$(".dot")` inside an `<svg>` claims to be an `HTMLElement` when it is an
`SVGElement`. That is the same lie libraries with this default tell. It shows
as a method that is missing at runtime (`.focus()` exists on both, `.click()`
does not), never as a type error. The alternative is the one we have: the
documented idiom is an error.

## What it costs

- **Types only.** No runtime change: the implementations are the same
  functions, so a page runs exactly what it ran.
- **For a TypeScript user, assignments to `Element` keep working.**
  `HTMLElement` is an `Element`. Code that narrowed by hand
  (`$(".x") as HTMLInputElement`) keeps compiling. Code that did
  `instanceof HTMLElement` checks becomes redundant, not wrong.
- **The checker copies the instance helpers' signatures**, as it already
  did, because they are not exported values it can take `typeof` of. The copy
  is checked against the library in its tests: a component typed through
  `jq79`'s own source gets the same answers.

## Rejected

- **Leaving `Element` and documenting a cast.** Every `$self(".x").focus()`
  in a typed component would need `as HTMLElement`, which in a JavaScript
  component means a JSDoc cast around a call. That is the docs contradicting
  the types.
- **`any`.** It drops the tag-name precision for nothing.
- **Inferring from the selector's text** (`"input.search"` → input). Template
  literal types could parse a leading tag name. It is clever, slow to type-check,
  and wrong for `"form input"`, where the element is the last compound. A tag
  name alone, as `querySelector` does it, is the rule people already know.

## Still open

- `.value` on `$self(".editor")` (a textarea found by class) still needs
  `$self("textarea")` or `$self<HTMLTextAreaElement>(".editor")`. That is
  the point of the type argument, not a gap.
