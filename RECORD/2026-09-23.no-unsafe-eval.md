# Running under a CSP without `'unsafe-eval'`

**Status:** plan, written before `src/` or `dev/` was touched. It starts from
a question, "can jq79 run without `unsafe-eval`?", whose answer today is *no*.
A decision was made the same day: **"no compiler" is not a principle, "no
bundle required" is.**

## The problem

Every piece of code a component carries reaches the engine through
`new Function`:

| What | Where ([`src/jq79.ts`](../src/jq79.ts)) | Compiled as |
|---|---|---|
| interpolations, directives, `@event` handlers, `:model` writes, prop and slot defaults | `compileScoped`, `compileWith` | a `const` prologue, or `with ($scope)` |
| setup scripts | `runSetupScript` | `with ($scope)`, sloppy, inside an async arrow |
| factory scripts | `runFactoryScript` | strict, no `with` |

On a page whose `script-src` lacks `'unsafe-eval'`, each of those throws
`EvalError`. Measured in jsdom, with `globalThis.Function` swapped for one that
throws the way a CSP does:

```
<p class="s">static</p>          -> renders
<p>{{ msg }}</p>                 -> "<p></p>", and nothing in the console
<script>let n = 1</script>...    -> mount() throws EvalError
```

The middle line is the worst of the three. `compileWith` catches everything and
caches it as a syntax error, so a page under CSP renders every binding empty and
says nothing about why.

Neither delivery mode avoids eval today. The Vite plugin is
[a loader, not a compiler](../docs/vite-plugin.md#a-loader-not-a-compiler): the
module it emits is `new Component79(src)` over the verbatim source, so a bundled
component evals exactly like a fetched one. A setup script also *cannot* move
into a module as it is written, because `with` is a SyntaxError in strict code
and every ES module is strict.

## The constraint, restated

The tagline has been "no compiler, no bundler". It now splits in two:

- **No bundle required** stays. A component must keep working from a static host
  with nothing but the browser's own module loader.
- **No compiler** goes. A per-file compile step is allowed: one `.html` in, one
  `.js` out next to it, with no module graph. That step is what CSP will cost.

The eval path stays exactly as it is. A page that allows eval keeps working
unchanged, with the CDN build and `Component79.fetch("/card.html")`. The
compiled path is an addition for pages that don't allow eval. The tutorial
compiles whatever its editor holds, so it will always be an eval page.

## The proposal

Compile each component to an ES module that carries, as function literals,
every function the runtime would otherwise build with `new Function`. The
runtime still parses the template at runtime: `DOMParser` is not eval, and CSP
doesn't govern it. The only change is that the runtime looks those functions up
instead of compiling them.

```
Card.html  ->  Card.html.js
```

```js
// Card.html.js - generated
import { Component79 } from "jq79"          // see Open: how this resolves
import __jq79_0 from "./Row.html.js"

export default new Component79(src, {
  filename: "Card.html",
  modules: { "./Row.html": __jq79_0 },
  compiled: {
    exprs: {
      "|msg": ($scope, $r) => { let $t; const msg = /* ... */; return (msg) },
      "$event|count++": ($scope, $r, $event) => /* ... */,
    },
    scripts: [function ($scope, $__effect, $__import, $__state /* , ...helpers */) { /* ... */ }],
  },
})
```

The output is served from any static host and imported natively, with no
bundler anywhere:

```js
// main.js, loaded by <script type="module" src="main.js"> under script-src 'self'
import App from "./App.html.js"
App.mount(document.body)
```

### What the runtime learns (a small change)

1. **A precompiled table in front of `new Function`.** `entryFor` already
   caches by `exprKey(expr, params)`, and that key is the source text, so a
   compiled definition's table can answer the same lookup. It needs its own
   map, because `Component79.debug()` clears `compiled` whenever `scopedNames`
   flips. A precompiled entry is also *exact* rather than heuristic: its
   `ReferenceError` is genuine, so it must never be demoted to `with`. Under a
   CSP there would be no `with` to demote it to anyway.
2. **Scripts as functions.** `runSetupScript` and `runFactoryScript` take the
   function the compiler emitted in place of a code string. Everything around
   the call stays the same: the scope proxy, the helpers, `$__state`, and
   `trackScript`.
3. **A loud miss.** An expression missing from the table falls through to
   `new Function`, which throws `EvalError` under a CSP. That error is caught
   and reported once, naming the expression, the CSP and the build command. It
   is not cached as a syntax error. This is worth shipping first and on its own,
   because it turns today's silent empty render into a message.

### What the compiler does (the real work)

The compiler lives in `dev/`. It runs on node, and `src/` must not import it.
It has three jobs.

**1. Find every function the runtime would build.** That means every
`(params, expr)` pair: interpolations, directives, `:each` lists and keys,
`:class.x`, `@event` handlers (`$event`), `:model` writes (`assignment(expr)`
with `$value`), `:setup` prop defaults and `:slot` defaults. It also means every
script block. The compiler must produce the same *keys* the renderer computes,
character for character, or the lookup misses. There are two ways to get there:

- reuse the runtime's own parse (`parseComponentString`) on node, under a DOM
  shim, plus a `bindingsOf(node)` exported from `src/` that returns what a
  node binds, written next to the directives it mirrors;
- write a second walker in `dev/`.

The first is the better choice, because drift between two walkers is exactly
the bug to avoid. A differential test keeps it honest. It renders every
component in the corpus with eval allowed, collects the keys the `compiled` map
actually filled, and asserts that `bindingsOf` returned each of them.

**2. Emit expressions without `with`.** The compiler emits the prologue form
that `compileScoped` builds today, which is already `with`-free, for reads.
`freeIdentifiers` refuses assignments, arrows, declarations and called names.
A real parser at build time (ESTree) can handle all of them:

- A name that is **written** (`count++`, `x = $value`) can't become a prologue
  `const`. The compiler rewrites it in place as a member of whichever object
  `with` would have found it on.
- A name that is **called** (`save()`) must keep its `this`. Under `with`, an
  unqualified call gets the scope object as `this` (checked: `with ($scope) {
  save() }` calls it with `this === $scope`). `const save = ...; save()` would
  make `this` undefined, which is why `freeIdentifiers` refuses called names
  today. The compiler emits a member call on the resolved object.
- Names **bound inside the expression**, such as arrow parameters, are left
  alone. A scanner couldn't guarantee that, and a parser can.

**3. Emit setup scripts without `with`.** This is the hard part, and the reason
the compiler needs a parser. `with ($scope)` in `runSetupScript` does four
things that a rewrite has to reproduce:

- **Resolution order.** The `has` trap on `scriptScope` decides it on every
  access: the store if it has the key, otherwise a helper (a function
  parameter), otherwise a global. A name found nowhere resolves to the
  *store*. So reading an undeclared name gives `undefined` rather than a
  `ReferenceError`, and assigning to one creates a store key. Both were
  checked: `typeof nothingHere` and `nothingHere` are both `undefined`, and
  `created = 5` renders as `{{ created }}`.
- **Implicit `this`** on unqualified calls, the same as for expressions.
- **Writes go through the store proxy's `set` trap.** That is what makes
  `fetchUser().then(u => { firstName = u.firstName })` reactive.
- **All of the above applies anywhere in the script.** A free identifier can sit
  in a nested function or a callback, and shadowing has to be right: params,
  block `let`, `var` and function hoisting, catch params, class names.

So the compiler runs `transformSetupScript` first, exactly as the runtime does,
then does a scope analysis of the result and rewrites every identifier that is
free in the whole script. Names the transform declares on the store become
`$scope.x` directly. Everything else goes through one resolver that follows the
`has` trap's order. `$__effect`, `$__import` and `$__state` stay parameters, as
they are today.

Factory scripts need none of this. They are already strict and `with`-free, so
the output of `transformFactoryScript` goes into the module verbatim, as a
function literal instead of a string. That is why they come first.

### Delivery, with no bundler anywhere

- **`npx jq79 build [dir]`** writes `x.html.js` next to every `x.html`. What
  gets deployed is still a directory of files.
- **`npx jq79 dev`** compiles on request. The server builds `/x.html.js` in
  memory from `/x.html`, so developing under a CSP needs no build command, and
  the `.html` stays the file you edit.
- **The Vite plugin** emits the same module instead of `new Component79(src)`,
  so a bundled app also works under a CSP with no extra step. The plugin already
  hoists `.html` imports into a `modules` map, which is exactly what the
  compiled module needs, so that code is shared.

## What it costs

- **Two semantics for the same source.** Every compiled function has an eval
  twin, and the two must agree. A differential run guards this. It runs the
  existing suite and the tutorial exercises in compiled mode, with
  `new Component79(src)` compiled on node and `globalThis.Function` blocked,
  against the same assertions. Anything the rewrite gets wrong fails a test
  that already exists.
- **Strict mode for setup scripts.** Modules are strict, and setup scripts run
  sloppy today. Several things change. Legacy octal literals and `with` in the
  author's own code stop parsing, and `delete name` becomes a syntax error. A
  write to a read-only property throws. A plain function called bare gets
  `this === undefined` instead of `globalThis` (checked: it is `globalThis`
  today). All of these are rare in a setup script, and all of them surface *at
  build time* with a file and line. That is better than today's runtime error
  inside an anonymous function.
- **Dependencies, in `dev/` only.** The compiler needs an ESTree parser: Vite's
  `parseAst` when running under Vite, `acorn` otherwise. The compile step's
  parse also needs a DOM. `src/` stays at zero dependencies. `jq79/dev` gains
  optional peers, the way it already has `vite`.
- **Output size.** Each distinct expression becomes a function literal, and the
  source string still ships, because the template is still parsed at runtime.
  The scripts' source could be stripped from that string.
- **The tagline.** The README, the package.json description and every doc's "No
  compiler, no bundler" banner change to "no bundler required", with the
  compiler described as the CSP path.

## Rejected

- **An expression interpreter in the runtime** (the approach of Alpine's CSP
  build). It needs no build step at all. But it puts a JS-expression parser and
  evaluator in the library, and runs the hottest loop through an interpreter
  instead of a JIT'd function. It accepts only a subset of JS, which the
  template docs would have to redefine. It also leaves setup scripts, the
  headline feature, uncovered, because interpreting whole programs is out of
  the question.
- **A classic-script sidecar that keeps `with`.** Classic scripts are sloppy,
  so the compiler could emit the runtime's own strings verbatim: identical
  semantics, and no parser needed. It is rejected for delivery. A classic
  script can't be `import`ed, so it needs a global registry and script-tag
  injection. Vite can't carry `with` inside a module at all. It remains the
  fallback if some construct turns out to resist the rewrite in job 3.
- **Compiling the template to DOM code** (the Svelte and Vue approach). That
  would remove `DOMParser` as well, but CSP never asked for that. It would also
  mean a second renderer to keep equal to the first.
  [The skeleton cloner](2026-08-24.clone-skeletons-measured.md) shows what one
  extra render path costs to keep honest.
- **`blob:` or `data:` module URLs** built from the source at runtime. Allowing
  them in `script-src` gives anyone who can inject text the same power that
  `'unsafe-eval'` does, so the CSP would be satisfied in letter only.
- **Detecting the CSP with a probe** (`try { new Function("") }`). On sites that
  collect CSP reports, every page load would file a violation. Instead, the
  error is caught when it actually happens.

## Order

0. The loud miss: catch `EvalError` and report it once. It is useful whatever
   happens to the rest of this plan.
1. The runtime hook: the `compiled` option, the precompiled map, and scripts as
   functions. It is tested with hand-written tables and `Function` blocked.
2. The compiler for expressions and factory scripts. From this step on, a
   component without a setup script runs under a CSP.
3. Setup scripts, with the differential run in place.
4. `jq79 build`, the dev server's `.html.js`, the Vite plugin, and the docs.

## Open

- **How the compiled module finds the runtime.** `import ... from "jq79"` is a
  bare specifier, so it needs an import map. An import map is an inline script,
  which a strict CSP admits only by hash or nonce. The alternatives are a
  `--runtime <url>` flag that the compiler writes into each module, or a module
  that exports plain data for the page to wrap (`new Component79(def)`). The
  second also suits the CDN global build.
- **Imports computed at runtime.** ``import(`./${name}.html`)`` in a script can't
  be hoisted. Under a CSP, `importResource` should map `.html` to `.html.js`
  for components that came from a compiled module.
- **Hot reload under a CSP.** `hotReplace(src)` recompiles in the browser.
  Under a CSP, the dev server would have to push a module URL to import
  (`/x.html.js?t=...`) instead of the source.
- **`<script lang="ts">`.** The Vite plugin compiles it through
  `transformWithEsbuild`. Without Vite, `jq79 build` either needs its own route
  for TypeScript or requires Vite for typed components.
- **Source maps.** A compiled module can carry a real source map back to the
  `.html`. That would finally give devtools the component's own line numbers
  (see [docs/setup-scripts.md](../docs/setup-scripts.md)). It isn't required,
  and it is cheap once the rewrite tracks positions.
- **`style-src`, which a strict CSP usually tightens as well.** A component's
  styles are injected as `<style>` elements, and `style-src` without
  `'unsafe-inline'` blocks those. This is separate from eval, but the same
  pages will run into it. The fix is either a nonce option or constructable
  stylesheets. Whether CSP governs constructable stylesheets still needs
  checking in a real browser.

## 2026-09-23, later: the `.html` keeps its name

**What changed:** in no-bundle mode, nothing is renamed from `.html` to `.js`.
The page keeps calling `Component79.fetch("/App.html")`, a script keeps writing
`import Row from "./row.html"`, and the `.html` stays the file that is deployed,
fetched and referenced. The proposal above had the author import
`./App.html.js`, and had the compiler rewrite every `.html` import to
`.html.js`. That part is superseded. The runtime hook, the compiler's three
jobs, the costs and the rejected list still hold. What changes is the shape of
the output, and who loads it.

**The output is a sidecar, not a replacement.** `jq79 build` leaves each
`x.html` untouched and writes `x.html.js` beside it. The sidecar is plain data:
the compiled functions, plus a hash of the source they were built from.

```
components/
  Card.html       <- unchanged: fetched, parsed, and referenced by this name everywhere
  Card.html.js    <- generated; the author never names it
```

```js
// Card.html.js - generated. It imports nothing
export default {
  source: "9f3c1a…",        // hash of the Card.html this was compiled from
  exprs: {
    "|msg": ($scope, $r) => { /* … */ },
    "$event|count++": ($scope, $r, $event) => { /* … */ },
  },
  scripts: [function ($scope, $__effect, $__import, $__state /* , ...helpers */) { /* … */ }],
}
```

**The runtime loads the sidecar.** In compiled mode, `fetchComponent(url)`
fetches `url` and imports `url + ".js"` in parallel. It already awaits the
fetch, so this adds no new asynchrony. It then checks the hash and registers
the tables before it builds the component. `import Row from "./row.html"` in a
script already goes through `importResource` to `fetchComponent`, so nested
components get their sidecars with no rewriting. That also covers an import
computed at runtime, ``import(`./${name}.html`)``, which was left open above.

```js
// main.js - the only place that knows about the CSP
Component79.compiled = true                    // the spelling is open, see below
Component79.fetch("/App.html").mount(document.body)
```

**A sidecar imports nothing.** Every function in it receives the runtime's
pieces as parameters, just as `new Function` receives them today: `$scope`,
`$r`, the helpers, and the setup-script resolver. So a sidecar needs no
`import "jq79"`, no import map, and no runtime URL. The first open question
above, how the compiled module finds the runtime, no longer comes up.

**A stale sidecar fails loudly.** If an `.html` is edited after the build, it
no longer matches the hash its sidecar recorded. The runtime then refuses the
sidecar and reports the file and `npx jq79 build`. It does not run an old
script against a new template. The dev server builds sidecars on request, so
during development they can't go stale. The hash only has to catch a rebuild
that someone forgot. `scopeHash` is 32-bit FNV. Whether that is wide enough,
or the check wants something wider, is open.

**Opt-in rather than detection.** The runtime can't know that a sidecar exists
without requesting it. On a page that allows eval, requesting one would cost a
404 and a console error for every component. Probing `new Function` stays
rejected, because of the violation reports. So compiled mode is declared once,
before the first fetch.

**Vite is unaffected.** In a bundle the author already writes
`import Card from "./Card.html"`. The plugin inlines the same tables into the
module it emits, and the sidecar's name never appears.

### Rejected, here

- **Compiling into the `.html` itself.** A fetched `.html` is text, and text
  becomes code only through eval. A file can be imported as a module only if
  it is served with a JavaScript MIME type, and a static host picks the MIME
  type from the file extension.
- **One manifest for the whole app**, meaning every component's tables in a
  single file that the page imports. It needs no opt-in, because importing it
  is the opt-in. But it loads every component's code up front, including code
  for components that are never fetched, and it is the first step toward a
  bundle.

### Open, updated

- **How the opt-in is spelled.** One option is a static switch in the entry
  module, as above. The other is a `<meta name="jq79" content="compiled">`,
  which is declarative, sits beside the CSP's own `<meta>`, and can be read
  before any script runs.
- **Components built from a string with no URL**, such as `new Component79(src)`
  in the page's own JS, have no sidecar to find. They need the Vite plugin or a
  table registered by hand. The runtime hook would expose that registration
  anyway.
- **Hot reload.** The dev server's push can name the sidecar to re-import
  (`x.html.js?t=…`) alongside the new source.
- **`<script lang="ts">` without a bundler** comes almost for free. If
  `jq79 build` compiles TypeScript, the sidecar carries the JS and the `.html`
  keeps the TS. Today `lang="ts"` works only through Vite.

## 2026-09-23, later still: no-bundle mode has no build step

**What changed:** no-bundle mode has no build step of any kind: no Vite, no
transpiler, and no `jq79 build`. Both sections above assumed a build step for
no-bundle mode, and that assumption is withdrawn. Two parts still stand. The
compiler plan now applies only to the Vite plugin, which can carry the
precompiled functions in the module it already emits. Step 0, the loud miss,
also stands.

**The limit.** Without a build, a component's code reaches the browser as text
inside the `.html`. A CSP without `'unsafe-eval'` exists precisely to stop text
from becoming code, so the runtime can't do that step itself. The only way left
is for the *browser* to load the code as a script. CSP judges a script by the
URL it comes from, not by what it contains. Two routes do that with no build
step. Both were checked in Chromium, with a page on which `new Function` throws
`EvalError`:

```
script-src 'self'          service worker script -> expression "hola", setup script count = 1
script-src 'nonce-r4nd0m'  <script nonce> inline -> expression "hola"
```

Both routes run *the same strings the runtime builds today*, `with` included,
because classic scripts are sloppy. So no-bundle mode needs none of the
compiler, the parser or the `with`-free rewrite described above, and it keeps
today's semantics exactly.

### 1. A service worker, for static hosts

A `jq79-sw.js` at the site root intercepts `x.html?jq79`. It reads `x.html`
from the origin and responds with a classic script that defines the
component's functions. The runtime loads that script with a `<script src>`, and
`script-src 'self'` admits it because the URL is same-origin. The `.html`
files, `Component79.fetch("/App.html")` and `import Row from "./row.html"` all
stay as they are today.

Costs:

- One more file, served from the site's own origin at the root. A service
  worker can't come from a CDN.
- HTTPS, with `localhost` as the exception.
- The first visit waits for the worker to activate.
- A hard reload (Shift+Reload) bypasses the worker, so that one load can't
  render.
- The worker must compile only text it fetched from the origin itself, and never
  text taken from the request. Otherwise an injected
  `<script src="/x.html?jq79&code=…">` becomes a CSP bypass.
- Workers have no `DOMParser`, so the worker can't enumerate the expressions
  itself. The page, which parses the template anyway, sends the list, and the
  worker checks every entry against the file it fetched.

### 2. A nonce, for server-rendered pages

If the page's CSP carries a nonce, jq79 creates a `<script nonce>` whose text is
the code and appends it. An inline script runs synchronously when it is
inserted, so this is a drop-in replacement for `new Function`, and a small
change. It only protects anything when the nonce changes on every response,
which takes a server. A static host serves the same nonce every time, and a
nonce that is known protects nothing. It is also text becoming code under a
different name: the page is trusting jq79 with its nonce.

### Rejected, here

**An interpreter inside jq79.** The reasons are the ones already given above:
its size, its speed on the hottest loop, and the fact that setup scripts would
need an interpreter for whole programs. It becomes the only option left if a
page can have neither a file at the site root nor a nonce.

### Recommendation

The service worker for static hosts, which is where no-bundle mode lives. The
nonce as a small addition for pages that already have one.

## 2026-09-23, the API: two explicit opt-ins, and the default untouched

**Decision (the user's):** the current behaviour stays exactly as it is, which
means eval by default. Running without `'unsafe-eval'` becomes an explicit
opt-in, and it can be spelled two ways:

```js
// vite.config
plugins: [jq79({ safeEval: true })]
```

```js
// no bundler
await Component79.safeEval()
Component79.fetch("/App.html").mount(document.body)
```

**Naming.** The Vite option was first written as `unsafeEval: true`. That reads
as the opposite of what it does, because today's default already needs
`'unsafe-eval'`. The proposal is to call it `safeEval` in both places. This is
open until confirmed.

**Where the two meet: one generator.** The generator is pure string code. It
turns a component's source into a *classic* script that defines the functions
the runtime would otherwise build. These are the same strings `new Function`
receives today, `with` included. Classic scripts are sloppy, so the semantics
are exact and nothing needs a JS parser.

The generator has to find every expression without a DOM, because a service
worker has no `DOMParser` and neither has node. It does this with a tokenizer
over attributes and text. The tokenizer runs after the runtime's own string
rewrites (`expandNameCase`, `expandPropsSpread`, `expandSelfClosingTags`). It is
checked against the `DOMParser` parse over the test corpus. The generator ships
to the browser inside the worker, so it lives in `src/`. The Vite plugin
imports it from there.

- **`Component79.safeEval()`** registers `jq79-sw.js`, served from the site
  root, and resolves once the worker controls the page, which is why it is
  async. From then on, `fetchComponent` also loads `x.html?jq79` with a
  `<script src>`. The worker fetches `x.html` itself and responds with the
  generator's output. The URL carries nothing but the path.
- **`jq79({ safeEval: true })`** runs the same generator at build time and emits
  its output as an asset. The component's module loads that asset before it
  constructs the component.

On both routes, the runtime consults a registry before `new Function`. In
safe mode, a miss never falls back to eval. It is reported once, naming the
expression.

**This supersedes the `with`-free rewrite, for now.** That is jobs 2 and 3 of
the compiler above. With classic scripts on both routes, nothing needs the
rewrite. It remains the way to drop the extra classic script from a Vite build,
if that ever matters.

**The limit.** In safe mode without Vite, only components that come from a file
work. `new Component79("<p>…</p>")` has no file for the worker to read, and a
worker that compiled text taken from the request would be a CSP bypass. The
nonce route, `safeEval({ nonce })`, has no such limit, for pages that have a
nonce per response.

**The default mode stays untouched.** One separate proposal: log a console error
when the CSP blocks eval, which is silent today, and point it at `safeEval`.
Whether that counts as touching the default is open.

**Order:**

1. The runtime registry and the safe-mode flag.
2. The generator and the tokenizer, with the differential check.
3. The worker and `safeEval()`.
4. The Vite option.

**Open:**

- How the Vite module waits for its asset. Top-level await is the plain answer,
  but the default build targets of Vite 5 and 6 predate it.
- How Vite's dev server serves that asset.
- Hot reload in safe mode.

## 2026-09-23, step 1 landed, and the plugin's option is `safeEval: true`

**The name is confirmed** as `jq79({ safeEval: true })` in Vite and
`await Component79.safeEval()` without it.

**What step 1 did.** The four `new Function` sites now go through one
`makeFunction(params, body, suffix)`. That function looks in a registry of
precompiled functions before it builds anything. The registry is fed by a global
queue, `self.__jq79precompiled`, which holds `[params, body, fn]` entries. The
runtime keys each entry itself, so the key format stays internal. The `//#
sourceURL` suffix is left out of the key: it depends on how the component was
loaded, and a generator couldn't spell it the way the runtime does.

`Component79.safeEval()` turns on a mode that never calls `new Function`. In
that mode, a missing expression is reported once and renders empty, and a
missing script throws, naming the file and the script's index. Without the
call, the only difference is that a registered function is used when one
exists, and it is the same function by construction. A page that registers
nothing takes the same path as before, because the key isn't even built.

`tests/safeEval.test.ts` records what the default mode passes to
`new Function`, precompiles exactly that, and renders again in safe mode with
`Function` blocked. The output is the same, clicks included. When lookup was
sabotaged to always miss, 4 of its 7 cases failed.

**Where a nonce belongs (proposed).** It does not belong in the plugin. A Vite
build can always precompile, and precompiling is stronger than a nonce, because
nothing is built at runtime. A nonce-only CSP without `'strict-dynamic'` would
still block the precompiled `<script src>` that jq79 injects. That can be fixed
without an option: jq79 copies the page's own nonce onto the script. The
`nonce` option belongs to `Component79.safeEval({ nonce })`, for no-bundle
pages served by something that issues a nonce per response.

## 2026-09-23, one vocabulary for both routes

**The API is standardized:** `safeEval` takes the same value in the plugin and
in the runtime.

```js
jq79({ safeEval: true })                      // Vite
jq79({ safeEval: { nonce: true } })           // Vite, on a page with a nonce
await Component79.safeEval()                  // no bundler, static host
await Component79.safeEval({ nonce: true })   // no bundler, page with a nonce
```

This supersedes the previous section's "the nonce doesn't belong in the plugin"
by giving `nonce` one meaning everywhere, which step 1 already has room for.
`makeFunction` looks up the precompiled registry *first*. The option only
decides what happens on a miss:

| | a hit (precompiled) | a miss |
|---|---|---|
| `true` | used | reported, never built |
| `{ nonce: true }` | used | built as a `<script nonce>` carrying the page's nonce |

- **With Vite**, both options precompile. `{ nonce: true }` adds a way through
  for whatever the build can't see: components built from strings at runtime,
  and edits during HMR.
- **Without Vite**, `true` gets its functions from the service worker, and a
  miss is reported. With `{ nonce: true }` there is no worker at all: nothing
  is precompiled, and every function is built through the nonce.

**Finding the nonce.** jq79 reads it from the page:
`document.querySelector("script[nonce]").nonce`. This was checked in Chromium,
under `script-src 'nonce-r4nd0m'` with the reading code loaded as a module:

- `document.currentScript` is `null`, because a module has no current script;
- `getAttribute("nonce")` returns `""`, because the browser hides it;
- the `.nonce` property returns `"r4nd0m"`;
- an inline script created with that value runs.

A CSP that works by nonce always has such a script, because it is the one that
loaded the page. The precompiled `<script src>` that jq79 injects on the `true`
route gets the same nonce, whenever there is one to copy. That keeps a nonce-only
CSP without `'strict-dynamic'` from blocking it, with no option needed.

**The difference between the two, stated plainly.** `true` never builds code in
the browser. `{ nonce: true }` does build code in the browser: it turns the
component's text into code, just as eval would. The difference is that only
jq79 can do it, because only jq79 holds the nonce. It is the right choice for a
page whose server issues a new nonce per response. On a static host, the nonce
never changes, and a nonce everyone knows protects nothing.

## 2026-09-23, `Component79.safeEval({ nonce: true })` landed

**How it works.** On a miss, `makeFunction` now calls `buildWithNonce`. It
inserts a classic `<script>` that carries the page's nonce, with the text laid
out the way `new Function` lays it out:
`function anonymous(params\n) {\nbody\n}` plus the same `//# sourceURL`.
Classic scripts are sloppy, so `with` compiles exactly as it does today. An
inline script runs synchronously when it is inserted, so this is a drop-in
replacement for `new Function`.

- **How the function comes back.** It comes back on the element itself
  (`document.currentScript`), not through a global.
- **Caching.** Built functions go into the precompiled map, so a setup script
  is built once, not once per instance.
- **Finding the nonce.** `pageNonce()` searches `script[nonce]` and reads the
  `.nonce` property. The attribute is only the fallback, for jsdom. With no
  nonce on the page, the promise rejects and safe mode stays on.

**Failures, told apart by what the insertion leaves behind:**

- **A syntax error** reaches window's `error` event, not the code that inserted
  the script. The listener takes it, cancels the report, and rethrows it where
  `new Function` threw. An expression renders empty and silent, and a script
  throws its `SyntaxError`, both as before.
- **A nonce the CSP refuses** leaves no function and no error event. That case
  is reported as "could not be built", without printing the nonce: a nonce has
  no business in a log.

**Checked two ways:**

- **In jsdom** (`tests/safeEval.test.ts`, 6 more cases). They cover where a
  miss goes, which nonce it carries, that nothing is left in `<head>`, one
  build per function across instances, precompiled functions winning, syntax
  errors, and a page with no nonce. jsdom runs an inserted script in a realm
  of its own, so these cases stay away from what that changes: an `instanceof
  ReferenceError`, and an async factory's promise. When the nonce was removed
  from the script, the first case failed. When the cache was removed, the
  second case failed.
- **In Chromium** (`npm run check:csp`, new). This serves `dist/jq79.js` with
  `script-src 'nonce-…'` and a fresh nonce per response, and fetches the
  component as a plain `.html` file. It makes three claims:
  - without `safeEval()`, mounting throws `'unsafe-eval' is not an allowed
    source`;
  - with `{ nonce: true }`, the component renders and reacts to clicks, `$:`
    included, with no CSP violation and no console error;
  - a decoy `<script nonce>` placed ahead of the real one gets the "refused"
    message.

  When the nonce was removed from the script, the four `nonce` claims failed.

**Known differences from `new Function`:**

- **A body that closes the function's brace early.** `new Function` refuses
  it; a script runs whatever comes after the brace. That text is the
  component's own, and a component can hold a `<script>` anyway, so this
  admits nothing a component couldn't already do.
- **One `<script>` insertion per distinct function**, the first time that
  function is needed. This has not been measured.

**Open:**

- **Trusted Types.** Under `require-trusted-types-for 'script'`, assigning
  `textContent` throws. Nothing handles that yet.
- **`jq79({ safeEval: { nonce: true } })` doesn't exist yet.** The generator
  isn't needed for it: until there is one, every function is a miss, and every
  miss is built with the nonce. So the plugin could ship this form now, if its
  modules call the runtime's `safeEval({ nonce: true })`.
- **Documentation.** User docs wait for the API to be complete: the service
  worker and the Vite option.
