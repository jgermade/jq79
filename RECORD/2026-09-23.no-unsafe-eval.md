# Running under a CSP without `'unsafe-eval'`

**Status:** plan, written before `src/` or `dev/` was touched. It starts from
a question, "can jq79 run without `unsafe-eval`?", whose answer today is *no*.
A decision was made the same day: **"no compiler" is not a principle, "no
bundle required" is.**

## The problem

Every piece of code a component carries reaches the engine through
`new Function`:

| What | Where ([`src/jq79.ts`](../src/jq79.ts)) | Compiled as |
|---|---|---|
| interpolations, directives, `@event` handlers, `:model` writes, prop and slot defaults | `compileScoped`, `compileWith` | a `const` prologue, or `with ($scope)` |
| setup scripts | `runSetupScript` | `with ($scope)`, sloppy, inside an async arrow |
| factory scripts | `runFactoryScript` | strict, no `with` |

On a page whose `script-src` lacks `'unsafe-eval'`, each of those throws
`EvalError`. Measured in jsdom, with `globalThis.Function` swapped for one that
throws the way a CSP does:

```
<p class="s">static</p>          -> renders
<p>{{ msg }}</p>                 -> "<p></p>", and nothing in the console
<script>let n = 1</script>...    -> mount() throws EvalError
```

The middle line is the worst of the three. `compileWith` catches everything and
caches it as a syntax error, so a page under CSP renders every binding empty and
says nothing about why.

Neither delivery mode avoids eval today. The Vite plugin is
[a loader, not a compiler](../docs/vite-plugin.md#a-loader-not-a-compiler): the
module it emits is `new Component79(src)` over the verbatim source, so a bundled
component evals exactly like a fetched one. A setup script also *cannot* move
into a module as it is written, because `with` is a SyntaxError in strict code
and every ES module is strict.

## The constraint, restated

The tagline has been "no compiler, no bundler". It now splits in two:

- **No bundle required** stays. A component must keep working from a static host
  with nothing but the browser's own module loader.
- **No compiler** goes. A per-file compile step is allowed: one `.html` in, one
  `.js` out next to it, with no module graph. That step is what CSP will cost.

The eval path stays exactly as it is. A page that allows eval keeps working
unchanged, with the CDN build and `Component79.fetch("/card.html")`. The
compiled path is an addition for pages that don't allow eval. The tutorial
compiles whatever its editor holds, so it will always be an eval page.

## The proposal

Compile each component to an ES module that carries, as function literals,
every function the runtime would otherwise build with `new Function`. The
runtime still parses the template at runtime: `DOMParser` is not eval, and CSP
doesn't govern it. The only change is that the runtime looks those functions up
instead of compiling them.

```
Card.html  ->  Card.html.js
```

```js
// Card.html.js - generated
import { Component79 } from "jq79"          // see Open: how this resolves
import __jq79_0 from "./Row.html.js"

export default new Component79(src, {
  filename: "Card.html",
  modules: { "./Row.html": __jq79_0 },
  compiled: {
    exprs: {
      "|msg": ($scope, $r) => { let $t; const msg = /* ... */; return (msg) },
      "$event|count++": ($scope, $r, $event) => /* ... */,
    },
    scripts: [function ($scope, $__effect, $__import, $__state /* , ...helpers */) { /* ... */ }],
  },
})
```

The output is served from any static host and imported natively, with no
bundler anywhere:

```js
// main.js, loaded by <script type="module" src="main.js"> under script-src 'self'
import App from "./App.html.js"
App.mount(document.body)
```

### What the runtime learns (a small change)

1. **A precompiled table in front of `new Function`.** `entryFor` already
   caches by `exprKey(expr, params)`, and that key is the source text, so a
   compiled definition's table can answer the same lookup. It needs its own
   map, because `Component79.debug()` clears `compiled` whenever `scopedNames`
   flips. A precompiled entry is also *exact* rather than heuristic: its
   `ReferenceError` is genuine, so it must never be demoted to `with`. Under a
   CSP there would be no `with` to demote it to anyway.
2. **Scripts as functions.** `runSetupScript` and `runFactoryScript` take the
   function the compiler emitted in place of a code string. Everything around
   the call stays the same: the scope proxy, the helpers, `$__state`, and
   `trackScript`.
3. **A loud miss.** An expression missing from the table falls through to
   `new Function`, which throws `EvalError` under a CSP. That error is caught
   and reported once, naming the expression, the CSP and the build command. It
   is not cached as a syntax error. This is worth shipping first and on its own,
   because it turns today's silent empty render into a message.

### What the compiler does (the real work)

The compiler lives in `dev/`. It runs on node, and `src/` must not import it.
It has three jobs.

**1. Find every function the runtime would build.** That means every
`(params, expr)` pair: interpolations, directives, `:each` lists and keys,
`:class.x`, `@event` handlers (`$event`), `:model` writes (`assignment(expr)`
with `$value`), `:setup` prop defaults and `:slot` defaults. It also means every
script block. The compiler must produce the same *keys* the renderer computes,
character for character, or the lookup misses. There are two ways to get there:

- reuse the runtime's own parse (`parseComponentString`) on node, under a DOM
  shim, plus a `bindingsOf(node)` exported from `src/` that returns what a
  node binds, written next to the directives it mirrors;
- write a second walker in `dev/`.

The first is the better choice, because drift between two walkers is exactly
the bug to avoid. A differential test keeps it honest. It renders every
component in the corpus with eval allowed, collects the keys the `compiled` map
actually filled, and asserts that `bindingsOf` returned each of them.

**2. Emit expressions without `with`.** The compiler emits the prologue form
that `compileScoped` builds today, which is already `with`-free, for reads.
`freeIdentifiers` refuses assignments, arrows, declarations and called names.
A real parser at build time (ESTree) can handle all of them:

- A name that is **written** (`count++`, `x = $value`) can't become a prologue
  `const`. The compiler rewrites it in place as a member of whichever object
  `with` would have found it on.
- A name that is **called** (`save()`) must keep its `this`. Under `with`, an
  unqualified call gets the scope object as `this` (checked: `with ($scope) {
  save() }` calls it with `this === $scope`). `const save = ...; save()` would
  make `this` undefined, which is why `freeIdentifiers` refuses called names
  today. The compiler emits a member call on the resolved object.
- Names **bound inside the expression**, such as arrow parameters, are left
  alone. A scanner couldn't guarantee that, and a parser can.

**3. Emit setup scripts without `with`.** This is the hard part, and the reason
the compiler needs a parser. `with ($scope)` in `runSetupScript` does four
things that a rewrite has to reproduce:

- **Resolution order.** The `has` trap on `scriptScope` decides it on every
  access: the store if it has the key, otherwise a helper (a function
  parameter), otherwise a global. A name found nowhere resolves to the
  *store*. So reading an undeclared name gives `undefined` rather than a
  `ReferenceError`, and assigning to one creates a store key. Both were
  checked: `typeof nothingHere` and `nothingHere` are both `undefined`, and
  `created = 5` renders as `{{ created }}`.
- **Implicit `this`** on unqualified calls, the same as for expressions.
- **Writes go through the store proxy's `set` trap.** That is what makes
  `fetchUser().then(u => { firstName = u.firstName })` reactive.
- **All of the above applies anywhere in the script.** A free identifier can sit
  in a nested function or a callback, and shadowing has to be right: params,
  block `let`, `var` and function hoisting, catch params, class names.

So the compiler runs `transformSetupScript` first, exactly as the runtime does,
then does a scope analysis of the result and rewrites every identifier that is
free in the whole script. Names the transform declares on the store become
`$scope.x` directly. Everything else goes through one resolver that follows the
`has` trap's order. `$__effect`, `$__import` and `$__state` stay parameters, as
they are today.

Factory scripts need none of this. They are already strict and `with`-free, so
the output of `transformFactoryScript` goes into the module verbatim, as a
function literal instead of a string. That is why they come first.

### Delivery, with no bundler anywhere

- **`npx jq79 build [dir]`** writes `x.html.js` next to every `x.html`. What
  gets deployed is still a directory of files.
- **`npx jq79 dev`** compiles on request. The server builds `/x.html.js` in
  memory from `/x.html`, so developing under a CSP needs no build command, and
  the `.html` stays the file you edit.
- **The Vite plugin** emits the same module instead of `new Component79(src)`,
  so a bundled app also works under a CSP with no extra step. The plugin already
  hoists `.html` imports into a `modules` map, which is exactly what the
  compiled module needs, so that code is shared.

## What it costs

- **Two semantics for the same source.** Every compiled function has an eval
  twin, and the two must agree. A differential run guards this. It runs the
  existing suite and the tutorial exercises in compiled mode, with
  `new Component79(src)` compiled on node and `globalThis.Function` blocked,
  against the same assertions. Anything the rewrite gets wrong fails a test
  that already exists.
- **Strict mode for setup scripts.** Modules are strict, and setup scripts run
  sloppy today. Several things change. Legacy octal literals and `with` in the
  author's own code stop parsing, and `delete name` becomes a syntax error. A
  write to a read-only property throws. A plain function called bare gets
  `this === undefined` instead of `globalThis` (checked: it is `globalThis`
  today). All of these are rare in a setup script, and all of them surface *at
  build time* with a file and line. That is better than today's runtime error
  inside an anonymous function.
- **Dependencies, in `dev/` only.** The compiler needs an ESTree parser: Vite's
  `parseAst` when running under Vite, `acorn` otherwise. The compile step's
  parse also needs a DOM. `src/` stays at zero dependencies. `jq79/dev` gains
  optional peers, the way it already has `vite`.
- **Output size.** Each distinct expression becomes a function literal, and the
  source string still ships, because the template is still parsed at runtime.
  The scripts' source could be stripped from that string.
- **The tagline.** The README, the package.json description and every doc's "No
  compiler, no bundler" banner change to "no bundler required", with the
  compiler described as the CSP path.

## Rejected

- **An expression interpreter in the runtime** (the approach of Alpine's CSP
  build). It needs no build step at all. But it puts a JS-expression parser and
  evaluator in the library, and runs the hottest loop through an interpreter
  instead of a JIT'd function. It accepts only a subset of JS, which the
  template docs would have to redefine. It also leaves setup scripts, the
  headline feature, uncovered, because interpreting whole programs is out of
  the question.
- **A classic-script sidecar that keeps `with`.** Classic scripts are sloppy,
  so the compiler could emit the runtime's own strings verbatim: identical
  semantics, and no parser needed. It is rejected for delivery. A classic
  script can't be `import`ed, so it needs a global registry and script-tag
  injection. Vite can't carry `with` inside a module at all. It remains the
  fallback if some construct turns out to resist the rewrite in job 3.
- **Compiling the template to DOM code** (the Svelte and Vue approach). That
  would remove `DOMParser` as well, but CSP never asked for that. It would also
  mean a second renderer to keep equal to the first.
  [The skeleton cloner](2026-08-24.clone-skeletons-measured.md) shows what one
  extra render path costs to keep honest.
- **`blob:` or `data:` module URLs** built from the source at runtime. Allowing
  them in `script-src` gives anyone who can inject text the same power that
  `'unsafe-eval'` does, so the CSP would be satisfied in letter only.
- **Detecting the CSP with a probe** (`try { new Function("") }`). On sites that
  collect CSP reports, every page load would file a violation. Instead, the
  error is caught when it actually happens.

## Order

0. The loud miss: catch `EvalError` and report it once. It is useful whatever
   happens to the rest of this plan.
1. The runtime hook: the `compiled` option, the precompiled map, and scripts as
   functions. It is tested with hand-written tables and `Function` blocked.
2. The compiler for expressions and factory scripts. From this step on, a
   component without a setup script runs under a CSP.
3. Setup scripts, with the differential run in place.
4. `jq79 build`, the dev server's `.html.js`, the Vite plugin, and the docs.

## Open

- **How the compiled module finds the runtime.** `import ... from "jq79"` is a
  bare specifier, so it needs an import map. An import map is an inline script,
  which a strict CSP admits only by hash or nonce. The alternatives are a
  `--runtime <url>` flag that the compiler writes into each module, or a module
  that exports plain data for the page to wrap (`new Component79(def)`). The
  second also suits the CDN global build.
- **Imports computed at runtime.** ``import(`./${name}.html`)`` in a script can't
  be hoisted. Under a CSP, `importResource` should map `.html` to `.html.js`
  for components that came from a compiled module.
- **Hot reload under a CSP.** `hotReplace(src)` recompiles in the browser.
  Under a CSP, the dev server would have to push a module URL to import
  (`/x.html.js?t=...`) instead of the source.
- **`<script lang="ts">`.** The Vite plugin compiles it through
  `transformWithEsbuild`. Without Vite, `jq79 build` either needs its own route
  for TypeScript or requires Vite for typed components.
- **Source maps.** A compiled module can carry a real source map back to the
  `.html`. That would finally give devtools the component's own line numbers
  (see [docs/setup-scripts.md](../docs/setup-scripts.md)). It isn't required,
  and it is cheap once the rewrite tracks positions.
- **`style-src`, which a strict CSP usually tightens as well.** A component's
  styles are injected as `<style>` elements, and `style-src` without
  `'unsafe-inline'` blocks those. This is separate from eval, but the same
  pages will run into it. The fix is either a nonce option or constructable
  stylesheets. Whether CSP governs constructable stylesheets still needs
  checking in a real browser.
