# Retire the anchors, where there is a box to replace them

**Status:** plan, written before `src/` was touched. It takes §2 of
[`2026-08-25.open-after-the-box.md`](2026-08-25.open-after-the-box.md), which
had been waiting on the box and now has it.

---

## The problem

`renderNestedComponent` opens with two comment nodes and a reason:

```ts
// two anchors bracketing everything this usage site ever renders: the
// instance's DOM is dynamic (the definition can resolve late or be swapped),
// so a caller that needs to move or remove this chunk later can't hold any
// of it - it holds the anchors, which never move on their own
```

Every word of that is still true, and it is now a description of **the box**.
`boundsOf` resolves an element as `{ first: el, last: el }`, the box is created
once per usage site and never replaced, and a component row in a `:each` already
moves as one node. So the anchors mark a range whose ends nothing reads.

Measured, on the built bundle in Chromium: a box today holds **five nodes** -
`<!--Name-->`, the child's own `<!--jq79-->`, its content, `<!--/jq79-->`,
`<!--/Name-->`. Three of those are the child's and are load-bearing (`detach`
walks marker to marker; `hotReplace` re-inserts at `endMarker.nextSibling`). Two
are the parent's, and are the subject here.

## The proposal

Create the anchors **only where `componentBox` returns a fragment** - a usage
site in a foreign namespace, where there is no box and they are still doing the
whole job. Where there is a box, the instance's DOM is appended to it directly
instead of inserted before an end anchor.

That is the entire change: one branch at the top of `renderNestedComponent`, and
one at its insertion point. `renderSlot` keeps its pair unconditionally - a
`<slot>` has no element of its own, which is the same reason the foreign case
keeps its own.

## What was checked before proposing it

Every consumer of that range, read rather than remembered:

- **`destroy()` → `detach()`** walks the child's *own* `startMarker` to
  `endMarker`, so removing a child's DOM never touched the parent's anchors.
- **`hotReplace`** computes `parent` and `before` from the child's own markers
  too (`marker.parentNode`, `endMarker.nextSibling`), which with a box is the box
  and `null`.
- **`$emit`** dispatches from the child's start marker and bubbles through the
  box like any element.
- **`boundsOf`** is the whole argument: an element resolves to itself.
- **`:if` and `:each`** hold what `renderNode` returned, which is the box.

## What it is worth

Two comment nodes per instance, so **five nodes inside a box become three**.

Two paired A/B runs, two builds alternating in one session, 1,000 component
instances per render, warm-up discarded:

| run | rounds | paired median (A − B) | rounds B won |
| --- | --- | --- | --- |
| 1 | 40 | +2.2 ms | 26 of 40 |
| 2 | 80 | +2.7 ms | 53 of 80 |

Both favour the change, and the sign replicates. **It is not a 6% claim**: the
round-to-round spread is 57-80 ms, twenty times the delta, so no single reading
says anything. What survives is the direction, twice, and ~2.5 µs per instance -
which is roughly what two `createComment` calls and two appends cost, and is
about 5% of the ~49 µs an instance costs in total.

So this is a simplification that pays a little, not an optimization. The reason
to do it is that the comment says the anchors exist to be a handle nobody holds.

## The risk, and where it actually is

**Nothing in the suite pins the anchors.** The probe patch above was run against
all 15 files: **927 tests, all passing, unchanged**. That is not reassurance -
it is the finding. Either they are redundant (which is the claim) or the tests
cannot see the difference, and a change nobody's checks can fail is exactly what
this branch has been writing down since PR #13.

So the change ships with checks that *would* have failed, per the house rule:

| claim | sabotage that must turn it red |
| --- | --- |
| a boxed instance's DOM lands inside its own box | append it to the box's parent instead |
| a boxed usage site renders no anchor comments | create them anyway |
| a foreign-namespace usage site still gets both anchors | drop them there too |
| a swapped definition replaces the DOM inside the same box | insert without removing |
| hot reload re-renders into the same box | - |
| a component row still moves as one node on reorder | (exists) |

## What was rejected

- **Retiring them everywhere.** A foreign-namespace usage site has no box by
  decision 4 of the wrapper plan - measured this session in three engines: a box
  inside `<svg>` computes `display: none` and takes the drawing with it. There
  the anchors are the only handle, so they stay, and the code has two cases.
- **One anchor instead of two.** A single marker would still need a walk to find
  the end of the chunk, which is what `removeRange` does today with two. It saves
  one node and keeps the mechanism.
- **A debug flag to keep the old shape.** Two shapes means two shapes to test,
  for a change whose whole point is that one of them is redundant.
- **Doing the same to `renderSlot`.** It has no element to be the handle. The
  invisible wrapper it renders is a separate open item and stays open.

## What is still open after it

- The **invisible wrapper** (`<template :slot>` and friends) still marks ranges
  with comments, and `boundsOf` still breaks on an empty fragment. Untouched.
- Whether a component's box should be reachable from its own `<style scoped>`
  (a `:host`-shaped selector). Still nobody's asked.

## Update, 2026-08-25: implemented, and one sabotage that could not reach its check

Two branches, as planned. `renderNestedComponent` asks whether `componentBox`
gave it an element; a boxed site creates no anchors and appends the instance's
DOM to the box, a foreign-namespace site keeps the pair and inserts before the
end anchor. Nothing else moved. **927 tests became 932.**

The end anchor is still read as `endAnchor.parentNode` rather than captured,
and the reason is worth keeping: before this usage site is inserted, that parent
is the fragment; after, it is whatever the fragment was inserted into.

### The five checks, and the four sabotages

| check | sabotage | went red |
| --- | --- | --- |
| a boxed instance renders only its own two markers | create the anchors anyway | yes |
| a foreign-namespace site keeps both anchors | treat every site as boxed | yes |
| a swap replaces the DOM inside the same box | insert into the box's parent | yes |
| a late definition lands in the box already there | the same | yes |
| hot reload re-renders inside the same box | (see below) | yes, on the fourth |

**The third sabotage did not reach the hot-reload check, and that is the
interesting part.** Appending to `wrapper.parentNode ?? wrapper` breaks only a
render that happens *after* the box is attached - during the first render the box
has no parent yet, so it fell back to the box and the initial insertion was
correct. The swap and late-resolution checks went red; the hot-reload one passed
under a sabotage that was supposed to break it.

So it got its own: `hotReplace` re-inserting at the box's parent rather than the
box. Red, along with "stays where it was mounted, among its siblings", which is
the check that has been guarding that line since before any of this.

The lesson is the one this branch keeps relearning, one level in: **a sabotage
proves a check can fail only for the failure that sabotage actually causes**.
Three checks going red together says nothing about the fourth.

### What the suite could not see

Worth writing down plainly, because it is the reason this change shipped with
five new checks rather than none: with the anchors retired and **nothing else
touched, all 927 existing tests passed**. Not one of them could tell whether a
component renders two comment nodes it never reads.

### The benchmark ran, and could not have been measuring this

`regressions: []` on an EPYC 9V45, every operation inside the runner's noise
except one: **create1k, +6.1%, slower in all four rounds, under a ±9.4% noise
band**.

Four rounds agreeing on the sign is the report's own "supporting evidence, not
proof - 4 coin flips land the same way 12.5% of the time". But there is a
stronger argument here than the statistics, and it is structural: **the whole
`src/` diff is inside `renderNestedComponent`, and the benchmark app never calls
it.** `frameworks/keyed/jq79/src/App.html` is 67 lines with no component tag in
it - checked, not remembered. No operation in that table can execute a line of
this change.

So the delta is unattributable to the diff by construction. What is left is
bundle layout perturbing the JIT, which nobody here can measure, and the
runner's own spread, which the report already names. One build against itself
has swung -23% to +50% on create1k
([`2026-08-23.where-the-create-time-goes.md`](2026-08-23.where-the-create-time-goes.md)).

The same fact cuts the other way, and that is the honest half: **the benchmark
cannot confirm the ~2.5 µs per instance either**. It is the same hole step 2 hit
with the box, recorded then and still true - anyone who wants that number in this
repo's table has to write the app that pays it: one with nested components in
the rows.
