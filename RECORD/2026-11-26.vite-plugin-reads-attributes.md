# The Vite plugin reads a tag's attributes, not a regex over them

## 2026-11-26 — the bug

Found in a consumer (doomus-rs): a component with a prop called `lang` that has a
default,

```html
<script :setup="{ email = '', lang = 'en' }" lang="ts">
```

reached the browser uncompiled, and the runtime warned that `<script lang="ts">`
needs the plugin. `typescriptAttr` looked the mark up with
`/\blang\s*=\s*(…)/` over the whole attribute string, and the first match is the
one *inside* the `:setup` value: `lang = 'en'`. `en` is not TypeScript, so the
block was left alone. Had it matched, `attrs.replace(LANG_ATTR_RE, "")` would have
cut the wrong `lang` too - out of the signature. `type` (`type = 'x'` in a
signature) and `<style lang>` had the same flaw, and so did `:setup` itself
(a `:setup=` inside another attribute's value).

The editor extension and the runtime were never affected: the extension reads
attributes with a real scanner (`readAttrs` in `editors/vscode/src/component.ts`)
and the runtime reads the parsed DOM.

## The fix

`dev/vite.ts` gets a small attribute reader, `readAttrs`: name, then an optional
`=` and a double-quoted, single-quoted or bare value - the HTML parser's reading -
with each attribute's span, so it is removed (or rewritten, for `:setup`) by
position. `lang`, `type` and `:setup` are looked up by exact (lowercased) name.
The emitted tag is unchanged for every case the tests already covered.

Tests: a `lang` + `type` prop with defaults in front of `lang="ts"` (compiled, only
the mark dropped, the signature intact), a `lang = 'ts'` inside a value with no
real `lang` (left byte-for-byte), and unquoted / single-quoted / uppercase marks.

## Not changed

`editors/vscode/src/literal.ts` still spots TypeScript in a *page's* `<script>`
(not a component's) with `TS_MARK_RE`, a regex of the same kind. A page script has
no `:setup`, so the false match needs an attribute value that literally contains
`lang=ts`; left as is, worth aligning if that reader is ever touched.
