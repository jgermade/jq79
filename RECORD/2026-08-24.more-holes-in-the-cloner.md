# More holes in the cloner

**Status:** proposal, then implementation. Takes §1 and §6 of
[`2026-08-24.what-is-still-open.md`](2026-08-24.what-is-still-open.md) in the
order that file recommends, and fixes a divergence found on the way in.

Not §2 (`<svg>`), §3 (`:each` + `:if`) or §5 (the per-definition instrument):
each of those is a decision or an instrument, and this is the part that is
neither.

---

## The problem

`plannableAttr` admits four things - a static attribute, `@event`,
`:class`/`:class.<name>`, and a single `:<name>` binding. Every other attribute
makes its subtree unplannable, which is the right default and also means a
template using `:text`, `:attrs`, `:value`, `:checked` or `:selected` gets
nothing from the clone path *for the whole subtree containing it*, not just for
that element. One `:text` in a row costs the row.

Widening an allowlist is the change most likely to introduce the bug the
allowlist exists to prevent, so the order below is the point as much as the
code is.

## What was already wrong: `:model`

Found while reading `plannableAttr` against renderNode, not while measuring.

`:model` is **not in `CONTROL_ATTRS`**. `:model.<name>` contains a dot and is
rejected by the last clause, but bare `:model` is not, so `plannableAttr`
accepts it as if it were a generic `:<name>` binding and `buildSkeleton` emits
an `attr` op for it. renderNode does something else entirely: `:model` binds
component tags only, and on a plain element it warns and binds nothing.

```
<div class="w"><span class="p">uno</span><input class="q" :model="who" /><span class="r">dos</span></div>
```

interpreted: `<input class="q">`
cloned:      `<input class="q" model="ada">`

The differential test did not catch it because its `:model` entry puts the
directive on a **component tag**, which is unplannable for a different reason -
so the case that diverges was the one nobody wrote down. Every corpus entry that
proves a directive falls through has to put it on a tag that would otherwise be
planned; that one did not.

Fixed by naming `:model` in the rejection rather than leaning on
`isControlAttr`, with a corpus entry on a plain `<input>`.

## Op order first (§6)

The differential test diffs the DOM, and reversing `plan.ops` changes no DOM
today because no admitted directive has an observable registration order. That
stops being true the moment `:value` lands: `:value` on a `<select>` has to run
after its `<option>`s exist, so the cloner has to grow an "after the children"
phase, and nothing in the test would notice if it did not.

So the test grows a second axis **before** the form-state holes, not after.

The instrument is a scope whose values are getters that log their own name:

```js
const raw = {}
Object.defineProperty(raw, "a", { get() { log.push("a"); return v }, ... })
```

Every effect evaluates its expression when it is registered, and every
expression resolves its names through the store proxy onto that raw object, so
**the read log is the registration order** as long as each binding in a template
reads a distinct name. It needs no hook into `fx.effect` and no export the
library would not otherwise have.

Rejected: spying on `fx.effect`. `EffectScope` is internal, the spy would have
to be installed from inside `src/`, and it would prove the order of the
*registration calls* rather than the order the expressions actually run in.
Rejected: snapshotting `plan.ops`. It only describes one of the two paths, so it
cannot diff them - and the whole value of this test is that it compares.

## The holes, in this order

- **`:text`** - a leaf, and the simplest op there is. The one thing it is not
  is a hole in a node with children: renderNode's `:text` branch replaces the
  element's content, and the children are never rendered. So a `:text` node is a
  leaf on *both* sides - `plannableNode` stops recursing there, `buildSkeleton`
  emits no children for it, and `countElements` does not count children the
  interpreted path would never build.
- **`:attrs`** - one effect that rewrites a key set, the same shape as the
  `attr` op with renderNode's body copied verbatim. It registers between the
  attribute walk and `:class`, which is where renderNode registers it.
- **`:value` / `:checked` / `:selected`** - registered **after** the subtree's
  children. `buildSkeleton` is recursive and `ops` is a flat list in
  registration order, so pushing these after the children loop gives exactly
  renderNode's order, for the same reason and by the same mechanism: a parent's
  ops land after every op of every descendant.

**`:html` is deliberately not on the list.** `:html.allowed` is a second
attribute feeding the same effect, and the warning renderNode emits for an
`:html.allowed` with no `:html` fires once per *render* there and would fire
once per *definition* here. That is a real difference in observable behaviour
for a directive whose whole job is sanitizing untrusted input, and it deserves
its own decision rather than a slot in a list of five.

`:if` and `:each` remain off the list for the reason the previous file gave:
they change the shape rather than filling a hole.

## What it costs

Nothing on the benchmark. `frameworks/keyed/jq79/src/App.html` uses `@click`,
`:class` and interpolation and none of the five directives admitted here, so
`create1k` cannot move and no `benchmark:ab` run would say anything about this
change. Claiming a number here would mean changing the benchmark row, and that
row is a comparison against other frameworks' rows, not a fixture.

What it buys is a claim about *coverage*, not speed: a row carrying a `:text` or
a bound `<input>` goes from "the whole subtree is interpreted" to "planned, with
one more op". The per-op cost is one entry in a flat array and one `atPath`
walk, which is what every existing hole costs.

`plannableAttr` gains a set lookup, on a path that runs once per definition.

## Two things the ops loop got on the way

Neither was in the plan; both are the kind of thing that only shows up once the
branches are written.

- **The chain is ordered by frequency, not by history.** `renderFromSkeleton`
  matches `op.kind` once per op per instance, so five new branches inserted
  ahead of `class` would have made every `:class` in every row of a 1,000-row
  list walk five extra comparisons to reach the body it wanted. Nothing
  measurable - but the ordering is free, and free is cheaper than measurable.
- **The chain now ends in a `never`, not in `class`.** It used to fall through
  to the class branch, so an op kind added and not implemented would have been
  *silently treated as a class op*. It is now a compile error naming the line.
  This file's whole subject is "somebody widens the allowlist and forgets the
  other half", and that half is worth having tsc check rather than the corpus.

## What is still open

- §2, §3, §5 of the previous file, untouched.
- `:html`, parked above with its reason.
- The new order axis compares the two paths against each other. It does **not**
  assert that either one matches a written-down expected order - so a change
  that reorders *both* paths identically still passes. That is the right trade
  for a differential test, and it is worth knowing it is the trade.
