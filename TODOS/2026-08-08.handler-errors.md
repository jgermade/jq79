# An exception in a handler reaches the console whichever way the handler was written

**Status:** proposal. From an outside report (`2026-08-08.outside-report.md`, item 5). Finishes
what `2026-08-08.reporting-issue.md` deliberately left: that one made a
*missing name* audible, this one makes a *thrown exception* audible.

## The problem

`docs/template-syntax.md` says the three `@event` styles are equivalent — "a
handler reference, an inline arrow, or an inline statement". They are not, once
something throws:

```html
<form @submit="onSubmit">              <!-- throws → console, with a stack -->
<form @submit="onSubmit($event)">      <!-- throws → nothing at all -->
```

`bindEvent` evaluates the attribute and then calls the result *outside*
`evalExpr`'s `try`. So a reference resolves to a function that is invoked in the
clear, while an inline call happens **during** the evaluation, inside the `try`
that exists for a completely different reason — and the handler's exception is
swallowed with it. `wireTagEvent` does the same thing on the component-tag
channel.

The common case is a `TypeError`: `Cannot read properties of undefined`, thrown
three frames into a service the handler called. Written one way you get a stack;
written the other way the click does nothing and the console is empty.

**The reporter expected `2026-08-08.reporting-issue.md` to cover this.** It
doesn't, and correctly so: that change reports `ReferenceError` and nothing
else, because `ReferenceError` is the failure that means "declared nowhere".
A `TypeError` from a half-loaded value is exactly the transient case its `catch`
exists to absorb. So the asymmetry survived the fix that looked like it would
close it.

## Why the `catch` is not load-bearing here

`evalExpr` swallows because a template expression is re-evaluated constantly —
once per effect run, once per interpolation, once per `:each` item — so a value
that is briefly undefined mid-render has to render empty rather than tear down
the render. Every word of that is about rendering.

**A handler expression is evaluated in an event listener.** It is not in an
effect, nothing re-runs it, and there is no mid-render moment to protect: it
runs when the user clicks, exactly once, and if it throws, the click did
nothing. There is no transient failure to absorb — only a bug to report. The
reason for the `catch` simply does not reach this path.

That is the whole argument, and it is what makes this a narrowing rather than a
new policy: the reference style has always let handler exceptions through, and
this makes the other two match it instead of the reverse.

## The proposal

An `evalHandler`, used by `bindEvent` and `wireTagEvent` in place of `evalExpr`.
Same compile, same scope, one rule at the `catch`:

- **`ReferenceError` still goes to the deferred reporter, and is still
  swallowed.** Not an exception to the rule but the same reasoning applied: a
  missing name is *not* decidable at throw time — an async factory's bindings
  land when it returns, so a click during that window throws for a name that is
  about to exist. `reportExprError` already re-checks at flush and stays quiet
  if it arrived. Throwing it instead would resurrect the false positive that
  `2026-08-08.reporting-issue.md` was built to avoid, and would lose the
  once-per-name dedupe and the wording that names the `function` trap.
- **Everything else propagates**, out of the listener, uncaught, with its stack —
  which is what the browser already does for the reference style.

So the rule is: *the one error class that might not be the author's fault yet is
reported and absorbed; every other exception is the handler's own and belongs in
the console.*

## What it costs

**A parent's tag handler now breaks the child's `$emit`.** On the component-tag
channel, `$emit` calls its listeners synchronously in a `forEach` and then
dispatches the DOM event; a listener that throws aborts both and the exception
surfaces inside the child that emitted. That is already true for the reference
style (`@files="onFiles"`), so this change makes the inline style join it rather
than inventing anything — but it does widen the blast radius of the change from
"a handler is louder" to "a broken parent handler can stop an emit mid-flight".
Recorded rather than mitigated: making `$emit` isolate its listeners is a
separate decision about the emit channel, not about which `try` a call lands in.

**Throwing out of a listener is not catastrophic.** `addEventListener` callbacks
that throw are reported on `window` and the other listeners still run; the
browser's own error path is the one being used.

`wireTagEvent` calls through `untracked`, which pops its dependency stack in a
`finally`, so an exception leaves nothing behind.

## Rejected

- **Catching in the handler path and `console.error`ing.** Loses the stack's
  place in the async chain, and invents a second way for jq79 to report a
  program's own exception when the browser's is already right there. It would
  also *change the reference style* to match the inline one — moving the wrong
  behaviour onto the good one.
- **Removing the `catch` from `evalExpr` entirely.** That is the render path,
  where the transient case is real. Out of the question.
- **Also un-swallowing the `:model` writeback** (`untracked(() => evalExpr(assignment(expr), …))`,
  which runs on input and could `TypeError` on an unreachable path). The same
  argument applies to it — it is an event-time evaluation, not a render — but it
  is a different attribute with a different failure story, and `:model` already
  warns at bind time when its target is not assignable. Left open rather than
  folded in.
- **Reporting non-`ReferenceError`s through the deferred queue too.** The queue
  holds live scopes and re-checks a *name*; a `TypeError` has no name to
  re-check, so there is nothing for the flush to ask. Throwing is the honest
  shape.

## Open

- **The `:model` writeback**, above.
- **Whether `$emit` should isolate its listeners** so one parent's broken handler
  doesn't stop the others, or the DOM dispatch. Pre-existing, and this change
  makes it reachable from one more spelling.

## Test

In `tests/Component79.test.ts`, beside the `names a template expression cannot
resolve` block:

- an inline call whose handler body throws a `TypeError` reaches an error
  listener — the regression this file exists to fix;
- a handler *reference* whose body throws does the same, unchanged;
- a missing name in a handler still warns once and does **not** throw, in both
  spellings;
- an inline statement (`@click="count++"`) still works, since it evaluates to a
  non-function and must not be treated as an error.

---

## 2026-08-08 — implemented

As proposed. `evalExpr` and `evalHandler` are now two `catch` clauses over one
`runExpr`, which compiles and calls and lets everything through — the difference
between the render path and the event path is exactly those two clauses and
nothing else, which is the point.

`bindEvent` and `wireTagEvent` are the only callers. The `:model` writeback was
left alone as planned.

What the tests had to account for, and the proposal didn't say: **an exception
in a listener does not propagate to whatever dispatched the event.** The browser
(and jsdom) report it on `window` instead, so `.click()` returns normally and
the test asserts on a `window` error listener rather than on a `toThrow`. The
component-tag channel is the one place it *does* propagate synchronously, since
`$emit` calls its listeners directly rather than through `dispatchEvent` — which
is the cost recorded above, now with a test that pins the reporting end of it.

Five new tests in `Component79.test.ts`. Two of them fail without the change
(the inline call, and the tag handler); the other three pin behaviour that must
*not* move — a handler reference, a missing name still warning once rather than
throwing, and `@click="count++"` still being an ordinary inline statement. No
existing test moved: nothing in the suite or the tutorial depended on a
handler's exception being swallowed.
