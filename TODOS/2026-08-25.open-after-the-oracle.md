# What is open after the oracle

**Status:** a list, and the successor to
[`2026-08-24.open-after-pr-12.md`](2026-08-24.open-after-pr-12.md), whose §1,
§2, §3, §4, §5, §7 and §8's actionable line are done - see
[`2026-08-25.what-this-branch-did.md`](2026-08-25.what-this-branch-did.md). That
file is not edited; this one replaces it as the map.

Not a proposal. Each item says what it is, what evidence exists, and how big it
looks. Ordered by what I would do first, which is not by size.

---

## 1. Firefox and WebKit have not answered yet

**The only thing gating a claim this branch makes.** The SVG attribute-name
oracle is verified in Chromium 141 and jsdom; the other two engines could not be
installed where it was written, because the network denies
`cdn.playwright.dev`. `.github/workflows/svg-attribute-names.yml` settles it -
it has never run.

Nothing to build. Read the first run, and read the level-2 table it prints even
when it passes: it is the only place the repo will hold *which* names each
engine adjusts. If an engine disagrees on a name, that is a fact about the
platform and the job says so without failing; if the *mechanism* disagrees with
that engine's own document parser, that is ours.

It also answers a question the implementation had to guess at - `DOMParser` or
`innerHTML` in an SVG context. They agree in Chromium. If they ever do not, the
job says which to keep.

## 2. `:attrs` writes a dead attribute without a word

**Small, and it would say something neither Vue nor Svelte says.** `:attrs`
passes its keys to `setAttribute` verbatim, which is right - it is the one
deliberate escape hatch - and on a foreign element that means
`{ strokeWidth: 4 }` writes an attribute SVG ignores, as silently as
`{ viewBox: box }` writes a good one. Measured; Vue and Svelte do the same and
also say nothing.

The oracle already computes the signal: `strokeWidth` lowercased does not come
back as `strokeWidth`, so it is not a name the parser ever produces. A warn
costs one lookup on a path that already runs per binding.

It was filed separately on purpose - it is a diagnostic decision, not a
rendering one - and it is still a decision: the same argument that killed
[`2026-08-07.unknown-directive-warn.md`](2026-08-07.unknown-directive-warn.md)'s
modal case applies here, that a diagnostic aimed at a common mistake may be a
sign the feature should exist instead.

## 3. What is left of the unknown-directive warn

Rewritten around its two survivors in a dated section, not implemented. They
want different instruments and should not be one item:

- **`:submit.prevent`** writes an attribute literally named `submit.prevent`
  holding the handler stringified. It has a structural signal `plannableAttr`
  already computes - a dotted `:` name belonging to no family - and cannot fire
  on a legal binding.
- **`:iff`** renders `iff="true"` and there is no structural signal at all. It
  needs a near-miss table against `CONTROL_ATTRS`, which is an instrument this
  library does not have and has its own false positives to argue about.

The first is small and safe. The second is a judgement nobody has made.

## 4. `:each` + `:if`, and the invisible wrapper

Unchanged from §4 of the previous list except that its cheap half shipped. The
warning is in; the wrapper is not, and the work there is still not the `:if` -
it is `boundsOf`, which resolves a fragment as
`{ first: node.firstChild!, last: node.lastChild! }` and breaks on an empty one.
`<template :slot>` sidesteps that by always inserting its own anchors, which is
the shape a wrapper would have to copy.

## 5. Two seams the branch left, both named where they live

- **The capture asymmetry.** A PascalCase key *already in scope* captures a
  foreign tag (`Mi` captures `<mi>`, the same trade `Td` has with `<td>`); a key
  that arrives later no longer does, because a foreign element is never a tag
  that may upgrade. Both are defensible, they are not the same rule, and only
  the second one moved.
- **`<annotation-xml>` stays off the clone path**, and takes its `<math>`
  ancestor with it, because `plannableNode` rejects a dashed tag and does not
  make the exception `mayUpgrade` now makes. Slower and correct. A page that
  renders one annotated formula pays nothing; nobody has one that renders a
  thousand.

## 6. Two measurement gaps, unchanged and still the right trade

- **`renders=8` never resolved.** Two attempts at the break-even curve gave
  +2.2%/46% and +8.5%/39%, both with a p25..p75 spanning ~55 points, because a
  chunk there is 480 renders and ~19ms. It needs a smaller chunk. Not needed for
  any answer so far; 1 and 100 bracket it.
- **The order axis is differential only.** It compares the two paths against
  each other and does not assert either matches a written-down expected order,
  so a change that reorders *both* identically still passes. That is the right
  trade for a differential test, and it is worth knowing it is the trade.

## 7. Housekeeping

- **The regression baseline still moves at the next release.** Unchanged from
  §8 of the previous list: that job measures against the last released tag, and
  the release after PR #12 re-baselines every operation. Nothing to do; anyone
  reading a surprising delta afterwards should know the floor shifted.
- **`moveRangeAfter` still moves a reorder one node at a time.** `swapRows` is
  7.8ms. Still not worth it.
- **Two files in this directory are dated the day before they were written.**
  `2026-08-24.clone-path-coverage-check.md` and `2026-08-24.mathml.md` were
  written in the small hours of the 25th, named for the session they continued.
  The repo's own `2026-08-24.*` files were committed at 00:53 on the 25th, so
  this is the house precedent rather than a slip - recorded because the next
  reader sorting by filename will see them out of order with their content.
- **The stress harness is not in the repo.** The flake in §8 needed every core
  busy and three suites at once to reproduce, and that was a shell loop, not a
  script. If it happens again, that is the method: spin loops per core, then
  `npx vitest run` repeatedly, then read which assertion failed rather than
  which file.

## 8. The part none of this touches

Unchanged and still honest: of the ~8ms of DOM, ~11ms of interpretation and
~30ms of effects per 1,000 rows in
[`2026-08-23.where-the-create-time-goes.md`](2026-08-23.where-the-create-time-goes.md),
the clone path took the middle third. The remaining ~30ms is one effect per
binding, and the two things priced against it - grouping a row's bindings, and
dropping `with` from expression evaluation - were both refused for good reasons.

`create1k` is ~33ms where Svelte is ~9ms. Closing that is a claim about what the
library is, not an optimization anybody has left.

## Update, 2026-08-25: §1 is closed - all three engines answered

[PR #13](https://github.com/jgermade/jq79/pull/13) ran the workflow for the
first time. **The oracle holds in chromium, firefox and webkit**, all three at
58 of 62 names adjusted, with the mechanism reproducing each engine's own
document parser and no collision anywhere. Chromium was 151, ten major versions
past the 141 it was designed on. Recorded in
[`2026-08-25.svg-attribute-names.md`](2026-08-25.svg-attribute-names.md).

§1 is spent. What replaces it on this list is smaller: the workflow's
cross-engine comparison could not run at all - the matrix isolates the engines -
so it now writes per-engine artifacts and a `compare` job reads them. That is
the third check in this branch that turned out unable to fail or unable to run,
which is the branch's own lesson and belongs at the top of anything that
follows: **write the sabotage before trusting the check.**

The benchmark on that run: no regressions, everything inside the runner's noise,
`replace1k` -1.3% faster in all four rounds. Nothing to act on, and the first
numbers measured against the 0.6.4 baseline.
