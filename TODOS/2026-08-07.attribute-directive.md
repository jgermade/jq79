# `:attr="expr"` — the single-attribute form, and one value rule for both

**Status:** decided (user's proposal, user's call on the value rule). Supersedes
[`2026-08-07.unknown-directive-warn.md`](2026-08-07.unknown-directive-warn.md),
which proposed warning on the very syntax this makes legal.

## The problem

jq79 binds attributes wholesale or not at all. `:attrs="expr"` takes an object
and writes every entry; there is no way to bind one attribute, so the single-key
object is the shape people actually write. In this repo, of the nine real uses
of `:attrs` outside the docs, **seven are one key**:

```html
tutorial/_app/components/Lesson.html   :attrs="{ disabled: index === 0 }"
tutorial/_app/components/Editor.html   :attrs="{ readonly }"
tutorial/_app/examples/Chart.html      :attrs="{ style: `width: ${(point.value / top) * 100}%` }"
tutorial/_app/components/Toc.html      :attrs="{ class: exercise.path === path ? 'link active' : 'link' }"
```

The braces and the quote-inside-a-quote are ceremony around one value — word for
word the argument that carried `:class.<name>` in
[`2026-07-21.class-shorthand.md`](2026-07-21.class-shorthand.md), which shipped
the same day it was proposed.

And the absence has a second cost: `:foo="expr"` on a real element is not an
error today, it is a *literal attribute*. `<img :src="'/x.png'">` renders
verbatim, no warn, image broken, expression source published in the markup. The
superseded plan proposed warning about it. Binding it is the better answer to
the same complaint.

## The proposal

### The directive

`:<name>="expr"` on a real element binds that one attribute, reactively:

```html
<button :disabled="busy">Save</button>
<a :href="`/users/${user.id}`">profile</a>
<div :aria-expanded="open"></div>
```

- **`:name` alone is shorthand for `:name="name"`**, like props and
  `:model.<name>`. `<input :disabled>` binds the scope's `disabled`.
- **Reserved names keep their meaning.** Everything `isControlAttr` claims is
  untouched: `:if`, `:each`, `:key`, `:with`, `:class`, `:class.*`, `:text`,
  `:html`, `:html.allowed`, `:attrs`, `:props`, `:props.*`, `:slot`, `:slot.*`,
  `:model`, and the three property directives `:value`/`:checked`/`:selected`.
  So `:value` can never mean the *attribute* `value` — it is the property, as
  [`2026-07-15.property-directives.md`](2026-07-15.property-directives.md)
  decided.
- **Component tags are unaffected.** There, every `:foo` is a parameter, and
  stays one whether or not the child's signature declares it — a jq79 component
  has no single root for an attribute to fall through to, the same reason
  [`2026-07-15.class-directive.md`](2026-07-15.class-directive.md) rejected
  `:class` there. What happens to an undeclared parameter is
  [`2026-08-07.signature-teeth.md`](2026-08-07.signature-teeth.md)'s business,
  not this plan's.
- **A tag that may still become a component is not an element yet.** The guard is
  the one `:model` already uses — `el instanceof HTMLUnknownElement ||
  node.tag.includes("-")`. `<Row :foo="foo" />` while `Row` is undefined must
  keep `:foo` as written, because the upgrade re-renders through
  `renderNestedComponent` where it is a parameter. Verified: it renders
  `<row :foo="foo">` today and must go on doing so.

### The value rule

One rule, shared by `:attr` and `:attrs`, because two similar-but-different
rules would be worse than either:

```
drop = BOOLEAN_ATTRS.has(name) ? !value : value == null
```

- **A boolean attribute is removed by any falsy value** and set to `""` when
  truthy. Presence is the whole message; `disabled="true"` and `disabled="0"`
  both disable, so the value carries nothing worth writing.
- **Every other attribute is removed only by `null`/`undefined`.** `false`, `0`
  and `""` are written as strings.

`BOOLEAN_ATTRS` is the HTML spec's list, not a jq79 convention — that is the
distinction that earns it a table in a codebase with no name tables. Nobody in
this repo decides what it contains:

```
allowfullscreen async autofocus autoplay checked controls default defer
disabled formnovalidate inert ismap itemscope loop multiple muted nomodule
novalidate open playsinline readonly required reversed selected
```

`checked` and `selected` are in it even though `:checked`/`:selected` are
property directives that never reach this path — `:attrs="{ checked: … }"` does.

**Why a list and not the DOM.** The obvious implementation is to ask the
element: `typeof el[name] === "boolean"`. Measured, it doesn't hold:

```
autofocus       jsdom: undefined     Chrome: boolean
aria-expanded   jsdom: object/null   Chrome: string
readonly        el.readonly undefined, el.readOnly boolean
```

A rule that consults the DOM behaves differently under test than in the browser,
and jq79's whole suite is jsdom — it would pin a semantics the browser doesn't
have. The kebab→camel gap (`readonly`→`readOnly`, `novalidate`→`noValidate`,
`formnovalidate`→`formNoValidate`, `ismap`→`isMap`) fails toward the dangerous
side on top of that: `readonly="false"` is read-only.

### What this fixes in `:attrs`

Two live defects, both from the current rule removing on `false` for everything:

- **`aria-expanded="false"` is unwritable.** Absent and `"false"` are different
  things to a screen reader, and `:attrs="{ 'aria-expanded': open }"` can only
  produce absent. Same for `data-*` flags.
- **`:attrs="{ disabled: items.length }"` disables the button when the list is
  empty** — `0` is not `null` and not `false`, so today it *sets* the attribute.
  [`tests/renderComponent.test.ts:1009`](../tests/renderComponent.test.ts) exists
  to pin that trap with the comment "so the trap stays documented". The new rule
  removes the trap instead of documenting it.

## What it costs

Patched the rule in and ran the suite: **647 of 649 pass**, and the whole
tutorial is green — `:attrs="{ readonly }"` and `:attrs="{ disabled: index === 0 }"`
behave exactly as before, because `false` still removes a boolean attribute.

The two failures:

- `:attrs sets boolean attributes for falsy values that are not null/undefined/false`
  — the pinned trap above. It is the intended fix; the test inverts.
- `applies :attrs attributes and keeps them in sync` — asserts
  `getAttribute("disabled") === "true"`, now `""`. Purely the canonical-value
  change; keeping `String(value)` would leave it passing.

Plus: the directive itself (an effect per bound attribute, next to `:class`'s),
the `BOOLEAN_ATTRS` set, the guard on possible-component tags, and
`docs/template-syntax.md` — a new section next to `:attrs`, which stops being
the only way to bind an attribute and becomes the way to bind *several*.

## Rejected

- **Warning on unrecognized `:` directives** — the superseded plan. It bought
  `:iff="ready"` catching a typo at the price of `:disabled` never working. The
  warn is not lost, it moves: on a component tag the signature knows what is
  undeclared, which is certainty rather than the guess an element could make.
  See [`2026-08-07.signature-teeth.md`](2026-08-07.signature-teeth.md).
- **`null`-only for every attribute, boolean list included.** Simpler, and
  measured against the suite it breaks the tutorial: `Editor.html`'s
  `:attrs="{ readonly }"` writes `readonly="false"` and the editor can no longer
  be typed into (`expected true to be false // editor.readOnly`), and
  `Lesson.html`'s two nav buttons stay disabled forever. Rejected by the user
  once the failure was concrete.
- **Falsy-removes for everything (today's `:attrs` rule), extended to `:attr`.**
  Zero new code, and keeps both defects above.
- **Deciding boolean-ness from the DOM.** See above: jsdom and Chrome disagree.
- **A different value rule for `:attr` than for `:attrs`.** The one thing worse
  than picking the wrong rule.
- **Setting the property instead of the attribute when one exists** (Vue's
  split). It dissolves the boolean question entirely — `el.disabled = false` has
  no presence semantics — but it reopens the boundary
  `2026-07-15.property-directives.md` drew on purpose, and needs the same
  name table the DOM probe needed. Its own proposal if wanted.

## Open

- **Whether a truthy boolean attribute is set to `""` or `String(value)`.**
  `""` is canonical and costs one test assertion; `String(value)` is what
  `:attrs` does today and leaves `disabled="true"` in the markup. Leaning `""`.
- **`:attr` and `:attrs` on the same element, both writing the same name.**
  `:attrs` is wholesale — each run removes what it set — so they would fight
  exactly as `:class` and `:attrs="{ class }"` do today, documented as "don't"
  in `2026-07-15.class-directive.md`. Same treatment, or a stated precedence.
- **`:style`** is still unproposed, and three of the `:attrs` uses above are
  `class` or `style` — the shorthand will absorb `style` whether or not a
  dedicated directive ever lands.
