# `with` is 60% of evaluating an expression, and worth 3-10% of an operation

**Status:** a measurement and a recommendation *not* to act on it yet. Written
after [`2026-08-23.create-gap-is-diffuse.md`](2026-08-23.create-gap-is-diffuse.md)
concluded the remaining distance to Svelte is all JavaScript and spread thin —
this prices the largest single identifiable piece of it. Nothing implemented;
the experiment below was reverted.

## Where the question came from

`selectRow` wakes 1,000 effects in ~4.2ms — about **4µs per effect run**,
against Svelte's ~1.25µs for the same work. Every one of those runs evaluates a
template expression, and jq79 compiles expressions to:

```js
new Function("$scope", ...params, `with ($scope) { return (${expr}); }`)
```

The compile is cached per expression. The **evaluation** is not: every run goes
through `with`.

## The decomposition

Timed in isolation, 200,000 iterations of `row.label` against a store proxy and
against a plain object:

| shape | ns/op |
|---|---|
| `with` + proxy — **what jq79 does** | **695** |
| `with` + plain object | 76 |
| direct member access + proxy | 279 |
| direct member access + plain object | 11 |
| `with` + proxy, wrapped in try/catch | 705 |

So of the 695ns: ~268ns is the proxy's `get` traps — the price of tracking,
irreducible — and **~416ns is `with`**. The `try/catch` that `evalExpr` wraps
every evaluation in costs ~10ns and is not worth a thought.

Why `with` is so much more expensive over a proxy than over a plain object:
it resolves every free identifier through `[[HasProperty]]`, so `row.label`
fires the proxy's `has` trap *as well as* two `get` traps, and consults
`Symbol.unscopables` besides.

## What removing it is actually worth

**Timing individual evaluations inside the browser does not work** — Chromium
coarsens `performance.now()`, so summing 1,001 deltas of a ~700ns call produced
`selectRow`'s expression time as 7.7ms out of a 5.8ms operation. 133%. The
clock, not the code.

The instrument that works is substitution: compile the same expressions
*without* `with` and compare the operation. A throwaway rewriter (prefix free
identifiers with `$scope.`, bail on anything with an arrow function or a
declaration) was enough to run the benchmark app correctly — 1,000 rows, the
`danger` class landing on the right row, labels updating.

Two back-to-back pairs, 10 samples each, trimmed mean:

| op | with | without | Δ | evals |
|---|---|---|---|---|
| selectRow | 4.51 / 4.76 | 3.99 / 3.52 | **−12% / −26%** | 1001 |
| create1k | 57.35 / 53.59 | 53.84 / 52.84 | −6% / −1% | 4002 |
| swapRows | 8.07 / 9.81 | 8.94 / 7.47 | +11% / −24% | 2012 |
| partialUpdate | 1.54 / 1.71 | 1.66 / 1.38 | +8% / −19% | 101 |

Only `selectRow` moves in the same direction in both pairs; everything else
oscillates, which is this container's noise band. But the isolated number
predicts exactly that: at 416ns saved per evaluation, `selectRow`'s 1,001 evals
are 0.42ms of its 4.5ms (**−9%**) while `create1k`'s 4,002 evals are 1.7ms of
57ms (**−3%**). Prediction and measurement agree where the signal is strong
enough to read.

**So: 3-10%, best on operations dense in evaluations per millisecond.**
`with` is 60% of an expression, an expression is 10-25% of an effect run, and
an effect run is a fraction of an operation. The percentages multiply down.

## Why not to do it now

The throwaway rewriter broke **six tests**, and not by being sloppy:

- `with` throws `ReferenceError` for a name that resolves nowhere, and
  `reportExprError` turns that into the message naming a dropped prop or a
  top-level `function` declaration that `transformSetupScript` left lexical.
  `$scope.foo` returns `undefined` silently, and the diagnostic disappears.
- The `has` trap is load-bearing for tombstones: it claims deleted keys so
  `user ? user.name : "none"` takes its else branch instead of dying of
  `ReferenceError` against `globalThis`.

A real implementation needs a JS identifier parser that can tell free names
from bound ones (`items.map(x => x.id)`), **and** a replacement for that error
channel. That is a lot of surface for 3-10%, against a branch that just took
`partialUpdate` 137× and halved the create path.

There is one consolation prize worth remembering if someone does it: the
`isNewKey` full sweep — the last genuinely O(all effects) path left in the
store — exists only because "`with` skipped the store entirely" for names that
did not exist yet (see `2026-08-23.narrow-the-wake-rule.md`). Compiling scope
access explicitly makes those reads trackable, and the sweep could become
precise. That is a second, unpriced win on the same change.

## The cheaper thing still untried

`2026-08-23.create-path-constants.md` left this open and it is still the better
first move: derive per-`TemplateNode` work (attribute classification, `:class.`
toggles, the static class set) **at parse time, stored on the node**, rather
than at render time behind a `WeakMap`. The `WeakMap` version measured neutral
to worse because the probe costs about what the `Object.entries` it replaces
costs; a plain field read has no probe. Small, no semantic risk, and it attacks
the same per-element repetition.
