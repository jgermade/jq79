# What is still open

**Status:** a list, written at the end of the branch that landed the parse-time
chain validator, the per-definition precompute and the skeleton clone path. Not
a proposal - each item says what it is, what evidence exists, and how big it
looks, so the next person can pick one instead of re-deriving the map. Items are
in the order I would do them.

Everything here was either measured on this branch or found while measuring
something else. Where a number appears without a file next to it, it came from
the instrument described in
[`2026-08-24.clone-skeletons-measured.md`](2026-08-24.clone-skeletons-measured.md)
and its per-case null control.

---

## 1. Teach the cloner more holes

**Small, measurable, no decision.** `plannableAttr` accepts four things today:
a static attribute, `@event`, `:class`/`:class.<name>`, and a single `:<name>`
binding. Everything else makes its subtree take the interpreted path - which is
correct, and also means a template using `:text`, `:attrs`, `:value`,
`:checked` or `:selected` gets nothing from the clone path at all.

Each is a bounded piece of work: an op kind, a branch in `buildSkeleton`, a
branch in `renderFromSkeleton`, and a corpus entry that already exists in
`tests/skeleton.test.ts` (the `SHAPE_CORPUS` entries are there precisely so
admitting one to the allowlist without implementing it turns red).

Worth doing in this order, by how much markup they gate:

- **`:text`** - a leaf hole, the simplest possible op, and the one most likely
  to sit inside an otherwise-plannable row.
- **`:attrs`** - one effect that rewrites a key set; the op is the same shape as
  `attr` with a different body.
- **`:value` / `:checked` / `:selected`** - these are the order-sensitive ones
  (`:value` on a `<select>` has to run after the `<option>`s exist), so they
  need the op list to grow an "after the children" phase. **Do not do these
  first**, and note that the differential test does not check op order (§6).

`:if` and `:each` are **not** on this list: they change the shape, not fill a
hole, and a subtree containing one is exactly what should fall through.

## 2. `<svg>`, and building skeletons from the parser's tree

**Measured as free, but it is a behaviour change.** `buildSkeleton` uses
`createElement`, so a skeleton inherits today's namespace behaviour exactly -
`<svg>` is an `HTMLUnknownElement` and therefore never plannable, and everything
stays as it was.

`parseComponentString` already builds a real DOM tree with `DOMParser` and
throws it away after `elementToAST`. Cloning the skeleton from *that* subtree
instead would give correct namespaces for free, which fixes `<svg>` - and takes
it out of the `HTMLUnknownElement` branch that the upgrade watch and the
unresolved-component throw both rely on
([`2026-08-12.undefined-component-throws.md`](2026-08-12.undefined-component-throws.md)
leans on it explicitly).

So it is two changes wearing one coat, and
[`2026-08-23.clone-static-skeletons.md`](2026-08-23.clone-static-skeletons.md)
was right that the `<svg>` half deserves its own decision. What is new is that
the machinery it needs now exists.

## 3. `:each` + `:if`, and the missing invisible wrapper

**A design decision, not a performance one, and it has been deferred twice.**
Today `:if` on a `:each` element is ignored with a warning: *"filter the list
expression instead"*. That is defensible - the combination has two plausible
meanings and Vue has shipped both and regretted one - but the reason people
write it is that **jq79 has no element that renders nothing**:

```
<template :if="a"><li>x</li></template>
  -> <ul><!--if--><template><li>x</li></template></ul>
```

The `<template>` lands in the DOM inert, so inside a `<tbody>`, a `<ul>` or a
flex container there is no way to wrap a `:each` in an `:if` without breaking
the layout. Hardening the rule without giving the wrapper leaves the user with
nowhere to go.

Two ways out, and picking is the work:

- a fragment wrapper (`<template :if>` renders its children in place, no
  element), which is what every other framework in the comparison has;
- or giving `:each` + `:if` one of its two meanings and documenting it loudly.

## 4. `removeRow` is 1.8% slower with the clone path on

**Small, consistent, and under the noise** - +3.7 / +1.8 / +0.9 across three
rounds of `benchmark:ab --flags`, against ±3.6% of that operation's own spread.
The gate would not look at it twice.

Written down because nothing in the clone path runs during a removal, so the
likeliest reading is that rows built by cloning lay out differently in memory
than rows built element by element. If it ever grows, this is the note saying it
arrived with a -23% on create, and the first thing to try is measuring a removal
over rows built both ways with the DOM volume held constant.

## 5. Does a template that renders **once** pay for its plan?

**Unresolved, and the instrument was the problem.** A definition rendered a
single time pays for `plannableNode` plus `buildSkeleton` and saves one
interpreted walk - analytically a wash. Measuring it needs a per-definition
instrument, and the one built for it had a null control of **±19%** (base
against itself), against a parse+render that costs ~154µs, nearly all of it
parsing.

It matters for a page of many small components rather than one big list, which
is a shape nothing in this repo measures. Fixing the instrument is the task, not
fixing the code.

## 6. Op order is not covered by the differential test

`tests/skeleton.test.ts` diffs the DOM, and reversing `plan.ops` changes no DOM
today, because every directive whose registration order is observable is
rejected by the allowlist. That is true until §1 lands `:value`.

Closing it means asserting on the order of registration rather than on the
result - a spy over `fx.effect`, or an op-order snapshot per corpus entry. Worth
doing **before** the form-state holes, not after.

## 7. Two stale files

- [`2026-08-07.unknown-directive-warn.md`](2026-08-07.unknown-directive-warn.md)
  argues that `:disabled`, `:src` and `:href` fall through to the DOM verbatim.
  **They do not any more** - `:<name>` is the single-attribute binding, and
  `<button :disabled="busy">` renders `disabled=""`. What is left of the
  proposal is the genuinely unknown case: a typo (`:iff`), and a directive
  written in the wrong syntax (`:submit.prevent` for `@submit.prevent`). It
  needs rewriting around those or closing.
- [`2026-08-23.clone-static-skeletons.md`](2026-08-23.clone-static-skeletons.md)
  is superseded in part (its header says so). Its "conservative classifier"
  section is the one that is actually wrong, not merely out of date - it accepts
  a subtree whose tags are known HTML, and a `Td` in scope captures every
  `<td>`.

## 8. The part the skeleton cannot touch

Of the budget in
[`2026-08-23.where-the-create-time-goes.md`](2026-08-23.where-the-create-time-goes.md)
- ~8ms of DOM anybody pays, ~11ms of interpretation, ~30ms of effects per 1,000
rows - **the clone path took the middle third and left the rest exactly where it
was**. A row where every element carries a binding still gains, but half as
much, which is that fact showing up as a number.

The remaining ~30ms is one effect per binding: allocate it, run it in a tracking
frame, resolve its names through `with ($scope)`, read them through the store
proxy, index the deps. Two things have been priced against it and both were
refused for good reasons - grouping a row's bindings into one effect (~8%, and
fine-grained updates are where jq79 actually wins) and dropping `with` from
expression evaluation
([`2026-08-23.with-in-expressions.md`](2026-08-23.with-in-expressions.md),
measured, recommended against *for now*).

Nothing here is a next step. It is the honest ceiling: after this branch,
`create1k` is ~33ms where Svelte is ~9ms, and closing that gap is a claim about
what the library is, not an optimization anybody has left.

## 9. Housekeeping

- **The regression baseline moves at the next release.** That job measures
  against the last released tag, so the release after this branch re-baselines
  every operation. Nothing to do; the next person reading a surprising delta
  should know the floor shifted here.
- **`moveRangeAfter` still moves a reorder one node at a time**, the open item
  [`2026-08-23.batch-range-removal.md`](2026-08-23.batch-range-removal.md) left:
  *"not worth it until it is"*. `swapRows` is 6.3ms. Still not worth it.
- **`03-components/08-slots` settles a tick later than every other tutorial
  exercise.** Found by the differential test's null control, which mounts each
  exercise twice interpreted before judging it. Not a bug - but
  `tests/tutorial.test.ts` waits a fixed tick, so it is one scheduling change
  away from being flaky.

## Update, 2026-08-24: §1 (mostly) and §6 are done

Landed in [`2026-08-24.more-holes-in-the-cloner.md`](2026-08-24.more-holes-in-the-cloner.md),
in the order §6-then-§1 that §6 asked for. Nothing above is rewritten - this
says which items moved.

- **§6 is closed.** The differential test grew a second axis: a scope of logging
  accessors, so the read log of a render is the order its bindings registered
  in. Verified by sabotage - moving the form-state ops before the children turns
  it red, and leaves the DOM diff green, which is exactly the gap §6 described.
- **§1 is done except `:html`.** `:text`, `:attrs`, `:value`, `:checked` and
  `:selected` are holes the cloner fills. `:html` is deliberately parked: its
  `:html.allowed` companion carries a warning that fires per render interpreted
  and would fire per definition cloned, which is a behaviour change and wants
  its own decision.
- **A divergence that predates all of this was found and fixed.** `:model` is
  not in `CONTROL_ATTRS`, so `plannableAttr` accepted the bare form as a generic
  `:<name>` binding: `<input :model="who">` rendered `model="ada"` cloned and
  nothing interpreted. The corpus entry for `:model` put it on a component tag,
  which is unplannable for a different reason - so a trip wire has to sit on a
  tag that would *otherwise be planned*, or it is not a trip wire.
- **§4's note still stands** and now has a second reason to be checked at the
  next release: more subtrees are planned than were when it was written.

Unchanged: §2, §3, §5, §7, §8, §9.

## Update, 2026-08-24: §2 and §5 are done, and §2 was not what it said it was

- **§2 is a rendering bug, not an optimization**, and it had four parts rather
  than one: the namespace, `viewBox` flattened by `setAttribute`, *every*
  binding inside an `<svg>` left in the DOM verbatim (an `HTMLUnknownElement` is
  a component that might still arrive, so its `:` attributes are kept as
  parameters), and `tagName.toLowerCase()` destroying `clipPath` and
  `linearGradient`. The last two were not in §2. Fixed by carrying the namespace
  on the AST node, read off the tree `DOMParser` already built and
  `parseComponentString` already threw away - so none of the "two changes
  wearing one coat" the item worried about was needed. See
  [`2026-08-24.svg-namespace.md`](2026-08-24.svg-namespace.md).
- **§5 is answered, and the guess in it was wrong.** A definition rendered once
  does *not* wash out: it pays +23% at the 3-element threshold, +11.5% at six,
  and reaches break-even somewhere around nine to twelve elements. The
  instrument is in tree as `npm run benchmark:once`, with a null control that is
  a coin flip instead of ±19%. See
  [`2026-08-24.one-shot-render-measured.md`](2026-08-24.one-shot-render-measured.md).
- **That opens something §5 did not ask for**: `MIN_SKELETON_ELEMENTS` was tuned
  on list rows, where the plan amortizes over a thousand instances, and it is
  the one-shot case that pays. Planning on the *second* render rather than the
  first would make a one-shot definition free and cost a 1,000-row list one
  interpreted render. Unmeasured, and the obvious next thing.

Unchanged: §3 (with a correction filed in
[`2026-08-24.template-directive-warning.md`](2026-08-24.template-directive-warning.md)),
§4, §7, §8, §9.

## Update, 2026-08-24: the plan is built on the second render

The follow-up the §5 update named is done —
[`2026-08-24.plan-on-the-second-render.md`](2026-08-24.plan-on-the-second-render.md).
`planOf` returns null the first time it sees a node, so a definition rendered
once never builds a plan, and a `:each` interprets row 1 and clones the rest.
The +23.1% and +11.5% one-shot costs both land on the null control now.

Two things worth carrying forward, both about measurement rather than the code:

- **A single well-powered run said the list win had vanished, and it was
  wrong.** Alternating the two builds three times each showed eager's own worst
  pass at -0.0%/52%, indistinguishable from lazy's worst. The clock cannot
  resolve a difference of that size on this box; counting can, and it is exact -
  eager clones 50 of 50 renders, lazy 49. §4's advice about reading a delta
  against its own noise applies to *this* file's numbers too.
- **The differential test can go vacuous without failing.** Making the plan
  lazy dropped the corpus entries that actually reach the cloner from 26/83 to
  5/83, silently. The check is to make `renderFromSkeleton` mark its root and
  confirm 26 entries fail; it belongs in anyone's hands who touches this area.
  It also turned up that `mountShadow` re-attaches rather than re-renders an
  instance that already has content, which is why the tutorial half needed an
  explicit `{}` to render twice.

Unchanged: §3 (with its correction filed separately), §4, §7, §8, §9 - and §9's
warning about the tutorial test's fixed tick is now a flake seen once, on
`03-components/06-spreading-props`, in one run out of four.
