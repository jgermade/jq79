# A template that renders once pays for its plan — measured

**Status:** measured, with an instrument that is in tree this time. Answers §5
of [`2026-08-24.what-is-still-open.md`](2026-08-24.what-is-still-open.md), whose
whole content was *"the instrument was the problem"*.

The answer is **no, it is not a wash**, which is what §5 guessed analytically. A
definition rendered once pays between **+23% and nothing**, depending only on
how big it is — and the threshold that decides whether it is planned at all sits
at the expensive end of that range.

---

## Why the old instrument could not see it

§5's instrument timed **parse + render** as one block: ~154µs, *"most of it
parsing"*, against a null control of **±19%**. The signal is a few µs of plan
work. It was never going to come out of that.

The fix was not a better clock. It was measuring a smaller thing:

1. **Parsing left the timed region entirely.** It is identical in both arms and
   it was ~90% of what was being timed. `planOf` is called from `renderNode` on
   first render, so a freshly parsed definition rendered once pays
   `plannableNode` + `buildSkeleton` + `renderFromSkeleton` inside the clock
   whether or not parsing is in there with it.
2. **Many distinct definitions, each rendered once.** One render is far too
   small to time, so K of them are timed as a block. Distinct, because the plan
   cache is a `WeakMap` keyed by AST node - which is also exactly the "page of
   many small components" shape §5 says nothing here measures.
3. **Chunk interleaving, not two big blocks.** The first version timed one
   1,500-definition block per arm - 84ms - and its null control had a **55
   point** spread, with one round at 173ms against a stable 83ms on the other
   side. Both arms were the same code. That is this box stalling, not a result.
   Chunks of ~60 definitions, alternating which arm opens each chunk, mean a
   stall corrupts one chunk of a hundred instead of half a round.
4. **A detached container.** Layout is identical in both arms and only adds
   variance. Removing it makes any plan cost a *larger* share of what is left,
   so the instrument errs toward finding a difference rather than hiding one.
5. **`window.gc()` before the clock**, via `--js-flags=--expose-gc`, so a
   round's garbage is collected between blocks rather than during one.

One thing that had to be measured before anything else could be: **`performance.now()`
is clamped to 100µs** in this page (not cross-origin isolated - checked, not
assumed). A single small render is ~5µs, so per-render timing is impossible and
the chunk has to be worth some milliseconds. That clamp is why chunks of 25
(~1.5ms) still carried ±3.4% of pure quantization, and why 60 is the floor.

## The null control

Same config as every row below, both arms `cloneSkeletons: true`:

```
  median chunk     +0.0%
  p25 .. p75       -6.5% .. +7.7%
  right faster     43/100 chunks  (43%)
```

A median at zero and a win rate near a coin. The p25..p75 band is still ±7, so
**the win rate is the discriminating statistic here**, not the band: 100 paired
chunks put a binomial standard deviation at ~5 points, so a rate near 4% or 59%
is a result and one near 43% is not.

## What it says

600 definitions, each rendered **once**, `cloneSkeletons` off vs on. A positive
delta means the clone path is **slower**.

| elements per definition | median chunk | clone-on wins | reading |
|---|---:|---:|---|
| **3** (the threshold) | **+23.1%** | 4/100 | decisively slower |
| **6** | **+11.5%** | 13/100 | slower |
| **9** | +2.8% | 29/100 | marginal - median inside the null band, win rate outside it |
| **12** | -1.9% | 59/100 | a wash |
| *null control* | +0.0% | 43/100 | — |

So the cost is real, it is monotone in definition size, and break-even for a
one-shot render is somewhere around **9 to 12 elements**.

### The instrument's own control: it finds the known win too

An instrument that only ever reports a cost is not obviously working. Rendering
each definition **100 times** - the plan built once and reused - flips the sign:

```
  median chunk     -6.2%
  right faster     47/60 chunks  (78%)
```

Which is the direction [`2026-08-24.clone-skeletons-measured.md`](2026-08-24.clone-skeletons-measured.md)
already recorded for lists. Smaller than its -20 to -49% because these
definitions are six tiny elements carrying three bindings, and that file is
explicit that the win scales with how much *fixed structure* a row has.

### What did not resolve

Rendering each definition **8 times** stayed noisy across two attempts (+2.2%
with 46% of chunks, then +8.5% with 39%, both with a p25..p75 spanning ~55
points). A chunk there is 480 renders and ~19ms, which is a big enough target
that the stalls came back. It needs a smaller chunk, and it is not needed for
the answer: 1 and 100 bracket it.

## What this means for the code

**`MIN_SKELETON_ELEMENTS = 3` was tuned on the wrong workload.** Its comment
says planning fragments of one or two elements "measured as a wash at best and a
regression on a row whose only fragments are that small" - a *row*, in a list,
where the plan amortizes over a thousand instances. At exactly that threshold, a
definition rendered once pays **+23%**.

Two ways to fix it, and this file is not picking:

- **Raise the threshold.** Cheap, one constant, and wrong in the other
  direction: it would take a 9-element `:each` row - which amortizes beautifully -
  off the clone path to protect a one-shot render that may not exist.
- **Plan on the *second* render, not the first.** `planOf` returns null the
  first time it sees a node and builds the plan the second time. A one-shot
  definition then never builds a plan at all and pays nothing; a 1,000-row
  `:each` pays one interpreted render out of a thousand and keeps the rest.
  That looks strictly better than a threshold on size, because it keys on the
  thing that actually decides - how many times a definition is rendered -
  rather than on a proxy for it. Unmeasured. It is the obvious next thing.

## Reproducing it

In tree, unlike its predecessor:

```sh
npm run benchmark:once                 # 1 render each, clone off vs on
npm run benchmark:once -- --null       # the floor, and read nothing that does not clear it
npm run benchmark:once -- --elements 12 --renders 4
```

Read the win rate before the median, and run the null for the exact config
first. Every number in this file came from that script on this box, and this box
stalls - which is the whole reason it is built the way it is.
