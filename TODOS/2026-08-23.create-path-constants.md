# The create path has no hot spot left, only constants

**Status:** proposal and result in one file — the work was small enough that
splitting them would say the same thing twice. Follows the re-profile of
`create10k` after [`2026-08-23.positional-refresh.md`](2026-08-23.positional-refresh.md).

## The measurement

`findComponentKey` is gone from the top of the profile (it was 13.7%; the
per-pass memo took it to 2.1%). What is left has no dominant frame:

| share | frame |
|---|---|
| 56.9% | `(program)` |
| 5.5% | `appendChild` (native) |
| 4.7% | `renderElement` |
| 4.5% | garbage collector |
| 2.1% | `renderNodes` |
| 2.1% | `findComponentKey` |
| 2.0% | `createElement` (native) |
| 1.5% | `createDocumentFragment` (native) |
| 1.4% | `addEventListener` (native) |
| 1.3% | the `@event` binding |
| 1.2% | the store's `get` trap |
| 1.1% | `insertDep` |

Native DOM construction is ~11.5% and irreducible — Svelte issues those same
calls. jq79's own JS is ~12.5% spread across six frames, and the GC is 4.5%.
There is nothing here to delete; there are only constants to shave.

Two are worth shaving.

### A DocumentFragment for every element's children

`renderElement` did `el.appendChild(renderNodes(node.children, ...))`, and
`renderNodes` always built a fragment. So every element with children got its
own fragment, filled it, and then emptied it into the element — 70,000
fragments for a 10,000-row table, and a second pass over every node.

The element is freshly created and not in the document yet, so the
intermediate state a fragment exists to hide is not observable. `renderNodes`
takes an optional `into` target and builds straight into the element. Callers
that need a standalone chunk — a component's content, an `:if` branch — omit
it and get the fragment they always got.

### Three allocations per effect, for a case that almost never happens

`indexEffect` gave every effect a `Map` of dep → trie node and a `Set` of what
the last run tracked, and `$effect` gave every effect an empty `deps` `Set`
that the first run immediately replaces. But once the redundant ancestors are
pruned, **almost every effect holds exactly one dep** — a row binding reads one
path — and the `Map` never holds more than that entry.

The single case now lives in two slots, and the `Map` is allocated only when a
second dep arrives. The two initial `Set`s become one shared frozen empty set,
since nothing ever writes to them. For 30,000 effects that is ~90,000 fewer
allocations, against the 4.5% the GC was taking.

## What it measured

Two back-to-back A/B pairs, means of both:

| op (mean, ms) | HEAD | after |
|---|---|---|
| replace1k | 61.6 | **52.9** |
| create1k | 58.1 | 53.7 |
| appendToLarge | 98.3 | 91.8 |
| create10k | 550.8 | 534.8 |
| removeRow | 15.2 | 15.9 |

Modest and worth stating carefully. The **first** pair showed `create1k` and
`create10k` dead flat (56.7 vs 57.2, 539.0 vs 534.7) and only the second showed
them down; `replace1k` is the one that moved consistently in both (52.9/52.8
against 63.0/60.2), and it is also the op that had carried an unexplained
+3-4ms since the container diff landed, which this appears to be what was
behind. Treat `create1k` and `create10k` as "probably a few percent", not as
the 7% the means suggest.

Neither change gets anywhere near the distance to Svelte (`create1k` ~54
against 9.1). That distance is not in any frame this profile can name.

## Rejected

- **Chasing `(program)`.** It is 57% of a profile whose total sampled time is
  three times the operation's real duration, so most of it is the sampler, not
  work. Reading anything into it needs a different instrument — a
  `devtools.timeline` trace that separates style, layout and script — not a
  sharper eye on this one.
- **Skipping `findComponentKey` for lowercase tags.** A scope key `Td` would
  legitimately match `<td>`, so the tag's case says nothing. The memo already
  took this from 13.7% to 2.1%; the rest is one `Object.keys` per element on
  the `:each` item scope, and removing that means teaching the walk which
  scopes cannot hold component names — bookkeeping for 2%.

## Open

- The remaining ~2% in `findComponentKey` is that per-element `Object.keys` on
  the item scope. `renderEach` knows the item scope's own names when it builds
  them and could mark a scope as holding no component name, the same way it now
  decides `readsPosition` statically.
- `insertDep` still splits every dep path into an array. Walking it with
  `indexOf` would avoid one allocation per dep per effect.
- The `@event` binding re-splits the event name and rebuilds its modifier
  `Set` for every element it binds. That is per-element work derivable from the
  template once, like the component-key memo and the positional check.
