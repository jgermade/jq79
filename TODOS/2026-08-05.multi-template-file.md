# `<template name="…">` — child components in the same file

**Status:** proposal.

## The problem

A component is a file. That's the whole model, and it's right for the components
a page mounts — but it prices the small ones out of existence. A row of an
`:each`, a list item, a badge, an empty state: each one costs a file, a fetch or
an import, and a name in someone's directory listing. So they don't get written.
The markup that should have been a child component stays inlined in its parent,
directives and all, and the parent grows a section it can't name.

Two things fall out of that today:

- **A component can't be recursive.** A tree node renders a tree node, and there
  is no way to say so: the definition would have to reference itself, and the
  only handle a component has on another is a URL or an import specifier — it
  can't fetch itself. Recursive components are the one shape jq79 currently
  can't express at all.
- **The unit of reuse and the unit of distribution are welded together.** A child
  that only ever renders inside one parent is still a separately fetched,
  separately cached, separately named public artifact.

## The proposal

A `.html` file is still one component. `<template name="Name">` blocks at the top
level of that file declare **additional components in the same file**, which are:

- **auto-imported** — visible by name to every component in the file, no import,
- **exported** — reachable from outside, alongside the file's own component.

```html
<!-- component1.html -->
<script :setup>
  let rows = []
</script>

<div>
  <C1Row :each="rows" />
</div>

<template name="C1Row">
  <li>{{ item.label }}</li>
  <style scoped>
    li { font-variant-numeric: tabular-nums; }
  </style>
</template>
```

```js
const C1 = await Component79.fetch("./component1.html")
const { C1Row } = C1
```

```js
import C1, { C1Row } from "./component1.html"   // through jq79/vite
```

The bundled form is the point: **default export plus named exports** is exactly
the shape of a JS module, and the runtime `fetch` is that namespace approximated
with own properties on the definition. One mental model, two delivery paths —
which is the same promise the Vite plugin already makes about component source
being portable between `src/` and `public/`.

### Semantics pinned

- **Top level only.** A `<template name>` nested inside another is not a
  declaration; the file's namespace is flat. Names are per file.
- **Names must be PascalCase.** This isn't a style rule, it's what makes the
  export safe: named templates hang off the definition as own properties, and
  every field `Component79` already has is lowercase (`template`, `scripts`,
  `styles`, `modules`, `filename`, `data`). `findComponentKey` already requires
  `/^[A-Z]/` to consider a scope key at all, so the constraint costs nothing and
  buys collision-freedom by construction. A non-PascalCase name is an error, said
  out loud at parse time.
- **A named template is an ordinary component.** Its own `<script>` blocks (both
  modes), its own `<style>`, its own props, its own signature. Nothing about the
  inside of a `<template name>` is special — it is the contents of a `.html` file
  that happens to be written inline.
- **Visibility is symmetric within the file.** Every component in the file sees
  every named template, including itself — which is what makes recursion work.
  The file's own component has no name, so nothing can reference *it*; that
  asymmetry is unavoidable and accepted.
- **A prop wins over a sibling of the same name.** Siblings are seeded on the
  store; a parent passing `:C1Row="Other"` overwrites the seed. That's deliberate
  substitution, and it keeps the rule in `docs/components.md` intact — what
  doesn't carry a `$` still comes from the parent, when the parent bothers to
  send one.
- **A bare top-level `<template>` (no `name`) is an error.** Reserved: if
  `<template :if>`-style invisible wrappers ever land, `name` is the discriminant
  that tells a declaration from a wrapper. Better to reserve it now than to
  discover someone's file means two things.
- **Scoping still stops at the component boundary.** A named template does not
  inherit the file's `<style scoped>`, because it is a different component. No
  new rule — but it is the opposite of what someone writing two templates in one
  file will assume, so it gets a line in the docs.

### How siblings resolve

Not a new resolution path. Sibling components are **seeded onto each component's
store before its setup script runs**, exactly the way `declareProps` seeds
declared prop names — and the store passes class instances through untouched
(`isPlainData` in `src/reactive.ts` names `Component79` in its comment), so a
definition keeps its identity, which `renderNestedComponent`'s `nextDef ===
currentDef` check depends on.

One seed makes all three call sites work, with no changes to any of them:

- as a tag — `findComponentKey` scans `Object.keys` up the prototype chain, so a
  store key is exactly what it's looking for;
- as an expression — `let Current = flag ? C1Row : C1Other` in a setup script,
  and the dynamic-component effect in `renderNestedComponent` follows it;
- inside `:each`, `:if`, anywhere else an expression is evaluated.

Note this is why seeding beats the `$emit` trick in `renderWith`: that proxy is
deliberately `has`/`get`-only so `Object.keys` never sees `$emit` — which means
the component-key scan wouldn't see a sibling added that way either.

Cycles are safe by the same mechanism that makes a late `await import(...)` safe:
the definition is read inside an effect, and a key that isn't a `Component79` yet
renders nothing and re-renders when it becomes one.

## What it costs

- **Parsing descends one level.** `parseComponentString` iterates
  `root.content.children`; a top-level `<template name>` shows up there as an
  element, but its children live in `.content`, not `.children`. The two string
  rewrites (`expandPropsSpread`, `expandSelfClosingTags`) run over the whole
  source first and keep working unchanged.
- **`scoped` must hash per template, not per file.** `scopeHash(component)` is
  computed from the entire source today. Left as is, every component in the file
  shares one `data-jq79` stamp and each one's scoped rules match the others'
  elements. This is a guaranteed bug, not a risk — the hash input becomes the
  template's own source.
- **Clones must carry the sibling map.** `renderNestedComponent` builds each
  usage site's instance from `{ template, scripts, styles, modules, filename }`.
  If siblings aren't in that list, a child rendered at a usage site loses the
  ones it could see in its definition. Same for `hotReplace`.
- **HMR keys by `filename#name`.** `hotRegistry` assumes file = component.
  `hotUpdate` reparses the file into a root plus N named parts and dispatches
  each to the instances registered under its key. Removing or renaming a
  `<template name>` that has live instances falls back to a full reload, joining
  the limitations already documented in `docs/vite-plugin.md`.
- **The Vite plugin emits named exports.** Today it emits one module with a
  default export; it now also needs to name what's in the file. The plugin stays
  a loader — it does not transform component content — because the names come
  from parsing tag attributes, not from rewriting anything inside them.
- **Docs.** `docs/components.md` (the new block, the export shape, the
  prop-beats-sibling rule, the scoping note) and `docs/template-syntax.md` (the
  reserved bare `<template>`).

## What it buys

Recursion, mainly — and that's new capability, not sugar:

```html
<template name="TreeNode">
  <li>
    {{ node.label }}
    <ul :if="node.children">
      <TreeNode :each="node.children" :node="item" />
    </ul>
  </li>
</template>
```

Worth a test of its own and a tutorial exercise, since it's the one shape the
library couldn't express before.

## Rejected

- **A file as a namespace of N equal components** (no default, `fetch` resolves
  to `{ A, B }`). It makes `Component79.fetch` return sometimes a component and
  sometimes a bag, forks every caller, and buys nothing the default-plus-named
  shape doesn't. It also has no natural JS module analogue, which the chosen
  shape has exactly.
- **File-level `<script>` shared by all templates in the file.** Tempting as "one
  place for the helpers", and it's a large new semantics — shared state between
  components through a back door, with no story for when it runs, what store it
  writes, or which instance owns it. Keeping the file's top level *as* the
  component removes the question entirely: a top-level script is that
  component's script, the way it always was.
- **`<component name="Row">` instead of `<template name="Row">`.** `<template>`
  is the tag the browser already refuses to render or execute the contents of,
  and that editors, formatters and HTML language servers already understand. A
  custom tag would be parsed as an unknown element, with its scripts live.
- **`id` instead of `name`.** `id` reads as a document-global handle and invites
  someone to reach for `getElementById`. `name` says "label within this file".
- **Requiring an explicit import of siblings** (`import { C1Row } from "./this"`).
  Honest, and it makes the feature worth roughly nothing: the cost being removed
  here is the ceremony, not the file.

## Open

- **Do named templates get their own `filename` for devtools?** Presumably
  `component1.html#C1Row`, so a setup script's `//# sourceURL` names something
  findable. Needs a look at what the browser does with `#` in a sourceURL.
- **Ordering.** Does a `<template name>` have to appear after the markup that
  uses it, or before, or is it free? Free is the answer the seed-into-store
  implementation gives for free; confirm nothing in parsing depends on order.
- **Does the file's component get an implicit name**, so a child could reference
  its parent? Says no above. Recursion at the file's own top level would then
  require moving it into a named template — which is fine, and maybe even
  clearer, but it should be a decision rather than an accident.
- **`Component79.fetch([urls])`** resolves to an array of the files' own
  components, each with its named templates hanging off it. Nothing to change,
  but worth a test that the array form doesn't drop them.

## 2026-08-05 — decisions: `name` is mandatory, `sourceURL` names the real file

Two of the open points above are closed, and one of them narrows what was
written earlier in this file.

### `<template>` always carries a `name`

Not "a bare `<template>` is reserved" — it is simply an error, everywhere, with
no future meaning held back for it. `<template>` is fully claimed by component
declarations.

The consequence is the part worth writing down: **if invisible directive
wrappers ever land** — the `<template :if="…">` shape that groups siblings
without emitting an element — **they cannot use `<template>`**. They'd need
their own tag (`<fragment>`, or a directive on a real element that removes it).
That's a cost this decision accepts in exchange for one unambiguous rule: inside
a `.html` component, a `<template>` declares a component, always, and a reader
never has to check an attribute to know which of two things they're looking at.

The rest holds: declarations only at the top level, so a `<template name>` nested
inside another is an error too — named or not.

### `//# sourceURL` points at the file, unsuffixed

No `component1.html#C1Row`. A named template's scripts are named after the real
file, because the point of the sourceURL is that the browser can *fetch* what it
names: a real URL keeps breakpoints across reloads and gives devtools a source
tree entry that is actually the source. A `#C1Row` suffix would be a URL that
resolves to the file anyway (the fragment never reaches the server), so it would
buy a label at the cost of pretending to be a distinct resource — and it would be
the only fake URL in the codebase.

What this forces: `ScriptLocation.index` becomes **file-wide, not per-component**.
Today it's the script's index among its component's scripts, which is enough
because a file is a component. With several components per file, a per-component
index would emit `component1.html?jq79-script=0` twice — once for the file's own
setup script and once for `C1Row`'s — and devtools would show only one of them,
which is exactly the failure the index was added to prevent. So the counter runs
across all script blocks in the file, in source order, and each parsed component
carries the indices its blocks were assigned rather than numbering them from
zero.

Line numbers stay as wrong as they already are (the `new Function` header shift,
documented above the naming helpers in `src/jq79.ts`) — a template nested in a
file doesn't make that worse, and doesn't fix it either. A source map is still
the only real answer, and still isn't in scope here.

## 2026-08-05 — addendum: a nameless `<template>` warns, it does not throw

Supersedes "a bare top-level `<template>` is an error" above, and the "error at
parse time" for a non-PascalCase name with it.

Warning and ignoring is the house style, not a softening: `:deep()` in a scoped
block, a non-assignable `:model` expression, a `:props` spread that isn't an
object, `<style lang>` that never reached the bundler — every one of them says
so on the console and degrades. A `<template>` that throws would be the only
place in the library where a malformed piece of markup takes the page down with
it. Parse-time throws are also the worst possible failure for HMR: one bad save
mid-typing and the whole file stops rendering, when the previous version was
fine.

So: **warn, naming the file, and leave the block out of the component.**

Non-PascalCase names get the same treatment for the same reason — and there the
warning is the entire value, because `findComponentKey` only ever considers
`/^[A-Z]/` keys, so `<template name="row">` would silently define a component no
tag could ever reference. That is precisely the class of mistake a warning
exists for.

### What "ignored" means, per position

`<template>` is a real HTML element with real semantics (inert content, parsed
into `.content`), and files may already contain one for native cloning. So
"ignored" cannot mean the same thing everywhere:

| position | `name` | behaviour |
| --- | --- | --- |
| top level | PascalCase | declares a component |
| top level | missing | **warn**, block dropped from the component |
| top level | not PascalCase | **warn**, block dropped from the component |
| nested | any | left alone — a plain, inert `<template>` element, no warning |

Dropping at the top level is what the browser already does *visually* (an inert
`<template>` renders nothing), so nothing that looks right today starts looking
wrong; the change is the console line. A top-level `<template>` that isn't a
declaration is almost certainly a declaration with a typo, which is why that
position is the one that warns.

Nested is left completely alone, and deliberately: that's where the legitimate
native use lives — a `<template>` inside the markup, cloned by hand from
`.content`. A warning there would fire on correct code. The cost is that a
declaration written one level too deep is silently not a declaration; it renders
as an inert element, i.e. nothing appears, which is a visible-enough symptom to
find. Revisit if that turns out to bite in practice.

## 2026-08-05 — closed: the file's component stays anonymous

The open point "does the file's component get an implicit name" is settled: **no**,
and for a better reason than the practical one.

The practical one still holds — a filename-derived name would exist only when a
filename does, and `filename` is optional (`new Component79(src)` from an inline
string has none, which is exactly how the tutorial compiles and mounts what's in
its editor). A component that works bundled and breaks inline is not a component
the library should be able to produce.

But the real reason is that the file's component is the **default**, and a
default is named by whoever imports it:

```js
import Anything from "./component1.html"        // the importer binds the name
const Whatever = await Component79.fetch("…")
```

That is precisely JS's own rule — `export default` is anonymous, named exports
carry their name across the boundary — and this design already committed to the
module shape. So the naming rule inside a file falls out of it rather than being
invented: **a component that has to be referenced by name is a `<template name>`;
the file's component is the one nobody inside the file needs to name.**

Consequence, unchanged and now principled rather than regrettable: recursion at
the top level moves into a named template, with the file's component becoming a
one-line usage of it. Wanting to name it is the signal that it wanted to be a
named template.

## 2026-08-05 — flaky-points audit

Read against the code rather than the plan. Two of these change what's written
above; the rest are decisions the implementation would otherwise make by
accident.

### 1. HMR would swap the wrong component into a child (decides itself, but loudly)

Not "the key needs a name suffix" — worse. `renderNestedComponent` builds every
usage-site instance with `filename: nextDef.filename`, and `hotRegister` keys on
`instance.filename` alone. So every live instance of every named template in a
file registers under **the file**, and `hotUpdate` hands each of them the parts
it parsed for the file's own component. A `C1Row` on screen would be replaced by
the root's template, silently, on the first save.

So the name is not bookkeeping: `ComponentParts` has to carry the template's
name, the clone at [jq79.ts:346](src/jq79.ts#L346) has to carry it too, and the
registry key becomes `filename#name` (bare `filename` for the file's own
component — it has no name, and that is consistent with it being the default).
This is the single highest-risk item in the whole proposal.

### 2. Where siblings actually live: store keys, or a prototype behind the store

The plan above says "seeded onto the store". That works, and it has two problems
worth reopening the decision for:

- **Stale definitions after HMR.** `hotReplace` re-renders an instance with the
  data it already has — which, under store seeding, already contains the *old*
  sibling definitions. A seed that skips existing keys (`if (!(name in store))`,
  the way script vars are pre-declared) would keep the pre-edit child on screen
  forever; a seed that overwrites can't tell a sibling apart from a parent's
  deliberate `:C1Row="Other"` override and would clobber it.
- **Siblings become data.** They'd show up in `Object.keys(store)`, in
  `jq79.data`, in anything that spreads the whole store.

The alternative is one line at [jq79.ts:1472](src/jq79.ts#L1472), where the store
is created from a fresh object literal:

```ts
const store = $reactive(Object.assign(Object.create(siblings), data))
```

Everything the seed was supposed to buy still works, and some of it for free:

- `has` and `get` on the store proxy both go through `Reflect`, so the prototype
  chain is honoured — `with (scope)` resolves a sibling name, and so does any
  template expression;
- `findComponentKey` walks `Object.getPrototypeOf` level by level and calls
  `Object.keys` on each, which is exactly a prototype object's own keys;
- **an own key shadows a prototype key**, so "a parent's prop wins over a
  sibling" stops being a rule to implement and becomes JS;
- HMR swaps the prototype object and every instance sees the new definitions,
  with no way to confuse them with data.

One thing to verify before committing to it: `isPlainData` is
`proto === Object.prototype || proto === null`, so the raw root object is no
longer "plain data". The root is wrapped directly rather than through
`isWrappable`, so this should be inert — but `walkLeaves` and anything else that
asks the question need a read before this is called safe. Recommendation:
prototype, pending that check; the fallback is store seeding plus an explicit
`Set` of sibling-seeded keys for `hotReplace` to overwrite.

### 3. Seeding order (only if store seeding wins)

Siblings go on after `$reactive({ ...data })` and skip names already present, so
a prop the parent passed — which is already in `data` — wins, and `declareProps`
(which skips anything not `undefined`) then fills defaults for the rest. Free
with the prototype variant.

### 4. Recursion meets cyclic data

A new failure mode: today no component can render itself, so an infinite render
is unreachable. With `<TreeNode>` referencing itself, a `node.children` cycle
recurses synchronously until the stack goes. The 100-round cut in the effect
runner does not apply — that guards effect wakeups, not render depth.

Recommendation: **no depth guard.** A `RangeError` names the recursion in its own
stack trace, and any cap deep enough to be safe for real trees is too deep to
prevent anything. But it gets a test that pins the behaviour and a line in the
docs beside the recursion example, so it's documented rather than discovered.

### 5. Which source the root's scope hash is computed from

"Hash per template" leaves the file's own component ambiguous. If it hashes the
whole file, editing any child template changes the *parent's* `data-jq79` stamp:
every instance re-stamps and the refcounted `<style>` in the head is torn down
and rebuilt on an edit that didn't touch it. The root hashes the file **with the
`<template name>` blocks removed**.

### 6. Nothing to decide (checked, works as is)

- The Vite plugin's `SCRIPT_BLOCK_RE` already scans every `<script>` in the file,
  so imports written inside a `<template name>` are hoisted today with no plugin
  change. One `modules` map, shared by every component in the file, is both what
  falls out and what's wanted.
- `acquireStyle` refcounts by content, so two templates in a file with identical
  CSS share one `<style>` — same as two identical files do today.
- Seeding new keys before any effect exists costs nothing, even though a new key
  normally re-runs every effect: at that point there are none.

## 2026-08-05 — resolutions to the audit

### 1. HMR applies to the file, not to the component

Settled, and it's simpler than the `filename#name` key proposed above: **the file
is the hot-reload unit**. The registry stays keyed by `filename` exactly as it is
— no change to `hotKey`, to the dev server, or to how the plugin invalidates.
What changes is dispatch: `hotUpdate` parses the file into its own component plus
its named ones, and hands each registered instance *the parts belonging to the
component it is*.

So an instance still has to know which component of the file it is — a `name`
field on `ComponentParts` and on the instance, carried through the clone at
[jq79.ts:346](src/jq79.ts#L346), read by `hotReplace` to pick its parts. A name
as a selector inside the file's parse, not as a registry key.

This also gives the right answer for free when a `<template name>` is renamed or
deleted: its live instances find no parts under their name, can't be patched, and
the file falls back to a full reload — the rule that already exists, arrived at
without a special case.

### 2. Siblings in the closure — yes, and it isn't an alternative

It's a requirement, and it exposes a hole in "one seed makes everything work":
that was only ever true for setup scripts and templates. **Factory scripts have
no `with`** — `runFactoryScript` compiles a plain strict-mode body with the
helpers as real parameters. A bare `C1Row` in a factory body would not resolve
through the store at all; it would be a `ReferenceError`.

So siblings are passed as **extra parameters to both compiled script bodies**,
alongside `$emit`/`$self`/the rest. In setup mode this composes with the existing
`with`: `scriptScope`'s `has` trap already declines any name that is a helper
(`!(key in helpers)`), so a sibling passed as a parameter resolves lexically and
never round-trips through the store. Real `const`-like bindings, invisible to the
data, in both script modes.

What the closure does *not* reach is the template: `findComponentKey` scans the
scope chain's own keys to turn `<C1Row>` into a lookup, and `evalExpr` evaluates
against the scope object. So the prototype from point 2 of the audit still
carries the tag/expression side. The two are complementary, and each covers what
the other can't:

- **prototype behind the store** → `<C1Row>` as a tag, and any template expression;
- **injected parameters** → `C1Row` as an identifier in setup *and* factory bodies.

### 3. Recursion with cyclic data, in detail

What actually happens, traced through the code:

Rendering is one synchronous stack. `renderNestedComponent` creates the child
instance inside `fx.effect(…)`, and an effect runs immediately on creation, so
the child's `render()` → `renderWith` → `renderNodes` → the next
`renderNestedComponent` all sit on the same stack — no async boundary, no
scheduler, nothing that could break the chain. Depth of recursion = depth of the
data, and each component level costs roughly a dozen frames, so the browser's
limit lands somewhere in the high hundreds of nested components.

The base case is always the data (`:if="node.children"`, an empty `:each`), never
the component — so a cycle in the data has nothing to stop it.

Two things checked, and both are better than feared:

- **Nothing is leaked.** `acquireStyle` runs *after* `renderNodes` in
  `renderWith`, so when the deepest level throws, every level on the stack is
  still inside its own `renderNodes` and no level has acquired a style. The
  half-built fragments are garbage, and `hotRegister` holds only `WeakRef`s.
- **The error is not swallowed.** The effect runner has no `try`/`catch` around
  `run()` (its `finally` only resets a flag), so the `RangeError` propagates out
  through the original `mount()` call.

So the failure is "nothing renders, and a `RangeError` reaches the caller" — not
corruption. Still: the stack is ~900 identical frames, and the page is dead.

**Recommendation reversed from the audit: add the guard.** A module-level depth
counter in `renderNestedComponent`, incremented around the child render, cut at a
generous cap (200 — deeper than any real UI tree, shallower than the stack
limit), with `console.error` naming the tag. This is precisely the shape of the
existing cut in the effect runner, which stopped an effect that writes what it
reads from dying by stack overflow and instead "cut it off and named it". Same
failure mode, same remedy, same wording.

The cost is honest and small: a legitimate tree deeper than the cap renders
truncated with an error on the console, instead of not rendering at all.

### 4. Scoping: a shadow root inside a shadow root

That's the model, and it settles the hash question by analogy rather than by
rule. Each `<template name>` is a boundary as hard as a nested shadow root:

- its `<style scoped>` reaches only its own elements, and is hashed from **its
  own source**;
- the file's own component is hashed from the file **with the `<template name>`
  blocks removed** — an outer shadow root's stylesheet doesn't contain the inner
  one's markup, so editing a child can't re-stamp the parent;
- nothing crosses in either direction, including the direction people will expect
  it to. A parent's `li { … }` does **not** style a `C1Row` that renders an
  `<li>`, even though both live in one file that looks like one document.

That last point is the doc line: *a `<template name>` is a shadow root inside a
shadow root — the file is a container, not a stylesheet*. And it means the
existing behaviour needs no exception for the same-file case: `mountShadow`
already renders nested components inside the parent's shadow root with their
styles inline beside them, and a named template is a nested component like any
other.

### 5. Seeding order — the example

Why order decides the outcome, with a component that declares a prop whose name
collides with a sibling:

```html
<!-- toolbar.html -->
<script :setup="{ Button }">          <!-- declared: a caller may substitute it -->
</script>

<Button :label="'Save'" />

<template name="Button">
  <button>{{ label }}</button>
</template>
```

Three orderings, three outcomes:

- **siblings → props data → `declareProps`.** The parent passed nothing, so
  `Button` is the sibling; `declareProps` skips it (it isn't `undefined`). The
  parent that *did* pass `:Button="Fancy"` had it in `data` before the seed, and
  the seed skips existing names, so the override wins. ✅
- **props data → siblings.** The seed overwrites, and `:Button="Fancy"` silently
  does nothing — the override is accepted and discarded. ❌
- **`declareProps` → siblings.** `declareProps` writes `Button = undefined` for a
  declared prop nobody passed. The seed's guard is `!(name in store)`, and the
  key now *exists* holding `undefined`, so the seed skips — `<Button>` resolves
  to `undefined` and renders nothing at all. A blank toolbar, no error. ❌

The prototype variant gets all three right with no ordering rule to remember:
a parent's prop is an own key and shadows the prototype; `declareProps` reads
`store[name]`, which finds the sibling through the chain and so skips; and
nothing can overwrite what it never wrote. That is the strongest argument for it
over seeding.

## 2026-08-05 — precedence by declaration, and the parent's hash input

### The signature decides, not the runtime

Replaces "an own key shadows the prototype" as the *explanation* of precedence.
Same outcomes in the common cases, but readable from the source instead of from
what the parent happened to pass:

```html
<script :setup="{ Button }"></script>       <!-- declared → the parent's -->
<Button :label="'Save'" />
<template name="Button">…</template>
```

```html
<script :setup></script>                     <!-- not declared → the file's -->
<Button :label="'Save'" />
<template name="Button">…</template>
```

Declaring a name is how a component says "this one comes from outside" — which
is the rule the library already runs on, now reaching sibling components too.
Implementation follows the rule directly: a component's sibling set is the file's
named templates **minus the names its own signature declares**. Static, decided
at parse time, with no ordering question left at runtime — which retires audit
point 5 rather than answering it.

**Open, and the only case the rule doesn't cover: declared, and the parent
passes nothing.** Two coherent readings:

- **`undefined`** — a declared prop nobody passed is `undefined`, exactly like
  every other prop today. `<Button>` renders nothing. Declaring is renouncing:
  the sibling becomes unreachable by that name inside this component.
- **The sibling, as the implicit default** — `{ Button }` reads as "substitutable,
  and mine is the fallback". This also falls straight out of documented prop
  semantics ("a default fills a prop that is `undefined`; the parent's value
  always wins; applied once at setup"): the file's own definition simply *is* the
  default for a prop whose name it shares.

The second makes `:setup="{ Button }"` a substitution point with a working
default, which is what a component library wants and what the first forces you to
write by hand — and there is no hand-written form available, since the name is
taken. Recommendation: the sibling as implicit default. Pending the call.

### The parent's hash input includes the whole file

Adopted, and it retires the objection in audit point 4 — which was priced before
"HMR applies to the file" landed. Once the file is the hot-reload unit, **every
instance of every component in it re-renders on any edit anyway**, so a parent
whose stamp changed because a child was edited costs nothing that wasn't already
being paid.

What it buys: `scopeHash` stays exactly as it is — hash the source string it was
handed, one function, one input, no surgery to excise the `<template>` blocks
from the parent's source before hashing.

Worth being explicit, because the sentence invites the wrong reading: this is
about the hash **input**, not the hash **value**. The file's own component hashes
the whole file; each named template hashes its own source; the values differ, so
the stamps differ, so the scopes stay as separate as the shadow-inside-shadow
model says they are. Nothing crosses — the parent merely reads more bytes to
compute a number.

## 2026-08-05 — closed: declaring is a contract, and using it unfilled is an error

The open case above (declared, parent passes nothing) is settled **against** the
"sibling as implicit default" recommendation:

- **Declared and used as a tag** → it has to be there, and it has to be a
  component. `<Button>` resolving to `undefined`, or to a string, or to anything
  that isn't a `Component79`, is a mistake and says so.
- **Declared and never used as a tag** → nothing happens. A signature is allowed
  to name something this component only passes along, or ignores.

"Fails" in the house sense: `console.error` naming the tag and the component, and
render nothing — the same shape as every other wiring mistake here (a
non-assignable `:model`, an unbound `model:update` name). Not a throw; a bad prop
must not take the page down.

Nothing is lost by the strict reading, which is what makes it the right one. The
substitutable-with-a-default pattern still works — by *not* declaring:

```html
<script :setup></script>       <!-- Button not declared -->
<Button :label="'Save'" />     <!-- the file's own… -->
<template name="Button">…</template>
```

A parent that passes `:Button="Fancy"` writes an own key on the store, which
shadows the prototype the siblings live on, so the parent's wins. So:

- **don't declare** → the file's own, substitutable by a parent that bothers;
- **declare** → a contract: it comes from outside, and using it unfilled is an
  error.

Two patterns, chosen by the signature, neither one needing the other's semantics.

### Where the check lands, and the one false positive to avoid

At the usage site — `renderNestedComponent`'s effect — because "if it isn't used
there is no error" is exactly a usage-site rule. A declared prop does create the
store key (`declareProps` pre-declares it as `undefined`), so `findComponentKey`
resolves the tag and the effect runs and can complain.

The care needed is that `undefined` is currently load-bearing: the effect renders
nothing while the value isn't a `Component79`, which is what lets `<Card>` appear
when an `await import(…)` in the parent resolves. Erroring on `undefined` on
sight would fire on every async import that hasn't landed yet.

Two levels, and the second is worth its cost:

- **Wrong type, immediately.** A value that is neither `undefined` nor a
  `Component79` can never become one by waiting. Error on the spot.
- **Declared, never passed, used.** Knowable synchronously, with no timers: at
  setup, `declareProps` can record which declared names it left `undefined`
  because nothing arrived in `data` — the parent has no binding for that name at
  all, so nothing can arrive later either. A tag reading such a name errors on
  first render. A prop the parent *did* pass, and which is `undefined` for now,
  stays silent and resolves when the parent's import does.

That distinction is a `Set` of unfilled declared names on the instance, and it
buys the precise message ("`<Button>` is declared as a prop and the parent passed
nothing") instead of a timing heuristic.

## 2026-08-05 — implemented

Shipped as described, with the decisions in the sections above. What landed, and
the two things the work itself changed:

- **Parsing** splits into `parseComponentString` (top-level `<template>` blocks
  out, the rest handed on) and `componentPartsFrom` (the script/style/markup
  split of one component, `<style scoped>` resolved against the source it was
  given). The file's own component hashes the whole file, a named one hashes its
  `<template>`'s contents, so the stamps differ and the scopes stay separate.
  Nameless / non-PascalCase / duplicate names warn and are dropped.
- **Resolution** is the prototype *and* the closure, as decided: the store's raw
  object is `Object.assign(Object.create(siblingScope), data)`, and the same
  siblings ride into both script compilers as parameters alongside
  `$emit`/`$self`. `siblingsInScope` drops the names the signature declares.
- **Precedence** needs no ordering rule: a parent's prop is an own key and
  shadows the prototype, and `declareProps` finds the sibling through the chain
  so it never overwrites one with `undefined`.
- **`UNFILLED_PROPS`** is a symbol-keyed, non-enumerable set on the store's raw
  object, so it rides the scope chain into `:each` item scopes without being
  data. `renderNestedComponent` reads it to tell "declared and nobody passed it"
  (an error) from "not yet" (silence, for an import in flight).
- **Depth guard** at 200 in `renderNestedComponent`, wrapped in `try/finally`.
- **HMR** keeps the registry keyed by filename; `hotUpdate` parses once and
  hands each instance the parts of the component it is, by `name`. A name that
  is gone returns 0 for the whole file, which is the existing full-reload
  fallback.
- **The Vite plugin** re-exports top-level declarations by name
  (`declaredComponents`, a depth-tracking tag scan, script/style bodies cut out
  first so a `<` in JS can't be read as a tag).

Two things the implementation found that the plan did not:

1. **A reparsed sibling loses its filename, and an instance with no filename is
   never tracked.** `parseComponentString` builds the sibling definitions before
   anyone has told it where the file came from; the constructor handed the
   origin down, but `hotReplace` did not — so after the *first* hot update, the
   children came back untracked and the *second* edit never reached them. Fixed
   by extracting `adoptSiblings()` and calling it from both. It surfaced as a
   test expecting 2 re-renders and getting 1, which is the only reason it was
   caught before shipping.
2. **`:each` takes `item in items`, always.** The plan's examples
   (`:each="node.children"`) were not valid syntax - the real form is
   `:each="child in node.children" :node="child"`. Worth noting only because
   every recursion example in this file is written the wrong way.
