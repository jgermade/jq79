# Teach `whatChanged` to recognise a splice

**Status:** a proposal, measured but not built. Written to be picked up cold:
everything needed to decide it, do it and check it is here.

`data = data.filter(row => row.id !== id)` - the most ordinary thing anyone
does to a list - costs a full sweep of the store's dependency index today. It
does not have to.

## What `removeRow` actually costs

Three measurements, Chromium, 1,000-row benchmark table:

**It scales with the list, not with what was removed.**

| quitar la fila 4 de | |
|---|---:|
| 250 rows | 3.6ms |
| 500 rows | 7.1ms |
| 1,000 rows | 14.5ms |
| 2,000 rows | 31.7ms |

**The position of the removed row decides the price.**

| removing from 1,000 | |
|---|---:|
| the first | 13.7ms |
| the middle | 13.6ms |
| **the last** | **3.8ms** |

**And the DOM is not in it at all.**

| removing one row's 8 nodes | |
|---|---:|
| `removeChild` | 0.10ms |
| moving them to a detached "trash" node | 0.10ms |
| `Range.deleteContents` | 0.10ms |

So the budget is roughly **3.8ms of `:each` pass** over the survivors (key map,
lookups, positions, longest increasing run - inherent to a keyed diff) and
**~9.8ms of dependency sweep** that the last-row case skips entirely.

The sweep is there because `whatChanged` gives up: removing anything but the
last element shifts every later index, more than half of them "differ",
`GIVE_UP` comes back, and `notify("data")` walks the whole subtree - waking all
~3,000 row bindings to re-render output that did not change.

## Why the give-up is unnecessary here

A store proxy is cached **by object** and keeps the path it was first wrapped
with. Probe, against `dist/jq79.global.js`:

```
identity of the proxy after the shift: true
paths notified when writing to the row that moved: [ 'data.2.label' ]
```

The row `{id:3}` moved from index 2 to index 1 and still notifies as
`data.2.label`. **Indices never tracked position**, so shifting them invalidates
no row binding.

The subtlety that makes the change safe - and the thing to get right - is what
happens to code that reads the array *by index* rather than through a `:each`
item:

- A `:each` row binding reads `row.label`, where `row` is the object's proxy.
  Its dep is that proxy's sticky path (`data.7.label`) and a splice does not
  touch it.
- `{{ data[6].label }}` reads the array first: the array's `get` records
  **`data.6`**, and then the property read goes through the *object's* proxy,
  recording its sticky path (`data.7.label`), not `data.6.label`.

So an index reader always holds the **slot** path, and waking the slots is
enough to make it re-read and pick up its new occupant. What is *not* needed is
the subtree under each slot, which is where the row bindings live.

That argument is the crux of this proposal. It is reasoned from the code and
from the probe above, not yet proven by a test - **write the test first**.

## The change

In `src/reactive.ts`, `whatChanged(previous, next)` currently answers with a
list of changed keys or `GIVE_UP`. Add a splice case before it gives up, for
arrays only:

1. `previous.length === next.length + 1` (a removal; the insertion case is the
   mirror image and worth doing in the same pass).
2. Walk forward to the first `k` where `$toRaw(previous[k]) !== $toRaw(next[k])`.
3. Verify `$toRaw(previous[i + 1]) === $toRaw(next[i])` for every `i >= k`.

O(n), no allocation - the same shape as the existing array walk. Anything else
(two removals, a reorder, a wholesale replacement) still gives up, correctly.

On a match, `notifyReplaced` should announce:

- the container path exactly (`data`) - this is what wakes the `:each`, which
  then does its own keyed diff and removes the row;
- `data.length`;
- the key-set path, as it already does when `keyCount` differs;
- and the **slots** `data.k` … `data.<previous.length - 1>` **exactly** - the
  effects sitting on those nodes, without the subtree sweep each one currently
  drags along.

The cost of that last step is one trie lookup per shifted slot, against a sweep
of every effect under the container.

## What to watch out for

- **`:each` must still hear it.** It reads the list expression, so the
  container's exact notification covers it - but assert that in a test rather
  than assuming it.
- **The removed element's own subtree.** Its bindings are about to be disposed
  by the `:each` pass; `runMatched` already skips effects that are gone. Waking
  them is waste, not error, but there is no reason to.
- **Nested stores** (`bridges`) and `$onAny` re-notification: `notifyReplaced`
  already has rules for both; the splice path must not bypass them.
- **The insertion case** (`[...data, row]` at the front, a `splice(k, 0, x)`)
  is the same walk with the roles swapped, and `2026-08-23.notify-the-difference.md`
  already made the append case cheap - check what it covers before writing new
  code.

## How to check it

- `npm test` - 740 tests, and add ones for the two readers above: a `:each` row
  whose object moved must NOT re-render, `{{ data[6].label }}` MUST.
- `npm run benchmark:ab -- --base main --rounds 4` on a quiet machine, or push
  it: the *Benchmark* workflow reports `Remove a row` against the PR's base
  with the runner's own noise beside it, and the *regression* job blocks if it
  goes the wrong way against the last release.
- The number to beat: `removeRow` was **-22.8%** against `main` (±5.9% noise,
  4 of 4 rounds) on this branch *before* any of this, from the allocation work
  alone. The sweep is the ~9.8ms on top of that.

## What else is on the table, in order

1. **This.** Best value for risk, and it is not only the benchmark:
   `list.filter(...)` is what every real app does.
2. **Clone static skeletons with `cloneNode`** instead of `createElement` per
   node - ~20% of `create1k`, and the largest piece left on the create path.
   Deliberately not bundled here: it is step one of "jq79 compiles at runtime"
   and changes what the library is inside. Its own file, its own decision. See
   `2026-08-23.where-the-create-time-goes.md`.
3. **The per-element scope walk in `findComponentKey`** - ~6% of `create1k`,
   contained, but it has to keep shadowing and late-arriving keys working.

And one thing **not** to do: grouping a row's bindings into a single effect
(~8% of `create1k`). Fine-grained updates are where jq79 actually wins -
`partialUpdate` is 1.6ms against Preact's 11.9, React's 8.8 and Svelte's 1.7 -
and that is the wrong thing to trade for 8% of the operation it is slowest at.
