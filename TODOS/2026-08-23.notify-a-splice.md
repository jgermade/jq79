# Teach `whatChanged` to recognise a splice

**Status:** a proposal, measured but not built. Written to be picked up cold:
everything needed to decide it, do it and check it is here.

`data = data.filter(row => row.id !== id)` - the most ordinary thing anyone
does to a list - costs a full sweep of the store's dependency index today. It
does not have to.

## What `removeRow` actually costs

Three measurements, Chromium, 1,000-row benchmark table:

**It scales with the list, not with what was removed.**

| quitar la fila 4 de | |
|---|---:|
| 250 rows | 3.6ms |
| 500 rows | 7.1ms |
| 1,000 rows | 14.5ms |
| 2,000 rows | 31.7ms |

**The position of the removed row decides the price.**

| removing from 1,000 | |
|---|---:|
| the first | 13.7ms |
| the middle | 13.6ms |
| **the last** | **3.8ms** |

**And the DOM is not in it at all.**

| removing one row's 8 nodes | |
|---|---:|
| `removeChild` | 0.10ms |
| moving them to a detached "trash" node | 0.10ms |
| `Range.deleteContents` | 0.10ms |

So the budget is roughly **3.8ms of `:each` pass** over the survivors (key map,
lookups, positions, longest increasing run - inherent to a keyed diff) and
**~9.8ms of dependency sweep** that the last-row case skips entirely.

The sweep is there because `whatChanged` gives up: removing anything but the
last element shifts every later index, more than half of them "differ",
`GIVE_UP` comes back, and `notify("data")` walks the whole subtree - waking all
~3,000 row bindings to re-render output that did not change.

## Why the give-up is unnecessary here

A store proxy is cached **by object** and keeps the path it was first wrapped
with. Probe, against `dist/jq79.global.js`:

```
identity of the proxy after the shift: true
paths notified when writing to the row that moved: [ 'data.2.label' ]
```

The row `{id:3}` moved from index 2 to index 1 and still notifies as
`data.2.label`. **Indices never tracked position**, so shifting them invalidates
no row binding.

The subtlety that makes the change safe - and the thing to get right - is what
happens to code that reads the array *by index* rather than through a `:each`
item:

- A `:each` row binding reads `row.label`, where `row` is the object's proxy.
  Its dep is that proxy's sticky path (`data.7.label`) and a splice does not
  touch it.
- `{{ data[6].label }}` reads the array first: the array's `get` records
  **`data.6`**, and then the property read goes through the *object's* proxy,
  recording its sticky path (`data.7.label`), not `data.6.label`.

So an index reader always holds the **slot** path, and waking the slots is
enough to make it re-read and pick up its new occupant. What is *not* needed is
the subtree under each slot, which is where the row bindings live.

That argument is the crux of this proposal. It is reasoned from the code and
from the probe above, not yet proven by a test - **write the test first**.

## The change

In `src/reactive.ts`, `whatChanged(previous, next)` currently answers with a
list of changed keys or `GIVE_UP`. Add a splice case before it gives up, for
arrays only:

1. `previous.length === next.length + 1` (a removal; the insertion case is the
   mirror image and worth doing in the same pass).
2. Walk forward to the first `k` where `$toRaw(previous[k]) !== $toRaw(next[k])`.
3. Verify `$toRaw(previous[i + 1]) === $toRaw(next[i])` for every `i >= k`.

O(n), no allocation - the same shape as the existing array walk. Anything else
(two removals, a reorder, a wholesale replacement) still gives up, correctly.

On a match, `notifyReplaced` should announce:

- the container path exactly (`data`) - this is what wakes the `:each`, which
  then does its own keyed diff and removes the row;
- `data.length`;
- the key-set path, as it already does when `keyCount` differs;
- and the **slots** `data.k` … `data.<previous.length - 1>` **exactly** - the
  effects sitting on those nodes, without the subtree sweep each one currently
  drags along.

The cost of that last step is one trie lookup per shifted slot, against a sweep
of every effect under the container.

## What to watch out for

- **`:each` must still hear it.** It reads the list expression, so the
  container's exact notification covers it - but assert that in a test rather
  than assuming it.
- **The removed element's own subtree.** Its bindings are about to be disposed
  by the `:each` pass; `runMatched` already skips effects that are gone. Waking
  them is waste, not error, but there is no reason to.
- **Nested stores** (`bridges`) and `$onAny` re-notification: `notifyReplaced`
  already has rules for both; the splice path must not bypass them.
- **The insertion case** (`[...data, row]` at the front, a `splice(k, 0, x)`)
  is the same walk with the roles swapped, and `2026-08-23.notify-the-difference.md`
  already made the append case cheap - check what it covers before writing new
  code.

## How to check it

- `npm test` - 740 tests, and add ones for the two readers above: a `:each` row
  whose object moved must NOT re-render, `{{ data[6].label }}` MUST.
- `npm run benchmark:ab -- --base main --rounds 4` on a quiet machine, or push
  it: the *Benchmark* workflow reports `Remove a row` against the PR's base
  with the runner's own noise beside it, and the *regression* job blocks if it
  goes the wrong way against the last release.
- The number to beat: `removeRow` was **-22.8%** against `main` (±5.9% noise,
  4 of 4 rounds) on this branch *before* any of this, from the allocation work
  alone. The sweep is the ~9.8ms on top of that.

## What else is on the table, in order

1. **This.** Best value for risk, and it is not only the benchmark:
   `list.filter(...)` is what every real app does.
2. **Clone static skeletons with `cloneNode`** instead of `createElement` per
   node - ~20% of `create1k`, and the largest piece left on the create path.
   Deliberately not bundled here: it is step one of "jq79 compiles at runtime"
   and changes what the library is inside. Its own file, its own decision. See
   `2026-08-23.where-the-create-time-goes.md`.
3. **The per-element scope walk in `findComponentKey`** - ~6% of `create1k`,
   contained, but it has to keep shadowing and late-arriving keys working.

And one thing **not** to do: grouping a row's bindings into a single effect
(~8% of `create1k`). Fine-grained updates are where jq79 actually wins -
`partialUpdate` is 1.6ms against Preact's 11.9, React's 8.8 and Svelte's 1.7 -
and that is the wrong thing to trade for 8% of the operation it is slowest at.

## 2026-08-23, later: built, and the crux argument needed one correction

**This is now landed**, on `claude/notify-splice-x5jknt`: `splicedAt` in
`src/reactive.ts`, `notifyReplaced` waking the shifted slots exactly, one clause
added to `indexable`, and ten tests.

### The test the file asked for first is the one that found the hole

The section above says an index reader "always holds the **slot** path, and
waking the slots is enough to make it re-read". It holds the slot as a *tracked*
dep. It does not keep it as an *indexed* one. `indexable` drops every ancestor
of a deeper dep, so `{{ data[6].label }}` - which tracks `data`, `data.6` and
`data.6.label` - is indexed at the leaf alone. And the comment justifying that
pruning says why: "a write to 'data' or 'data.5' reaches 'data.5.label' through
the subtree sweep anyway". The sweep is the thing this proposal removes, so the
pruning stopped being safe the moment the slots were woken exactly.

Written straight from the proposal, the change was silently wrong in exactly the
way the file said to check: the `:each` rows behaved, and `{{ data[6].label }}`
went on showing the old row's label after a removal ahead of it.

The fix is one clause: an ancestor whose last segment is all digits is a
**slot**, and slots are kept. This is
[`wake-the-item-not-the-slot.md`](2026-08-23.wake-the-item-not-the-slot.md)'s
option 1 ("stop pruning ancestors") in the narrowest form that works - slots
only, not every ancestor - and the cost lands only on effects that read a slot
*and* something under it: the `:each` list effect, which now holds `data.k`
beside `data.k.id`. A row binding never reads the array, holds a single dep and
returns before that code runs, so the 3,000 bindings this is all about pay
nothing.

### What actually wakes the `:each`, measured rather than assumed

The file expected the container's exact notification to carry it. It doesn't:
the list effect reads `data`, but `data` is pruned as an ancestor of
`data.k.id`. What carries it is **`data.length`**, which a splice always changes
and which `notifyReplaced` has collected exactly since
[`notify-the-difference.md`](2026-08-23.notify-the-difference.md). The slot deps
now reach it too. Both are asserted in the tests.

### Still open

- The **insertion** case shares the walk and is tested, but no benchmark
  operation inserts at the front, so it is unmeasured.
- The extra slot deps are a real cost on paper (the `:each` list effect holds
  twice the deps it did) that no measurement on this machine can resolve. The
  isolated instrument from
  [`each-pass-allocations-and-moves.md`](2026-08-23.each-pass-allocations-and-moves.md)
  is the one that could see it.
- Two removals at once, or a `sort`, still give up and sweep. `sort` is the
  interesting one: it is a permutation, so the same argument applies whole -
  no element changed, only positions - and the slots it would have to announce
  are most of the list.

### What CI measured, and the cost that could not be found

The *Benchmark* job on the PR, on a quieter runner than the one above
(4 rounds, noise ±5.5-9% on most operations):

| operation | base | head | delta | per round | verdict |
|---|---:|---:|---:|---|---|
| **Remove a row** | **12.1ms** | **4.8ms** | **-59.1%** | -63.0 / -56.9 / -60.2 / -58.1 | faster, every round |
| Update every 10th row | 1.4ms | 1.4ms | +5.5% | +7.7 / +7.4 / +3.6 / +3.6 | slower every round, under the noise |
| Clear 10,000 rows | 85.8ms | 89.3ms | +5.5% | +9.7 / +8.5 / -0.3 / +2.6 | inside the noise |

Three runners now agree on `removeRow` at -59% to -63%. `partialUpdate` is the
one that leaned the same way in all four rounds, and it is the operation this
branch has most reason to protect - so the slot deps kept by `indexable` were
put to an **isolated instrument**: no DOM, `$reactive` alone, a list effect
reading 1,000 slots and their keys plus three bindings per row, 6 rounds
alternating between a copy of the pre-change `reactive.ts` and this one.

It said +46% on building the index. It was wrong, and the way it was wrong is
worth keeping: with the slot rule **disabled** - the two builds then being the
same code - it still said +35%. Whichever copy ran *second* in a round measured
13-15ms against the other's 8-10ms, because the first run leaves the heap it
grew behind. Alternating the order per round collapses the difference to
nothing in either direction, on both the build and the write.

So the cost of the slot deps is **not measurable here at all**, in either
direction, and `partialUpdate`'s +5.5% is 1-2 ticks of a clock that quantises
to 0.05ms on a 1.4ms operation - which is the same reason `run-ab.mjs` refuses
to gate anything under 5ms.

**One refinement was written and then reverted**, and it is the lead worth
following if someone gets a real instrument: a slot ancestor is redundant when
the effect *also* holds `<container>.length`, because a splice always changes
the length and announces it exactly - so the `:each` list effect, the only
effect that holds a slot dep per row, could keep none of them. It is two lines
in `indexable`. It was reverted because nothing here can show it helps, and
shipping it would mean the diff is no longer the one CI measured at -59%. It
also couples the pruning to `notifyReplaced` always announcing the length
exactly, which is true today and would need to be written down as an invariant
rather than left implicit.

### The reverted refinement, un-reverted: `clearLarge` found the cost

The section above reverted it for want of evidence. A second CI run, on a
quieter runner still, produced the evidence:

| operation | base | head | delta | per round | noise | verdict |
|---|---:|---:|---:|---|---:|---|
| Remove a row | 15.6ms | 6.7ms | -57.6% | -55.7 / -59.1 / -57.4 / -57.8 | ±8.0% | faster, every round |
| Update every 10th row | 1.9ms | 1.9ms | **0.0%** | -2.6 / -2.6 / +2.6 / +5.3 | ±7.9% | inside the noise |
| **Clear 10,000 rows** | 110.3ms | 115.4ms | **+4.5%** | +4.2 / +5.9 / +4.5 / +4.5 | **±2.7%** | **slower, every round** |

`partialUpdate` went to zero, which settles that lean as the clock. `clearLarge`
is the opposite: its delta **exceeds its own noise**, and four rounds landed
within 1.7 points of each other. That is the first signal on this branch that
clears the bar in the wrong direction, and it has a mechanism.

`data = []` never reaches the splice path at all - `whatChanged` returns
`GIVE_UP` on the empty-side guard before anything else - so the notify is
byte-for-byte what it was. What changed is the **size of the index that has to
be torn down**: the `:each` effect over 10,000 rows was holding `data.k`
beside `data.k.id`, twice the entries, every one of them removed one at a time
when the list goes.

So the clause is in after all: a slot ancestor is redundant when the effect
also holds that container's `length`. The list effect keeps none of its slot
deps; an index reader, which reads no length, keeps all of it. `create10k` had
already said this was invisible on the *building* side (-0.1%); it is the
teardown that shows.

The invariant it rests on now has a test of its own -
*"wakes a slot reader that also read the length, through the length"* - so if
the splice path ever stops announcing the length exactly, something goes red
instead of a binding going quietly stale.

### And what the clause cost on its way in

The run that carried it (`f699e7b`):

| operation | base | head | delta | per round | noise | verdict |
|---|---:|---:|---:|---|---:|---|
| Remove a row | 14.8ms | 6.6ms | -56.2% | -54.9 / -53.7 / -57.6 / -59.6 | ±12.9% | faster, every round |
| Clear 10,000 rows | 106.0ms | 109.0ms | +2.6% | +9.2 / -0.8 / -0.9 / +6.0 | ±8.4% | inside the noise |
| Append 1,000 to 10,000 | 69.3ms | 73.0ms | +5.4% | +2.0 / +3.2 / +7.6 / +9.3 | ±9.6% | slower every round |

`clearLarge`'s tight signal is gone - the per-round signs no longer agree and
the delta halved. That is **not** proof the clause fixed it: this run's noise
on that operation was ±8.4% against the previous run's ±2.7%, so it could not
have resolved a +4.5% either way. What can be said is that the sharp,
repeatable version of the signal did not survive, and the mechanism it had is
gone by construction.

`appendToLarge` is the one to look at now: it has leaned slower in all four CI
runs of this branch (+4.3%, +3.5%, +5.4%), the last of them in every round.
Part of that was self-inflicted and is fixed - the clause built a
`` `${container}.length` `` string for **every slot it met**, which for a list
effect is one per row, ~10,000 allocations per re-sync. The containers whose
length an effect tracks are now resolved in one pass over its deps, and the
container of each segment is carried down the walk instead of being re-sliced.
No behaviour changes; the walk allocates exactly what it allocated before this
branch.

Whether anything is left in `appendToLarge` after that is unmeasured, and it is
the open question this file ends on.
