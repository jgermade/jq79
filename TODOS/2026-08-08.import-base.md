# fix: a relative import resolves against the component that wrote it

`import("./x.js")` in a setup or factory script currently resolves against
`dist/jq79.js`, and `import("./x.html")` against the page. Both should resolve
against the `.html` file the call was written in — the one base every other
relative reference on the web platform uses.

Status: proposal.

## Today

A component fetched from `/components/app.html`:

```html
<script :setup>
  const { opfsService } = await import("./services/opfs.service.js")
  const Row = await import("./row.html")
</script>
```

Neither specifier means what it reads as.

`import()` in a script is rewritten to `$__import`
([`transform.ts`](../src/transform.ts)), which lands on `$import` and then
`importResource` ([`jq79.ts`](../src/jq79.ts)):

```ts
const importResource = (url: string): Promise<any> =>
  /\.html?([?#]|$)/.test(url) ? fetchComponent(url) : import(url)
```

Two different bases fall out of those two branches, and neither is the
component:

- `import(url)` is a *native* dynamic import evaluated inside the library
  module, so the browser resolves it against **`dist/jq79.js`**.
  `./services/opfs.service.js` becomes
  `/node_modules/jq79/dist/services/opfs.service.js` — a 404 in every layout.
  It is not a browser rule we can opt out of: a specifier resolves against the
  module holding the `import()`, and the only module in play is ours.
- `fetchComponent` calls `fetch(url)`, which resolves against **the document**.
  `./row.html` becomes `/row.html`, not `/components/row.html` — right only
  when the components sit in the page's own directory, which is why
  [`tests/fixtures/no-bundle`](../tests/fixtures/no-bundle) (all flat) has
  never caught it.

So a nested component can only reach a sibling by writing the path from the
site root, and a plain `.js` module can't be reached relatively at all. Under
the [Vite plugin](../docs/vite-plugin.md) both work, because literal specifiers
are hoisted into the `modules` map at build time and `$import` finds them there
before any of this runs — which is why the bug reads as "it works bundled".

There is a third symptom worth recording: the `jq79.global.js` build is loaded
by a classic `<script src>`, where a dynamic `import()` resolves against the
document instead of the script. The same component therefore resolves `.js`
imports differently depending on which artifact the page loaded.

## The proposal

One base for every specifier the runtime resolves: **the component's own file**.

`$import` gains a resolution step between the `modules` lookup and
`importResource`:

1. the `modules` map, keyed by the **literal specifier as written** — unchanged,
   so nothing about a bundled build moves;
2. specifiers starting with `./` or `../` are resolved against
   `new URL(this.filename, document.baseURI)`, falling back to
   `document.baseURI` when the component has no filename;
3. `importResource` with the result.

`this.filename` is already carried for exactly this kind of question — it names
scripts in devtools and keys the hot-reload registry — and `hotKey` already
absolutizes it the same way, for the same reason ("the same file reaches the
runtime under different names… resolving against the page is what settles
them"). This is that sentence applied one level further out.

```
page  /index.html
app   /components/app.html      import("./services/opfs.service.js")
                                  → /components/services/opfs.service.js
                                import("./row.html")
                                  → /components/row.html
```

### Only `./` and `../`

Everything else passes through untouched:

- **bare** (`"lodash"`, `"jq79"`) — resolving it would produce a URL and take
  the specifier away from the import map / native resolver that owns it.
  `new URL("lodash", base)` also silently yields a *path*, which is worse than
  the error the browser would have raised.
- **root-absolute** (`/x.js`) and **full URLs** — already mean one thing under
  any base, so resolving them changes nothing but the string.

That keeps the rule the browser's rule rather than a third one of our own, and
it bounds the blast radius to the single form that is broken today.

### An inline component has no filename

`new Component79(src)` with no `filename` keeps `document.baseURI`: today's
behavior for `.html`, and a strict improvement for `.js` (page-relative instead
of dist-relative). There is nothing better to fall back to — the source came
from a string, so it has no location.

Siblings in a [multi-template file](2026-08-05.multi-template-file.md) already
inherit the file's filename, so they resolve against it too, which is right:
they *are* that file.

## What it costs

**`./x.html` changes meaning.** Today it resolves against the page; after this
it resolves against the component. Code breaks only if a component whose
directory differs from the page's writes `./sibling.html` *intending* the
page's directory — i.e. writing `./` to mean "not next to me". Working code
that lives in a flat layout sees no change (both bases agree), and working code
in a nested layout is already written root-absolute, because relative was the
option that didn't work.

It is still a behavior change to the fetch chain and belongs in the release
notes, not in a patch bullet.

**Hot reload gets more precise, not less.** The child is now fetched under its
resolved URL, so `fetchComponent` records `filename: "/components/row.html"`
where it used to record `"/row.html"` — which is the key the
[dev server](../docs/dev-server.md) watches under. Nested directories start
matching where they previously missed.

## Rejected

**Rewrite `import.meta.url` in the transform.** The natural JS spelling
(`new URL("./x.js", import.meta.url)`) can't work: setup scripts compile with
`new Function` because they need `with`, and `import.meta` in a Function body
is a SyntaxError. Faking it — rewriting the token to an injected string —
means the scanner has to distinguish `import.meta` from `import(` from
`obj.import.meta`, and hands users a spelling that looks like the real thing
and isn't. The cost lands on every script to fix a call the runtime can
resolve on its own.

**Resolve at parse time, rewriting specifiers into the compiled code.** Moves
the base from the instance to the definition, so a component reparsed from
another location gets stale URLs baked in, and the `modules` map (keyed by the
literal) stops matching. Resolution belongs where the instance is.

**Leave `.js` alone and fix only `.html`.** Halves the change and keeps the
worst half of the confusion: two branches of one function, two bases, no rule
a user could state.

## Still open

- Under Vite, `filename` is the **build-time source path**
  (`relative(config.root, file)`, e.g. `src/components/app.html`). Hoisted
  literals never reach this code, but a *computed* specifier
  (`import(`./${name}.js`)`) falls through to runtime resolution and would
  resolve against a path that doesn't exist in the built output. It doesn't
  work today either (it resolves against the chunk), so this is not a
  regression — but the honest fix is for the plugin to emit
  `import.meta.url` as the filename rather than the source path, and that is
  its own change.
- Whether `Component79.fetch("./app.html")` called from a *module* should
  resolve against that module rather than the page. Same class of problem, one
  level up, and the same answer is not obviously available: the library can't
  see its caller's URL.
