# Where create1k's and replace1k's milliseconds actually go

**Status:** a measurement, plus the one change it justified (landed). It
answers the question `2026-08-23.create-gap-is-diffuse.md` left standing —
*why are create and replace still the two slow operations* — with a budget
rather than a profile, because the sampler could never attribute the time
(50-63% of every CPU profile on this branch lands in `(program)`).

## Method

Sampling was the wrong instrument, so this is ablation. The benchmark row is
built up one directive at a time and each variant is timed the way
`scripts/lib/benchmark-ops.mjs` times a click — set `data`, drain the
microtask queue — 20 passes, first 5 discarded, median reported. Chromium
1194, the same 4-core Xeon 2.10GHz box the published results were made on.
`_ablation*.mjs`-style drivers, not checked in: they are twenty lines of
`page.evaluate` around `new Component79(src).mount(host)`.

A hand-written control builds the *same* 8 elements and 2 listeners per row
with `document.createElement`, so the floor is measured and not guessed.

## The budget, per 1,000 rows

| variant | create |
|---|---|
| vanilla control — 8 elements + 2 listeners per row, by hand | **9.0ms** |
| jq79, 8 elements per row, zero bindings | 18-22ms |
| + 2 text interpolations | ~30ms |
| + 2 `@click` | ~37ms |
| + `:class` (the full benchmark row) | **41-45ms** |
| tear the same 1,000 rows down (`data = []`) | 7.5ms |
| replace 1,000 rows with 1,000 new ones | **55-60ms** |

So `replace1k` is not its own problem: it is `create1k` plus the teardown of
the outgoing rows, and both halves are already accounted for above.

## What each piece of a row costs

Measured on a one-`<td>` row, so the deltas are the directive alone (create,
per 1,000 rows):

| row template | create | delta |
|---|---|---|
| `<tr :each :key><td>x</td></tr>` | 7.1-7.6ms | the floor for 2,000 elements |
| `<td>{{ 1 }}</td>` | 8.6-8.7ms | +1.3µs — effect + compiled call, no deps |
| `<td>{{ row.id }}</td>` | 10.4-11.0ms | +3.4µs — adds the proxy read and the dep index |
| `<td :text="row.id">` | 9.1-9.7ms | +2.0µs — the same binding without `interpolate`'s regex |
| `<td @click="select(row.id)">` | 8.3-8.5ms | +1.0µs |
| `<td :class="{ danger: … }">` | 12.8-13.4ms | +5.5µs |
| `<td :class.danger="…">` | 13.9ms | the shorthand is not cheaper |

Three things worth keeping:

- **A `:class` binding is the most expensive directive in the row**, ~4x a
  text interpolation, and all three spellings (object, string, `.danger`
  shorthand) cost the same. The price is the effect plus `classNames` plus the
  `classList` diff, not the object literal — so there is no template-side
  workaround to recommend to users.
- **`{{ }}` costs ~1.4µs more than `:text`** for the identical binding: that is
  `interpolate`'s `String.replace` over the whole text node, per instance.
- **Element construction itself is ~2.3µs against the control's ~1.1µs.**
  Every element pays `findComponentKey`, the attribute walk, and the
  `HTMLUnknownElement` check before any binding exists.

## The change this justified

`renderNode` allocated, *for every element it rendered*: one array of pairs
from `Object.entries(node.attrs)`, one two-element array per attribute inside
it, and three more arrays for the `entries().filter().map()` that collects
`:class.` toggles — which the overwhelming majority of elements do not have.
A 1,000-row benchmark row is 8,000 elements, so that is tens of thousands of
short-lived arrays per pass, and the scavenger shows up in every trace.

Both walks are now `for...in` with no intermediate arrays, and the toggle list
stays `null` until a `:class.` attribute is actually found. Nothing read the
pairs as pairs, so the semantics are identical; the 740 tests pass unchanged.

Seven interleaved before/after runs, medians:

| | before | after |
|---|---|---|
| create1k | 42.6ms | 37.0ms (**-13%**) |
| replace1k | 58.7ms | 45.6ms (**-22%**) |

Replace gains more than create because it allocates the garbage twice over —
once for the outgoing rows' render, once for the incoming — while also
running teardown, so it was the pass most exposed to the scavenger.

The published `benchmark-results.json` / `comparison-results.json` were not
regenerated here: a fair comparison run has to re-measure every framework on
one machine in one session, and this was measured on a shared VM alongside
other work.

## What is left, and what it would take

The remaining distance is what the previous file called diffuse, and this
budget says the same thing in numbers: after the fix, ~9ms of the ~37ms is DOM
the control pays too, ~10ms is per-element interpretation, and the rest is
one effect per binding — allocate it, run it inside a tracking frame, resolve
its names through `with ($scope)` (see the `with` note in
`docs/development.md`), read them through the store proxy, index the deps in
the trie. Svelte pays none of that per element because its compiler resolved
it all at build time.

Two things measured but not landed, both small:

- **The per-element scope walk in `findComponentKey`.** Even memoized, every
  element re-walks the `:each` item scope's own keys before reaching the
  memo's base. Short-circuiting it entirely (a spike that breaks shadowing, so
  not shippable as written) is worth ~2.7ms of create1k — ~6%. A shippable
  version would cache "this scope level declares no capitalised key" on the
  item scope when `renderEach` creates it.
- **Splitting a text template's `{{ }}` parts at parse time**, so a single-
  expression text node calls the compiled function directly instead of going
  through `String.replace`. Worth ~1.4µs per interpolation, ~2.8ms on this row.

Anything larger is still structural, and `2026-08-23.create-gap-is-diffuse.md`
already names the two honest options.
