# Where create1k's and replace1k's milliseconds actually go

**Status:** a measurement, plus the one change it justified (landed). It
answers the question `2026-08-23.create-gap-is-diffuse.md` left standing —
*why are create and replace still the two slow operations* — with a budget
rather than a profile, because the sampler could never attribute the time
(50-63% of every CPU profile on this branch lands in `(program)`).

## Method

Sampling was the wrong instrument, so this is ablation. The benchmark row is
built up one directive at a time and each variant is timed the way
`scripts/lib/benchmark-ops.mjs` times a click — set `data`, drain the
microtask queue — 20 passes, first 5 discarded, median reported. Chromium
1194, the same 4-core Xeon 2.10GHz box the published results were made on.
`_ablation*.mjs`-style drivers, not checked in: they are twenty lines of
`page.evaluate` around `new Component79(src).mount(host)`.

A hand-written control builds the *same* 8 elements and 2 listeners per row
with `document.createElement`, so the floor is measured and not guessed.

## The budget, per 1,000 rows

| variant | create |
|---|---|
| vanilla control — 8 elements + 2 listeners per row, by hand | **9.0ms** |
| jq79, 8 elements per row, zero bindings | 18-22ms |
| + 2 text interpolations | ~30ms |
| + 2 `@click` | ~37ms |
| + `:class` (the full benchmark row) | **41-45ms** |
| tear the same 1,000 rows down (`data = []`) | 7.5ms |
| replace 1,000 rows with 1,000 new ones | **55-60ms** |

So `replace1k` is not its own problem: it is `create1k` plus the teardown of
the outgoing rows, and both halves are already accounted for above.

## What each piece of a row costs

Measured on a one-`<td>` row, so the deltas are the directive alone (create,
per 1,000 rows):

| row template | create | delta |
|---|---|---|
| `<tr :each :key><td>x</td></tr>` | 7.1-7.6ms | the floor for 2,000 elements |
| `<td>{{ 1 }}</td>` | 8.6-8.7ms | +1.3µs — effect + compiled call, no deps |
| `<td>{{ row.id }}</td>` | 10.4-11.0ms | +3.4µs — adds the proxy read and the dep index |
| `<td :text="row.id">` | 9.1-9.7ms | +2.0µs — the same binding without `interpolate`'s regex |
| `<td @click="select(row.id)">` | 8.3-8.5ms | +1.0µs |
| `<td :class="{ danger: … }">` | 12.8-13.4ms | +5.5µs |
| `<td :class.danger="…">` | 13.9ms | the shorthand is not cheaper |

Three things worth keeping:

- **A `:class` binding is the most expensive directive in the row**, ~4x a
  text interpolation, and all three spellings (object, string, `.danger`
  shorthand) cost the same. The price is the effect plus `classNames` plus the
  `classList` diff, not the object literal — so there is no template-side
  workaround to recommend to users.
- **`{{ }}` costs ~1.4µs more than `:text`** for the identical binding: that is
  `interpolate`'s `String.replace` over the whole text node, per instance.
- **Element construction itself is ~2.3µs against the control's ~1.1µs.**
  Every element pays `findComponentKey`, the attribute walk, and the
  `HTMLUnknownElement` check before any binding exists.

## The change this justified

`renderNode` allocated, *for every element it rendered*: one array of pairs
from `Object.entries(node.attrs)`, one two-element array per attribute inside
it, and three more arrays for the `entries().filter().map()` that collects
`:class.` toggles — which the overwhelming majority of elements do not have.
A 1,000-row benchmark row is 8,000 elements, so that is tens of thousands of
short-lived arrays per pass, and the scavenger shows up in every trace.

Both walks are now `for...in` with no intermediate arrays, and the toggle list
stays `null` until a `:class.` attribute is actually found. Nothing read the
pairs as pairs, so the semantics are identical; the 740 tests pass unchanged.

Seven interleaved before/after runs, medians:

| | before | after |
|---|---|---|
| create1k | 42.6ms | 37.0ms (**-13%**) |
| replace1k | 58.7ms | 45.6ms (**-22%**) |

Replace gains more than create because it allocates the garbage twice over —
once for the outgoing rows' render, once for the incoming — while also
running teardown, so it was the pass most exposed to the scavenger.

The published `benchmark-results.json` / `comparison-results.json` were not
regenerated here: a fair comparison run has to re-measure every framework on
one machine in one session, and this was measured on a shared VM alongside
other work.

## What is left, and what it would take

The remaining distance is what the previous file called diffuse, and this
budget says the same thing in numbers: after the fix, ~9ms of the ~37ms is DOM
the control pays too, ~10ms is per-element interpretation, and the rest is
one effect per binding — allocate it, run it inside a tracking frame, resolve
its names through `with ($scope)` (see the `with` note in
`docs/development.md`), read them through the store proxy, index the deps in
the trie. Svelte pays none of that per element because its compiler resolved
it all at build time.

Two things measured but not landed, both small:

- **The per-element scope walk in `findComponentKey`.** Even memoized, every
  element re-walks the `:each` item scope's own keys before reaching the
  memo's base. Short-circuiting it entirely (a spike that breaks shadowing, so
  not shippable as written) is worth ~2.7ms of create1k — ~6%. A shippable
  version would cache "this scope level declares no capitalised key" on the
  item scope when `renderEach` creates it.
- **Splitting a text template's `{{ }}` parts at parse time**, so a single-
  expression text node calls the compiled function directly instead of going
  through `String.replace`. Worth ~1.4µs per interpolation, ~2.8ms on this row.

Anything larger is still structural, and `2026-08-23.create-gap-is-diffuse.md`
already names the two honest options.

## The teardown, which is half of replace1k and all of clearLarge

`2026-08-23.create-gap-is-diffuse.md` left `clearLarge` open at +23ms against
what this branch found it, unprofiled. Decomposed the same way, 10,000 rows,
by building the row up from nothing:

| | create10k | clearLarge |
|---|---|---|
| static row, 8 elements, **no binding effects at all** | 214ms | **39.7ms** |
| + 2 interpolations (20,000 effects) | 327ms | 57.2ms |
| full row (30,000 effects) | 421ms | 76.2ms |
| hand-written control: remove 80,000 nodes | — | **6.1ms** |
| core alone: dispose 30,000 one-dep effects | — | 19.9ms |

Three things fall out of it:

- **~34ms of `clearLarge` is jq79's per-row bookkeeping with no effects
  involved at all** - 6.1ms of the 39.7ms is the DOM. That is ~3.4µs a row for
  the `EffectScope` (two arrays and four closures per row), the entry record,
  the range, and the `:each` key map. It is the largest single piece of the
  teardown and it is not the dep index, which is where the branch had been
  looking.
- **Effects add ~1.2µs each to the teardown**, but the core disposes them for
  ~0.66µs (19.9ms for 30,000). The gap - call it 16ms of the full row's 76ms -
  is `notify` collecting all 30,000 into the matched set on the way to waking
  the one `:each` effect that then disposes them. They are checked against
  `effects` and skipped, so the collection is pure cost: `data = []` knows it
  is replacing the whole container.
- **Removing DOM is nearly free** (6.1ms for 80,000 nodes) and needs no work.

## Compiling at runtime: what it would and would not buy

"No compiler" in `AGENTS.md` is a claim about the *build*, not about codegen -
`compileExpr` already calls `new Function` for every expression in every
template. So generating code once per component definition breaks no promise.
The question is only what it recovers, and half of that is now measured.

**Deriving the per-node work once and keeping it on the node: a wash.** This is
the option `2026-08-23.create-gap-is-diffuse.md` left open after the `WeakMap`
spike failed - a field read instead of a probe. Built it: a `NodePlan` under a
symbol on the `TemplateNode`, holding the attribute classification as typed
ops, the `:class.` toggle list and the static class `Set`, so `renderNode`
examines no attribute name at all and the render loop is a switch on an
integer. 740 tests pass. Eight interleaved runs against HEAD:

| | HEAD | plan on node |
|---|---|---|
| create1k | 39.7ms | 37.9ms |
| replace1k | 51.1ms | 52.9ms |

Inside the noise of this box (±10ms run to run), in both directions. Reverted.
The lesson is the same one the `WeakMap` spike taught, and it is now the
second time it has been paid for: **the classification was never the cost - the
allocation was**, and the `for...in` change above already took it. String
`startsWith` tests on a handful of attribute names are free.

**Where a real runtime compiler would actually get its money.** Re-measured on
HEAD, per 1,000 rows:

| | |
|---|---|
| hand-written control, `createElement` per node | ~8ms |
| hand-written control, `cloneNode` of the row | ~5ms |
| jq79, 8 elements per row, zero bindings | ~19ms |
| jq79, the full benchmark row | ~50ms |

So ~11ms is jq79 walking the AST and deciding what to build, ~8ms is DOM
anybody would pay, and the remaining ~30ms is one effect per binding:
allocate, run inside a tracking frame, resolve names through `with ($scope)`,
read through the proxy, index the deps.

Codegen attacks the first two: emit, once per definition, a function that
clones a `<template>` for each contiguous static subtree and reaches its
binding points by `firstChild`/`nextSibling` instead of re-deriving the tree.
That is the ~11ms plus ~3ms of the floor - call it 20% of create1k, and it
composes with everything above.

It does **not** attack the ~30ms, and only a slice of that slice is the effect
*count*. Measured in the core alone, no DOM involved - 1,000 rows of three
bindings each, `store.$effect` straight over a `$reactive`:

| arrangement | create | write to 100 rows |
|---|---|---|
| 3 effects, one dep each (what renderNode does) | 8-10.6ms | 0.5-0.6ms |
| 1 effect reading three deps (what Svelte compiles) | 4.5-6.9ms | 0.5-0.6ms |
| 1 effect, one dep (the floor) | 2.6-3.7ms | 0.4-0.6ms |

So an effect costs ~1.9µs simply to exist and ~1.9µs per dep it tracks: about
half and half. Grouping a row's three bindings into one effect removes the
fixed cost of the second and third only - **~3.8ms per 1,000 rows, ~8% of
create1k** - and leaves every dep exactly where it was. The rest of the ~30ms
is the dep tracking itself, the proxy reads, evaluating through `with`,
`interpolate`'s regex and the `classList` diff.

The notify side does not object: re-running one effect that reads three deps
costs the same as waking one of three. What grouping *would* cost is redundant
DOM writes - a row whose label changed would re-write its id text node too -
which is why Svelte's `set_text` compares before writing, and why jq79's text
binding would have to as well.

Svelte gets the grouping for free because it knows at compile time which
signals a row's bindings read; jq79 would have to extract identifiers from
expression source to do the same. That is possible - it already parses the expressions - but it is the
point where the runtime stops being an interpreter with a cache in front of it
and becomes a compiler with a second implementation of `renderNode` to keep in
sync. Worth its own file and its own decision, not a drive-by.


## Second pass: what landed, and what the box could not answer

Four changes were picked off the list this file leaves at the end. Three
landed; one was dropped by its own measurement; and the box stopped being able
to price any of them, which is the most useful thing in this section.

**Dropped: skipping the effect sweep when a container is replaced wholesale.**
The idea was that `data = []` collects all 30,000 row effects into the matched
set only to skip them - the `:each` effect runs first and disposes them. A
probe around `notify` says the collection is **8.6-11.3ms of an 80ms
`clearLarge`**, not the ~16ms this file inferred, and `runMatched` is the other
70ms. Not worth reordering a notify for: running exact-path effects before
subtree ones changes the creation-order guarantee `runMatched` exists to keep.

**Landed, in the order the probe found them:**

| | before | after |
|---|---|---|
| `fx.dispose` inside `clearLarge` | 27.7-35.2ms | 23.3-34.1ms |
| DOM removal inside `clearLarge` | 19.4-21.9ms | 16.2-20.9ms |

- **`EffectScope` is a class.** It is built once per `:each` row, and the
  closure form allocated two arrays and four closures for every one of them -
  70,000 objects for a 10,000-row table, to hold three disposers each. Methods
  live on the prototype, the arrays are built on demand, the per-effect options
  object is one per scope instead of one per effect, and `dispose` detaches its
  list rather than `splice(0)`-ing a copy of it.
- **A removal run is a span, not a list of the ranges inside it.** Only its two
  ends are ever read, and clearing 10,000 rows was building a 10,000-entry
  array to hand over two of them. The dead-entry test is a flag on the entry
  instead of a `Set` lookup per row.
- **Text templates are split into parts once, not re-scanned per instance.**
  `interpolate` ran `String.replace` over the whole text on every run of every
  instance; the parts are cached by template text, like `compileExpr`'s
  functions. A single-expression node writes `String(value ?? "")` directly.
  Isolated, on a three-expression text node: create1k 17.9/19.2ms -> 16.4/16.8.
  On the benchmark row - one expression per text node - it is a wash.
- **A text binding compares before writing.** What `set_text` does in Svelte's
  compiled output, and what makes a grouped or refreshed re-run free when the
  string did not change.

## Measuring on this box, which is the caveat over everything above

Late in this session the shared VM became too noisy to price a change under
~50%. The paired in-page harness - both bundles in one document, alternating
rounds - run with **HEAD against itself** produced deltas of +22%, -23%, -9%,
+17%, +50%, -5% on create1k and replace1k across three runs. Anything in this
file at that magnitude is a description of one afternoon's VM, not of the code.

What did survive is what was measured either **in isolation** (a micro over
`$reactive` with no DOM, a probe with `performance.now()` inside the operation)
or **by sign across separate processes** - the `for...in` change was 7 of 7
runs in the same direction on replace1k, which is worth more than any single
pair of medians. Use those two methods here, not a stopwatch around a click.
