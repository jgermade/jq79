# Replacing a list should notify what changed in it, not the whole list

**Status:** proposal. Follows the profile of `appendToLarge` taken after
[`2026-08-23.batch-range-removal.md`](2026-08-23.batch-range-removal.md).
Nothing implemented at the time of writing.

## The measurement

`appendToLarge` — `data = [...data, ...buildData(1000)]` over 10,000 existing
rows — costs **208ms**, against 58ms to build 1,000 rows from nothing. Profiled:

| self | share | frame |
|---|---|---|
| 320.7ms | 55.9% | `(program)` |
| 27.7ms | **4.8%** | the text-interpolation effect (`textContent = interpolate(...)`) |
| 21.5ms | 3.7% | the store proxy's `get` trap |
| 12.3ms | 2.1% | the `:class` directive's effect |
| 9.7ms | 1.7% | `appendChild` (native) |

The top JS frames are not the thousand new rows being built — they are the
**thirty thousand bindings of the ten thousand existing rows re-running**.
`data = [...]` notifies `"data"`, and the subtree sweep wakes everything
indexed under it. Every one of those effects re-reads the same row object and
writes back the string it already wrote.

An independent check of the order of magnitude: `partialUpdate` runs ~300
effects in 1.4ms, so ~200 runs/ms; 30,000 spurious runs is ~150ms of the 208.

## Why the sweep is wrong here

The array object changed. Almost nothing *in* it did — `[...data, ...new]`
holds the very same row objects at indices 0..9999, and `Object.is` says so.
The subtree sweep is a statement about paths, not about values: `data.5.label`
is "under" `data`, so it is woken, even though `data[5]` is the same object it
was and `label` on it is the same string.

The store already refuses this kind of pointless wake elsewhere — a primitive
write that changes nothing notifies nobody
(`2026-07-15.effect-runner-hardening.md`). This is the same idea one level up.

## The proposal

When a write replaces an array or plain object with another array or plain
object at the same key, compare them **one level deep** and notify only what
differs, instead of notifying the container and sweeping its subtree:

- effects whose dep is the container path *exactly* (and `deep` ones) still
  wake — the container really did change, and `{{ data }}` or a prop forwarding
  it must hear it;
- for each index/key where `Object.is(oldRaw[k], newRaw[k])` is false, notify
  `container.k` normally, which sweeps that element's subtree — correct, that
  element is a different value;
- if the key set changed, wake the key-set dep, and for an array notify
  `container.length`.

One level is enough for the case that matters: elements that are the same
object are skipped wholesale, and elements that differ are notified as a
change, whatever is inside them. `data = data.map(r => ({...r}))` — every
element a fresh object — notifies every index and ends up doing exactly what
today does, plus one `Object.is` per element.

### The `length` rule has to be split

`"list.length"` currently wakes the array's whole subtree, because a truncation
deletes the dead slots below the proxy and an effect that read `list[0]` has no
other way to hear it (`2026-08-23.narrow-the-wake-rule.md`, mechanism 2). That
is a statement about **shrinking**. Growing an array removes nothing, so an
effect that read `list[5]` is unaffected — and if the coarse rule stayed as it
is, notifying `length` after an append would wake the 30,000 effects this
change exists to leave alone.

So the sweep on a `length` write becomes shrink-only. The `:each` effect still
wakes on either, because it reads `length` on its way through `list.map` and
holds it as an ordinary dep.

## What it costs

- One `Object.is` per element on every array/object assignment. For an 11,000
  element array that is 11,000 comparisons against the 30,000 effect runs it
  avoids.
- A second `notify` shape (wake this node exactly, don't sweep) alongside the
  existing one. `notifyKeys` is already that shape, so it is a generalization
  of code that exists rather than a new concept.
- `$on`/`$onAny` listeners on the container still fire once for the container,
  as they do now, and now *also* fire for the changed elements. That is more
  faithful than today (a listener on `"data.3"` currently hears nothing when
  `data` is replaced with an array whose element 3 differs) but it is a
  behaviour change to pin.
- The same-reference deep-touch channel is untouched: that is
  `store.user = sameObject`, where old and new are the *same* object, not two
  objects with equal contents. Diffing only happens when they are different
  objects.

## Rejected

- **Skipping the DOM write when the rendered value is unchanged**
  (`if (el.textContent !== next) el.textContent = next`): treats the symptom
  and, by the profile, barely touches it — the cost is in re-running the
  effect (interpolate, the `get` traps), not in the assignment. Worth doing on
  its own merits some day; it is not this.
- **Diffing recursively** rather than one level: an element that differs is a
  changed value and its subtree should be swept, which is what a plain notify
  on it already does. Recursing would only pay off for `data = structuredClone(data)`,
  which no benchmark and no sane code does.
- **Comparing by value rather than by reference** (deep equality on rows):
  turns a cheap identity check into an arbitrary-cost one, and would make the
  store's behaviour depend on what is inside the data.

## Open

- `removeRow` (`data.filter(...)`) gains almost nothing: dropping index 3
  shifts every element after it, so 997 of 1,000 indices genuinely differ.
  Index-keyed paths make a splice look like a rewrite; only object identity
  keyed paths would fix that, which is the Svelte-style rewrite already
  rejected in `2026-08-23.narrow-the-wake-rule.md`.
- The per-effect allocations (`indexEffect`'s `Map`, `$effect`'s `reindex`
  `Set`) are still the ~13% the `clearLarge` profile named. Untouched here.

## 2026-08-23 — implemented

Landed as proposed. 735 tests green, unchanged.

Measured back-to-back against the same build with the change stashed (the
container drifts between runs, so only paired runs are comparable):

| op (mean, ms) | HEAD | with the diff |
|---|---|---|
| **appendToLarge** | **217.3** | **104.1** |
| create1k | 58.3 | 58.3 |
| create10k | 570.5 | 546.6 |
| clearLarge | 135.9 | 121.7 |
| replace1k | 61.7 | 65.3 |
| partialUpdate | 1.63 | 1.61 |
| removeRow | 26.1 | 25.3 |

`appendToLarge` **217 → 104**, which is the ~150ms of spurious wakes the
proposal predicted, minus what the list diff itself costs. Everything else is
flat except `replace1k`, which came in 3-4ms high on all four paired runs —
small, consistent, and not explained by the ~500 loop iterations it does before
giving up. Left as measured rather than explained away.

### Two things the proposal got wrong

- **The `length` rule did not need splitting.** The plan said the coarse
  shrink-or-grow sweep on `"list.length"` would have to become shrink-only, or
  it would undo the whole change. It doesn't: `notifyReplaced` collects the
  length dep *exactly* rather than going through `notify`, so the sweep never
  enters the picture. The rule is untouched and truncation still behaves as it
  did.
- **The same-reference write reaches this code, and must not be diffed.**
  `replaceable` originally tested only that both sides were containers of the
  same kind. But the deep-touch channel — a parent's prop sync re-assigning the
  *same* `user` object into the child's store, which
  `2026-07-15.effect-runner-hardening.md` records as load-bearing — arrives
  here as previous === next. Diffing it finds nothing changed and silences it,
  which broke the two prop tests and the tutorial's highlight layer.
  `previous !== next` is now the first thing `replaceable` checks.

### And one the measurements taught

Notifying each changed path through its own `notify` re-ran an effect once per
path it depends on: the nested-store test went from `[1, 2, 1]` to
`[1, 2, 2, 2, 1, 1, 1, 1]`. All the paths now contribute to one set that runs
once at the end, which is both correct and cheaper.

The first working version then *cost* time on every operation that ends up
sweeping anyway — `clearLarge` +9ms, `create10k` +19ms — because it built
`Object.keys` arrays and a `Set` of up to 20,000 entries before discovering
that everything had changed. `whatChanged` now walks arrays by index with no
allocation at all, returns early when either side is empty, and gives up the
moment more than half the elements differ. That took the overhead to zero on
every op except the `replace1k` residue above.

## Still open

- `removeRow` is unchanged, as predicted: `filter` shifts every element after
  the removed one, so 997 of 1,000 indices genuinely differ and the diff gives
  up. Index-keyed paths make a splice look like a rewrite.
- The per-effect allocations (`indexEffect`'s `Map`, `$effect`'s `reindex`
  `Set`) are still the ~13% the `clearLarge` profile named.
