# The first render waits for the setup script, and `$mounted()` is how a script lets go

**Status:** proposal, not implemented. Raised in conversation as "could the
script be evaluated first and the HTML rendered on the next tick?", which is
[rejected below](#rejected) — the shape that survives is different.

## The problem

A `:setup` script with a top-level `await` renders its template before its
values exist. The docs already describe the behaviour this file wants rather
than the one the runtime has — [setup-scripts.md:63](../docs/setup-scripts.md)
says:

```html
<script :setup>
  let items = await fetchItems()   // runs before render
</script>
```

It does not run before render. Line 74 of the same file confesses it: `items` is
pre-declared `undefined`, the template renders against that, and the assignment
updates the DOM when it lands. Since `e7ffe6c` the intermediate state is not even
quiet — `{{ user.name }}` over a `user` a fetch will fill reports in red, once,
every page load. That report is correct on its own terms and it is the second
file to note that it is churn for components that were only ever waiting.

The first render happens too early. Not by a tick — by however long the script
takes.

## Why "wait for the script" is not enough on its own

The obvious rule, *the template renders when the scripts settle*, deadlocks
against the helper that exists to sequence exactly this:

```html
<script :setup>
  await $mounted()   // script waits for mount → mount waits for render → render waits for script
  $self(".list").focus()
</script>
```

`$mounted()` resolves in `attach()` ([jq79.ts:2621](../src/jq79.ts)), which needs
`this.content`, which needs the render, which under the new rule is waiting on
this script. Three-way cycle, and it catches the documented idiom.

## Proposal

Treat the `$mounted()` call as the script's **yield point**, not merely as a
promise it awaits:

> The first render waits for each `:setup` script until it **returns** or calls
> **`$mounted()`**, whichever comes first.

The cycle is cut because a script that wants the DOM must ask for it, and asking
is what releases the render. Read as a contract it is one sentence to the author:
*whatever you want on screen before the first paint, do it above `$mounted()`.*

`:mounted` falls out of this for free and needs no special case: `defer` already
prepends `await $mounted()` to the script's own first line
([jq79.ts:2534](../src/jq79.ts)), so a `:mounted` script is one that yields at
line 0 — which is precisely today's behaviour for it. The same is true of every
fully synchronous script, which returns before anything else can run. **The rule
changes the behaviour of exactly one class of script: one that awaits something
other than `$mounted()`.**

### Mechanics

Four changes, none of them structural.

**1. A per-script gate.** `instanceHelpers` is already built inside the
`forEach` ([jq79.ts:2543](../src/jq79.ts)), so each script can be handed its own
`$mounted` that releases its own gate and returns the same shared promise:

```ts
let release!: () => void
const gate = new Promise<void>(resolve => { release = resolve })
gates.push(gate)
const $mountedForScript = () => { release(); return mounted }
```

Per script rather than per instance on purpose: one script yielding must not
release the render on behalf of another that is still fetching. The gate also
resolves when the script's own promise settles, which means `runSetupScript` and
`runFactoryScript` have to return the promise they currently only hand to
`trackScript`.

**2. A synchronous fast path.** The factory path already detects a fully
synchronous body with a flag set at the end of the compiled wrapper, and calls
the factory before the first render on the strength of it
([jq79.ts:2087](../src/jq79.ts)):

```ts
`return (async () => { ... }\n;$__exports.done = true })()`
...
if ($__exports.done) invoke() // fully-sync body: factory runs before first render
```

`runSetupScript` gets the same appended flag — after the `with` block, on its own
line, so the author's line numbers do not shift. If every gate is settled by the
time the `forEach` returns, the render runs synchronously exactly as it does
today. This is what keeps the change off the ~330 synchronous `mount()`
assertions in the test suite.

**3. Markers first, nodes later — `render()` and `mount()` stay synchronous.**
The instance already brackets its output between `startMarker` and `endMarker`
and holds it in a fragment while detached, and `detach()` already collects
whatever sits between them, including nodes `:if`/`:each` inserted after mounting.
So the deferred render needs no new machinery — it is the same anchor trick those
directives use:

```ts
content.append(this.startMarker, this.endMarker)   // render() returns with this
this.content = content
Promise.all(gates).then(() => {
  if (marker !== this.startMarker) return          // destroyed or re-rendered meanwhile
  this.endMarker!.parentNode!.insertBefore(renderNodes(this.template, templateScope, fx, shadow), this.endMarker!)
  this.renderDone = true
  this.settleMounted()
})
```

The stale-generation guard is the one `$emit` and `$updateModel` already use.
Styles stay synchronous where they are — they do not depend on the template, and
acquiring them late would flash the component unstyled.

**4. `$mounted()` resolves on render *and* attach, last one wins.** Today
`attach()` calls `resolveMounted()` directly; it becomes `settleMounted()`,
which fires only once both `renderDone` and `mountRoot` are set. Without this the
documented guarantee inverts — a script would wake to markers and no DOM.
`hotReplace` ([jq79.ts:2348](../src/jq79.ts)) changes the same call.

## What it costs

Four consequences, each with the disposition decided in conversation.

### 1. The whole template waits, not just what depends on the value — accepted

```html
<script :setup>
  let user = await fetchUser()
</script>
<h1>Perfil</h1>
<p>{{ user.name }}</p>
```

Today `<h1>Perfil</h1>` paints immediately and `{{ user.name }}` reports. Under
the rule nothing paints — not even the `<h1>`, which depends on nobody — until
the fetch lands. Static chrome and skeletons are collateral: the unit that waits
is the template, and there is no finer one.

Accepted because it is the point of the file, and because the escape is the same
helper, one line higher:

```html
<script :setup>
  await $mounted()               // paint the <h1> now
  let user = await fetchUser()   // fills in reactively, as today
</script>
```

This is a behaviour change for existing components, not just a timing one. It is
cheap here because the library currently has one user.

### 2. A factory that yields renders with nothing bound — warn

A factory's bindings reach the store when the module body returns and `invoke()`
merges them. Yielding before that publishes nothing:

```html
<script :setup :mounted>
  export default () => ({ count: 0 })
</script>
<p>{{ count }}</p>
```

`:mounted` yields at line 0, so the template renders with `count` undefined,
warns as a missing name, and fills in after. That is what happens today for any
async factory ([jq79.ts:108](../src/jq79.ts) says so), so nothing regresses — but
under a rule that reads "yielding means I published what I meant to publish", it
looks like a contradiction, and the author has no way to publish earlier.

The normal case is unaffected, because there the call sits *inside* the factory
and the merge is already promise-shaped:

```html
<script :setup>
  export default async () => {
    await $mounted()      // yields → render → attach → resolves → merge
    return { count: 0 }
  }
</script>
```

Only a yield in the module body is broken-looking, which is exactly what
`:mounted` on a factory script produces. Disposition: `console.warn` when
`:mounted` is applied to a factory script, naming the reason. No semantic change.

### 3. A parent no longer waits for its children — accepted

`renderNodes` is synchronous, so a component tag renders and mounts its child on
the same stack ([jq79.ts:858](../src/jq79.ts)). Under the rule an async child
contributes its two markers and fills in later, so a parent that reaches into a
child's DOM after its own mount finds holes:

```html
<script :setup>
  await $mounted()
  console.log($$self(".row").length)   // today: 3 · after: 0 if Row has an async :setup
</script>
<Row :each="r in rows" />
```

Accepted as the honest consequence of an async boundary: "everything is ready" is
now a per-component claim, not a per-tree one. Deliberately *not* fixed now — see
[Still open](#still-open) for the version that would.

### 4. An await that never resolves is a blank component and silence — warn

```html
<script :setup>
  await new Promise(() => {})   // a bug, or an endpoint that never answers
</script>
<p>Cargando…</p>
```

Today `Cargando…` paints. Under the rule nothing paints, forever, with nothing in
the console. This is the worst failure mode of the four because it does not look
like an error — it looks like a component nobody mounted.

Disposition: a timer armed with the deferred path that warns after a few seconds
(`jq79: <Foo> has been waiting on its :setup script for 3s — is an
await $mounted() missing?`) and **keeps waiting**. Worth building on day one; the
first cost above will produce this symptom eventually.

## Rejected

- **Render on the next tick** — the original question. One microtask is an
  arbitrary fence: it only rescues promises already resolved, and even
  `$import` through the bundler's modules map
  ([jq79.ts:2494](../src/jq79.ts)) is more than one turn away. It does not close
  the race, it moves it, and it would pay the full price of an asynchronous first
  render for a fraction of the benefit. The value of `$mounted()` as the boundary
  is that the author chose it.
- **Wait for the scripts with no yield point.** The three-way deadlock above,
  which catches the documented `await $mounted()` idiom.
- **Make `render()` and `mount()` return promises.** The natural reading of an
  async render, and unnecessary: markers are mountable before their contents
  exist, so the entire synchronous surface (`new Component79(src).mount("#app")`,
  the `PendingComponent79` chain) survives untouched. An async API would also
  have forced every one of the ~330 `mount()` calls in the suite through an
  `await`.
- **Render anyway after the point-4 timeout.** Makes the moment of the first
  render depend on wall clock — a component would paint differently under load
  than on a fast machine. Warning and waiting keeps the semantics deterministic
  and the diagnosis just as loud.
- **One `$mounted` per instance rather than per script.** Simpler, and wrong: two
  scripts where the second yields would release the render while the first is
  still fetching, silently reintroducing the bug this file fixes for anyone who
  splits their setup in two.

## Still open

- **Making `$mounted()` await pending descendant renders**, which is the fix for
  cost 3. Mechanically it is registering the instances created during
  `renderNodes` and adding a `Promise.all` over their render completions to
  `settleMounted`. It is the only one of the four that costs real code, it can be
  added later without changing the rule, and it should wait for the first time
  the hole is actually felt.
- **Whether the deferred render should stay outside the parent's effect.** Today
  a child renders on the parent's stack, so reads made while rendering it land in
  whatever effect is active — the same donation the `modelWriteback` comment
  ([jq79.ts:818](../src/jq79.ts)) works around with `untracked`. Deferring removes
  it by construction. That is probably an improvement and is currently an
  unverified side effect, which is the wrong way to acquire one.
- **The point-4 delay is a guess**, and unlike the expression-report timer it has
  no notion of dev vs. production to hide behind. Three seconds, always warning,
  is the starting position.
- **`pendingScripts` gets less load-bearing.** The missing-name queue defers its
  flush until no script is running, because a factory's names arrive late. Under
  this rule the non-yielding case has its names before the render and never
  enqueues. Nothing breaks and nothing needs changing; the machinery is simply
  covering a narrower case than it was built for, and someone will eventually
  wonder why it exists.

## Test

In `tests/Component79.test.ts`:

- a `:setup` with a top-level `await` renders **nothing** — no markers' worth of
  content between them — until the promise settles, then renders once, complete;
- the same script with `await $mounted()` above the fetch paints the static part
  immediately and fills in after, matching today;
- a fully synchronous `:setup` renders synchronously: `mount()` then a
  synchronous `innerHTML` assertion, no `await` anywhere, as the existing tests
  do — this is the fast path, and it is the regression that would hurt most;
- `:mounted` still renders immediately;
- two scripts, the first awaiting and the second yielding: the render waits for
  the first (the per-script gate);
- `destroy()` between the yield and the deferred render leaves nothing behind and
  throws nothing (the generation guard);
- a parent whose child has an async `:setup` mounts with the child's markers in
  place and the child's DOM arriving after — cost 3, asserted rather than
  discovered;
- `:mounted` on a factory script warns;
- a script that never settles warns after the delay, under fake timers, and the
  component stays blank.

`docs/setup-scripts.md` needs the paragraph at line 74 rewritten, since it
documents the behaviour this file removes — and the comment at line 63 becomes
true without being touched.

## 2026-08-08, later: implemented, and two things the code said back

Shipped as proposed — the rule, the four dispositions, the synchronous fast path.
694 existing tests passed with three rewritten (below) and no change to the ~330
synchronous `mount()` assertions, which is the outcome the fast path was for. Two
things turned up that the plan had not considered.

### The synchronous render may not cost a stack frame

The first draft ran both paths through one `paint()` closure — the obvious
factoring, and wrong. A component that nests itself recurses through `renderWith`
once per level, and `MAX_NESTING_DEPTH = 200` is calibrated against the actual
stack rather than against anything principled. One extra frame per level was
enough to blow the stack at a depth *below* the guard: the cyclic-data test in
`tests/multiTemplate.test.ts` went from a named `console.error` and 200 rendered
nodes to a bare `RangeError` and nothing rendered at all.

The synchronous branch is now written out inline, duplicating three lines, and
`docs/development.md` records why. Worth stating plainly because the duplication
looks exactly like something a later cleanup would remove: the guard is only as
good as the frame budget it was measured against, and nothing in the code makes
that dependency visible except the comment and that one test.

### A script that never settles silences missing-name reporting page-wide

Not caused by this change, but made reachable by it. `trackScript` increments a
module-level `pendingScripts`, and `scheduleExprReportFlush` refuses to flush
while it is above zero — so a component whose script never settles pins the
counter for the life of the page, and *every other component's* missing-name
warnings are swallowed from then on. The new "never settles" test exposed it
immediately by silencing five reporting tests further down the file.

The test now settles its hanging promise on the way out, which is the right fix
for the test and no fix at all for the runtime. Left open deliberately rather
than patched in passing: the counter is a page-wide gate on a per-component
condition, and the honest repair is per-instance reporting — which is now the
third file to defer that.

### The three tests whose premise this change removes

Rewritten rather than deleted, since each still has a guarantee to make; the
guarantee is just now reached by a different route.

- `stays quiet while an async factory's bindings are still on the way` → the
  silence is no longer a deferred re-check that found the name had arrived, it is
  that nothing read the name early. Renamed to say so.
- `a default reaches the template even before an async factory has run` → there is
  no "before" any more. It asserts the single complete render instead.
- The `02-no-bundle/01` tutorial exercise taught the old timing in its solution's
  comments ("the stamps show up bare and grow their sticker when the file lands").
  Its *point* is the runtime fetch, not the timing, so it keeps the behaviour it
  demonstrates by adding `await $mounted()` above the import — which makes it the
  first place in the tutorial where the yield appears in a setting that motivates
  it.
