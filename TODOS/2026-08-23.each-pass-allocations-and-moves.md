# The :each pass: two real reductions, and a benchmark that barely notices

**Status:** two results and the instruments that produced them, both landed
(`perf(each): stop building a scope per row per pass`, `perf(each): move only
the rows that moved`). Written because the headline is a warning, not a win:
**both changes remove work that is provably there, and the browser benchmark
moves by 2-6%.** The next person should know what was measured, what the
harness can and cannot see, and which two guesses this file got wrong before
it got anything right.

Follows [`create-gap-is-diffuse.md`](2026-08-23.create-gap-is-diffuse.md), which
closed the create path, and picks up its open item: "`swapRows` (+1ms) and
`selectRow` (+0.6ms) have never been profiled above the noise floor."

## The hypothesis, and the first null result

`renderEach` built the item's scope - an `Object.create` plus three
`defineProperty` calls - before it could evaluate the row's `:key`, and then,
for every row the diff turned out to be *reusing*, dropped it. Reuse is the
common case: `removeRow` reuses 999 of 1,000 rows, `swapRows` 998. So every
pass allocated a thousand scopes and three thousand descriptors that rendered
nothing, plus a thousand `[at, item]` pairs from normalizing the list.

Three interleaved A/B rounds in Chromium, medians of the per-round medians:

| op | base | after | delta |
|---|---|---|---|
| create1k | 57.95 | 53.85 | -7.1% |
| removeRow | 17.7 | 17.8 | +0.6% |
| selectRow | 5.05 | 5.3 | +5.0% |
| swapRows | 9.25 | 8.85 | -4.3% |
| **clearLarge** | 117.3 | **127.85** | **+9.0%** |

`clearLarge` empties the list: `length` is 0, the loop body never runs, and not
one line of the change is reachable from it. It measured 9% worse. **That is
the noise band of this harness on this machine**, and inside ±10% nothing in
the table means anything - including the two numbers that flattered the change.

## The instrument that could see it, and the one that could not

Chromium's clock cannot resolve ~1ms inside a 17ms operation, so the pass was
timed out of the browser instead, over jsdom, 150 passes a round, both bundles
in one process alternating rounds so process-level JIT luck lands on both
sides. First attempt, a far swap (rows 1 and 998): **-0.7%, flat**. A CPU
profile of it says why:

| share | frame |
|---|---|
| 52.5% | `SymbolTree._node` (jsdom) |
| 16.4% | `SymbolTree.index` (jsdom) |
| 7.3% | `Node-impl._insert` / `_remove` (jsdom) |
| ~3% | anything in jq79 |

jsdom's tree implementation is 20x a browser's, so a workload with DOM volume
in it measures jsdom. **Timing jq79's own JS through jsdom only works where the
pass moves nothing.** Swapping two *adjacent* rows is such a pass - a full
1,000-row diff, two insertions - and there the change is worth:

| ms/pass | base | after |
|---|---|---|
| median of 8 alternating rounds | 3.78 | **2.76** |

**-27%, about 1ms per 1,000-row pass.** Real, and permanently invisible to a
benchmark whose noise band is ±1.8ms on the operation that contains it.

## What the profile handed over instead

The far-swap profile was 90% DOM churn for a swap of two rows, which is not a
thing a diff should be able to produce. Counting insertions per pass on a
1,000-row keyed list:

| operation | insertBefore, before | after |
|---|---|---|
| swap rows 1 and 998 | **997** | **2** |
| remove a row | 0 | 0 |
| append a row | 1 | 1 |

The positioning walk asked of every entry that it follow the one before it and
moved it when it did not - minimal for an append, quadratic for a reorder,
because one row out of place puts every row behind it out of place too. The fix
is the one Vue and Svelte reach: the longest strictly increasing run of the
positions the entries held last pass names the rows already in order relative
to each other, and only what is not in it moves. Patience sorting, O(n log n),
over an array the diff fills as it goes.

## And the second null result

Removing 995 DOM mutations from `swapRows` is worth, in Chromium:

| op | base | after | delta |
|---|---|---|---|
| swapRows | 9.3 | **8.7** | **-6.5%** |
| create1k | 56.95 | 54.45 | -4.4% |
| removeRow | 19.3 | 18.9 | -2.1% |
| everything else | | | flat, within ±1.6% |

So the 997 moves cost about **0.6ms**, not the 8ms that would have explained
the operation. Moving an already-attached node is cheap in a real browser; it
was expensive only in jsdom, which is what made it look like the answer.
`swapRows` is still 8.7ms against Svelte's 1.1, and this file cannot say where
that time goes.

Two things keep the change worth having anyway. It is 995 mutations that no
longer happen, and their *layout* cost is not in these numbers at all: the
harness settles a click over a few microtasks, never a frame, which is why
[`create-gap-is-diffuse.md`](2026-08-23.create-gap-is-diffuse.md)'s trace found
"No `Layout`. No `RecalculateStyles`." in the measured window. On a page whose
rows are heavier than four `<td>`s, that is the part that bites. And quadratic
DOM churn on reorder is a property of the algorithm, not of this table.

## Open

- **Where `swapRows` (8.7ms) and `removeRow` (18.9ms) actually go.** Both are a
  single 1,000-row diff pass with almost no DOM work left in them. The isolated
  pass costs ~2.8ms of JS-plus-jsdom; the operation costs three to seven times
  that. Nothing here has profiled the operation itself with an instrument that
  can attribute it - `devtools.timeline` tracing, as used for `create1k`, is the
  one that worked.
- **Regenerating the committed results files was skipped, and should be.**
  `release.yml` runs `npm run benchmark` and `npm run benchmark:comparison` on
  the runner before `npm run site`, so the published pages are always built from
  numbers measured during the release - the committed JSON is a snapshot of the
  repo, not the source of what `/benchmark/` shows. Regenerating it by hand here
  would only record this machine's luck, and every delta above is inside or
  barely outside the harness's own noise band anyway.
- The bucket `Map` still allocates an array per key per pass, and `seen` a Set
  entry per row, for a duplicate-key case that is a user error. Same class of
  allocation as the scopes this branch removed, and now a larger share of what
  is left.
