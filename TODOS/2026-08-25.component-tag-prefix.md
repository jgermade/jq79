# A component tag the browser cannot mistake for an element

**Status:** proposal. Not implemented; `src/` is untouched.

The decision this rests on is the author's, and it is a principle rather than a
fix: **respect native behaviour.** If `circle` is a native tag, there should
never be a library component of that name - and a word that is not an element
today may be one tomorrow.

---

## What happens now

A component tag is written PascalCase, and the HTML parser lowercases it. What
comes out is *the native element of that name*:

```
<svg><Circle />      ->  tag "circle"    component "Circle"   ns SVG
<svg><circle r="1"/> ->  tag "circle"                         ns SVG
<table><tbody><Tr /> ->  table / tbody / tr       (a real <tr>, placed inside)
<table><tbody><Row/> ->  row / table / tbody       (evicted, foster-parented out)
```

Three things follow, and none of them was decided by anyone:

1. **A component tag inside an `<svg>` is indistinguishable from the native
   element** but for the stamp. `plannableNode`, `createFor`, `foreignAttrName`
   and `mayUpgrade` all read `tag` and `ns`, and all of them see a circle.
2. **A component is placed correctly only when its name happens to be a valid
   child of its parent's content model.** A row component works if you call it
   `Tr` and not if you call it `Row` - measured through jq79's own parse, and
   identical in jsdom and Chromium 151, because table foster-parenting is
   ancient and universal.
3. **Any component name that matches an element captures it.** 70 of 90
   ordinary one-word component names collide - `Table`, `Form`, `Label`,
   `Header`, `Text`, `Path`, `Filter`, `Circle`. Measured, and the reason this
   file exists.

## The proposal

Rename component tags in the pre-parse rewrite, so the browser never sees a name
it can resolve to an element:

```
<Circle />        ->  <c79-circle :jq79-component="Circle" />
</UserCard>       ->  </c79-user-card>
```

**Hyphenated, and that is not cosmetic.** `c79-circle` is a *valid custom
element name*, so the browser builds an `HTMLElement` for it; `c79circle` is an
`HTMLUnknownElement`. Measured. The hyphen is the shape the platform reserves
for what is not native, which is the principle this file rests on, applied to
our own tags. And it reads for itself in the inspector: a developer who finds
`<c79-circle>` knows what it is and whose it is, where `<circle>` looks like
markup they wrote.

Every PascalCase tag, one word or several - **not** only the colliding ones,
because the point is that today's safe name is tomorrow's element. `c79circle`
is not a name HTML, SVG or MathML has or will have, so:

- the parser cannot build a native element from it;
- nothing downstream can mistake `node.tag` for an element's;
- a component that fails to resolve leaves `<c79-circle>` in the DOM - which
  names itself, where today it leaves a plausible-looking `<circle>`.

`stampComponentTag` keeps stamping the **original** name, so `node.component`
stays `"Circle"` and every consumer of it is unchanged.

### Resolution moves to the stamp

`findComponentKey(scope, node.tag)` cannot work on `c79circle`. Resolution reads
`node.component` instead - which is the claim the author actually made - and
keeps the dashed path for `<drop-area>`, a shape that cannot collide with a
native element for the same reason custom elements cannot.

That closes the capture in both directions: `<circle>` written in lowercase can
never resolve to a `Circle` in scope, and `<Circle />` can never be parsed as a
circle.

### The rewrite has to close tags too

`expandNameCase` rewrites open tags only (`OPEN_TAG_RE` does not match `</x>`),
which is fine today because the parser lowercases both ends to the same name.
Renaming one end and not the other would leave `<c79circle>` closed by
`</circle>` and the parser would nest whatever follows. A close-tag pass comes
with this, and `</slot.x>` keeps its own (it is lowercase and unaffected).

## Step 2: the same rename, in the CSS

The prefix is internal, so the author never types it - not in the template and
not in the stylesheet. A `<style scoped>` naming a component gets the same
rewrite its selectors already get for the scope attribute:

```css
Circle  { color: red }      ->   c79-circle[data-jq79="…"] { color: red }
```

Which is only worth anything if the element is *there*, so this settles the
question the first draft left open: **the prefixed tag stays in the DOM**. A
component stops being a pair of comment anchors around loose content and
becomes an element that names itself in the inspector.

### And that needs a default of `display: contents`

An element where there was none is a box where there was none, and a component
inside a flex or grid parent would become an inline wrapper holding the real
child. `display: contents` removes the box and leaves the children in the
parent's layout - measured, flex and grid come out identical to the unwrapped
case.

So `c79-* { display: contents }` ships as the default, and an author who wants
the wrapper to *be* a box overrides it:

```css
c79-panel { display: flex; gap: 8px }   /* opts out, deliberately */
```

Which is the point of step 2: the wrapper is addressable by the name the author
chose.

## What it costs, said plainly

- **A component can no longer sit in table-row position.** `<Tr />` stops being
  placed inside its `<tbody>`, because it stops being a `tr` to the parser.

  Under the principle above this is not a loss: it only worked because *the
  browser interpreted a component tag as a native element*, which is the thing
  being stopped. But it is a capability that exists today and it goes, and the
  next person wanting a row component reaches for `:each` on the `<tr>` itself -
  which is what `frameworks/keyed/jq79/src/App.html` already does.

  **Only table position.** `<select>` was checked and costs nothing: Chromium
  151 keeps `<Card>` and `<c79-card>` alike inside a `<select>`, since the
  customizable-select parsing changes. Which turned up a divergence worth its
  own line: **jsdom drops an unknown child of `<select>` and Chromium keeps it**,
  so a component inside a `<select>` behaves differently in this repo's tests
  than in a browser. Not caused by anything here, and not fixed by it.

- **`<mychip>` stops becoming a component.** An unknown, undashed lowercase tag
  that turns into a component when an async factory writes the key in later has
  a corpus entry written for it on purpose. With this, the author writes
  `<MyChip />` or `<my-chip>`. Same discipline the platform requires; still a
  documented behaviour being withdrawn.

## What was rejected, and why

- **A warning instead of a change** - preventive on one-word names, or precise
  at the capture. The preventive one fires on **23 of this repo's own 28
  component names**, tutorial included; a warning that sounds on nearly
  everything stops being read, and stops protecting. The precise one is exact
  and free, but it only reports the collision - it does not prevent it, and it
  cannot say anything about a name that collides only after the platform ships
  an element.
- **A wrapper *instead of* the rename.** It gives the inspector its name back
  and fixes nothing: `Circle` would still swallow `<circle>`. The rename is what
  does the work; the wrapper is what makes it visible and addressable.
- **Making the resolution read the stamp, without renaming the tag.** Fixes the
  capture at zero cost and keeps `<Tr />` working. Rejected on the principle:
  the tag would still *be* a native element to the parser, and the muddle in (1)
  above would stay.

### The selector cost, sized

An element in the tree is an element selectors have to walk past, so `>`, `+`,
`~` and `:nth-child` crossing a component boundary stop matching. Measured:
`.grid > .item` goes from 2 matches to 0.

**But scoped styles are already unable to cross that boundary**, which is the
measurement that sizes this. A parent's `<style scoped>` is rewritten to demand
the parent's stamp, and a child component's root does not carry it:

```
parent   <div class="list" data-jq79="155h7tu">
child    <p class="row">                          (no stamp)
rewritten  .list > .row[data-jq79="155h7tu"]      (never matches, today)
```

So the cost falls only on **global CSS** - a plain stylesheet, or a `<style>`
without `scoped` - reaching across a component boundary with a child or sibling
combinator. Inside jq79's own scoping there is nothing to lose, because it was
already lost.

## Still open

- **`<drop-area>` keeps resolving `DropArea`** under this proposal. It is
  custom-element-shaped and cannot collide with a native name, so it stays - but
  it is now the one path where a lowercase tag becomes a component, and that
  asymmetry should be written down rather than discovered.
- **The prefix is `C79`**, chosen to match the library. It is invisible to
  authors and appears only in a failed render's DOM, so its shape matters less
  than that it can never be a native name.
- **Nothing here changes what anyone writes.** That is the claim to check first
  in review: `<Circle />` in the template, `Circle { … }` in the stylesheet, and
  the prefix nowhere an author has to type it.
- **Whether the anchors survive.** A component has an element now, so the pair
  of comment anchors that exists *because* it had none may be redundant for the
  component case - `boundsOf` could resolve the wrapper. Anchors stay regardless
  for `:if`, `:each` and `<template :slot>`, so this is a simplification to
  weigh separately, not part of the change.

## Update, 2026-08-25: the wrapper is always, and what a component looks like now

The last section leaves "whether the anchors survive" open, and answering it
needs the thing step 2 assumes: **every instance gets its `<c79-name>`, always.**
That was asked and decided; the reasoning is below because the alternative
sounds cheaper than it is.

### What a component is in the DOM today: four or five comments and no element

Measured, three components - one root, two roots, and a root whose `:if` is
false:

```
one root     <div class="w"><!--One--><!--jq79--><p class="a">uno</p><!--/jq79--><!--/One--></div>
many roots   <div class="w"><!--Many--><!--jq79--><h2>t</h2><p>c</p><!--/jq79--><!--/Many--></div>
no root      <div class="w"><!--None--><!--jq79--><!--if--><!--/jq79--><!--/None--></div>
```

Two pairs: the usage site (`<!--One-->…<!--/One-->`) and the instance's own
render bounds (`<!--jq79-->…<!--/jq79-->`). Four nodes, five when the root is
conditional, and not one element among them.

### Why "sometimes" is not an alternative

The tempting version wraps only when it is needed - only a multi-root component,
or only a name that collides. Neither works:

- **The shape of the tree would depend on runtime content.** The same component
  renders one root or two according to its data. A wrapper that appears only in
  the multi-root case means `.grid > .item` stops matching the moment the
  component adds a second node. The parent's CSS would break according to what
  the child decided to render that render.
- **The empty case has nothing to hang off.** A component whose root carries a
  false `:if` has no root that *is* the component.
- **"Only when it collides" reintroduces exactly what the rename removes.** The
  principle this file rests on is that today's safe name is tomorrow's element;
  a wrapper conditional on the current element list is conditional on the thing
  that moves.

So "always" is not uniformity for its own sake. It is the only version where the
tree is predictable from the source without knowing the state.

### The consequence: the wrapper is the handle the anchors exist to be

`renderNestedComponent`'s own comment says why the anchors are there - the
instance's DOM is dynamic, so a caller that needs to move or remove the chunk
later cannot hold any of it, and holds the anchors instead. A wrapper *is* that
handle, and it is stable by construction. `boundsOf` could resolve the wrapper,
and four or five comment nodes per instance become one element.

The anchors stay regardless for `:if`, `:each` and `<template :slot>`, which
mark ranges with no element of their own. It is the **component** pair that
becomes redundant, and that is still a simplification to weigh on its own
evidence rather than part of this change.

**The cost of "always":** a component that renders nothing stops being invisible
and becomes `<c79-none></c79-none>` in the tree. With the `display: contents`
default it changes no layout, but it is there, and a parent's `:empty` stops
matching.

### Two questions this does not answer

- **Which version it lands in.** It withdraws `<mychip>` and it moves a
  component out of table-row position, so it is 0.7 with a migration note, not a
  patch.
- **What scope stamp the wrapper carries under `<style scoped>`.** Not measured.
  Today a child component's root carries no stamp from its parent, so "the
  child's stamp" is the answer that preserves current behaviour and "the
  parent's" would let a parent style the child's box - a new capability, and
  therefore a decision rather than an inference.

## Update, 2026-08-25: step 1 landed, and a third withdrawal nobody had named

**Status: implemented.** The rename and the resolution are in `src/`; step 2 (the
CSS rename, the wrapper in the DOM, `display: contents`) is untouched and stays a
proposal. What follows is what the code does, what it cost that this file did not
predict, and how each claim was checked.

### What went in

- **The rewrite renames every capitalized tag.** `componentTagName` in
  `expandNameCase`: `<Circle />` → `<c79-circle :jq79-component="Circle" />`,
  `<UserCard>` → `<c79-user-card>`. The stamp still carries the original name, so
  `node.component` is `"Circle"` and every consumer of it is unchanged.
- **The close-tag pass came with it**, as this file said it had to:
  `CLOSE_COMPONENT_RE` rewrites `</UserCard>` the same way. `</slot.x>` keeps its
  own pass.
- **Resolution reads the stamp.** `componentKeyOf(node, scope)` is now the only
  place that decides what a tag resolves to, and it accepts two spellings: the
  capitalized name off `node.component`, and a dashed tag (`<drop-area>` →
  `DropArea`). An undashed lowercase tag resolves to nothing, whatever is in
  scope.
- **The upgrade watch narrowed to the same two spellings.** `mayUpgrade` reads
  `node.component !== undefined || node.tag.includes("-")` where it read
  `el instanceof HTMLUnknownElement`, so `<mychip>` no longer waits for a `MyChip`
  to arrive. A capitalized tag that resolved to nothing still waits, as
  `<c79-mychip>`, and still holds its `:` bindings verbatim as parameters.
- **The clone path stopped asking whether a scope key captured one of its tags.**
  `plan.tags` and the `findComponentKey` call per distinct tag are gone -
  `SkeletonPlan` no longer carries `tags` at all. A plannable tag is undashed,
  unstamped and a name the parser knows, which is exactly the set `componentKeyOf`
  answers "no" to. This is the first thing the rename *pays for* rather than
  costs.
- **Diagnostics read the name the author wrote.** `tagLabel(node)` is
  `node.component ?? node.tag`; without it every warning about a component tag
  would have started naming `<c79-user-card>`, a name nobody typed.

### The third withdrawal: a capitalized tag no longer falls back to an element

This file named two things it withdraws - `<Tr />` in table-row position, and
`<mychip>`. There is a third, and it only became visible when the tests ran:

**A capitalized tag that resolves to no component used to render the native
element of that name, when one existed.** `<DIV class="shouty">` rendered a div;
`<A></A>` rendered an anchor. That was never a decision either - it fell out of
the unresolved-component throw needing three conditions, one of which was
`el instanceof HTMLUnknownElement`, "without [which] `<DIV>` would be [fatal],
though it renders a perfectly good div". The rename removes the element that
clause was reading: a stamped tag is a `c79-*` one, so it is never the element it
was named after, and the check is gone with it.

So `<DIV>` throws now, with the message the typo case already had - *`<DIV>` is
not defined ... In scope: (none)*. Two tests moved with it:

- `tests/multiTemplate.test.ts` "leaves an HTML element written in caps alone"
  became "judges an HTML element written in caps like any other capitalized tag".
- `tests/renderComponent.test.ts` "a component's own tag inside its template
  renders one level and stops" - the anti-recursion demonstration - used to lean
  on exactly this fallback: the inner `<A>` found no `A` in the child scope and
  rendered an `<a>` anchor. It throws instead. The property it was written for
  (no runaway recursion, because a PascalCase key can never arrive through an
  attribute) is unchanged; the way it stops is louder.

Loud over silent is the reason this was taken rather than exempted. The
alternative was to treat a tag with no lowercase letter (`DIV`, `A`, `SPAN`) as
shouty HTML rather than a component claim - which would have kept `<DIV>` working
and made a component named `ABC` silently unresolvable, trading a loud error on a
legacy spelling for a silent failure on a legal component name.

### The version question, still not answered by anyone

This file says it is "0.7 with a migration note, not a patch". Nothing here cuts
a release, and the branch does not bump the version. The migration note has three
lines to write, not two: `<Tr />`, `<mychip>`, and the fallback above.

### How each new claim was checked

The rule at the top of
[`2026-08-25.open-after-pr-13.md`](2026-08-25.open-after-pr-13.md) is *write the
sabotage before trusting the check*. Every new assertion was broken on purpose
first, and the one that mattered is the third:

| sabotage | what failed |
| --- | --- |
| drop the close-tag pass | "closes the renamed tag too, so the siblings after it stay siblings" |
| `componentTagName` returns the tag unchanged | "renames every capitalized tag", "builds an HTMLElement for the renamed tag" - **and nothing else**, which is the honest reading: the other five tests in that block check *resolution*, which the stamp already carried |
| prefix `c79` instead of `c79-` | "builds an HTMLElement for the renamed tag" (the element becomes `HTMLUnknownElement`) |
| `componentKeyOf` falls back to the tag for a lowercase name | "never resolves an undashed lowercase tag, whatever is in scope" |
| `tagLabel` returns `node.tag` | "names the component the author wrote in its messages" |

The two corpus entries this file predicted would change meaning did:
`<mychip>` became `<my-chip>` (the upgrade watch still has a live trip wire, on
the spelling that still upgrades), and "a scope key that captures an HTML tag"
became "a scope key named after an HTML tag captures nothing" - it moved out of
`SHAPE_CORPUS` and into the corpus proper, because the subtree it guards now
*clones*, which is the retired capture check said in the differential test's own
terms.

The eviction from table position is pinned rather than left to be rediscovered:
"cannot sit in table-row position any more" asserts the component renders and
that it renders *outside* the table it was written in.

### What this does not touch, and what to read next

- **Step 2 is unstarted**, and with it every question about the wrapper: the CSS
  rename, `display: contents`, and which scope stamp the wrapper carries. Today a
  resolved component still renders as a pair of comment anchors and no element -
  the `c79-*` tag exists only in the source and in the DOM of a component that
  has not resolved yet.
- **§4 of the open list** (the invisible wrapper, `boundsOf` on an empty
  fragment) is still waiting on step 2, not on this.
- The benchmark's own answer for this branch belongs beside it, not here: the
  only claim step 1 makes about speed is that it *removes* work from the render
  path (one `findComponentKey` per distinct tag per planned subtree), and a delta
  under the runner's noise is not a result.

**The A/B benchmark did not run here.** `npm run benchmark:ab -- --base main`
builds both checkouts fine and then cannot launch: the environment this was
written in has Playwright's chromium at revision 1194 and the installed
`playwright` wants 1234, and installing browsers is not this session's to do. The
*Benchmark* workflow measures every pull request that touches `src/` against the
branch it targets, on one runner, alternating - which is the method this repo
trusts anyway. Read it there.

**Two smaller consequences, recorded so they are read rather than discovered.**
`<Slot />` and `<Template />` are component claims now: the library's own tags
are the lowercase `<slot>` and `<template>`, and a capitalized spelling of either
is renamed like any other. `renderNode`'s "so `<slot>` is `<slot>` even in a file
that happens to have a component named `Slot` in scope" still holds for the
lowercase tag, which is the one it was written about. And `plannableNode` still
refuses an unknown undashed tag, but the reason changed: it is no longer a
component in waiting, so that clause is conservative now, not load-bearing.

**The benchmark ran on CI, and found nothing.** `70b57cd`, four alternating
rounds on an EPYC 7763: `regressions: []`, every operation inside the runner's
noise except `replace1k` (-3.0%) and `swapRows` (-3.2%), both "faster every
round, under the noise". `create1k` read -10.6% with a ±18.2% spread and one
round at +7.5% - the shape this repo already calls a non-result. Numbers in
[`2026-08-25.what-the-tag-rename-did.md`](2026-08-25.what-the-tag-rename-did.md).
