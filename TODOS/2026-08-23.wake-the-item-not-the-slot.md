# Wake the item, not the slot it happens to sit in

**Status:** proposal. `src/reactive.ts` is untouched; the spike below was built
out of tree - a copy of `src/`, patched and bundled with esbuild - so its
numbers are real and its test run has not happened yet. Two halves, one of
which invalidates the measurement the other half's heuristic was calibrated
against.

Follows [`where-the-list-operations-go.md`](2026-08-23.where-the-list-operations-go.md),
which counted the problem: **removing one row of a thousand re-runs 2,997
bindings**, about two thirds of the operation's 18.9ms. Svelte re-runs none.

## The theory that was wrong

The obvious reading is that a dependency is a path, so removing a row shifts
every row behind it and invalidates every dep along with it. That is not what
happens, and the reason is worth stating because it is load-bearing in the
other direction too.

`wrap(raw, path)` returns the cached proxy for `raw` and **ignores the path it
was asked for** (`src/reactive.ts`) - the cache is keyed by object, which
`AGENTS.md` records as an invariant because `:each` diffs its items by
reference. So a row's proxy keeps the path it was first wrapped at, for life.
`rows.4.label` does not mean "the label of whatever is at slot 4". It means
"the label of the object first seen at slot 4", wherever that object has since
moved to. **The dep index is already keyed to the object below the first level;
it just spells the key like a path.**

That has a consequence: a read of a value *inside* a container always tracks
the slot as well - `rows[4].label` records `rows.4` on the way through, then
`<that object's path>.label`. Nobody reaches a nested value without recording
the slot they reached it through.

## What actually happens

`removeRow` is `data = data.filter(...)`. Against the previous array, 997 of
1,000 indices now hold a different object, so `whatChanged` hits its bail-out -
`changed.length * 2 >= span` - and returns `GIVE_UP`, and `notifyReplaced` falls
back to a plain `notify("rows")`, which sweeps the entire subtree. Every dep
under `rows` matches. Every row's bindings run.

The set of items barely changed; only their positions did. The container diff
is positional, so a shift looks to it like a wholesale replacement.

## The proposal

**Half one: a changed slot wakes exactly, without the subtree sweep.**
`notifyReplaced` currently calls `effectsFor(child)` per changed key, whose
comment reads "an element that differs is a changed value, and notifying it
sweeps its own subtree, which is what a changed value deserves". The paragraph
above says the subtree under a slot does not belong to the slot - it belongs to
the object that was wrapped there, and that object's own values did not change.
Whoever read *through* the container holds the slot dep and is woken by the
exact wake; whoever holds only a deeper dep got the object from somewhere else
(a `:each` item scope) and is looking at an object that did not change.

**Half two: the bail-out threshold no longer measures what it was set against.**
`GIVE_UP` exists because reaching each changed key through its own trie walk
"costs more than the single sweep it replaces" - and it was calibrated when each
of those walks ended in a subtree sweep. With half one, a changed key costs one
`nodeAt` walk of two segments. A sweep of a 10,000-row table's trie is ~40,000
nodes. The comparison has to be redone before the threshold is trusted; the
spike simply removes it for arrays.

## What the spike measured

Bindings re-run per operation, 1,000-row keyed list, counted exactly:

| operation | today | half one | both halves |
|---|---|---|---|
| **removeRow** (4th of 1,000) | **2,997** | 2,997 | **0** |
| swapRows | 6 | 0 | 0 |
| append one row | 6 | 3 | 3 |
| selectRow | 1,000 | 1,000 | 1,000 |
| partialUpdate (every 10th) | 100 | 100 | 100 |

`selectRow` and `partialUpdate` are unchanged, which is the point: those wakes
are the ones that have to happen. `removeRow` goes to zero, which is correct -
the rows that remain show the same items holding the same values, and the list
structure is the `:each` effect's business, not the bindings'.

Half one alone does nothing for `removeRow` because `removeRow` never reaches
the per-slot path: it bails out first. That is why they are one proposal.

## And what it breaks: 15 tests, every one of them a reorder

The spike was run against the suite. It fails 15 tests, and the pattern is
exact - **removals work, reorders silently do nothing.** Verified directly on a
1,000-row list:

| | today | spike |
|---|---|---|
| remove one row | 999 rows, correct | 999 rows, correct, **0 bindings re-run** |
| swap two rows | rows move | **the DOM never moves** |

The reason is `indexable`, and it is the other half of the sweep. It drops every
dep that is an ancestor of another dep the same effect holds - explicitly
"because a write to an ancestor sweeps anyway", and dropping them is "a third of
the index to build, hold and tear down on a list of any size". So effects keep
their **deepest** deps, and wakes are expected to travel **down**.

The `:each` list effect reads `list[index]` - a dep on the slot, `rows.4` - and
then the item's key, `rows.4.id`. The first is pruned as an ancestor of the
second. What is left to wake the list:

- a **removal** changes `rows.length`, which the effect also reads, and
  `notifyReplaced` already collects that one exactly. It wakes. ✓
- a **reorder** changes no length and no key set. The only thing that reaches
  the list effect is the subtree sweep of a changed slot - the very thing this
  proposal removes. ✗

So the sweep and the pruning are one design, not two, and half one cannot land
on its own. That is the finding; the rest of this file is what to do with it.

## The shape it would have to take

Two candidates, both real work, neither touching the public surface:

1. **Stop pruning ancestors**, so a slot dep survives and an exact wake reaches
   whoever read the slot. The pruning comment prices this in advance: a third of
   the index, on every list, forever. It is the honest version and the expensive
   one.

2. **Stop tracking the item's key inside the diff.** If the `:each` read its key
   without registering a dep, its slot deps (`rows.4`) would have nothing deeper
   to be pruned against, an exact slot wake would reach the list effect, and a
   row's own binding (`rows.4.label`) still would not. Narrow, cheap, and only
   available now: `perf(each): read a plain :key off the item` made the key a
   direct property read, which is one `untracked` away from not registering.

   It does change something observable, though: today writing a row's `id`
   re-diffs the list, and it would stop doing that. Svelte and Vue re-diff when
   the list changes, not when a key value does, so there is a defensible answer
   either way - but it is a decision, not an implementation detail.

Both still owe an answer on the two rules the exact wake does not implement:
`effectsFor`'s bridge case (`if (bridges.has(path))`, for an effect that read
through a nested store and holds the bridge path and nothing below it), and the
`deep` direction, where `effectsFor` collects every ancestor's `deep` set on the
way down and `collectExact` collects one node's.

And half two - removing the bail-out - still owes its own measurement on
`replace1k`, `create1k` and `clearLarge`, which replace a container wholesale and
would enumerate every slot instead of sweeping once. The isolated instrument
from [`each-pass-allocations-and-moves.md`](2026-08-23.each-pass-allocations-and-moves.md)
is the one that can see it; the browser cannot.

None of this touches the public surface. `$reactive`, `$toRaw`, `$effect` and
the proxy semantics are unchanged throughout - it is entirely about which
effects a write reaches.
