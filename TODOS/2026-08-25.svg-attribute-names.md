# A bound camelCase SVG attribute, answered by the parser's own table

**Status:** proposal, then implementation. Closes §1 of
[`2026-08-24.open-after-pr-12.md`](2026-08-24.open-after-pr-12.md), which framed
it as a product call between a table of ~55 names and the documented limitation
that ships today. There is a third option, and it needs neither.

---

## The problem, restated with what was missing

```html
<svg :viewBox="box">   <!-- renders view-box="0 0 10 10", which SVG ignores -->
<svg viewBox="0 0 10 10">  <!-- fine: static, the parser adjusts it -->
```

`expandNameCase` rewrites `:viewBox` to `:view-box` before parsing, because the
HTML parser would lowercase it anyway and `:firstName` has to survive. For SVG's
camelCase attributes that rewrite is wrong, and it is wrong silently.

**What §1 does not record: there is already a spelling that works.**

```html
<svg :attrs="{ viewBox: box }">                  <!-- viewBox="0 0 10 10", reactive -->
<feGaussianBlur :attrs="{ stdDeviation: n }" />  <!-- stdDeviation="5", reactive -->
```

`:attrs` carries the name inside an *expression*, which the rewrite never
touches, and `setAttribute` lowercases the qualified name only on HTML elements.
So the capability has always been there. What is missing is ergonomics, and a
line of documentation. That matters for the decision: the table would buy a
spelling, not a capability.

## The proposal

The HTML parser has its own table for adjusting foreign attribute names - it is
what makes a written-out `viewBox` survive. **Ask that table instead of shipping
a copy of it.**

```js
new DOMParser().parseFromString(`<svg><feGaussianBlur stddeviation="x"/></svg>`, "text/html")
  .querySelector("feGaussianBlur").getAttributeNames()   // ["stdDeviation"]
```

The rule, memoized per namespace and name:

```
resolveAttrName(el, name):            // name is already kebab; see below
  if el.namespaceURI is HTML or null  -> name
  if !name.includes("-")              -> name
  flat = name.replace(/-/g, "").toLowerCase()
  real = ask(el.namespaceURI, flat)   // memoized
  return real !== flat ? real : name
```

**Why it resolves from the kebab name and not from what the author wrote:**
`:viewBox` and `:view-box` both arrive as `view-box`, deliberately - "both
spellings mean the same name" is the rule the docs promise. The resolution
cannot know which was written, so it has to be a pure function of `(kebab, ns)`.
That makes a collision the only thing that could sink it: a real kebab attribute
whose de-dashed form is an entry in the table would start being rewritten.

**Measured before writing a line: 58 dashed SVG attribute names, zero
collisions.** Every presentation attribute (`stroke-width`, `stroke-dasharray`,
`clip-path`, `font-size`, `flood-color`, `marker-end`, `text-anchor`,
`pointer-events`, …) plus `data-*` and `aria-*`. None of their de-dashed forms
is in the table.

## What it measures

Chromium 141 - the same version in which the IDL trick died
([`2026-08-24.svg-namespace.md`](2026-08-24.svg-namespace.md)):

| | |
|---|---:|
| camelCase names the parser table answers correctly | **58 / 62** |
| disagreement with what the same browser does written-out | **0 / 62** |
| false positives over 16 must-stay-as-written names | **0** |
| collisions over 58 dashed names | **0** |
| cost, first sighting of a name | 0.027 ms |
| cost, memoized | 0.000019 ms |
| bytes shipped | none |

The four it "gets wrong" - `contentScriptType`, `contentStyleType`,
`externalResourcesRequired`, `filterRes` - are the four SVG 1.1 attributes SVG 2
removed, and Chromium lowercases them written-out too. That is why the
disagreement column is zero: for every name, bound behaves like written-out.

jsdom gives the same 58/62 and the same 0/0, so the tests pin the semantics the
browser has - which is the objection that killed the IDL trick, and it does not
apply here.

**MathML comes free and correct**, asked in its own namespace:
`definitionurl -> definitionURL`, `mathcolor` untouched. One entry, no
maintenance.

## Why this is not the trick that was rejected

The IDL trick asked "which family does this name belong to", a question with no
ground truth, and jsdom and Chrome disagreed. This asks the table that decides
the *static* case, in the browser rendering the page. The acceptance criterion
is "a bound attribute behaves like the same attribute written out", and it is
answered by the same engine that will answer it for real. It cannot drift from
that browser's own behaviour, because it is that browser's own behaviour.

Note this criterion holds **for the names in the table**, not universally: a
bound `:strokeWidth` gives `stroke-width` where written-out `strokeWidth` gives
`strokewidth`. The rewrite is deliberately better than raw HTML there, and that
stays true. **The rewrite is right; it needs exactly one exception, and the
parser's table is the list of exceptions.**

## Where it lands

Two lines, plus ~14 for the resolver.

| site | change |
|---|---|
| `renderNode`, the `:name` branch | resolve once, outside the effect |
| `buildSkeleton`, the `attr` op | emit the resolved name |

The skeleton's element already exists when the op is built (`createFor` knows
`node.ns`), so the resolution is **once per binding per definition** on the clone
path and once per binding per instance interpreted - never inside an effect, and
`renderFromSkeleton` does not change at all.

`:attrs` is deliberately untouched, which is why the resolution does not live in
`applyAttr` (both `:attrs` arms call it). The line is: **jq79 resolves the names
it can see in the source; the contents of an expression are the author's,
verbatim.**

## What was rejected, and what it cost to find out

Five routes, all of which end at the same wall - *a camelCase name in the source
is ambiguous, and only a table resolves it; the only question is whose*:

- **A table of ~62 names.** 965 bytes raw, **+459 B gzip on the real bundle
  (+2.19%)**, permanent maintenance, and completeness that cannot be verified
  locally - a partial table is silently inconsistent, which §1 says itself.
- **`parseFromString(src, "image/svg+xml")`.** Dead on arrival: in XML a colon
  is a namespace-prefix separator, so `:viewBox` is a QName syntax error and
  **no jq79 directive parses at all**. Plus `&&` in an interpolation is fatal,
  `<` in an expression is fatal, an unclosed tag is fatal, and
  `<foreignObject><p>` comes back in the SVG namespace instead of HTML - a
  regression against behaviour that has a test today.
- **Desugaring `:viewBox` to `:attrs` at parse time.** Relocates the question.
  On raw source it would preserve the author's spelling and so break
  `:strokeWidth`, which works today; on the AST the name is already kebab and
  the same decision is still waiting.
- **Extracting the SVG and rendering it specially, or as dynamic `innerHTML`.**
  `innerHTML` *does* apply the adjust table - the same four semantics, measured
  - so the idea is sound and it is the same mechanism as this proposal, with the
  parse left in the hot path: **0.0187 ms per update against 0.00045 ms for a
  `setAttribute`, 41×**, plus the reassignment destroys node identity (measured:
  the element is a different object and its listeners are gone), which takes
  `@click`, focus, CSS transitions, SMIL and `:each` keyed diffing with it - and
  it would route ordinary bindings through the door `sanitizeHTML` exists to
  guard.
- **Assigning the property instead of the attribute.** **0 of 16 SVG properties
  are writable** - they are read-only animated values (`SVGAnimatedRect`,
  `SVGAnimatedLength`, `SVGAnimatedEnumeration`, …), and only 12 of 16 exist at
  all: `stdDeviation`, `baseFrequency`, `attributeName` and `repeatCount` have
  no IDL, which is the dead end already on the record. The `baseVal` path does
  work, and costs a marshaller per type over **8 types**, enum constant tables
  (`gradientUnits.baseVal = "userSpaceOnUse"` throws; it wants `1`), string
  decomposition, and it is not idempotent (`viewBox.baseVal.width = 10` on an
  unseeded element yields `"0 0 10 0"`). `setAttribute` takes a string and is
  right 16 of 16.
- **Hand-parsing the foreign subtrees.** It would have to find the boundary
  (`<svg>` nests), switch back to HTML inside `<foreignObject>`, `<mtext>` and
  `<annotation-xml encoding="text/html">`, reproduce the foreign-content
  breakout list (measured: `<math><annotation-xml :encoding="e"><p>` puts the
  `<p>` *outside* the `<math>`) and reimplement HTML's error recovery - and a
  tokenizer that does all that costs more than the 459 bytes it exists to avoid.

## The prior art, which says something useful

Vue 3.5.41 and Svelte 5.56.10, same template, compiled:

```js
// Vue      <svg :viewBox="box"><circle :strokeWidth="w" :stroke-width="w2"/></svg>
_createElementBlock("svg", { viewBox: _ctx.box }, [ … { strokeWidth: _ctx.w, "stroke-width": _ctx.w2 } ])
// Svelte
$.set_attribute(svg, 'viewBox', box);  $.set_attribute(circle, 'strokeWidth', w);
```

**Neither translates. Both write the author's spelling verbatim**, and both have
the same hole - `strokeWidth` is a dead attribute in Vue and Svelte too, with no
warning. They can afford it because their own parser reads the template source,
so the case is never destroyed. jq79 hands the template to the browser's parser
by design, which is precisely Vue's documented *in-DOM template* caveat, and
Vue's answer to that mode is "use SFCs" - get a compiler. jq79 has refused one.

The tables both ship are worth knowing about:

| | table | where | for what | bytes to the browser |
|---|---|---|---|---:|
| Svelte | ~270 SVG names, lowercase → canonical | `fix-attribute-casing.js`, **in the compiler** | the case of *static* attributes | 0 |
| Vue | `isKnownSvgAttr`, 259 names | `@vue/shared`, **shipped** | `shouldSetAsProp`, hydration - **not** casing | 2.7 KB |

So a runtime casing table is something nobody ships, because everybody else has
a build step. **This proposal is Svelte's `fix_attribute_casing` without the
compiler**: the same algorithm - lowercase, look up, return the canonical
spelling - with the browser's table instead of a bundled one.

## The alternative it beats, and by what

Marking the camelCase origin in the rewrite and adopting the Vue/Svelte contract
inside foreign elements needs no table, no oracle and no browser dependency, and
it is coherent. It is also **the only option that breaks templates that work
today**: `:strokeWidth` would stop resolving to `stroke-width` and start writing
a dead attribute, silently, and SVG's presentation attributes are kebab and
commonly bound. This proposal is strictly additive. That is the whole of the
argument between them.

## What is still open

- **Firefox and WebKit are unverified.** Chromium 141 and jsdom agree; the other
  two engines were not available here. The risk is bounded - the answer comes
  from the engine rendering the page, so it cannot disagree with that engine's
  own static behaviour - but the *mechanism* could differ (a browser whose
  `DOMParser` does not apply foreign-content adjustment the way its document
  parser does). The next file is a CI workflow that settles it across
  chromium/firefox/webkit, on PRs touching `src/` and on a weekly schedule,
  because what can change here is a browser, not this repo.
- **Whether `DOMParser` or an `innerHTML` probe is the better question to ask.**
  They agree in Chromium; the workflow should compare both and keep whichever
  matches the document parser in all three.
- **`:attrs` still writes a dead `strokeWidth` without a word**, and so do Vue
  and Svelte. The same oracle can detect it - `strokeWidth` is not a name the
  parser ever produces - and that is a diagnostic decision, filed separately so
  a commit does not carry two arguments.

## 2026-08-25 - a third pass found the shortcut and the vacuous check

Two more, both found by re-running the review on the corrected code, both
reproduced before being believed.

**The dash shortcut skipped a spelling people write.** `foreignAttrName`
returned early on any name without a dash, on the reasoning that only a kebab
name could need un-kebabing. But the parser's table is keyed on the *flat*
name, so it claims `viewbox` too - and it claims it for a written-out attribute:

```
<svg viewbox="0 0 10 10">    static   ->  viewBox   works
<svg :viewbox="box">         bound    ->  viewbox   dead
```

The static form works and the bound one does not, which is exactly the asymmetry
this whole file exists to remove, and the docs written for it promise "write the
name however you like". The guard is gone. What it was saving is a memoised Map
hit per foreign binding; what it cost was a silent hole.

The collision question had to be asked again, because every foreign name now
reaches the table rather than only the dashed ones. **83 undashed names measured
in Chromium - `fill`, `cx`, `d`, `points`, `in2`, `result`, `transform`, `href`,
`values`… - none claimed.** They are in the corpus now, and the render tests
assert every one of them arrives as written.

**And the cross-engine check could not fail on half of what it claimed.** Its
"ground truth" was `insertAdjacentHTML`, which runs the *fragment* parsing
algorithm - the same one `innerHTML` runs. So the `innerHTML vs document parser`
comparison was a thing tested against itself: structurally unable to disagree,
and the header's claim that it compares the mechanism against "that engine's own
document parser" was not true of the code under it.

It uses `page.setContent` now - one document, parsed by the document parser,
holding every probe. Both comparisons are live: sabotaging the mechanism so it
answers `viewbox` for `viewbox` fails with *"asking for viewbox answers viewbox,
the document parser says viewBox"*, and a claimed name in the must-stay corpus
fails as a collision.

That is the second time in this branch a check turned out to be unable to fail,
after the differential test's vacuity in
[`2026-08-24.clone-path-coverage-check.md`](2026-08-24.clone-path-coverage-check.md).
Worth stating plainly: **a check nobody has sabotaged is a check nobody has
tested.** Both gates of this one now have a recorded sabotage that fires.

## 2026-08-25 - Firefox and WebKit answered, and they answered the same

The only thing gating a claim this file makes, open since it was written:
*"Chromium 141 and jsdom agree; the other two engines were not available
here."* [PR #13](https://github.com/jgermade/jq79/pull/13) ran the workflow for
the first time.

| engine | level 1 | names adjusted |
|---|---|---:|
| chromium (Chrome/151.0.7922.34) | **holds** | 58 / 62 |
| firefox | **holds** | 58 / 62 |
| webkit | **holds** | 58 / 62 |

All three: the mechanism reproduces that engine's own document parser for every
one of the 203 names asked, `DOMParser` and `innerHTML` agree with it and with
each other, and none of the 141 names that must arrive as written - 58 dashed,
83 undashed - is claimed by any engine's table. Blink, Gecko and WebKit give the
same count and the same answers.

Two things worth more than the three green ticks:

- **Chromium was 151, not the 141 this was measured on.** Ten major versions on
  from the build that happened to be in the container, and the same 58/62. The
  design never rested on that build.
- **`set -o pipefail` is confirmed live** - the log reads
  `shell: /usr/bin/bash --noprofile --norc -e -o pipefail {0}`. Without the fix
  recorded above, a failing check would have reported `tee`'s exit code and
  passed the build.

So the "still open" entry at the top of this file is closed, and the entry about
`DOMParser` versus an `innerHTML` probe with it: both agree with the document
parser in all three engines, so there is nothing to choose between them.

### And the level-2 comparison could never run

Every one of the three jobs printed:

```
## the table, engine by engine
   only <engine> ran, so there is nothing to compare
```

The matrix puts each engine on its own runner, so no job in it can see the
others. The comparison that was the whole of level 2 - which names each engine
adjusts, side by side - was code that structurally never executed, and the three
engines agreeing was something read out of three logs by hand.

**Third time in this branch a check turned out unable to run**, after the
differential test's vacuity and the fragment-parser ground truth. Each engine
writes its answers to an artifact now, and a `compare` job that `needs` them all
does the comparing. It reports and never fails, which is the right posture: an
engine that does not adjust a name gives the same answer for the attribute
written out, so a difference there is the platform's, not this library's.
Exercised locally against a fabricated engine that disagrees on `stdDeviation`:

```
   61 of 62 names identical across chromium, firefox
   1 differ - the platform's answer, not this library's:
     stdDeviation                 chromium=stdDeviation  firefox=stddeviation
```

**And the compare job failed on its first run**, for a reason more basic than
the one predicted: the script imported `playwright` at the top level, and the
job that compares reports has no `node_modules` - it only checks out, sets up
node and downloads artifacts. `--compare` reads JSON and needs no browser at
all, but it never got to read a line.

The import is lazy now, inside the path that launches a browser. Reproduced the
CI condition to check it: running the script from a directory where
`playwright` does not resolve, which is where it failed before and where it
now compares two engines and exits 0.

Fourth thing in this branch that only appeared when the code actually ran.
