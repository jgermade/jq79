# An expression that throws anything should say so, not only a missing name

**Status:** proposal, implemented the same day. Follows
[2026-08-08.reporting-issue.md](2026-08-08.reporting-issue.md), which shipped the
`ReferenceError` half and deliberately left this half silent.

## The problem

Reported from an app, and reduced to this:

```html
<script :setup>
  const games = { Sonic1: {}, Sonic2: {} }
</script>

<button type="button" :each="game, gameKey in games" :key="gameKey"
    :disabled="!games[gameKey].is.loaded"
>
    Load {{ gameKey }}
</button>
```

`games.Sonic1` has no `is`, so `.is.loaded` throws `TypeError`. `evalExpr`
catches it and returns `undefined`; `disabled` is a boolean attribute, so a
falsy value removes it. Both buttons render **enabled** — the opposite of what
the author wrote — and the console says nothing at all:

```html
<!--each--><button type="button">Load Sonic1</button><button type="button">Load Sonic2</button>
```

The previous file called this "the transient case the catch exists to absorb"
and wrote a test asserting the silence. That was right about `{{ user.name }}`
with a `user` that is still loading, and wrong as a general rule: the two are
the same error, and the difference is not visible when it throws.

## Why the ReferenceError trick doesn't transfer

That path is quiet-until-decidable because it can ask a *pure* question later:
recover the name from the message and test `name in scope`, which evaluates
nothing. There is no such question for a `TypeError`. Re-evaluating the
expression to see if it still throws is exactly what
[the previous file rejected](2026-08-08.reporting-issue.md#re-checking-by-re-evaluating-the-expression-is-unsafe)
— `@click="count++ + missing"` increments again — and it stays rejected.

What *is* pure is watching the ordinary evaluations that were going to happen
anyway. An expression whose value is merely late is re-evaluated when the value
arrives, because the reads that did land registered as dependencies: the failing
expression reads `games`, then `games[gameKey]`, then `.is` (which returns
`undefined` and registers) before `.loaded` throws. So the effect re-runs on the
write, and the expression succeeds.

That turns "is this transient?" into a question the runtime can answer by
waiting: **transient means it succeeds later.**

## Proposal

A second queue beside the existing one, with a different re-check and a
different clock:

- **Queue on any non-`ReferenceError` throw**, keyed by expression text alone —
  not `message|expr` like the other queue. The expression is the unit the author
  edits, and one broken path usually throws one message; keying finer would let
  a `:each` enqueue an entry per distinct message.
- **Clear the entry when the same expression next evaluates successfully.** This
  is the re-check, and it costs one `Map.delete` on a hot path guarded by
  `failedExprs.size`, which is `0` in every component that has nothing wrong.
- **Report on a timer, not a microtask** — `FAILED_EXPR_DELAY = 1000`. The
  microtask flush the other queue uses is far too early: a value from `fetch`
  arrives many tasks later, and the whole point of clearing on success is to let
  it. A second is long enough to cover a local fetch and short enough that the
  warning is still visibly part of the page load.
- **Hold it behind `pendingScripts`,** like the other queue, re-armed when a
  script settles. Cheap, and consistent.
- **The queue holds no scope,** only two strings — so unlike `pendingReports` it
  can't retain a live component. It keeps the same `MAX_PENDING_REPORTS` cap
  anyway, for the console's sake rather than the heap's.
- **Message names both readings,** because at the moment it prints the runtime
  genuinely doesn't know which it is: what threw, the expression, and the fix for
  each case (`a?.b` or `:if` if the value is late).

## What it costs

**A false positive is possible and unretractable.** A fetch slower than the
delay warns about correct code, and nothing takes it back when the value lands.
This is the trade the previous file refused to make; it is made now because the
silence it bought turned out to hide a wrong render, and because clearing on
success shrinks the window to "slower than a second" rather than "asynchronous
at all".

**One second of wall clock in tests.** They use fake timers.

The dedupe is per expression *text*, module-level, so two components sharing an
expression share a warning — the same compromise `compiled` and the other queue
already make, for the same reason.

## Rejected

- **Warn at throw time.** Every `{{ user.name }}` over a value that loads warns
  on first render. The failure this file exists to fix is silence about a wrong
  render; replacing it with noise about a right one is not progress.
- **Key on `message|expr`, matching the other queue.** A member access that
  throws under two different messages is one bug in one expression, and the
  author fixes it once.
- **Clear on success inside `evalHandler` too.** It rethrows everything but
  `ReferenceError`, so it never enqueues here; adding the delete would be dead
  code that looks load-bearing.
- **Route an unrecognised `ReferenceError` message here.** An engine whose
  wording `MISSING_NAME_RE` doesn't know currently stays quiet. Sending it to
  this queue would work — clearing on success covers the async-factory case that
  made it undecidable — but no engine in the matrix produces one, so the change
  would be untested by construction. Left as written.
- **Report through `$effect`'s error path instead of a module queue.** Would give
  a per-instance gate and a component name in the message. Rejected for the same
  plumbing reason as last time: `evalExpr` is module-level and the scope it gets
  may be a `:each` or `:with` proxy over the store.

## Still open

- **The message can't name the component.** Both queues print the expression
  only. A `:each` row and a typo in a shared partial look alike in the console.
  This is the strongest argument for the per-instance gate, and it is now the
  second file to defer it.
- **A one-second delay is a guess.** If false positives show up in practice, the
  honest fix is not a bigger number but re-arming the timer while any component
  on the page still has an in-flight `fetch` — which the runtime doesn't track
  today.
- **`:disabled` on a thrown expression still renders enabled.** Failing open is
  what a boolean attribute does with `undefined`, and changing it would mean
  giving a failed evaluation a value distinct from a legitimate `undefined`.
  Out of scope here; the warning is the fix.

## Test

In `tests/Component79.test.ts`, beside the existing block:

- the reported case — a `:each` over objects missing a nested key — warns once,
  naming the expression, and only after the delay;
- `{{ user.name }}` with a `user` that arrives before the delay stays silent
  (the old "stays quiet when the value is merely not loaded yet" test, kept, and
  now meaningful: it passes because the value *arrives*, not because nothing
  looks);
- a value that never arrives warns;
- a `:each` of many rows says it once, not once per row;
- `hotReplace` clears it, so the next typo in the same expression text is heard.
