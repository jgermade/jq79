# The clone-path coverage check, run by the test suite

**Status:** proposal, then implementation. It is §3 of
[`2026-08-24.open-after-pr-12.md`](2026-08-24.open-after-pr-12.md), and it
automates the manual procedure at the bottom of
[`2026-08-24.plan-on-the-second-render.md`](2026-08-24.plan-on-the-second-render.md).

---

## The problem it is fixing

`tests/skeleton.test.ts` is a differential test: it renders a corpus with
`cloneSkeletons` off and again with it on, and diffs the DOM and the order the
bindings register in. Every assertion in it is of the form "the two paths
agree" - and **two paths that agree because the second one never ran also
agree.** Nothing in the file asserts that the clone path executed.

That is not hypothetical. It happened, inside the branch that became PR #12:
building the plan on the second render rather than the first took the corpus
from 26 entries reaching the cloner to 5, and the suite stayed green. It was
caught by hand, and the procedure that caught it lives in prose:

> make `renderFromSkeleton` mark its root, run `tests/skeleton.test.ts`, and
> confirm 26 entries fail.

Nothing runs that. It is the shape of thing this branch caught by accident and
would not catch twice.

## The proposal

Count the clone path's executions per entry, from the test, and assert the count
per entry.

**The detector is one line of arithmetic, not a hook.** `renderFromSkeleton`'s
`plan.skeleton.cloneNode(true)` is the *only* deep clone in `src/` - the one
other `cloneNode` anywhere in the library is the sanitizer copying a text node
in [`dom.ts`](../src/dom.ts), shallow, and `deep === true` tells them apart. So a
spy on `Node.prototype.cloneNode`, installed by the test around a render and
removed after it, counts exactly the times the cloner ran:

```ts
const stop = cloneCounter()   // patches Node.prototype.cloneNode
render()
const clones = stop()         // puts it back, hands over the count
```

Nothing ships to the browser to support it. The library is not aware it is being
watched. The pristine method is captured at module load and restored from there,
with an `afterEach` behind it, so a test that throws mid-count cannot leave the
prototype wrapped for the tests after it - a leak whose symptom would be wrong
counts in *other* tests, at the exact moment somebody is debugging this one.

### What each entry asserts

The corpus grows a fifth field per entry, one of three words, and it says more
than "does the cloner run":

| word | meaning | entries |
|---|---|---:|
| `never` | unplannable, or below `MIN_SKELETON_ELEMENTS`. The trip wires | 19 |
| `second` | one instance per render: the first is interpreted, the second clones | 19 |
| `both` | a `:each` - the row is rendered twice inside one render, so the first render clones too | 2 |

Three assertions fall out, and the second is the one that is new:

1. **With cloning off, nothing clones.** Universal, no per-entry data - it says
   the flag means what it says, and it is what makes the interpreted arm a
   control rather than an assumption.
2. **The first render clones only for `both`.** This is
   *plan-on-the-second-render*, asserted rather than described. Nothing tested
   it before; it was measured once by counting, in a benchmark, and left.
3. **The second render clones exactly for `second` and `both`.** This is §3
   proper: an entry that stops reaching the cloner fails by name.

For the tutorial half the expected set is a list of five exercise names, and it
is asserted **one-way**: every name in the list must reach the cloner. An
exercise that newly starts cloning is coverage, not a regression, and making the
tutorial's authors update a list in a test file to add an exercise is a toll on
the wrong people. The staleness that one-way invites - a name that no longer
matches any exercise stops being checked, silently - is closed by a sixth test
that asserts every name in the list is a real exercise.

## What it found on the way in

The new instrument and the prose procedure were run against each other, on the
same tree. They agree exactly: **26 of 83**, the same 26, 21 corpus entries and
5 tutorial exercises.

That is worth having on the record, because they measure different things and
did not have to agree. The marker attribute counts entries whose *compared
markup* contains something a clone produced; the spy counts *calls*. A clone
whose root never reaches the innerHTML being compared - a row the mutation
removes, a subtree an `:if` swaps out - would show up in one and not the other.
Today no entry is in that gap. If a future entry is, the spy is the one to
believe: it asks the question directly.

Numbers the counting turned up that the marker could not:

- `:each of a plain row` clones **3 times in the first render and 4 in the
  second** - two rows, then two more after the mutation. Per-entry counts are
  asserted as `> 0`, not by value, because these numbers move with anything that
  changes how often a binding re-runs, and that is not what this check is about.
- Four corpus entries that look plannable never clone: `:if chain`, `:with`,
  `:text and :html` and `:attrs`. The first three carry a shape-changing
  directive that makes the whole subtree unplannable; `:attrs` is two elements,
  under `MIN_SKELETON_ELEMENTS`. They are `never` on purpose, and now the file
  says so where before it was silent about it.

## What proves it works

A check that cannot fail is the thing it is replacing. Four sabotages, each run
against the finished test file, each reverted:

| sabotage | fails | which assertion |
|---|---:|---|
| nothing is ever plannable (`planOf` returns `null`) | **26 of 84** | "no longer reaches the clone path" |
| the plan is built on the FIRST sighting again | **19** | "the plan is built on the SECOND render" |
| `MIN_SKELETON_ELEMENTS = 1` | **19** | "this entry is a trip wire and it just became plannable" |
| a name in the tutorial list renamed | **1** | "names exercises that exist" |

The first is the whole point: 26, by name, the same 26 the marker attribute
finds. The third is worth reading twice - at `MIN_SKELETON_ELEMENTS = 1` every
DOM diff and every order diff in the file still passed, and the only thing that
noticed was the coverage assertion.

## What it costs

One `WeakMap`-free monkeypatch per render in one test file, and 40 words in the
corpus. Nothing in `src/`. **This change does not touch the library.**

## What was rejected

- **A counter behind a debug flag** - `Component79.debug({ countClones: true })`,
  or a `__clones` on the module. It ships a test's needs to every page, and
  `plan-on-the-second-render` already rejected its sibling (a flag that forces
  eager planning) for the better reason: a test that runs against a
  configuration no page runs is how a second render path gets a bug only
  production sees.
- **Asserting the total, 26 of 83.** It is one number for forty independent
  facts: it fails as "25" with no name attached, and it fails on every corpus
  entry added. Per-entry is strictly more informative and no more code.
- **Exact clone counts per entry.** They encode how many times a binding
  re-runs, which no part of this is about, and they would turn every unrelated
  render-count change into a failure in this file.
- **Making the tutorial half two-way** (an exercise that clones and is not
  listed fails). See above: the toll lands on people adding tutorial exercises,
  and what it buys is the news that coverage went up.

## What is still open

- The check answers "did the cloner run", not "did it run **where it should**".
  An entry that clones a two-element fragment somewhere unintended and skips the
  subtree it was written for still passes. The DOM and order diffs cover the
  *correctness* of whatever did run, so what is unguarded is narrower than it
  sounds: coverage moving within an entry.
- `Node.prototype.cloneNode` is a global patch inside a test file. Vitest runs
  the tests in a file in sequence, so nothing observes it mid-flight today; a
  future `test.concurrent` in this file would make the counts lie. It is not
  worth a guard until somebody writes one.
