# A list only needs the reposition refresh when its template reads a position

**Status:** proposal. Follows the profile of `removeRow` taken after
[`2026-08-23.notify-the-difference.md`](2026-08-23.notify-the-difference.md).
Nothing implemented at the time of writing.

## The measurement

`removeRow` costs ~25ms and is the one operation this branch made *worse*
(17.3ms before any of it). Profiled, its attributable JS is the same three
frames as every other list operation — the text-interpolation effect (5.3%),
the `:class` effect (2.3%), the store's `get` trap (3.7%) — i.e. the row
bindings running. There are only ~3,000 of them and they should run at most
once.

They run twice. `data = data.filter(...)` shifts every element after the
removed one, so the container diff gives up and sweeps: every row binding
wakes. Then the `:each` diff finishes, notices that 997 entries changed
`$index`, and calls `fx.refresh()` on each — which re-runs every effect
registered on those entries, all 3,000 of them, a second time.

Disabling the refresh outright confirms it: **25.3ms → 15.9ms**, below where
this branch started. It is not a correct change — that refresh is what
`2026-07-15.effect-runner-hardening.md` added to fix a genuinely flaky seam —
but it prices the problem exactly.

## Why the refresh exists, and why it is usually pointless

`$index` and the `:each` named bindings are plain scope variables, untracked by
design. A binding that reads *only* those tracked nothing, so no notification
can ever wake it, and a keyed reorder would leave it stale. `renderEach`
therefore refreshes every reused entry whose position changed.

But it refreshes **every effect on the entry**, because it cannot tell which
ones read a position. And in the overwhelmingly common list — the benchmark's
included — *no* binding reads one:

```html
<tr :each="row in data" :key="row.id" :class="{ danger: row.id === selected }">
  <td>{{ row.id }}</td>
  <td><a @click="select(row.id)">{{ row.label }}</a></td>
</tr>
```

Nothing here mentions `$index`. Every one of those 3,000 refreshes recomputes a
string that cannot have changed.

## The proposal

Decide it once per `:each`, statically, from the template.

The positional names are `$index` and the `, at` name (`item, i in items` /
`(value, key) in props`) — **not** the item name, which nearly every binding
reads and which is not what goes stale. If the item template mentions neither,
no entry can hold a position-only binding, so `moved` never needs collecting
and `refresh()` never needs calling.

The check is a syntactic walk of the item node's own attributes and its
children's attributes and text, looking for those names as identifiers. It runs
once, when the `:each` is set up, not per render and not per row.

Over-approximating is safe and is the point: a false positive costs a refresh
that was not needed, which is exactly today's behaviour. A false negative would
be a stale binding, and the walk cannot produce one — anything that can reach
`$index` has to name it somewhere in that subtree, including a prop expression
handing it to a nested component (`<Row :n="$index">`), which is an attribute
on a node inside the item.

## What it costs

- One walk of the item template per `:each` at setup. Proportional to the
  template, not to the list.
- Templates that *do* read `$index` keep paying exactly what they pay now.
  This makes the common case free, it does not make the real case cheaper.
- A binding that reaches a positional name through something the walk cannot
  see as text — `scope["$" + "index"]`, an expression assembled at runtime —
  would go stale. Template expressions are source text in the template; there
  is no such construction today, and the same assumption is already load-
  bearing everywhere the parser reads names out of expressions.

## Rejected

- **Refreshing only effects with no deps.** Cheap and almost right: a binding
  that reads only `$index` tracked nothing, so `deps.size === 0` finds exactly
  the ones the refresh was added for. But a binding that reads `{{ $index }}`
  *and* `{{ row.label }}` has deps, and would be skipped. It happens to survive
  today because a reorder usually notifies the paths those deps sit on — which
  is an argument that it usually works, not that it does. The seam this
  refresh closed was flaky in precisely that way; a fix that is "probably
  notified anyway" puts it back.
- **Making `$index` a tracked value** (backing it with the store, or serving it
  from a getter that records a dep): rejected once already in
  `2026-07-15.effect-runner-hardening.md` for leaking into `Object.keys`,
  `$onAny` and hot-reload snapshots. A getter on the item scope avoids that but
  puts a function call on every read of every item binding, on the hot create
  path, to save work on reorders.
- **Skipping the DOM write when the recomputed value is unchanged**: makes the
  refresh cheaper rather than rarer, and by the profile the cost is the
  evaluation (`interpolate`, the `get` traps), not the assignment.

## Open

- `removeRow` also wakes every row binding through the container sweep, because
  `filter` shifts every later element and index-keyed paths make that look like
  a rewrite. That is the same limitation
  `2026-08-23.notify-the-difference.md` closed for appends and left open here;
  only identity-keyed paths would fix it.
- The per-effect allocations (`indexEffect`'s `Map`, `$effect`'s `reindex`
  `Set`) remain untouched, and an experiment removing the redundant-dep pruning
  entirely — on the theory that it spread effects across the trie and made the
  container sweep walk more nodes — moved nothing outside noise. The index's
  upkeep is not where these operations spend their time.

## 2026-08-23 — implemented

Landed as proposed: `mentionsAny` walks the item node's attributes, its
children's attributes and their text for `$index` and the `, at` name; when
neither appears, `renderEach` stops collecting `moved` and the refresh never
runs. 737 tests green (735 plus two new pins).

| op (mean, ms) | HEAD | with the check |
|---|---|---|
| **removeRow** | **25.2 / 22.9** | **15.9 / 17.4 / 15.5** |

`removeRow` ~24 → ~16, which is also below the 17.3 it measured before any of
this branch's work — the one operation the branch had made worse is now the
one it improved most in relative terms. Everything else is flat.

### On the measurements

Two consecutive paired runs showed `clearLarge` 20-30ms *worse* with the
change, which is impossible by construction: `clearLarge` reuses no entry, so
`moved` is empty either way and the only added work is one template walk at
setup. A third run put it at 119.7ms, the lowest reading of the day. The
container drifts in bursts, and a single A/B pair is not enough to call
anything under ~10% — `clearLarge` alone ranged 119.7 to 154.2 across
thirteen runs today on builds that differ in nothing that touches it.

### The tests

Two pins, both of which fail against the unconditional refresh or against a
walk that misses a case:

- a moved entry whose item hands `$index` to a nested tag as a **prop** still
  refreshes — this is the case that forces the walk to descend into children's
  attributes rather than only checking the item node's own;
- a ten-row list with two entries swapped, whose template names no position,
  runs the two moved rows' bindings **once each rather than twice**. The list
  is ten rows so that the container diff notifies those two indices precisely
  instead of giving up and sweeping, which is what makes the double run
  visible: without the check it records `["u9", "u8", "u8", "u9"]`.

The existing "keeps a binding that reads ONLY `$index` fresh across keyed
reorders" pin (`renderComponent.test.ts`) is what guards the other direction,
and it passes unchanged.

### Rejected on the way, with evidence

Before profiling `removeRow` I acted on the theory that the redundant-dep
pruning was the problem — that spreading each row's effects across the trie
made a container sweep walk ~4,000 nodes where it used to iterate one set of
3,000. Removing the pruning entirely moved nothing outside noise, so that
theory is wrong and pruning stays. The index's upkeep is not where these
operations spend their time; the profile says it is the row bindings, and they
were simply running twice.
