# What renderEach and renderNodes re-derive per instance, derived once instead

**Status:** landed, with one of the three changes measured as **not worth
anything on its own** and kept for what it is rather than what it does. Follows
[`2026-08-24.clone-skeletons-measured.md`](2026-08-24.clone-skeletons-measured.md),
which recommended taking the changes that need no second render path first.

Three things the create path re-derived for every instance of a template, all
of them fixed by the source:

1. **Everything `renderEach` reads off its node.** `EACH_PATTERN.match`, the
   `:key` analysis, the `{ ...node.attrs }` rest-spread and the `{ ...node }`
   item node, and `mentionsAny` - a walk of the *whole item subtree* looking
   for `$index`. `renderEach` runs once per render of its parent, so for a
   `:each` nested inside another that was all of it, per row of the outer one.
   Now an `EachPlan`, cached per node.
2. **The `:if`/`:elseif`/`:else` grouping in `renderNodes`.** The sibling walk
   plus a `branches` array and one object per branch, re-built per instance -
   per row, for a chain inside a `:each`. Now a `Chain`, cached per `:if` node.
   `renderConditional` only reads the branches, so one array serves every
   instance.
3. **`findComponentKey`'s per-level `Object.keys`.** Even memoized, the walk
   scanned every scope level below the memo's base for every element rendered.
   An `:each` item scope holds `item`, `$index` and maybe the `, at` name, and
   whether any of those could name a component is decided by the template -
   so the scope is marked plain at creation and the walk skips it.

And one allocation: `renderNode` looped `[":checked", ":selected"]` over a
literal array, allocating the array *and* its closure for every element it
rendered.

## Counted, exact, machine-independent

`create1k` on the benchmark row (8 elements, 1,000 rows):

| | before | after |
|---|---:|---:|
| scope levels scanned by `findComponentKey` | **8,004** | **4** |
| keys read and regex-tested inside them | **16,016** | **16** |
| `Object.keys` arrays allocated for that | 8,004 | 4 |
| arrays + closures for `:checked`/`:selected` | 16,000 | 0 |

## Timed, which is a weaker story

One page per build, alternating rounds, each case against its own null control
(the method and why it has to be that way:
[`2026-08-24.clone-skeletons-measured.md`](2026-08-24.clone-skeletons-measured.md)).

| caso | create | rondas |
|---|---:|---|
| `wide` - 12 elementos por fila | **-14.2%** | 10/15 |
| `nestedwide` - `:each` dentro de `:each`, plantilla interna de 10 elementos | **-11.0%** | 11/15 |
| `benchmark` - 8 elementos por fila | -5.8% / -13.9% / +2.0% | 13/21, 15/21, 11/21 |
| `conditional` - una cadena `:if` en la fila | -3.4% | 13/21 |

**The benchmark row was measured three times and disagreed with itself** -
-5.8%, -13.9%, +2.0%. Two ms out of twenty-six is under this box's noise, and
three runs is what it took to be sure that is what is happening rather than a
result. The counted table above is what actually justifies the change; the
clock only confirms the sign where there is more per-element work to remove
(`wide`) or a subtree walk per row to remove (`nestedwide`).

`nestedwide`'s `replace` read -30.0% (12/15), and its null control that session
ran +6.9% *against* the new build, so if anything that is understated. It is
still one case, and `replace`'s null reaches 17% elsewhere - do not quote it
without the null beside it.

**The `:checked`/`:selected` hoist is not measurable.** 16,000 fewer
allocations per `create1k` and the benchmark row did not move (+0.4%, 9/21,
before the scope change landed on top of it). Kept because it is strictly less
work and reads no worse, not because it does anything. Worth remembering next
time an allocation count looks like a result: the `for...in` change that was
worth -13% removed the same order of allocations, so the count alone does not
predict the clock.

## The one that could have broken something

Marking a scope "declares no PascalCase key of its own" is only safe for scopes
jq79 creates and never adds a key to. **A store must never be marked**: a setup
script's `const Row = await $import(...)` arrives as a new key *after* the
template has rendered, which is the whole reason the tag memo lives for exactly
one pass.

And the marking has to respect a capitalised loop name, because that is not a
mistake - it is how a list of components is rendered:

```html
<Cell :each="Cell in cells" />
```

Two tests cover it: that one, and an outer component resolved from inside a
plain-named loop.

763 tests pass.
