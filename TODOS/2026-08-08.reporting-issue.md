# A template expression that names nothing should say so

**Status:** proposal. Condensed from a longer draft (kept out of `TODOS/` as
`reporting-issue.md`), whose central claim turned out to be wrong — see
[Where the first draft was wrong](#where-the-first-draft-was-wrong).

## The problem

A handler is never called, and nothing is logged:

```html
<!-- parent -->
<script :setup>
  function onFiles(event) {          // <-- the bug
    store.files = Array.from(event.detail)
  }
</script>
<DropForm @files="onFiles" />
```

`$emit` fires. `onFiles` is never invoked: no error, no warning, nothing in
devtools. The same silence hides any typo'd name in any template expression —
`{{ usre.name }}`, `:class="activ"`, `@click="handleClik"`.

## Root cause

Two layers swallow it, neither of which logs.

**1. `function` declarations never reach the store.** `DECLARATION_START_RE`
([`src/transform.ts`](../src/transform.ts)) covers only `let` / `var` / `const`,
so a top-level `function` stays an ordinary lexical declaration inside the
`with` block and never becomes a store property:

```
transformSetupScript("function onFiles(e) {}\nconst g = () => {}")
  → { vars: ["g"], code: "function onFiles(e) {}\ng = () => {}" }
```

**2. The evaluator catches everything.** Expressions compile to a `with`-wrapped
function, so an unresolvable name falls through to `globalThis` and throws a
real `ReferenceError` — which `evalExpr` discards
([`src/jq79.ts`](../src/jq79.ts)). The handler binder then reads `undefined` as
"nothing to do", and the emit looks like it had no subscriber.

The `catch` is deliberate and stays. An expression re-evaluates on every effect
run — once per interpolation, once per `:each` item — so `{{ user.name }}` with
a not-yet-loaded `user` has to render empty rather than tear down the render.

## Why `ReferenceError` is the reportable one

The two failures are distinguishable at the language level:

```
with-scope, unknown name           → ReferenceError: nope is not defined
with-scope, undefined member       → TypeError: Cannot read properties of undefined
```

In `:setup` mode every name a component declares — script vars, props — is
pre-declared on the store *before* the script runs, so it always resolves,
possibly to `undefined`. The `templateScope` `has` trap is deliberately
non-total, so unknown names fall through to `globalThis` where genuine globals
(`console`, `Math`, `fetch`) still resolve. A `ReferenceError` therefore means
the name is declared nowhere: a typo, a dropped prop, or a `function`
declaration that never reached the store.

## Where the first draft was wrong

It generalized that to *"a `ReferenceError` cannot be transient"*. It can — in
**factory** mode. A factory's bindings land on the store via `Object.assign`
when it returns, so an async factory renders once before any of them exist:

```
async-factory   render 1:  <p></p>      → ReferenceError: greeting is not defined
                render 2:  <p>hola</p>     (the value arrives a tick later)
sync-factory                             → no error
setup + top-level await                  → no error (vars are pre-declared)
{{ usre.name }} typo                     → ReferenceError, correctly
```

Measured by patching `evalExpr` to warn and running the four cases. Unguarded,
every `{{ x }}` in an async-factory component warns once — and, with a
module-level dedupe Set, permanently for the session — pointing an author at
correct code and telling them to rewrite it.

The rule worth writing down is the asymmetry: **`:setup` pre-declares its names
before rendering; factory mode cannot**, because they aren't known until the
factory returns.

## Proposal

Report `ReferenceError` out of `evalExpr`, deduped, behind a gate that lets
in-flight scripts finish first:

- **Dedupe on `message|expr`**, module-level. An expression re-evaluates per
  effect run and per `:each` item; un-deduped this is thousands of lines.
  Keying on the message too keeps distinct missing names in one expression
  apart. Module scope matches the `compiled` cache: a missing identifier is a
  property of the source, not of an instance.
- **Don't warn at throw time. Queue and re-check.** On a later task, re-evaluate
  against the same scope and warn only if it still throws.
- **Hold the flush while any script is in flight.** A module-level counter,
  incremented by `runSetupScript` / `runFactoryScript` and decremented when
  their promises settle; flush at zero. This is what makes the async-factory
  case quiet without guessing at timings.
- **Message names the fix**, since the `function` trap is the case that prompted
  this: template expressions resolve against the component store — a top-level
  `let`/`var`/`const`, a declared prop, or a global — and
  `function name() {}` is not on the store; write `const name = () => {}`.
- **Clear the Set on hot update** (`hotReplace`). Note there is no existing line
  to sit beside: `compiled` is never cleared, correctly, since it is keyed by
  expression text. Without the clear, the author fixes the typo, saves, and
  never sees a warning for the next typo in the same expression text.

`instanceof ReferenceError` is fine as written — `compileExpr` builds functions
with `new Function` in jq79's own realm. If expressions are ever compiled
against another document's realm, switch to `(error as Error)?.name`.

## What it costs

A never-settling script promise suppresses every warning on the page. That is
the deliberate direction of the trade: this proposal exists to remove a silent
failure, so it must not add a *loud wrong* one.

The deferred flush also means the warning no longer arrives on the same tick as
the failed evaluation — acceptable for an authoring diagnostic.

## Rejected

- **Warn immediately on `ReferenceError`.** The first draft's patch. False
  positives on every async-factory component, unretractable.
- **Gate per instance by reaching from a scope back to its store.** Exact rather
  than timing-dependent, and the settled moment already exists
  (`result.then(invoke)` in `runFactoryScript`). Rejected for now on plumbing:
  `evalExpr` is module-level, and the scope it receives may be a `:each` or
  `:with` proxy over the store, so it needs a forwarding key and a check that
  reading it doesn't register as a dependency. Worth revisiting if the counter
  proves too blunt.
- **Extend `DECLARATION_START_RE` to `function`.** Closes the specific trap, but
  rewriting `function f() {}` to `f = function f() {}` **loses hoisting**, so
  code above the declaration that calls `f` breaks. Consistent with `const`
  already not hoisting, but a behavior change for existing components — a
  separate, versioned decision. Ship the diagnostic first.

## Still open

- **Declared but undefined** stays silent: `let onFiles` never assigned resolves
  fine, and the handler binder no-ops. A warning there would have to be
  restricted to bare identifier-path expressions, since `@click="count++"`
  legitimately evaluates to a non-function. Lower value; leave it unless it
  shows up in practice.
- **`docs/setup-scripts.md`** says top-level `let` / `var` / `const` become
  store properties and never mentions function declarations, while every handler
  example uses `const save = () => …`. The exclusion should be explicit there,
  since the warning text points authors at it.

## Test

Alongside the existing style in `tests/Component79.test.ts`:

- a missing handler warns exactly once across two clicks, and the message
  contains `missingHandler is not defined`;
- `{{ user.name }}` with `user` undefined stays silent (`TypeError` path);
- an async factory component whose template reads its bindings warns **not at
  all** — the regression this file exists to prevent.
