# Where removeRow, swapRows and selectRow actually go

**Status:** a result. It closes the open item every file on this branch has
carried since [`create-gap-is-diffuse.md`](2026-08-23.create-gap-is-diffuse.md)
- "`swapRows` (+1ms) and `selectRow` (+0.6ms) have never been profiled above
the noise floor" - and it turns out none of the three is the create gap in
another costume. Each has its own cause, each cause has a name, and two of them
are cheap to state and expensive to fix.

Written after [`each-pass-allocations-and-moves.md`](2026-08-23.each-pass-allocations-and-moves.md),
whose lesson is the method here: **do not time anything through jsdom that
moves DOM nodes, and do not trust a Chromium delta smaller than 10%.** What
survives both is counting. Counting is exact, machine-independent, and it is
what produced everything below.

## Instrument 1: how many bindings does an operation re-run?

Every dynamic binding of the benchmark's row routed through a counter, so one
call is one effect run. A 1,000-row keyed list:

| operation | text bindings | class bindings | total effect runs |
|---|---|---|---|
| selectRow | 0 | 1,000 | **1,000** |
| swapRows | 4 | 2 | **6** |
| **removeRow** (4th of 1,000) | 1,998 | 999 | **2,997** |
| partialUpdate (every 10th) | 100 | 0 | 100 |
| append one row | 4 | 2 | 6 |

`removeRow` re-runs **999 rows' worth of bindings to delete one row**. Svelte
re-runs none. At the 4.2µs per effect run measured in
[`with-in-expressions.md`](2026-08-23.with-in-expressions.md), 2,997 runs is
~12.6ms of the operation's 18.9 - about two thirds of it, by arithmetic rather
than by trace, and the remainder is one diff pass plus the teardown.

**The cause is that a dependency is a path.** A row's `label` binding depends on
`rows.4.label`, so its identity in the dep index is *the slot it sits in*.
Remove the fourth row and every slot from the fourth on holds a different item,
which is a change under every one of those paths, and every row behind the hole
wakes to re-render itself with what is now its own item. The output is right and
the work is O(n). Fixing it means keying dependencies to the object rather than
to the path it was reached through - per-key dep sets on the raw object, Vue's
model - which the public `$reactive`/`$toRaw` surface would survive unchanged
and the store's internals would not.

## Instrument 2: how many whole-list diff passes does it trigger?

One `:key` evaluation per row per pass, so calls divided by rows is the pass
count. The mutations are the benchmark app's own:

| operation | how the app writes it | passes |
|---|---|---|
| **swapRows** | `data[1] = data[998]; data[998] = a` | **2.0** |
| the same swap as one array replacement | `data = next` | 1.0 |
| removeRow | `data = data.filter(...)` | 1.0 |
| selectRow | `selected = id` | 0 |
| partialUpdate | 100 writes to `row.label` | 0 |

`swapRows` wakes six bindings and then runs the entire 1,000-row diff **twice**,
once per indexed write, because jq79 patches the DOM synchronously inside the
handler: there is no point at which a handler's writes are still pending, so
there is nothing to batch them into. Svelte, Vue and React all take the second
write into the same flush. It also means the diff sees the intermediate state -
after the first write two rows hold the same item, and the duplicate-`:key`
warning fires on a swap that is perfectly legal.

Batching a handler's writes into a microtask would halve this one and pay off
on any handler that writes more than once. It is also the one fix here that
changes what a user can observe: 739 tests write to a store and assert against
the DOM on the next line, and they are right to.

## Instrument 3: what a pass is made of

The allocation work made the isolated pass valid to profile (2 DOM moves, no
volume), so this is a `--cpu-prof` of 400 adjacent-row swaps over a 1,000-row
list, unminified, self time:

| share | frame |
|---|---|
| 23.6% | the store proxy's `get` trap |
| 17.3% | the `:each` effect body - the diff loop itself |
| 13.9% | the compiled expressions (`new Function`, no URL) |
| 5.6% | garbage collector |
| 3.4% | `sync` - re-indexing an effect's deps after a run |
| 3.0% | the effect runner |
| 2.3% | `compileExpr` |
| 1.3% | `wrap` |
| 0.6% | `whatChanged` - the container diff |

**37% of a pass is evaluating expressions** - the `get` traps that make
tracking work plus the `with`-scoped closures that read through them - which is
the same 695ns/op, 60% of it `with`, that `with-in-expressions.md` priced and
recommended leaving alone. A pass evaluates one `:key` per row, so a 1,000-row
list pays 1,000 of them to discover that nothing changed.

## What this says about the three operations

- **removeRow (18.9ms vs 1.2)**: path-keyed dependencies. Structural, invisible
  from outside, and the most invasive of the three to fix.
- **swapRows (8.7ms vs 1.1)**: two passes where one would do, plus 1,000 `:key`
  evaluations per pass. Fixing the first is batching, which is a behaviour
  change; fixing the second is making the reuse check cheaper than an
  expression evaluation.
- **selectRow (5.3ms vs 1.25)**: 1,000 class bindings, which Svelte re-runs too.
  This one is *already understood* - it is 4.2µs per binding against 1.25µs, and
  where that goes is priced to the nanosecond in `with-in-expressions.md`.

None of the three is the create gap, and none of them is closed by compiling the
template. That was the question this file was opened to answer, and the answer
is no: **the create path and the list path need different work, and the list
path is the one with named, unfinished causes in it.**

## Open

- `compileExpr` rebuilds its cache key - `${params.join(",")}|${expr}` - on
  every evaluation, not every compile: 2.3% of a pass, spent looking up a memo.
  The params list is empty for every template expression that is not a handler.
- The `:key` evaluation per row per pass is 1,000 `with`-scoped calls to decide
  reuse. A key that is a plain member expression (`row.id`, which is what a key
  almost always is) could be read directly instead of compiled and evaluated.
- Nothing here has traced the operations in Chromium. The counting is exact and
  machine-independent, and the arithmetic that converts it to milliseconds
  borrows a per-effect cost measured elsewhere on this branch. A
  `devtools.timeline` trace would confirm the conversion; it would not change
  the counts.
