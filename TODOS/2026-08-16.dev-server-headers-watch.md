# `devServer({ headers, watch })`

**Status:** proposal.

## The problem

Two things the dev server can't do, both of which end with someone abandoning it
for a bundler they didn't want.

**1. It sends the headers it chose and nothing else.** A page that needs
`SharedArrayBuffer` needs `Cross-Origin-Opener-Policy` and
`Cross-Origin-Embedder-Policy`; a component fetched from another origin needs
`Access-Control-Allow-Origin`; someone testing a `Content-Security-Policy`
before deploying behind one needs to send it here first. The server serves the
bytes a static host would serve — but a static host is *configured*, and the
headers are the configuration. Not being able to reproduce them means the one
class of bug this server exists to catch (what a static host actually does) is
the one it can't.

**2. It watches exactly one directory: the one it serves.** That is the whole
project when the project is a folder of `.html` files, and it stops being the
whole project the moment anything generates into it — a Sass build writing
`app.css`, a `tsc --watch` writing `app.js`, components kept in a sibling
package. Editing the *source* of a served file changes nothing until you save
something inside the root by hand.

## The proposal

```js
devServer({
  rootDir: "public",
  headers: { "cross-origin-opener-policy": "same-origin" },
  watch: ["components", "styles/theme.scss"],
})
```

### `headers`

A flat map, sent on **every** response: pages, components, `client.js`, the
event stream, the redirects, the 404s. Not per-route — a dev server's headers
are the host's headers, and a host applies them to everything.

Names are lowercased once at startup. Header names are case-insensitive but an
object is not, and `{ "Cache-Control": ... }` spread over the server's own
`cache-control` would otherwise go out as two lines rather than replacing it.

**`content-type` and `content-length` stay the server's.** They describe the
bytes of the response they're on — `content-length` most of all, since a wrong
one truncates the body or hangs the socket — and a global header that
contradicted them would break every response it was set on. Everything else the
options say wins, `cache-control` included.

### `watch`

Extra files and directories, watched **on top of** `rootDir`, which keeps being
watched recursively as it is now. Paths resolve against the process's cwd, the
same way `rootDir` does, so every path in the options reads the same way.

What a change does depends on where the file is, and the rule is the one already
in the server: the runtime can only swap a file it can name, and it names a file
by the url it fetched it from.

- **inside the root** — unchanged: `.html` pushes an `update`, anything else a
  `reload`. (Listing a path inside the root is a no-op: the recursive watch
  already has it. It is skipped rather than double-watched.)
- **outside the root** — always a `reload`, carrying the path relative to the
  root (`"../components/row.html"`) rather than an absolute one, which would
  publish the machine's directory layout to the page for a string only used in a
  log line. There is no url to swap into: the file is served from nowhere.

A **single file** is watched through the directory it sits in, filtered to its
basename, not through a watcher on the file itself. A watcher on a file follows
the inode, and an editor's atomic save renames a *new* inode over it — the
watcher survives as a handle on a file nothing will write to again, which is the
worst failure available here, because it works once and then quietly stops.

A path that doesn't exist **throws, before the server listens**. The alternative
is a server that starts, prints its url, and doesn't watch what you told it to;
the only evidence would be a reload that never comes, which reads as a bug in the
server rather than a typo in the config.

### The CLI gets both

```sh
jq79 dev public -w ../components --header "cross-origin-opener-policy: same-origin"
```

Repeatable, both of them. `-H` is already `--host`, so the header flag is
`--header` and spelled out. Leaving these to the JS API only would mean writing a
script to get a header, on the path chosen specifically for not writing scripts.

## What it costs

- **`headers` is unvalidated.** A nonsense name or a value with a newline in it
  is node's `writeHead` to reject, and it throws per-response rather than at
  startup. Accepted: validating header syntax is a spec-sized job for a config
  the author reads back on the very next request.
- **A `reload` for outside files, always** — even for an outside `.html` that a
  page has mounted. It could be resolved: if the file's *served* copy exists
  somewhere under the root, its url is knowable. But that's a mapping the server
  doesn't have and would have to guess, and guessing wrong swaps the wrong
  source into a live instance.
- **More watchers, and node's recursive watch is not free** on a large tree.
  That was already true of the root; `watch` makes it possible to point at three
  more. Nothing here mitigates it beyond the existing dotfile/`node_modules`
  skip, which now applies inside each extra directory too.
- **A symlinked directory inside the root is now reachable**, where before it was
  invisible (`fs.watch` doesn't follow links). Not a goal, but the containment
  check runs on real paths — so a link whose target lives outside the root reads
  as outside, and gets watched. Correct, and worth naming because it means
  `watch: ["public/vendor"]` can be a real watcher rather than a skipped no-op.

## Rejected

- **Applying `headers` through `setHeader` before routing** so node merges them.
  One line, and it inverts the rule: `writeHead` takes precedence over
  `setHeader`, so the server's `cache-control: no-store` would beat the author's,
  and only the headers the server *doesn't* set would land. The precedence has to
  be explicit to be the one documented.
- **Per-route or glob-keyed headers** (`{ "/api/*": {...} }`). A second matching
  language for a server whose whole claim is that it doesn't transform anything.
  If it ever arrives it should arrive as a function, not a pattern table.
- **`watch` replacing the root watch** when it names a path inside the root — as
  a way to narrow the watch on a big directory. Two rules for one option, decided
  by where a path happens to live; and narrowing what's watched is a different
  feature (an `ignore`) wearing this one's name.
- **Skipping a missing `watch` path with a `console.warn`.** Friendlier to a
  build output directory that doesn't exist yet, and it puts the one signal you
  get in the startup log, above the url, where it scrolls away and is never seen
  again.
- **chokidar**, which would make the file watch atomic-save-proof without the
  parent-directory trick. It is a dependency, and `jq79/dev` has none — the site
  build already pays for chokidar and this server deliberately doesn't.

## Test

- a configured header is on a page, a component, `client.js`, the event stream
  and a 404, and it does **not** displace `content-type`/`content-length`;
- `{ "Cache-Control": "max-age=60" }` replaces the server's `no-store` rather
  than arriving beside it;
- a change in an outside watched directory sends a `reload` whose url is the
  relative path, and no `update`;
- a single watched file outside the root reports, and its neighbours in the same
  directory do not;
- a `watch` entry inside the root still hot-updates under its served url, rather
  than being downgraded to the outside path's reload. (That it is skipped rather
  than double-watched is *not* observable from the outside: the debounce
  collapses a duplicate event, and — measured — a single save already arrives as
  two frames often enough under load that counting them is a flaky test, on the
  root watcher as much as on this one.)
- `watch: ["nope"]` throws from `devServer()`.

## Still open

- **Whether `headers` should reach the SSE stream at all.** It does, on the
  "everything a host would touch" rule, but the stream is the server's own
  endpoint and a CSP strict enough to matter could plausibly break it. No
  evidence either way yet.
- **A `watch` entry that is created later** (the build output directory that
  doesn't exist at startup) still throws. If that turns out to be the common
  case, the answer is watching its parent until it appears, not downgrading the
  throw.

## 2026-08-16 — `watch` takes handlers, not paths

Same day, before any of it shipped. `watch: string[]` is replaced by:

```js
watch: [{ pattern: "styles/**/*.scss", fn: files => build(files) }]
```

### Why the path list was the wrong shape

It could only ever produce a page reload, and the section above talks itself into
that being enough: *"whatever generates into the root triggers the reload by
itself."* True — and it says the quiet part. The thing that generates into the
root is a build step, and a path list watches for one without being able to run
one. You still need a second watcher, in a second process, to do the only work
the reload was waiting on.

A handler makes the option earn its place: the server already knows what changed
and when, and it is already debouncing the burst. What was missing was somewhere
to put the two lines that compile it.

```js
// what this now replaces: a second watcher, a second process, and the reload
// racing whichever of the two got there first
watch(["styles"], build)     // chokidar, in another terminal
```

### The rules

**A glob, not a path.** A path can't say "the .scss files but not the .css ones",
which is exactly the distinction a handler needs. Matched with
`path.matchesGlob` — no dependency, and the syntax everyone already writes.
Patterns resolve against the cwd, like `rootDir`, and a **bare directory means
everything under it**: `"../shared"` is normalized to `"../shared/**"`, because
as a literal pattern it would open the directory and match nothing inside it —
a mistake invisible until a save doesn't fire.

**Watching starts at the literal head of the pattern.** A glob is a filter and a
watcher needs a directory to open, so `styles/**/*.scss` opens `styles/`. Same
throw as before if it isn't there, now on the head rather than the whole path.

**One call per burst, serialized.** `fn(files)` gets every path of the burst that
woke it, absolute. A save touching four files is one build. A batch arriving
mid-run waits for the run — the `building`/`queued` shape
[`scripts/site-dev.mjs`](../scripts/site-dev.mjs) already uses, for the same
reason: a build racing itself writes half of each.

**A handler never costs you hot reload.** Inside the root, the root's behaviour
is unconditional — `.html` hot-swaps, everything else reloads — and a matching
`fn` runs *as well*. This is the rule the whole design turns on. The tempting
alternative is "a pattern claims its files", which would let
`{ pattern: "**/*.scss", fn: sass }` skip the pointless reload for a source file
the browser never fetched. Rejected: it also lets
`{ pattern: "components/**", fn: log }` silently disable hot reload for the
components the server exists to hot-reload. A footgun that takes away the
feature you came for is worse than a redundant reload, and the redundant reload
has an ordinary fix — keep your sources outside the directory you serve.

**Outside the root, the handler is the whole answer.** A matched file runs its
`fn` and sends nothing; what the `fn` writes into the root comes back round as a
change with a url, and that is what reloads the page. An entry with **no** `fn`
still reloads directly, which is the entire old feature, kept as the degenerate
case rather than as a second option.

### What it costs, on top of the above

- **Node 22.5+**, for `path.matchesGlob` (CI is on 24). The alternatives were a
  dependency or a hand-rolled matcher, and a hand-rolled glob is a bug farm that
  disagrees with every other glob the user writes.
- **`fn` runs unsandboxed, in the server's process.** It is a dev server reading
  a config the author wrote; the same is true of every bundler plugin. But an
  `fn` that hangs hangs its entry's queue, and only its entry's queue.
- **The CLI can only build fn-less entries** (`-w '../ui/**'`), because an
  argument can't carry a function. Named in `--help` so it doesn't read as a
  missing feature.

### Test

Added on top of the list above: the handler gets both files of a burst and
nothing its pattern missed; a handler writing into the root produces the reload
for the *written* file and none for the source; a file inside the root still hot
-updates while its handler runs; a throwing handler is logged, names its pattern,
and the server keeps serving.
