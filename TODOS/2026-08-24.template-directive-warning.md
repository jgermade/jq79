# A directive on a nested `<template>` says nothing

**Status:** proposal, then implementation. Small, and deliberately not the
feature next to it.

Closes the only part of §3 of
[`2026-08-24.what-is-still-open.md`](2026-08-24.what-is-still-open.md) that is a
defect rather than a missing feature. It does **not** add the invisible wrapper.

---

## The problem

Two silent failures, found by probing rather than reported:

```html
<ul><template :if="show"><li>uno</li><li>dos</li></template></ul>
```
```
show=true  -> <ul><!--if--><template><li>uno</li><li>dos</li></template></ul>
```

The `:if` works exactly as written: it decides whether the `<template>` is
inserted. What the author wanted was for its *children* to appear, and they
never can - a `<template>`'s children live in `.content`, which is native HTML
behaviour and not a bug. So the page shows nothing, in both states, and the
console says nothing at all.

The second is worse, because the directive is not merely invisible - it is
dropped:

```html
<Panel><template :slot.header :if="show"><h2>cabecera</h2></template></Panel>
```

With `show=false` the header **renders anyway**. `partitionSlots` finds the
node by `slotAttrOf` and takes `child.children` as the slot's content; nothing
on that path ever looks at `:if`. Verified.

Neither is a rendering bug to fix. The first is native semantics; the second is
a real design question (should a slot-filler be conditional?) that this file is
not answering. Both are worth a console line, which is the house style for
exactly this - `:model` on a plain element, `:deep()` outside a scoped block, a
`:props` spread that is not an object.

## Where this came from, and a correction

§3 frames the missing piece as "jq79 has no element that renders nothing" and
proposes `<template :if>` as a way out.
[`2026-08-05.multi-template-file.md`](2026-08-05.multi-template-file.md) says a
wrapper "cannot use `<template>`" and would need its own tag.

**That sentence is broader than the reasoning under it.** Its argument is about
the *top-level* position, where `<template>` declares a component and a reader
should not have to check an attribute to know which of two things they are
reading. Nested, there is no such ambiguity, and the library already ships the
shape it forbids: `<template :slot.header>` is a nested `<template>` carrying a
jq79 directive, and it renders **no `<template>` element at all** - its children
are lifted in place between anchors.

So the rule the code actually follows is already:

| nested `<template>` | meaning |
| --- | --- |
| bare | the native inert element (cloned by hand from `.content`) |
| carrying a jq79 directive | a jq79 construct - which is what `:slot` is |

Recorded here because the next person to read §3 will hit the same sentence.
Making `<template :if>` render its children in place stays available, and stays
out of scope: the work there is not the `:if` but `boundsOf`, which resolves a
fragment as `{ first: node.firstChild!, last: node.lastChild! }` and would break
on an empty one. `:slot` sidesteps that by always inserting its own anchors.

## The proposal

One check, at parse time, in `validateChains` - which already walks every node
of every definition once, before any data exists, for exactly this class of
"the template says something it does not mean".

It fires on a **nested** `<template>` carrying `:if`, `:elseif`, `:else` or
`:each`, with two messages:

- **with a `:slot` attribute** - the directive is *ignored*: a slot's content is
  its children as written. Put it inside, on the content.
- **without one** - the directive works and shows nothing: put it on the
  elements themselves.

`:each` is included because it is the same misconception with the same fix, and
one line more.

### What deliberately does not warn

- **A top-level `<template>`.** `parseComponentString` pulls declarations into
  `declarations` before `componentPartsFrom` ever runs, so `validateChains` only
  ever sees nested ones. No exclusion needed - the position is structural.
- **A bare nested `<template>`.** That is the legitimate native use, and the
  2026-08-05 addendum is right that warning there would fire on correct code.
  The directive is the discriminant, and nothing else is.
- **Every other directive on a `<template>`** - `:text`, `:with`, `@click`.
  Invisible too, but nobody writes them expecting a fragment; the two above are
  the ones the shape invites. Widening later is one entry in a list.

## What it costs

Nothing at render: `validateChains` runs once per definition, and this is an
attribute check on nodes it already visits. Nothing at all for a template with
no nested `<template>` in it.

The risk it carries is firing on correct code. A `<template :if>` written to
*conditionally provide something clonable* is the case that would - exotic, and
degraded to a console line rather than a broken page, which is the trade every
other warning in the library makes.

## What is still open

- The invisible wrapper itself (§3), untouched, with its cost named above.
- Whether a slot-filling `<template>` *should* be conditional. The warning says
  the directive is ignored, which is true today, and does not argue it should
  stay that way.
