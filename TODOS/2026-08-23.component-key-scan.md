# The component-name scan runs once per element, and it is the create path's hot spot

**Status:** proposal. Written after profiling the create path, which
[`2026-08-23.narrow-the-wake-rule.md`](2026-08-23.narrow-the-wake-rule.md) left
open as "that gap is `renderNode`/`renderEach` building DOM, and needs its own
profile". This is that profile. Nothing implemented at the time of writing.

## The measurement

A CPU profile of `create10k` (Chromium, 50µs sampling, the benchmark app built
unminified so the frames carry real names), aggregated by self time:

| self | share | frame |
|---|---|---|
| 461.3ms | **13.7%** | `findComponentKey` (`src/jq79.ts:391`) |
| 104.8ms | 3.1% | `renderElement` |
| 98.7ms | 2.9% | `appendChild` (native) |
| 94.4ms | 2.8% | garbage collector |
| 65.1ms | 1.9% | `createElement` (native) |
| 59.9ms | 1.8% | `renderNodes` |
| 50.7ms | 1.5% | the store proxy's `ownKeys` trap |

`(program)` takes 57%, which is sampling overhead and native work the profiler
cannot attribute; the shares above are of everything sampled, so treat them as
proportions rather than milliseconds. **`findComponentKey` is the single
largest attributable JS cost on the create path, by a factor of four.**

## Why it costs that much

```ts
const findComponentKey = (scope, tag) => {
  const normalized = tag.replace(/-/g, "").toLowerCase()
  for (let obj = scope; obj && obj !== Object.prototype; obj = Object.getPrototypeOf(obj)) {
    for (const key of Object.keys(obj)) {
      if (/^[A-Z]/.test(key) && key.replace(/-/g, "").toLowerCase() === normalized) return key
    }
  }
  return null
}
```

`renderElement` calls it for **every element it builds**. The benchmark row is
`<tr>` + four `<td>` + an `<a>` + a `<span>`, so 10,000 rows is ~60,000 calls,
and every one of them walks the whole scope chain — item scope, component
scope, store proxy, the null-prototype siblings object — calling `Object.keys`
at each level. That is ~180,000 throwaway arrays (the GC line above), ~700,000
regex tests, and 60,000 trips through the store proxy's `ownKeys` trap, to
answer a question whose answer is `null` for every one of those tags.

**Confirmed, not assumed:** replacing `/^[A-Z]/.test(key)` with a `charCodeAt`
range check — which removes essentially all 700,000 regexes — moved
`create10k` from 837.8ms to 837.8ms. The regex is not the cost. The chain walk
and its allocations are, and the only fix that helps is not doing them.

## The proposal: memoize per render pass, not per element

The answer depends on the tag and on which names are in scope, and *not* on
anything that varies between one row and the next: `findComponentKey` returns
the scope **key**, not the value behind it, so every row of a `:each` resolves
`td` (and `Row`) identically. Within one run of the list effect the chain's key
sets cannot meaningfully change either — a store write during the run marks the
effect dirty and restarts the whole pass against settled state (the reentrancy
guard from `2026-07-15.effect-runner-hardening.md`).

So: a `Map<tag, key | null>` that lives for exactly one render pass. Set it
around the body of `renderEach`'s effect and around a component's own render,
restore the previous one in a `finally` (they nest — a component inside a row
renders inside the row's pass). `findComponentKey` consults it when one is
installed and falls through to the scan when none is.

60,000 chain walks become one per distinct tag per pass.

### Why it must not outlive the pass

`TODOS/2026-08-08.setup-yield-render.md` records that the template renders
*before* the setup script settles: `const Row = await $import(...)` lands after
the first render, as a new store key. So a cached "no component called `Row`"
must not survive — and it doesn't need to, because a new key re-runs every
effect in the store (the `isNewKey` sweep), which re-enters the render with a
fresh memo. Caching the scan on the scope objects instead, in a `WeakMap`, is
what breaks here: nothing invalidates it when the import lands.

## What it costs

- One `Map` per render pass, and a module-level slot to hold the current one -
  the same shape as the existing render-time nesting counter.
- A tag that resolves differently at two points *within a single synchronous
  pass* would be memoized wrongly. That needs a scope's PascalCase key set to
  change mid-render without the change re-running the effect, which the
  reentrancy guard already rules out for store writes.
- The scan itself is untouched, so nothing changes for the first element of
  each tag, for a component rendered once, or for the error path
  (`componentCandidates`, which only runs when a tag failed to resolve).

## Rejected

- **A `WeakMap<scope, Map<normalized, key>>` cache**, rebuilt per scope object:
  faster still (the store level would be scanned once ever rather than once per
  pass) and wrong for the late-import case above, with no cheap way to notice
  the key set changed - checking would mean `Object.keys` again, which is the
  cost being removed.
- **`for (const key in scope)`**, which walks the chain with no array
  allocation at all: measured, and it fails 5 tests - sibling components
  declared by `<template name="Row">` live on a null-prototype object on the
  store's *prototype* (`siblingsInScope`, `jq79.ts:2130`), and `for...in` does
  not reach them the way the explicit walk does. Not pursued; the memo makes
  the walk rare enough that its inner loop stops mattering.
- **Resolving the tag once at parse time, onto the `TemplateNode`**: the node
  is shared across every scope the template renders in, and a tag resolves
  against the scope, so this would need a per-node-per-scope key anyway - which
  is the WeakMap above.

## Open

- The remaining attributable create-path cost after this is `renderElement`
  itself (3.1%) and native DOM calls, which are irreducible without changing
  what jq79 builds. `create1k` at ~80ms against Svelte's 9ms is not explained
  by anything in this profile's top 25; the bulk sits in `(program)`, and
  finding out what that is needs a different instrument than a sampling
  profiler.
- `renderEach` still reads all 1,000 items to diff them, holding a dep on each
  (carried over from the previous file's Open list). Untouched here.

## 2026-08-23 — implemented

Landed as proposed: `scanComponentKey` is the old function unchanged,
`findComponentKey` walks from the caller's scope up to the pass's base scope
(checking own keys as it goes, so a name introduced under the base still
shadows) and consults the memo only once it gets there. `renderEach`'s effect
body is wrapped in `inRenderPass(scope, ...)` — the one place that renders the
same tags thousands of times. 735 tests green, unchanged.

Two measured runs, against the numbers this branch already had:

| op (mean, ms) | before this file | after | vs. original baseline |
|---|---|---|---|
| create1k | 79.9 | **50.6 / 50.8** | 82.6 |
| replace1k | 92.7 | **50.3 / 51.0** | 75.3 |
| create10k | 837.8 | **566.8 / 515.0** | 729.3 |
| appendToLarge | 222.1 | 201.3 / 197.9 | 186.2 |
| clearLarge | 160.8 | 161.0 / 155.4 | 103.9 |
| partialUpdate | 1.4 | 1.3 / 1.4 | 171.9 |

`replace1k`'s regression from the wake-rule change is gone and it is now well
ahead of where it started; `create1k` and `create10k` are ~35% below the
original baseline. The whole benchmark is now at or better than the original
on every operation except `removeRow` (+5ms), `appendToLarge` (+15ms) and
`clearLarge` (+55ms).

### Where `clearLarge` actually goes

Profiled directly rather than assumed, since it is the one substantial
regression left. Clearing 10,000 rows:

| self | share | frame |
|---|---|---|
| 109.9ms | **40.1%** | `removeChild` (native) |
| 102.7ms | 37.5% | `(program)` |
| 13.9ms | 5.1% | `$effect`'s registration/disposal closure |
| 11.2ms | 4.1% | `removeDep` |
| 10.0ms | 3.6% | `indexEffect`'s disposer |
| 4.4ms | 1.6% | `runMatched` |

The index costs ~13% of it and is the regression; **`removeChild` alone is
three times that.** `removeRange` unlinks every row one node at a time, and a
`:each` that empties completely could hand the whole span to the DOM in one
call instead. That is the next thing worth doing for this operation, and it is
a `renderEach`/`removeRange` change with nothing to do with reactivity — a
separate file when someone takes it.
