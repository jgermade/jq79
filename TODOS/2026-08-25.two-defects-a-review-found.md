# Two defects a review of the branch turned up

**Status:** proposal, then implementation. Neither comes from the branch that
found them - a code review pointed at `main...HEAD`, and local `main` sits at
0.5.12, so the range was 44 commits (PRs #8 through #12) rather than the eight
this branch added. Both were then reproduced by hand, and one was bisected,
because a review is a lead and not a result.

They are unrelated and both are small. They are in one file because they were
found together and neither is worth a file's worth of framing on its own.

---

## 1. A replaced object with the same number of keys leaves `Object.keys` stale

**A rendering bug, shipped, and it predates 0.6.0.**

```html
<p>{{ Object.keys(bag).join('|') }}</p>
```

```
store.bag = { a: 1, b: 2, c: 3, d: 4 }   ->  a|b|c|d
store.bag = { a: 1, b: 2, c: 3, e: 9 }   ->  a|b|c|d   *** stale ***
store.bag = { a: 1, b: 2 }               ->  a|b       fine
```

`notifyReplaced` wakes the `@keys` dep - the one an effect records when it reads
`Object.keys(container)` - on one condition:

```ts
if (keyCount(previous) !== keyCount(next)) collectExact(keysPath(dotKey))
```

The **count**, not the set. Swap a key for another and the count is unchanged,
so nothing wakes. An effect whose only surviving dep is `<path>.@keys` never
re-runs - `indexable` prunes the container ancestor, so there is no broader dep
left to catch it. A `:each` over the same object survives only because it also
holds per-value deps.

### Bisected

| | |
|---|---|
| `02193be` 0.5.12 | fine |
| `ba52844` index effect deps in a path trie | fine |
| `441fc03` wake only the effects a write concerns | fine |
| **`fe388a5` notify what changed in a replaced container** | **stale** |
| every release since, up to and including this branch | stale |

So it arrived with `notifyReplaced` itself, which is what that commit was for.
The review guessed the mechanism right and its age wrong; the table is the
answer.

### The fix, and it is free

`whatChanged` already builds the union of both key sets on the object path:

```ts
const keys = new Set([...Object.keys(previous), ...Object.keys(next)])
```

A union larger than either side's own count *is* a key-set change, so the
answer is sitting in a variable that already exists. `Difference` grows a
`keysChanged` field, set at each of the four return sites:

- **arrays** - the keys are `0..length-1`, so a length change is exactly a
  key-set change, and the existing comparison is already right. No new work on
  the path that walks 10,000 elements.
- **objects** - the union is compared against each side's own key array, both
  of which the union was built from. No new allocation, and `notifyReplaced`
  stops calling `keyCount`, which was building both arrays a *second* time on
  every object replacement. That leaves `keyCount` with no callers, so it goes.

`notifyReplaced` then asks `difference.keysChanged` instead of counting.

The wake becomes strictly more inclusive - it fires in a case where it fired
never - so it cannot cause a missed update, and the cost is two comparisons
against arrays that were already built. **No performance claim is made here**: the
benchmark row replaces arrays, this only moves the object branch, and this box
cannot resolve a difference that small (see the AGENTS.md warning that any
delta under the runner's noise is not a result).

## 2. `Component79.debug` accepts a flag it does not have

```js
Component79.debug({ cloneSkeleton: false })   // singular: a typo
// -> { cloneSkeletons: true, cloneSkeleton: false }
```

Measured: no warning, the typo is written into `debugFlags`, and it is echoed
back in the return value. So a caller reading the result sees `cloneSkeleton:
false`, believes cloning is off, and it is still on - which is exactly the
question that flag exists to answer ("a bug report whose reporter can say *it
goes away with cloning off*").

The guard only tests the value:

```ts
if (typeof value === "boolean") debugFlags[key as keyof DebugFlags] = value
else console.warn(`jq79: Component79.debug ignored "${key}" - the flags are booleans, and the ones it knows are: …`)
```

A typo with a boolean value passes it. The message it *would* have printed
already names the right remedy - it lists the flags it knows - so the fix is to
reach it: check the key against `debugFlags` before the value. From PR #11,
which is where the flag was introduced.
