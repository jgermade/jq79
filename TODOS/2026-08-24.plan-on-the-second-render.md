# Plan on the second render, not the first

**Status:** proposal, then implementation. Follows directly from
[`2026-08-24.one-shot-render-measured.md`](2026-08-24.one-shot-render-measured.md),
which measured the thing this fixes.

---

## The problem it is fixing

A definition rendered **once** pays for a plan it never reuses. Measured, at
matched configuration, one render each:

| elements per definition | median chunk | clone-on wins |
|---|---:|---:|
| 3 (the `MIN_SKELETON_ELEMENTS` threshold) | **+23.1%** | 4/100 |
| 6 | **+11.5%** | 13/100 |
| 9 | +2.8% | 29/100 |
| 12 | -1.9% | 59/100 |
| *null control* | +0.0% | 43/100 |

`MIN_SKELETON_ELEMENTS = 3` was tuned on list rows, where the plan amortizes
over a thousand instances. At exactly that threshold, a one-shot render pays
+23%.

Raising the constant is the obvious fix and it is the wrong one: it would take a
9-element `:each` row - which amortizes beautifully - off the clone path in
order to protect a one-shot render that may not exist in the page at all.
Element count is a proxy, and it is a proxy for the wrong thing.

## The proposal

Key on the thing that actually decides: **how many times a definition is
rendered.** `planOf` returns `null` the first time it sees a node and builds the
plan the second time.

```
one-shot definition   -> no plan is ever built. Pays nothing.
:each of 1,000 rows   -> row 1 interpreted, rows 2..1000 cloned.
```

The cost is one interpreted render per definition, once, ever - and it is paid
only by definitions that go on to be rendered again, which are exactly the ones
that can afford it. `renderEach` calls `renderNode` per row and `renderNode`
calls `planOf`, so the list case needs no special handling: it falls out.

`MIN_SKELETON_ELEMENTS` stays where it is. It is still doing its own job -
keeping two-element fragments out of the cloner - and this change is about a
different axis.

### The state machine

`skeletonPlans` is a `WeakMap` with two meaningful states today: absent (not
examined) and `null` (examined, not plannable). A third is needed - "seen once,
not examined yet" - and it is a `WeakSet`, not a sentinel in the map, so the
map's type stays what it says.

Note what is deliberately *not* counted: this is "seen a second time", not
"rendered twice simultaneously". Two instances of a definition on a page reach
the second render through the same path as one instance rendered on two
occasions, and both should get the plan.

## What this breaks, and it is the interesting part

**The differential test goes vacuous, silently.** `tests/skeleton.test.ts`
renders each corpus template once per arm. With the plan built on the second
render, the "cloned" arm never clones - every assertion still passes, and
nothing is being tested. That is a worse outcome than a bug, because it looks
like success.

Two places, and both need the *same* fix rather than a flag:

- **The corpus.** Each template is rendered twice per arm now, and both renders
  are compared. This is strictly better coverage than before: it proves the new
  invariant this change introduces - that the interpreted first render and the
  cloned second render produce the same DOM and register in the same order.
- **The tutorial exercises.** Worse there: `mount()` builds a fresh
  `new Component79(source)` each time, so each mount is a *first* render of a
  brand new AST and no mount would ever clone. The component has to be built
  once and mounted twice, so the second mount sees the AST the first one marked.

Rejected: a debug flag that forces eager planning for tests. It would mean the
tests exercise a configuration no page runs, which is how a second render path
gets a bug that only production sees - the exact failure mode this whole area is
arranged to prevent.

## What it costs

One `WeakSet.has` per node on the path that already does a `WeakMap.get`, and
one `WeakSet.add` per node per definition, once.

Against that: a list pays one interpreted row it did not pay before. On
`create1k` that is one row in a thousand, which is 0.1% of an operation whose
own round-to-round spread is several percent - not measurable, and in the
direction the gate does not care about.

## What it measured

**Prediction 1 held, and it is the whole point.** Same instrument, same
configuration, same null control as the table above:

| elements | before | after | null control |
|---|---|---|---|
| 3 | +23.1%, 4/100 wins | **+0.0%, 41/100** | +0.0%, 46/100 |
| 6 | +11.5%, 13/100 wins | **+0.0%, 44/100** | +0.0%, 46/100 |

Both land exactly on the floor. The one-shot cost is gone, not reduced.

**Prediction 2 could not be answered by the clock, and did not need to be.**
The first well-powered run said the list win had vanished - +0.0% at 44/400
chunks against eager's -7.1% at 76% - which would have been a serious
regression. Alternating the two builds three times each says otherwise:

```
LAZY   -3.3%/58%   -3.7%/64%   -0.0%/54%
EAGER  -0.0%/52%   -7.4%/74%   -6.7%/71%
```

Eager's own worst pass is -0.0% at 52%, indistinguishable from lazy's worst.
The single run was an artifact, of exactly the kind
[`2026-08-23.where-the-create-time-goes.md`](2026-08-23.where-the-create-time-goes.md)
exists to warn about, and this box cannot resolve a difference of this size at
this configuration.

**Counting answers it exactly, where the clock cannot.** With the plan built
eagerly, 50 renders of one definition clone 50 times. With it built on the
second sighting, they clone 49:

```
50 renders of ONE parse ->  seen=6  cloned=49
:each of 50 rows        ->  seen=6  cloned=49
```

So the cost is not an estimate with an error bar. It is **exactly one
interpreted render per definition, once, ever** - 2% of the renders at N=50,
0.1% at `create1k`'s thousand rows, and 1/N for everything else. That is an
arithmetic bound, and it is worth more here than another afternoon of medians.

## What it broke, and what that cost

The vacuity was real and it was measurable. Sabotaging `renderFromSkeleton` so
every cloned root carries a marker attribute, and counting which corpus entries
notice:

| | entries that reach the cloner |
|---|---|
| before this change | 26 / 83 |
| after, tests untouched | **5 / 83** |
| after, tests fixed | 26 / 83 |

The 5 that survived were the `:each` entries - templates that render a row more
than once inside a single mount, which is the one shape that still reached a
second sighting.

The tutorial half needed one more fix than the plan anticipated.
`mountShadow` only renders when the instance has no content yet, so mounting an
already-rendered component **re-attaches the DOM it already built** rather than
rendering again: the second mount reached no plan at all, and two of the 26
stayed dark even after the component was hoisted out of `mount()`. Passing an
explicit `{}` forces `renderWith` with exactly the arguments the no-data call
makes, and the count came back to 26.

## Reproducing it

```sh
npm run benchmark:once -- --null
npm run benchmark:once --                       # the one-shot cost: now nil
npm run benchmark:once -- --renders 50          # noisy here; count, do not clock
```

And the coverage check, which is the one worth repeating whenever this area is
touched: make `renderFromSkeleton` mark its root, run `tests/skeleton.test.ts`,
and confirm 26 entries fail. A number lower than that means some part of the
corpus has stopped exercising the clone path.
