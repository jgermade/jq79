# feat: slots

Content projection for jq79 components: a component's tag children render inside
the component, where it puts a `<slot>`. Scoped slots included — the child can
hand data to content it didn't write.

Status: proposal, nothing implemented.

## Today

A component tag's children are dropped, silently. `renderNestedComponent` reads
attributes only. So a component can be parameterised by data, never by markup:
no wrappers (modal, card, panel), no shared list renderer, and every scrap of
inline markup has to become its own component with its own props.

## The syntax

The child declares holes:

```html
<!-- Card.html -->
<section>
  <header><slot.header>Untitled</slot.header></header>
  <slot />
  <footer :if="$slots.footer"><slot.footer /></footer>
</section>
```

The parent fills them:

```html
<Card :title="t">
  <template :slot.header>
    <h2>{{ t }}</h2>
    <small>{{ subtitle }}</small>
  </template>

  <p>{{ body }}</p>
</Card>
```

A slot can pass data to the content — the half that makes this composition
rather than decoration:

```html
<!-- List.html -->
<ul>
  <li :each="item in rows" :key="item.id">
    <slot :item="item" :index="$index" />
  </li>
  <p :if="!rows.length"><slot.empty>Nothing here</slot.empty></p>
</ul>
```

```html
<List :rows="rows" :slot="{ item, index }">
  {{ index }}. <b>{{ item.label }}</b> — {{ currency(item.total) }}
</List>
```

`currency` is the parent's, `item` is the child's. That sentence is the feature.

### The whole surface

| written | means |
| --- | --- |
| `<slot />` | the default hole |
| `<slot.header-bar>…</slot.header-bar>` | a named hole, with fallback content |
| `<slot.row :item="item" />` | a hole that passes props to the content |
| a component tag's own children | content for the default slot |
| `:slot="{ item }"` on a component tag | names the default content binds |
| `<template :slot.row="{ item }">` | content for a named slot, and its names |

The dot marks the named variant on both sides, like `:model.<name>`,
`:class.<name>` and `:props.<n>` already do. Names are kebab-case where written
(tag names and attribute modifiers are lowercased by the HTML parser) and
camelCase where read: `<slot.header-bar>` ↔ `:slot.header-bar` ↔
`$slots.headerBar`.

`<template>` now means one thing per attribute — `name="Pascal"` declares a
component in the file, `:slot.<name>` fills a slot, neither is a plain inert
element. Position is checked (a misplaced one warns), never interpreted.

## The rules

1. **Content belongs to the parent.** Its AST, its scope, its effects, its
   scoped styles. The child decides *where* it goes and *whether* it goes, never
   what the names in it mean.
2. **Slot props are declared, not injected.** `:slot="{ item }"` keeps every
   bare name in the parent's file introduced by the parent — the same reason
   `:each` requires `item in rows`. Optional: without it the content just sees
   the parent's scope.
3. **What isn't projected isn't rendered.** No `<slot>`, or one behind a false
   `:if`, and the content's effects never exist.

Plus: every attribute of a `<slot>` is a slot prop (the name is in the tag, so
there are no reserved ones); fallback content renders in the child's scope; a
`<slot>` may render many times, each copy with its own effects; `$slots` is a
static map of filled names; slots stop at the component boundary, and a `<slot>`
written *inside* slot content forwards the parent's own.

## How it works

- **Thunks, not DOM.** The usage site partitions the tag's children by slot name
  and hands the instance `name -> (slotProps, fx) => Node`. Instances are
  replaced (definition swap, hot reload), so a pre-rendered fragment would leak
  effects and can only be inserted once.
- **The map rides the store under a symbol** (the `UNFILLED_PROPS` trick):
  travels the scope chain, never appears as data. Also on the instance, because
  `hotReplace` re-renders from a spread.
- **Slot props are lazy accessors** evaluating in the child's scope on every
  read — `createWithScope`'s design, so tracking stays read-precise.
- **`<style scoped>` lands right for free:** slot content is stamped with the
  parent's hash at parse time, so the parent's scoped rules reach it and the
  child's don't.

### The one thing that isn't free

An effect currently lives in exactly one store's `effects` set, and only that
store's `notify` walks it. Scoped-slot content reads the parent's store *and*
the child's, so the effect record has to be registrable with both: one record,
one initial run, two sets. Tracking already works across stores (`trackerStack`
is module-level); only the waking doesn't.

Accepted with it: deps are path strings with no store namespace, so identical
paths in both stores collide — a spurious re-run, never a stale render.

## 2026-08-06 — addendum: implemented, and what the coding decided

Shipped as described. The syntax table, the three rules and the mechanics all
survived contact with the code; what follows is only what the plan left open,
plus the one thing it got wrong.

### The open questions, answered

- **Duplicate `<template :slot.x>`: first wins, with a warning.** Not "last
  wins", and not concatenation. The precedent was already in the file: two
  `<template name="X">` in one file keep the first and warn. Concatenating would
  be the only place in jq79 where writing a thing twice means something other
  than a mistake, and a duplicate is always a mistake — the fix is to delete
  one, not to guess which the author meant.
- **A tag with both a `<template :slot>` and loose children** warns and renders
  the `<template>`: the explicit form beats the implicit one, and silently
  dropping half the markup is exactly the failure this warning exists for.
- **`$slots` is in both script contexts.** It rides the template scope beside
  `$emit` (same proxy, same shadowing rule) and is passed as an instance helper,
  so setup and factory scripts both see it. It costs one entry in a map that
  already existed, and a component that wants to branch on its content in a
  script shouldn't have to reach for the template to do it.
- **`:each` on a `<slot>` falls out**, as hoped — `renderNodes` intercepts
  `:each` before the tag is looked at, so `<slot.row :each="item in rows"
  :item="item" />` renders the content once per row with the item scope in
  place. Covered by a test so it stays that way.
- **A `<slot>`'s directives stay the renderer's.** The plan said every attribute
  of a `<slot>` is a slot prop "since there are no reserved ones". True of
  *names* — the slot's own name is in the tag, so nothing like Vue's `name=` is
  taken — but `:if`/`:each`/`:with` mean on a `<slot>` what they mean on every
  other tag, so they are skipped rather than passed. `@event` too: there is no
  element there to listen on.

### Two things the plan didn't mention

- **`parsePropsPattern` gained `as`**, as scoped. What it is *for* turned out to
  be worth stating: the props signature wants the key (`{ user: renamed }`
  declares `user`), the slot binder wants the local name (`renamed`). One field
  serves both readings, and a nested pattern (`{ item: { label } }`) still binds
  nothing — it declares the prop and names no variable.
- **A plain nested `<template>` now keeps its children.** The `.content` descent
  the slots needed also fixed a bug next door: `elementToAST` read `childNodes`,
  which is empty for a `<template>`, so a nested one rendered as an empty
  element and `cloneNode` of its `.content` gave nothing. The clone-from-content
  use the multi-template plan wrote its "left alone" rule to protect was never
  actually working. It renders into `.content` now, still inert, still unwarned.

### The thing the plan got wrong: the stack budget

"The one thing that isn't free" was right about *what* costs — an effect record
in two stores — and wrong about the currency. The cost that mattered was **JS
stack, not bookkeeping**.

`MAX_NESTING_DEPTH = 200` is documented as "deeper than any real tree, shallower
than the JS stack". Measured, the real ceiling for a self-rendering component
was **218 levels** — 9% of headroom, not the comfortable margin the comment
implies. Registering effects with a second store put `$effect` over it: the
cyclic-data test (which asserts the guard cuts at 200 rather than the stack
giving out) started failing with a `RangeError`, and only inside the real test
file, whose `describe`/`expect` frames are what tipped it.

Recovered by keeping `$effect` the shape it had — the extra work moved into
`attachAndRun`, reached only when a scope actually carries other stores, so the
common effect's frame is unchanged. The ceiling is **212** now: the guard still
holds, with 12 levels to spare instead of 18.

Worth writing down because the next feature will pay the same tax without
knowing it: **any per-level frame growth in `renderWith`/`renderNestedComponent`
/`$effect` comes straight out of that 12.** If it goes, the answer isn't to
shave locals (measured: worth ~1 level) but to lower the guard — the number is a
budget, and it is currently spent almost to the edge.

### One design note that only appeared while coding

`ALSO_WAKEN_BY` is read off the *scope*, not passed at each call site. A scope
that carries it hands the arrangement to everything rendered inside it — nested
`:each` item scopes, an `:if` branch, the prop-sync effects of a component
written inside slot content — without any of those knowing slots exist. The
alternative (threading the extra store through `createEffectScope`'s callers)
would have touched every renderer for a case only one of them has.
